# Исправления предобучения PRAGMA по аудиту 2026-11-02: дизайн

Дата: 2026-11-03. Статус: дизайн согласован с владельцем по частям, ждёт его ревью спека.

## Цель

Убрать несостыковки, из-за которых PRAGMA училась не той задаче, что задумана, и проверить каждое
исправление по правилу принятия (README, раздел 13). Мерило — `probe --baseline` по `usr` и
`catboost_plus_usr` на val; MLM val_loss — вторичный и у кандидатов 3 и 4 несравним.

## Основания

Отчёты пяти аудиторов и проверка происхождения эталона — `audit/2026-11-02-pretrain-contracts/`
(A цикл обучения, B данные между этапами, C внутренности модели, D честность сравнения, E паритет
информации, F происхождение; скрипты замеров — `scripts/`). Грубых ошибок нет (утечки будущего,
пересечения клиентов, ошибки выбора чекпойнта, сдвига сравнения с CatBoost); найдено:

| 1 | Вес клиента в E1′ ≈ 1/(клиентов в его micro-batch'е): `(loss + w·aux)·count` (`src/mlm/train.py:1376-1377`), `aux` — среднее по клиентам micro-batch'а (`src/mlm/model.py:529`). | 2 | Порядок клиентов одинаков во всех эпохах: `Source.order = range(count)` (`src/mlm/inputs.py:169`) | B, C | перекос п. 1 повторяется каждую эпоху; E5 волны 4 не запускался |

## Решения владельца (2026-11-03)

- Четыре изменения проверяются **по одному, жадно**: принятое входит в следующие прогоны. Порядок:
  1 нормировка E1′ → 2 перемешивание → 3 маска без дублей → 4 шкалы сумм.
- Маска: зависимые поля события **закрываются группой**; при маске события закрываются и его ключи
  (E6); `event_type` не цель механизмов value и key.
- Группы — **явный список в конфиге** плюс колонка в отчёте маски.
- Нормировка E1′ — **точно по окну**: MLM — среднее по целям окна, E1′ — среднее по клиентам окна.
- Шкала суммы — **своя на каждый тип события** (`split_by: "event_type"`).
- Устройство — переключатели в конфигах; значение по умолчанию — поведение эталона.

## Ограничения

- Обучение, пересборка данных, embed, plus_usr, probe и шаг 0 — только по команде владельца.
  Коммиты — только по его команде.
- До решения по кандидату поведение по умолчанию не меняется: со значениями по умолчанию маска,
  поток и шаг побитно равны нынешним, а чекпойнт эталона грузится как прежде.
- Статистики и словарь — только по train. Тесты не читают и не пишут `data/`.
- Одинаковые вход и конфиг дают одинаковый результат (на CPU — побитно).
- Решения — по val; test — один раз в конце, у победителя.

## 0. Шаг 0: шумовой пол CatBoost

Аудит D: CatBoost обучается один раз с seed 42, и ни bootstrap, ни временный пол `plus_usr` 0,005
(со старых данных) не включают его разброс по seed.

- Скрипт `audit/2026-11-03-pretrain-fixes/catboost_seeds.py` (venv churn_baseline, только чтение):
  `churn.train.fit_task` с seed 43–47 на готовых признаках и векторах `ref-2026-10-09` для
  `catboost` и `catboost_plus_usr`; печатает PR-AUC val каждого seed, среднее, размах и разброс Δ
  `plus_usr − catboost`. Минуты на CPU.
- По итогу владелец обновляет временный пол `plus_usr` в README §13.

## 1. Кандидат 1: E1′ — среднее по клиентам окна

`MlmConfig.aux_per_client: bool = False`.

- `RecentTypes.forward` возвращает поэлементные квадраты ошибок `[B, 4, 54]`
  (`F.mse_loss(..., reduction="none")`); `ModelOutput.aux` — этот тензор. Свёртку делает цикл
  обучения; `validate` aux по-прежнему не учитывает. Остальные потребители `ModelOutput.aux`
  (`src/mlm/diagnostics.py` и др.) находятся в плане и сворачивают так же, как сейчас.
- Флаг выключен: `aux.mean()` по всем элементам — та же свёртка, что сейчас; шаг побитно прежний.
- Флаг включён:
  - окно сначала собирается списком micro-batch'ей (`grad_accum_steps` штук или хвост эпохи);
    по меткам клиентов считаются `T` — целей MLM окна и `C` — клиентов окна;
  - `aux_клиента` — среднее его 4 × 54 ячеек; каждый micro-batch делает
    `backward(Σ CE / T + w · Σ aux_клиента / C)`; деление на `T` в
    закрытии окна при этом не повторяется;
  - micro-batch без целей MLM даёт только E1′ (сейчас теряется целиком, `train.py:1373`);
  - телеметрия: `aux` — среднее по клиентам.
- Масштаб E1′ к MLM сохраняется, `usr_aux_weight = 1.0` сохраняет смысл.

## 2. Кандидат 2: перемешивание порядка

`MlmConfig.shuffle_order: bool = False`.

- `train_source(config, masking, epoch)` задаёт `Source.order` перестановкой групп строк из
  `stable_hash("order", seed, epoch)`; клиенты внутри группы строк — перестановкой из
  `stable_hash("order", seed, epoch, группа)`. `seed` — `MlmConfig.seed`: его меняет реплика
  шумового пола (`train-seed43.json`), и у реплики порядок свой; маска от него не зависит.
- Перестановка внутри группы — там, где группа уже прочитана (`Source._rows`); путь `Prefetch`
  делит `order` по воркерам, как сейчас.
- Val не перемешивается.
- Маска клиента зависит от его id и seed эпохи, а не от позиции; `micro_batches_done` при resume
  указывает в тот же поток.

## 3. Кандидат 3: маска без дублей

- `MaskingConfig.field_groups: tuple[tuple[str, ...], ...] = ()`. Конфиг кандидата:
  - `{direction, transaction_amount}`;
  - `{app_domain, firebase_screen, operation}`;
  - `{campaign_code, offer, template, purpose}`;
  - `{is_online, operation_channel}`;
  - `{mcc, merchant_category, merchant_name}`.
- Правило: если значение стало целью механизмом value или key, все присутствующие поля его группы в
  **том же событии** закрываются `[MASK]` и становятся целями. Значения, ушедшие в `[UNK]`, — как
  сейчас (не цели). Механизм event закрывает все значения события и так.
- Веса информативности не меняются. Доля целей растёт за счёт партнёров; отчёт маски показывает
  насколько.
- `MaskingConfig.event_type_event_only: bool = False` — при `True` `event_type` не выбирается целью
  механизмами value и key; цель только у механизма event.
- `MlmConfig.hide_event_keys: bool = False` — при маске события его `key_ids` заменяются `[MASK]`
  внутри модели. Код волны 4 восстанавливается из коммита 62170f4 (`src/mlm/model.py:574-590`,
  `src/mlm/settings.py:163-164`, `src/mlm/train.py:647, 674, 972`) и сверяется с нынешними путями
  sdpa и flash. При `ZERO_MASK` (embed, LoRA) событий под маской нет — флаг ни на что не влияет.
- Проверка конфига: ключ группы не из реестра ключей событий, ключ в двух группах или группа из
  одного ключа — `ConfigError`. Новые поля — в `as_dict`/`from_dict`, то есть в чекпойнте и в
  `data_record`.
- Отчёт маски (`src.masking.report`) — колонка «доля целей с видимым партнёром»: пары ключей события
  с `H(B|A)/H(B) < 0,05` по выборке train (логика `scripts/check8.py`, `check9.py` аудита B),
  для каждой пары — покрыта ли она группой. После изменения доля по группам — 0; непокрытые пары
  видны.
- Конфиг кандидата: `--masking-config` с `field_groups` и `event_type_event_only: true`, `--config` с
  `hide_event_keys: true`.

## 4. Кандидат 4: шкала суммы по типу события

- Конфиг `fit`: у `transaction_amount` `split_by: "event_type"` вместо `"direction"`. Код шкал не
  меняется: `split_by` уже делит шкалу по категориальному ключу события
  (`src/tokenization/numeric.py:438-461`), `event_type` — такой ключ. Словарь +~170 токенов
  (`transaction_amount_<тип>_bucket_N`).
- Тип в имени токена — не утечка, пока `event_type` цель только при маске события, где сумма
  закрыта; при маске суммы тип и так виден в том же событии. Если кандидат 3 отвергнут, поле
  `event_type_event_only` остаётся в коде (остальной код кандидата 3 удаляется) и включается в
  конфиге кандидата 4: без него сумма выдавала бы цель `event_type`.
- Риск: у редких типов может не набраться значений на 16 различных границ. До прогона —
  проверить, что `fit` делает с совпавшими границами, и посмотреть число диапазонов по типам.
- Защита lineage (аудит B): `05_dataset/<группа>/meta.json` получает отпечаток словаря
  (`vocabulary_digest()`), `Source` отказывает при расхождении с текущим словарём. Без этого
  частичная пересборка после нового словаря читалась бы молча со старыми номерами токенов.
- Перед пересборкой `data/03–07` текущего эталона копируются в `data/runs/data-<эталон>/`
  (~1,5 ГБ; свободно 929 ГБ): `embed` и LoRA сверяют sha `05`.
- Пересборка: `python -m src.pipeline --from fit --args fit="--config <конфиг>"` (03–07, ~35 мин).

## 5. Прогон кандидата и решение

Каждый кандидат — отдельной командой владельца, отдельной цепочкой (`setsid nohup`):

1. `python -m src.mlm.train --config <c>.json [--masking-config <m>.json] --out data/runs/<имя>`,
   5 эпох, seed 42.
2. `python -m src.downstream.embed --checkpoint data/runs/<имя>/best_checkpoint.pt --tag <имя>`.
3. Из `churn_baseline/` его venv: `python -m churn.plus_usr --tag <имя>`.
4. `python -m src.downstream.probe --tag <имя> --baseline <текущий эталон>`.
5. Итог в `audit/2026-11-03-pretrain-fixes/README.md`: Δ и интервалы по `usr` и `catboost_plus_usr`,
   log-loss, вердикт по правилу §13, телеметрия (val_loss там, где сравним). Решение — владельца.
6. Принято: флаг становится поведением по умолчанию, старая ветка кода и её тесты удаляются, имя
   прогона — новый эталон для `--baseline`. Отвергнуто: код переключателя удаляется, итог остаётся
   в аудите.
7. Только после этого — следующий кандидат.

Конфиги кандидатов — `audit/2026-11-03-pretrain-fixes/configs/`. Цикл ~1 ч 45 мин; у кандидата 4
ещё ~35 мин пересборки. GPU-прогон LoRA на нынешнем эталоне — до кандидата 4 или после
восстановления копии данных; при смене эталона LoRA перезапускается на новом по команде.

## 7. Тесты

Синтетический мир, `tests/`; CPU-часть быстрая.

1. Флаги по умолчанию: маска, порядок и градиент шага побитно равны нынешним (на CPU); чекпойнт со
   старым конфигом грузится.
2. `aux_per_client`: одно окно и то же окно, разбитое на micro-batch'и, дают одинаковый градиент
   при `usr_aux_weight > 0` (основа — `scripts/test_aux_partition.py` аудита A); вклад клиента в E1′
   не зависит от длины соседей по micro-batch'у; micro-batch без целей MLM даёт градиент E1′.
3. `shuffle_order`: эпохи дают разный порядок, одна эпоха — тот же; маска каждого клиента не зависит
   от порядка; resume посреди эпохи даёт тот же поток.
4. Групповая маска: на множестве розыгрышей ни у одной цели value/key нет видимого партнёра по группе
   в том же событии; `event_type_event_only` — `event_type` не цель при value и key и цель при event;
   ошибки конфига групп.
5. `hide_event_keys`: у закрытого события ключи — `[MASK]`; пути sdpa и flash совпадают (CUDA, в
   допусках `tests/test_cuda_flash.py`).
6. Отчёт маски: колонка партнёров на мире с заведомо зависимыми полями.
7. Отпечаток словаря в `05`: отказ при расхождении.
8. `split_by: "event_type"`: шкалы по типам, у типа своё условие; тип, которого train не видел, —
   `[UNK]` (существующее поведение `split_by`).
