# Скорость fit токенизатора (2026-10-07)

Задача: ускорить `python -m src.tokenization.run fit`, не меняя ни словаря, ни статистики, ни
BPE, ни весов значений.

**Итог:**

- fit на 1000 клиентах быстрее в **1.30×** (104.6 → 80.3 с, среднее двух прогонов);
- процессорного времени в **2.7–3×** меньше;
- все семь артефактов **побайтно те же**, и полный слепок `FitStatistics` тот же.

Замеры воспроизводит `bench.py`: он пишет в `--root`, это раскладка data/ во временном каталоге.
Код «до» — снимок рабочего дерева перед правками fit, через `PYTHONPATH`.

```bash
.venv/bin/python audit/2026-10-07-tokenizer-fit-speed/bench.py prepare --root <scratch> --events <events.parquet> --profile <profile.parquet>
.venv/bin/python audit/2026-10-07-tokenizer-fit-speed/bench.py run --root <scratch> --label <имя>
.venv/bin/python audit/2026-10-07-tokenizer-fit-speed/bench.py profile --root <scratch>
.venv/bin/python audit/2026-10-07-tokenizer-fit-speed/bench.py counts --root <scratch>
```

**Вход:**
- лента препроцессинга той же scratch-выгрузки (1000 клиентов, окно train, 2 729 355 событий,
  17 групп строк по 64 клиента);
- анкета RAW.

Машина та же, что в `audit/2026-10-07-generator-speed`.

## 1. Как fit устроен

```
02_preprocessed/train/events.parquet + 01_raw/train/profile.parquet
  → Group → Group.histories(final_cutoff) → Group.history(client) по одному
  → read_train → scan → FitStatistics
  → value-vocab, buckets, bpe, value-weights → final-vocab
```

Корпус читается **один раз**: `run_fit` передаёт один `TrainCorpus` в value-vocab, buckets, bpe и
value-weights. Это подтверждено: `read_train` вызывается один раз за fit.

## 3. Повторное чтение групп строк — подтверждено

- В ленте 17 групп строк по 64 клиента (последняя — 40); раскрытая группа весит 54 МиБ, сжатая —
  2.2 МиБ, читается за 0.07 с.
- `Group.history(client)` читала группу строк своего клиента целиком: **1000 чтений групп строк**
  на 17 групп, около 59 на каждую. Это около 2.2 ГиБ раскрытия, 18.9 с времени и больше половины
  CPU fit: раскрытие идёт потоками Arrow.
- Файл — 39 МиБ сжатых; прочитано около 59 × 39 МиБ ≈ 2.2 ГиБ сжатых данных.
- **После:** 17 курсоров, каждая группа строк читается ровно один раз — 39 МиБ.

## 4. Внесённые изменения

**F1. Потоковый обход группы** (`preprocessing/read.py`).
- **Как работает.** `histories()` без явного списка клиентов идёт курсорами: по одному
  `iter_batches` (куски по 2048 строк) на каждую группу строк. Клиенты выдаются в прежнем порядке
  `sorted(client_id)` слиянием отсортированных отрезков: внутри группы строк препроцессинг кладёт
  клиентов по возрастанию id.
- **Целостность.** Клиент, разрезанный границей куска или группы строк, собирается целиком.
  Клиент ленты без анкеты пропускается, как и прежде.
- **Когда включается.** Поток возможен, если строки каждого клиента идут подряд и внутри каждой
  группы строк клиенты по возрастанию. Это проверяется по колонке `client_id` при построении того
  же индекса, что и раньше; иначе — прежний путь через `history`.
- **Без изменений:** `Group.history(client_id)` и его поведение. Тело вынесено в `_build`, его
  зовут оба пути.
- **Почему нельзя проще.** Обход в порядке файла дал бы то же самое быстрее и проще, но он не
  годится: метка значения в `value_weights.json` берётся у первой встреченной категории, сводимой
  к `[UNK]`, и зависит от порядка клиентов.
- **Память:** 17 курсоров держат около 300 МиБ против 0.9 ГиБ раскрытой ленты. На train это
  около 133 курсоров по ~13 МиБ.

**F2. `scan` без лишней работы** (`tokenization/scan.py`).
- Тип значения определяется один раз и передаётся в `_note_key`, `_add_categorical`,
  `_add_numeric` и `value_text`.
- Значения события читаются из `event.values` без копии `model_values()`: `scan` их не меняет,
  это закреплено тестом.
- `_note_key` без вызова метода и `setdefault`.

**F3. Смысловой ключ поля** запоминается по паре (поле, источник).
- `key_for` — чистая функция реестра; ошибка по-прежнему возникает каждый раз.
- В `model_event` метод `get` привязан к локальной переменной.
- Порядок ключей значений не менялся: от него зависит порядок токенов при кодировании.

**F4. Календарь** — `tolist()` вместо `float()` по одному: массив `float32`, а числа Python те же.

**Проверка историй.** Хеш историй всех 1000 клиентов одинаков у старого кода (по одному), нового
потока и нового `history`. Сверялись события, значения с порядком ключей, календарь, анкета,
вехи и ограничения.

## 7. Не менялось и почему

- **`sorted(values.items())` в `scan`.**
  - Около 2% времени.
  - Хэш выборки (`клиент, номер события, ключ`) от порядка не зависит, артефакты тоже. Но порядок
    решает, какую из нескольких ошибок одного события `scan` назовёт первой.
- **Хэш выборки чисел** — 2.9 млн вызовов blake2b, около 2 с.
  - Вариант с общим префиксом через `blake2b().copy()` дал бы тот же хэш, но выигрыш на коротких
    строках сомнителен.
- **`NumericSketch._trim`** — 39 сортировок, около 4 с.
  - k наименьших по `(хэш, значение)` должны совпасть точно. `heapq.nsmallest` или
    `numpy.lexsort` это сохраняют, но на 4% не принято.
- **Поиск диапазона `locate` при весах и диапазонах** — около 2–3 с.
  - Кэш по значению точен, оставлен на потом.
- **Анкета в `Group.__init__`** — 0.04 с на 1000 клиентов.
- **Многопроцессность `scan`.**
  - Выборка чисел и счётчики не зависят от порядка, слияние возможно.
  - Но метки `value_weights` и `example_raw` берутся у первого встреченного значения. Нужен
    отдельный контракт слияния — не внедрялось.

## 8. Что осталось

- **Сборка истории в Python** — около 45 с из ~80: словарь на строку (`to_pylist`), проекция,
  `ClientEvent`.
  - Ускорить её может только сборка значений прямо из колонок Arrow — только непустые ячейки и
    без словаря на строку.
  - Это крупная правка `read.py`. Выход уже закреплён тестами (`tests/test_tokenizer_fit_scan.py`
    и хешем историй), но делать её — отдельное решение.
  - **Сделано позже**, в аудите `2026-10-07-tokenizer-encode-speed` (E2): сборка по колонкам.
    Fit — 81.1 → 57.3 с; все семь артефактов и слепок `FitStatistics` те же.
- **Счётчики `scan`** — около 30 с Python на 16–19 млн значений.
