# Скорость препроцессинга (2026-10-07)

Задача: ускорить этап canonical (`python -m src.preprocessing.run preprocess <group>`), не
меняя ни смысла данных, ни проверок RAW.

**Итог:**

- на 1000 клиентах этап быстрее в **1.74×**: 22.2 → 12.8 с, среднее трёх чистых пар;
- `events.parquet` **побайтно тот же**;
- все ошибки на негодных выгрузках прежние, кроме одной найденной и исправленной ошибки
  `check_raw`.

Замеры воспроизводит `bench.py`; код «до» — снимок 1e973be через `PYTHONPATH`:

```bash
.venv/bin/python audit/2026-10-07-preprocessing-speed/bench.py run --raw <RAW> --out <scratch> --batch 64 --hash
.venv/bin/python audit/2026-10-07-preprocessing-speed/bench.py counts --raw <RAW> --out <scratch>
.venv/bin/python audit/2026-10-07-preprocessing-speed/bench.py profile --raw <RAW> --out <scratch>
.venv/bin/python audit/2026-10-07-preprocessing-speed/bench.py errors --out <scratch>
```

**Вход:** scratch-выгрузка Generator 1.0.1, 1000 клиентов, окно train, 2 729 355 событий, RAW
45 МиБ. Машина та же, что в `audit/2026-10-07-generator-speed`.

## 1. Как этап был устроен

1. **`check_raw`.**
   - Манифест, схемы и число строк.
   - По каждой группе строк ленты читаются 4 колонки и проверяются: `client_id` не пуст;
     `event_time` разбирается `parse_event_time` в цикле Python; `source` из контракта; `type`
     из payload (`event_types_of` — разбор JSON).
   - Профиль читается дважды: на уникальность и на моменты, вехи и работу.
2. **`build_group`** читает профиль в третий раз — ради вех.
3. **`iter_client_batches`** читает ленту целиком второй раз и трижды переводит `client_id` в
   список Python.
4. **`parse_batch`.**
   - `type` извлекается ещё дважды: в нём самом и внутри `iter_event_types`.
   - На каждый тип строится маска по всей пачке и фильтруется вся пачка. Разбор payload идёт
     по типам через `pyarrow.json`.
   - Таблица полной ширины переставляется обратно в исходный порядок.
5. **`build_batch`.**
   - `event_time` разбирается в Python второй раз.
   - `lifelong_sources`: `type` в четвёртый раз, цикл по всем строкам пачки, `json.loads`
     строк-источников.
   - `normalize_text` в Python, `select`/`cast`, приоритет типа через `to_pylist`, затем
     `sort_indices` и `take`.
6. **`TableWriter.write`** — ещё раз `select`/`cast`, затем запись zstd.
7. **`_clients`** — третий проход по `client_id` ленты и ещё одно чтение профиля, только ради
   числа клиентов в строке терминала.

## 4. Внесённые оптимизации

**P1. Время события — векторно.** `rawdata.strict_event_times` и `event_times`.
- Строгая запись генератора — `ГГГГ-ММ-ДДTчч:мм:сс±ЧЧ:ММ` (25 байт) или с тремя знаками
  миллисекунд (29 байт). Она разбирается по байтам буфера Arrow, а момент в UTC считается
  арифметикой.
- Проверяются цифры и разделители по позициям, месяц, день месяца с учётом високосных лет, час до
  23, минута и секунда до 59, смещение до 23:59, годы 1900–2200.
- Всё прочее уводит всю колонку на прежний построчный `parse_event_time` с той же ошибкой. Это и
  `24:00`, которое Python принимает, и пробелы, `Z`, шесть знаков дробной части, переполнение у
  крайних лет.
- Шаблон чисто ASCII, поэтому совпадение по байтам равносильно совпадению по символам.
- В `check_raw` векторная проверка стоит первой; построчная, с номером первой плохой строки,
  идёт, только если строгой не прошла вся группа строк.
- Проверено на 33 краевых записях, в срезах массива и на 200 тыс. случайных моментов
  1950–2100 со смещениями до ±23:59: где быстрый путь даёт ответ, он побитно равен построчному.

**P2. `type` — один разбор на пачку.**
- `parse_batch` отдаёт колонку типа дальше, и `lifelong_sources` берёт её же.
- `iter_event_types` больше не нужен и удалён.

**P3. Группировка по типу одной сортировкой.**
- Вместо маски на каждый тип — устойчивая сортировка номера типа: группы и порядок строк внутри
  них те же.
- Типы обходятся в том же порядке первого появления.
- Разбирается выборка только payload, а не всей пачки.

**P4. Без обратной перестановки широкой таблицы.**
- Сортируется таблица в порядке разобранного payload, а последний ключ — исходный номер строки.
- Сортировка «ключи, затем исходный номер» по определению даёт порядок устойчивой сортировки
  исходной пачки.
- Переставляются 4 колонки конверта вместо 58 колонок payload.

**P5. `normalize_text` — по словарю колонки.** Функция та же, она вызывается на каждое разное
значение один раз (`normalize_column`).

**P6. Приоритет типа векторно.** `index_in` по справочнику — то же, что `priority.get(name,
unknown)`.

**P7. `lifelong_sources`** обходит только строки тех типов, что бывают источниками вех. Прежний
обход остальные строки пропускал.

**P8. Границы клиентов по номерам.** `iter_client_batches` ищет их по кодам `dictionary_encode`
вместо строк Python. При пустом `client_id` — прежнее сравнение строк.

**P9. Без прохода `_clients`.** Клиенты ленты собирает тот же обход пачек, которым проверяется
неразорванность ленты. Клиенты только с анкетой берутся из уже прочитанного профиля. Число то
же: объединение клиентов ленты и анкеты.

**P10. Профиль в `check_raw`** читается один раз на обе проверки.

**Исправление.** В `check_raw` `pc.or_` заменён на `pc.or_kleene`.
- `or_(null, null)` даёт null, поэтому строка с пустым (null) `client_id` проходила проверку RAW.
- Останавливала её уже canonical с `CanonicalError`, хотя комментарий обещал проверку RAW.
- Теперь `RawContractError`, раньше и с правильным классом. Это усиление проверки.

| после | 1024 | 14.7 | 1.51 | 1.96 | порядок клиентов другой |

Прогоны на `batch_clients` больше 64 шли с одним занятым ядром (однопоточный замер генератора).

**`batch_clients`.** Сортировка идёт внутри пачки: по `client_id`, затем по времени, а пачки —
в порядке файла.
- Чем крупнее пачка, тем больше клиентов пересортировывается по строковому id: состав строк и
  порядок событий внутри клиента те же, а порядок клиентов в файле меняется.
- По условию задачи порядок обязан совпадать, поэтому **лучший и прежний — 64**.
- Выигрыша по времени крупные пачки к тому же не дают, а память растёт.

**Потоки Arrow** (два прогона на каждое значение, после правок):

| потоков | время, с | CPU, с |
|---|---|---|
| 4 | 12.8 / 12.9 | 18.4 / 18.5 |
| 6 | 12.6 / 13.4 | 19.7 / 20.8 |
| 12 (по умолчанию) | 12.9 / 12.6 | 22.9 / 22.3 |

- По времени разницы нет, меньше потоков экономят только CPU.
- Выход при любом числе потоков побайтно тот же.
- Глобальная настройка не менялась.

**Ввод-вывод.**
- Учёта ввода-вывода по процессу в WSL2 нет.
- Чтение — число проходов на размер RAW: было около 3 × 45 МиБ сжатой ленты, стало около 2 × 45.
- Запись — 39 МиБ, она не изменилась.

## 6. Равенство выхода и ошибок

**Выход.** `events.parquet` старого и нового кода совпадают:
- sha256 файла;
- логический хеш строк, а значит, все колонки, значения, null, порядок клиентов и событий,
  пометка источника вехи, нормализованный текст и моменты;
- схема и метаданные (`period_start`, `period_end`);
- 17 групп строк;
- 1000 клиентов.

**Ошибки.** `tests/test_preprocessing_errors.py` — 20 негодных выгрузок поверх годной:
- пустой и null `client_id`;
- нечитаемое время и время без пояса;
- чужой источник;
- битый JSON и пустой payload;
- нет `type`, неизвестный тип, лишний ключ, не тот тип значения, нет обязательного поля;
- разорванный клиент;
- два профиля одного клиента;
- неверный `as_of`;
- веха без `source_id`, без источника в ленте, с другим временем;
- записи о работе не по времени и после `as_of`.

`bench.py errors` сравнивает точные тексты: они совпадают во всех случаях, кроме null
`client_id` — это исправленная ошибка, описанная выше.

**Тесты эквивалентности** — `tests/test_preprocessing_equivalence.py`, 36 случаев:
- время;
- нормализация на юникодных случаях: кириллица, латиница, NBSP, табуляции и переводы строк,
  составные и разложенные символы, турецкие `İ` и `ı`, `ß`, лигатуры, полноширинные символы,
  пустые строки и строки из пробелов, None;
- порядок сгруппированной по типам таблицы против прежнего.

## 7. Что дальше

- **Многопроцессность.** Пачки клиентов независимы, и при двух проходах (проверка и сборка)
  этап мог бы идти в 2–4 процесса. Порядок пачек в файле и первая ошибка сохраняются, если
  результаты пишутся по номеру пачки. Это отдельное решение; при нынешних 13 с на 1000 клиентов
  (около 2 мин на train) нужды в нём нет.
- **Архитектурный остаток.**
  - Проверка RAW и сборка — два прохода с разбором `type` и времени в каждом.
  - Слить их в один можно только ценой контракта «ни строки на диск до полной проверки» и
    порядка, в котором при нескольких поломках называется первая. Не принято.
