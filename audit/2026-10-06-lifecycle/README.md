# Customer Lifecycle (CAPP) в mini_pragma_v2

Источник — Excel мобильной команды `CAPP Customer lifecycle stages.xlsx` (корень репозитория):
1 лист, 7 стадий, текст правил и SQL банка.

**Конечный процесс:**

```
история → PRAGMA → [USR] → прогноз churn / At Risk → risk score
        → lifecycle и бизнес-контекст → NBA / NBO
```

**Три слоя не смешиваются:**
- **Representation:** PRAGMA → `[USR]`.
- **Prediction:** `[USR]` и разрешённые признаки до T → вероятность.
- **Decisioning:** риск + стадия + продукты + eligibility + контакты → действие или оффер.

Стадия на момент t — **бизнес-разметка наблюдаемого поведения**.
- Это не скрытое состояние генератора и не вход PRAGMA.
- Это и не признак моделей по умолчанию.
- Стадия Churn на t («уже 60+ дней без действия») и downstream-цель «уйдёт в (T, T+60]» — разные
  сущности.

## Что в Excel

SQL банка точнее текста, и он задаёт главное:

| ячейка | что | как в SQL |
|---|---|---|
| E7 | активация за 7 дней | MIN регистрации; MIN операции активации; список целевых операций — пустая заглушка (все) |
| G7 | MAU | визит = успешная авторизация в приложении; `churned_flag` — в MAU m−3 и m−2, нет в m−1 и m0 |
| H7 | CORE → спад | недели ISO по визитам; high = среднее за 4 недели ≥ 4, серия ≥ 4 недель; low = среднее за 2 недели ≤ 2, серия ≥ 2; спад — первая low-серия после начала последней high-серии |
| I7 | Loyal → At Risk | закрытие премиальных карт: Тау (`DC_VIP*`, `DC_VRTV*`) и Алем (`DC_ALEM`, `DC_VRT_ALM`, `DC_ALM_NR`) |
| E8 | Churn | 60+ дней с последнего успешного визита |

## Excel → синтетика

| понятие | в проекте | реализовано |
|---|---|---|
| регистрация (CAPP) | веха анкеты `app_registered` — датирована, читается причинно | да |
| регистрация в банке | веха `bank_registered`; события `client_registered` нет | не нужна правилам |
| визит | `app_operation`, `operation ∈ {login, biometry_login}`, `status = success` — каждая сессия начинается ровно с одного входа | да, `activity.is_visit` |
| действие клиента | `activity.is_client_action` (без обязательств, G4) | да |
| целевое действие | действие клиента или продукт по заявке (`product_opened`, `application_approved`); `card_activated` не считается — в генераторе он автоматический | да, `activity.is_target_action` |
| MAU / WAU | по визитам; месяц календарный, неделя ISO | да |
| DC / CC / CL / DEPO | семейство по `product_id` из справочника (`churn/products.py`); в событии семейства нет | да |
| премиальная карта | `prd_tau`, `prd_alem` (I7) | да |
| VIP как статус клиента | признака нет | Loyal = CORE + премиальная карта |
| close to VIP | не формализовано | **нет** |
| депозит < 15 млн и «etc.» | не подтверждено; таких депозитов в синтетике почти нет | **нет** |
| владение продуктами | по событиям: открытие, миграция, закрытие, первое упоминание договора до окна | да, с недосчётом |
| закрытие премиальной карты клиентом | в генераторе механизма нет: дебетовые карты закрываются только миграцией | правило есть, событий нет |

## Решения владельца (2026-10-06)

| вопрос | решение |
|---|---|
| целевое действие | действие клиента или открытие продукта по заявке; `card_activated` не считается |
| Churn-стадия | 60+ дней без **действия** клиента (визиты входят в действия) |
| выход из At Risk | стадия пересчитывается заново по свежим фактам |
| владение продуктами | по событиям, недосчёт помечен; реестр договоров в RAW — позже, при перегенерации |
| обязательства (G4) | взнос по кредиту и пополнение под платёж или выписку — не действие; досрочное погашение — действие |
| остальное по умолчанию | Growing = визит в месяце после активации (ветка «w/ DC» без своего порога); визит = успешный вход; каденция — сутки; close to VIP и депозит 15 млн не реализованы |

## Реализация

`churn_baseline/churn/lifecycle.py`:
- `history(events, registered, until)` — таблица переходов `client_id`, `started_at`, `stage`,
  `previous_stage`, `reason`;
- `stage_at(history, t)` — стадия на момент;
- правила — `Rules` со ссылками на ячейки Excel.

**Время:**
- Стадия считается на конец местного дня D по событиям дня D и раньше. `started_at` — местная
  полночь после D.
- Недельные правила — по завершённым неделям ISO, месячные — по завершённым месяцам.
- Переход в момент s зависит только от событий раньше s.

**Правила:**
- Приоритет: Churn > At Risk > Loyal > CORE > Growing > Activated > New.
- Активные стадии растут только по цепочке, вниз — через At Risk.

**Выход из At Risk:**
- Выход — когда условие входа перестало выполняться: целевое действие, действие, визит, неделя
  без спада, снова премиальная карта.
- Новая стадия — по фактам с начала At Risk:
  - Growing — визит после начала у клиента, который уже был Growing;
  - CORE — high-серия, начавшаяся после спада;
  - кто возвращается в Activated, отсчитывает Growing от месяца выхода.
- Выход из Churn — любое действие, стадия пересчитывается так же.

**Чего стадия не делает:**
- в признаки `churn_baseline` и во вход PRAGMA не идёт;
- генератор её не читает.

**Тесты:**
- `churn_baseline/tests/test_lifecycle.py` — 25 тестов:
  - каждое правило на ленте, собранной руками; клиент 5→5→6→5 не At Risk, 6→5→3→1 — At Risk;
  - свойство без утечки: обрезка ленты на M не меняет переходов до M;
  - клиент, все события которого позже M;
  - событие ровно в M;
  - детерминизм;
  - стадия не попадает в признаки.
- `churn_baseline/tests/test_activity.py` — G4, визит, целевое действие.
- `tests/test_lifecycle_products.py`:
  - справочник продуктов совпадает с каталогом генератора;
  - этапы PRAGMA (кроме генератора) не обращаются к `truth/`.

**Диагностика** — `report.py`, только читает:

```bash
cd churn_baseline
.venv/bin/python ../audit/2026-10-06-lifecycle/report.py --raw ../data/01_raw/val \
    --until 2026-05-01 --cutoff 2026-03-01 --leakage 2025-06-15 2026-01-01
```

## Что видно и что вынести мобильной команде

- **CORE ~30%.** Порог «4+ визита в неделю» лежит на медиане генератора: у обычного клиента около
  4 сессий в неделю. Долю CORE в банке может дать только мобильная команда. Генератор под неё не
  подгоняется без этой цифры.
- **Loyal почти пуст** (0.4–0.6%):
  - премиальные карты есть лишь у 1–2% клиентов;
  - закрывать их клиент не умеет, поэтому Loyal → At Risk по I7 в данных не бывает.
- **Activated держится долго** (~14%). Growing требует визита ровно в месяце после активации.
  Кто вернулся из Churn не визитом, а покупкой, остаётся Activated, пока не зайдёт в приложение в
  следующем месяце.
- **Стадия на T сильно разделяет метку churn:**
  - At Risk и Activated — 17–20%;
  - Growing и CORE — 0.6–2.5%.

  Это ожидаемо: стадии построены на давности и частоте, то есть на тех же счётчиках. Подавать
  стадию в модели как признак не предлагаю: она производная от тех же счётчиков.

## Основная задача проекта (решение владельца 2026-10-06)

Варианты задач на стадиях были исследованы:
- будущий At Risk — режимы A1–A3: строгий, любое ухудшение, по стадиям;
- исход At Risk — режимы B1–B3: churn против recovery, три класса, время до исхода.

2026-10-06 владелец решил не вводить новые цели. Код и тесты этих вариантов удалены; находки
сохранены ниже как справка.

**Основная и единственная цель проекта — churn на горизонте 60 дней** (`churn_active90`):

```
история клиента до T → PRAGMA → [USR] после энкодера истории → P(churn в следующие 60 дней)
история клиента до T → стадия CAPP на T → диагностика, срезы качества, контекст NBA/NBO
```

Lifecycle — бизнес-интерпретация, диагностика синтетики, срез результатов и будущий контекст
NBA/NBO. Он не цель обучения и не признак. Сравнение моделей прежнее:
- признаки → CatBoost;
- `[USR]` → логистическая регрессия;
- признаки + `[USR]` → CatBoost.

Метрики: PR-AUC — главная; ROC-AUC и log-loss; парный bootstrap разниц.

### Определение цели простыми словами

Код — `churn_baseline/churn/` (`target.py`, `activity.py`, `features.py`, `build.py`,
`sources.py`); он не менялся, кроме маски G4.

- **A. Кто в строках.**
  - Клиенты группы, у которых до T было хотя бы одно собственное действие.
  - Из них в задачу идут активные за последние 90 дней: действие в `[T − 90 дней, T)`. Это
    «active90» в имени — отбор строк, а не горизонт.
  - Клиенты train, чьё прошлое в продолжении разошлось с выгрузкой, исключены.
- **B. Что видит модель.**
  - Только события строго раньше T. Событие ровно в T не входит никуда.
  - Анкета откатывается к T по `profile_change`; вехи берутся только раньше T. Снимочные поля
    анкеты (договоры, `holds_*`, лимиты) исключены: они описывают клиента после T.
  - PRAGMA получает ту же историю до T. Сверку с набором 05 делает `src/downstream`.
- **C. Действие клиента** — `activity.is_client_action`: событие, которое начал сам клиент.
  - Не действие: события банка, начисления, автоплатежи, зачисления от третьих лиц.
  - С G4 не действие и обязательства: взнос по кредиту, пополнение под платёж и под выписку.
  - Визит и целевое действие — отдельные понятия, на метку не влияют.
- **D. Метка.** y = 1, если в окне `(T, T + 60 дней]` у клиента нет ни одного собственного
  действия; иначе y = 0.
- **E. Горизонт** — 60 дней (`config.HORIZON`).
- **F. Недостаточное наблюдение невозможно по построению.**
  - T val и test — 1-е число месяца, в котором лежит «конец выгрузки − 60 дней»: окно целиком
    внутри выгрузки.
  - У train продолжение обязано кончаться позже `T + 60 дней`, иначе сборка отказывает
    (`sources.read_future`).
- **G. Будущее train.**
  - Выгрузка train кончается ровно в T.
  - Окно метки берётся из продолжения: те же клиенты, прожитые генератором дальше
    (`src.generator.continuation train --days 60`).
  - Прошлое продолжения сверено с выгрузкой построчно. Из продолжения берётся только метка;
    признаки и строки — из выгрузки до T.

### Справка: что показали отвергнутые варианты

Полезно для интерпретации стадий; новыми целями не стало.
- **Growing → At Risk** срабатывает только в полночь после конца календарного месяца: при T на
  1-м числе — на T + 31. Окно короче месяца этот переход не видит.
- **Activated, замолчавший после 14 дней от регистрации,** уходит в Churn, минуя At Risk (train:
  209 из 213 таких уходов). Для Activated в Excel нет другого правила At Risk — это кандидат в
  дыру определения, вопрос мобильной команде.
- **Из At Risk на T за 60 дней** (train, 541 клиент) 266 выходят в активную стадию, 155 уходят в
  Churn, 120 остаются At Risk. Остаются в основном спады CORE с продолжающейся редкой
  активностью и Growing без визитов, но с другими действиями.

### Срез результата по стадии

`report.py --scores <прогнозы> --cutoff <T>` печатает для каждого сценария и каждой стадии на T:
- число строк, ушедших и их долю;
- PR-AUC и ROC-AUC — только если в срезе не меньше 10 положительных и 10 отрицательных; иначе
  «мало».

Стадия считается по ленте до T и в модель не попадает.
