# Обвязка обучения: val, старт, чекпойнты, телеметрия (2026-10-08)

Задача: сократить время вокруг прохода модели, не меняя ни одного числа обучения. Это:
- val и её разбор по целям;
- старт прогона;
- записи чекпойнтов;
- телеметрия.

Модель и её проход здесь не менялись — их ускорение в `audit/2026-10-08-model-speed`. Код «до»
этой задачи — дерево после той задачи (снимок через `PYTHONPATH`).

- Принято одно изменение — разбор val по целям (`Detail`) кодами вместо строк и `target_losses`

  и не прошли порог: выигрыш меньше 0.1–0.3% эпохи или риск для гарантий.

**Шум.** Скорость CPU машины сама плавает в 2 раза: одна и та же работа numpy шла 160–318 мс. Одна
и та же val тех же весов шла от 14 до 62 с. Поэтому:
- части обвязки меряются подменами по месту, с синхронизацией CUDA на границах;
- val — на фиксированных micro-batch (`model-speed/bench.py valpass`) и чередованием версий;
- равенство проверено побайтно на детерминированном пути flash.

```bash
B=audit/2026-10-08-orchestration/bench.py
.venv/bin/python $B run      --root <scratch> --label <имя> --epochs 2 [--plain] [--deterministic] [--steps N] [--resume] [--patience P --min-delta D]
.venv/bin/python $B detail   --root <scratch> --checkpoint <ckpt> --label <имя> [--workers N] [--plain] [--repeat K]
.venv/bin/python $B snapshot --root <scratch> --checkpoint <ckpt>
.venv/bin/python audit/2026-10-08-model-speed/bench.py valpass --root <scratch> --checkpoint <ckpt> --label <имя> --parts
```

`run` — настоящий `train()` с `--out` в `<scratch>/12_train/<label>`; `data/12_train` не
трогается. Подмены по месту дают время частей, они не меняют результат:
- старт: модель, лимит CUDA, горизонт, sha256, открытие источников, первая порция `Prefetch`;
- val: модель, `Scores`, `target_losses`, `Detail`, словарь, переносы GPU→CPU;
- каждая запись чекпойнта: `torch.save` и `os.replace` отдельно, размеры;
- телеметрия и печать.

## 1. Поток эпохи

```
train эпохи (Prefetch: новый процесс подготовки, forkserver)
↓ close_window последнего окна
validate()      Prefetch val: новый процесс; load_final_vocab + key_names (на каждую val)
                на micro-batch: pack → проход (полные логиты) → Scores.add: loss.item(), int ×2
                → Detail.add: target_losses (.cpu() nll и top-1) → группировка на CPU
↓ Detail.summary
best / stale, печать, append_telemetry (строка эпохи)
↓ snapshot() — ссылки на тензоры, без копий
epoch_NN.pt     torch.save(tmp) → os.replace   (веса, конфиг, история; без AdamW)
best_checkpoint.pt — только при улучшении: torch.save(tmp) → os.replace
checkpoint.pt   torch.save(tmp) → os.replace
↓ следующая эпоха: новый Prefetch train
```

| что | где |
|---|---|
| GPU→CPU | `Scores.add` (loss.item, два int счёта); `target_losses` (nll и top-1); `torch.save` (каждый тензор состояния синхронно) |
| чтение файлов | sha256 трёх файлов при старте (`data_record`); `Source.sizes` один раз за свежий прогон (`horizon`); словарь на каждую val; группы строк в процессах подготовки |
| запись файлов | три `torch.save` на улучшившейся эпохе, два без улучшения; строка телеметрии на шаг и эпоху |
| sha256 | один раз за запуск, до первой записи; при продолжении — тоже раз, для сверки происхождения |
| `Source.sizes` | один раз за свежий прогон, ноль при продолжении (горизонт из чекпойнта) |

## 3. Внесённое изменение: разбор val по целям

**`Detail.add`** (`src/mlm/train.py`). Признаки целей берутся только на позициях целей, целыми
кодами:
- причина — номером в порядке появления;
- корзина длины истории — номером на клиента;
- ключ — своим номером словаря.

Имя группы подставляется один раз на группу.

Прежде каждая val строила object-массивы строк:
- причину на всю ширину клиента (`np.asarray(client.reason, dtype=object)`, ~37 тыс. строк на
  micro-batch);
- корзину на каждую цель;
- имя ключа на каждую цель.

Затем `np.unique` сортировал строки.

Почему суммы те же до бита:
- код однозначно задаёт имя, поэтому подмножество каждой группы и порядок целей в нём те же,
  что при сравнении строк;
- `nll[mask].sum()` даёт те же суммы.

Порядок обхода групп другой, но в `summary()` группы сортируются, и итог тот же. Проверки длины
признаков против числа целей остались. Ключ без имени в словаре теперь явная ошибка, а не
случайный `TypeError` сортировки.

**`target_losses`**:
- те же куски по `TARGETS_PER_CHUNK` и та же fp32-копия куска;
- NLL и top-1 кусков склеиваются на устройстве;
- на CPU переезжают два массива на micro-batch, а не два на кусок.

Значения те же.

**Цикл обучения** (из задачи model-speed): `Scores.record` получает уже прочитанный loss.
`Scores.add` остаётся для val и тестов.

**После** (те же прогоны):
- `Detail.add` на val — 0.56 с (было 1.06–1.17), из них `target_losses` 0.37 с;
- переносов `.cpu()` — 358 на val (было 546);
- `.item()` — 179, `int()` счёта — 358, без изменений;
- разбивка та же (sha256 `27ab976523c2fef6` у трёх версий кода);
- на фиксированных micro-batch val `Detail` 1.00–1.23 → 0.49–0.60 с, весь проход val 10.0 → 9.35 с.

## 4. Не принято и почему

| кандидат | замер | решение |
|---|---|---|
| `key_names` один раз на прогон | словарь 5632 токена: ~11 мс на val (чтение JSON и цикл) | <0.1% val. Сигнатура `validate(model, source, device, token_budget)` закреплена четырьмя тестами; кэш по пути означал бы горячую подмену словаря |
| кэш `Source.sizes` / горизонта | один проход по длинам за свежий прогон: 1.38 с на 1000 клиентах (~12 с на 8500), ноль при продолжении | читается один раз; `shuffle_row_groups` в коде нет. Порядок групп у всех эпох один, горизонт считается по эпохе 1 |
| кэш sha256 | 3 файла, 76 МиБ: 0.1 с тёплыми, 1.4–2.5 с холодными (tmpfs scratch в своп); ~610 МиБ на объёме обучения — около 0.6 с тёплыми | гарантия продолжения важнее секунд; кэш по mtime/inode оставляет риск устаревшего хеша |
| best/latest одной записью + жёсткая ссылка | `torch.save` 27.6 МиБ: 0.10 с отдельно (D2H с сериализацией 0.095, запись 0.02), 0.5–0.6 с в шумном прогоне; `os.link` 0.1 мс | одна запись на улучшившейся эпохе — 0.03–0.06% эпохи на объёме обучения, порог 1% не пройден. Атомарность и форматы не трогались |
| асинхронная запись чекпойнта | — | не делалась: нужен неизменный снимок CPU (копия), гонка с эпохой |
| сжатие чекпойнта | — | не делалось |
| буфер телеметрии | 0.24 мс на строку: 1065 строк за 2 эпохи — 0.25 с (0.06%) | не менялась: свежая строка видна дашборду, падение теряет минимум |
| печать | 1069 строк — 0.011 с | не менялась |
| val в процессе обучения (`Prefetch(val, 0)`) | чередованием в одном процессе: 14–20 с против 15–23 с с процессом подготовки; 2–3 процесса хуже (23–65 с) | разница в пределах шума; конфиг `loader_workers` не трогался |
| агрегация разбора на GPU | — | порядок сумм другой; побайтный итог не гарантирован |
| счёт val из полных логитов (голова один раз) | см. model-speed, D | строки полного умножения ≠ строкам кусков на 258 из 6208 M |

## 5. Проверки

**Детерминированный путь** (flash с `deterministic=True` подменой в инструменте), настоящий
`train()`, до против после:

| проверка | итог |
|---|---|
| 3 эпохи подряд: `checkpoint.pt`, `best_checkpoint.pt`, `epochs/epoch_01..03.pt` | побайтно равны |
| то же сравнение покрывает | история трёх эпох с `val_detail`, `train_scores`, лучший val_loss, patience, LR, шаги, генераторы, AdamW, расписание |
| ранняя остановка (patience 1, min_delta 10) | обе версии останавливаются на эпохе 2 (`early_stopping`, patience 1/1); оба чекпойнта побайтно равны |
| продолжение: план на 3 эпохи, `--max-steps 531` (остановка после полной эпохи 1), затем `--resume` до 3 | все пять файлов побайтно равны непрерывным 3 эпохам |

Первая попытка продолжения запускала первую часть с `--epochs 1`. Горизонт cosine тогда
замораживается на одну эпоху, и продолжение законно идёт по другой кривой LR. Это не сравнение,
поэтому её результат не учитывается.

**Сверка val:**
- `validate()` и проход val на одних весах у базы, после model-speed и после этой задачи дают те
  же `loss_sum`, `targets`, `top1`, `top5`;
- sha256 разбивки — `27ab976523c2fef6`;
- то же при 0, 1, 2 и 3 процессах подготовки.

**Тесты:**
- новый `tests/test_orchestration_speed.py` — 7 тестов. Прежние `Detail` и `target_losses` в тесте
  дословно:
  - разбивка равна прежней побитно и по JSON — все пять корзин, три причины, ключ только в одном
    batch, batch без целей, bf16-логиты с равными значениями, куски по 2, 7 и 2048;
  - `target_losses` побитно равна прежней;
  - ключ без имени — ошибка;
  - число признаков ≠ числу целей — ошибка.
- Тесты валидации, ранней остановки, чекпойнтов, продолжения, горизонта, происхождения и
  телеметрии — существующие, все проходят.
- Корневой `pytest`: 795 passed, 0 skipped (CUDA-тесты выполнены).
- `churn_baseline`: 169 passed.
