# Скорость сборки набора 05_dataset (2026-10-07)

Задача: ускорить `python -m src.dataset.run <group>`, не меняя ни одного примера:
- отбор контекста;
- маску целей;
- границы событий;
- время, календарь, анкету;
- поведение на ошибках.

**Итог:**

- сборка набора на 1000 клиентах быстрее в **1.9×**: в одной сессии 49.6 → 26.6 с (среднее двух
  прогонов итога), отдельно 45.5 → 22.1 с (2.06×)
- `samples.parquet` и `meta.json` **побайтно те же**, что у кода до правок; отчёт сборки тот же;
- раскладка по группам строк та же (32 примера), читатели обучения получают тот же вход.

Замеры воспроизводит `bench.py`. Он читает раскладку data/ из `--root` во временном каталоге
(словарь `03_vocab` и закодированную группу `04_tokenized/train`) и пишет выдачу в `--out`.
Настоящий data/ не трогается. Код «до» — снимок рабочего дерева перед правками dataset,
подключается через `PYTHONPATH`.

```bash
.venv/bin/python audit/2026-10-07-dataset-speed/bench.py run --root <scratch> --out <dir>/train --label <имя> [--timers] [--row-group-samples N]
.venv/bin/python audit/2026-10-07-dataset-speed/bench.py profile --root <scratch> --out <dir>/train
.venv/bin/python audit/2026-10-07-dataset-speed/bench.py compare --root <scratch> <dir1>/train <dir2>/train --left-label <имя1> --right-label <имя2>
.venv/bin/python audit/2026-10-07-dataset-speed/bench.py read --root <scratch> --out <dir>/train
```

**Вход** — закодированный train из аудита encode (побайтно равный выдаче кода до правок):
- 1000 клиентов, 2 729 355 событий, 22.8 млн токенов;
- 1000 групп строк — по клиенту.

Политика контекста по умолчанию: recent, 12 000 событий и 58 000 токенов. Под неё попадает часть
клиентов: 21.4 млн токенов после отбора.

## 1. Как сборка устроена (до)

```
04_tokenized/<group>/events.parquet + profile.parquet
  → TokenizedGroup: анкета целиком (to_pylist → dict по клиенту)
  → _client_rows: read_row_group(n).to_pylist() → словарь на строку
  → _client: TokenizedEvent(list(key_ids), list(value_ids), list(positions), list(calendar)),
             event_type_of (обход positions, describe, разбор имени), sort по времени
  → build_sample: eligible на событие, EventStub на событие, select → Selection(kept, excluded),
                  цикл по оставшимся (extend ×4, append ×4), _ints(list(...)), _utc_moments
  → Sample.check: обход событий, _check_positions на каждое событие (Python по токенам)
  → _row: .tolist() всех массивов → from_pylist пачки → write_table (zstd)
```

**Где что происходит:**
- **parquet читается** в `_client_rows` по группе строк, анкета — целиком при открытии;
- **объекты:**
  - словари строк — 2.73 млн;
  - `TokenizedEvent` — 2.73 млн, с четырьмя копиями списков;
  - `EventStub` — 2.73 млн;
  - `Selection` со списками номеров;
  - словари строк выдачи;
- **numpy:** `_ints`, календарь, маска, время — копия списка перед массивом;
- **повторные проходы:**
  - `n_tokens` — дважды на событие;
  - `_check_positions` по каждому токену;
  - `.tolist()` → `from_pylist` обратно в Arrow;
- **parquet пишется** в `_write` по 32 примера.

## 3. Внесённые изменения

**D1. Чтение закодированной группы** (`dataset/tokenized.py`).
- **Колонки вместо словаря на строку.** `read_row_group(n).to_pydict()`: `to_pylist` у таблицы
  строит словари в Python поверх того же `to_pydict`.
- **Строки клиента режутся по номерам.** Клиент на границе групп строк собирается целиком, как
  раньше.
- **Без копий:** `TokenizedEvent` берёт списки как прочитаны. `to_pydict` отдаёт свои, и больше
  их не держит никто; тест закрепляет, что сборка клиента не меняет.
- **Тип события:**
  - готовая карта `event_type_names` (номер значения → тип) вместо `describe` и разбора имени;
  - поиск ключа типа — `list.index` с проверкой `positions == 0`, тот же первый подходящий
    токен.
  - Номер не из карты идёт прежним путём: неизвестный номер остановит `describe`, имя другого
    вида даст `None`.
  - `event_type_of(artifacts, row, key)` для `downstream/at_cutoff.py` тот же.
- **Сортировка** по времени осталась: она устойчива и задаёт порядок явно. Ключ —
  `attrgetter`.

**D2. Отбор контекста по границе** (`dataset/context.py`).
- `border(sizes, policy)` — сколько самых старых событий уходит за границу.
- Оставшиеся — непрерывный хвост `events[cut:]`, поэтому `EventStub` и списки номеров для сборки
  не нужны.
- `select(stubs, policy)` и `Selection` остались прежними для тестов и API, и `select` теперь
  считается через `border`.
- `_check_limits` проверяет самое длинное событие, а событие называет только при нарушении — тот
  же первый номер.

**D3. Сборка примера** (`dataset/sample.py`).
- Плоские массивы — `chain.from_iterable` по оставшимся событиям, без цикла с extend/append на
  событие.
- `event_starts` — накопленная сумма длин.
- Ошибка календаря называет то же первое событие.
- `_ints` без лишней копии `list()`. Массив по-прежнему новый: `np.array`, а не `np.asarray`.
- **Время** (`_utc_moments`) через Arrow, когда все моменты в UTC: `ZoneInfo("UTC")` от pyarrow
  или `timezone.utc`. Отсчёт от эпохи тот же, что у `replace(tzinfo=None)` → `datetime64[us]`.
  Другие пояса и наивное время — прежним путём.

**D4. Проверка примера векторно, с прежним обходом для текста ошибки** (`Sample.check`).
- `_events_hold` проверяет массивами все условия прежнего обхода:
  - события подряд от нуля и покрывают все токены;
  - у каждого хотя бы один токен;
  - маркер `key == value` на нулевой позиции;
  - `positions` внутри события — ноль или предыдущая плюс один;
  - первое значение начинается с нуля.
- Не сошлось — прежний обход (`_check_events`) называет первое нарушение тем же текстом.
- Остальные проверки — длины, анкета, время анкеты, пространство ID, `[PAD]` — без изменений.

**D5. Запись прямо из массивов** (`dataset/build.py`, `_table`).
- Колонка-список = плоские значения пачки (`np.concatenate`) и смещения (`cumsum`) →
  `pa.ListArray.from_arrays`.
- `NaT` анкеты — маска null, как `None` у `from_pylist`.
- Без `.tolist()` и `from_pylist` — и файл выходит побайтно тем же.
- Смещения list — int32. Пачка, у которой колонка длиннее 2³¹−1 значений, идёт прежним путём
  через `from_pylist`. Проверено тестом с пониженным пределом.

## 5. Ответы по пунктам

1. **Время сборки до:**
   - train (1000 клиентов): 45.5 с;
   - val и test отдельно не мерились: закодированных val/test нет, сборка линейна по токенам;
   - пара «до/после» подряд — раздел 4.
2. **Главные узкие места до:**
   - чтение закодированной группы — 48%;
   - `build_sample` — 40%: цикл по событиям, `np.asarray` от списков, время, проверка;
   - запись — 8.5%.
3. **Доля чтения закодированной группы:** 47.7% до; после — 59% под профилировщиком (16.6 из
   28.1 с): остальное ускорилось сильнее.
4. **Доля восстановления типа события:** 8.0% до (4.2 с); после — 1.9 с под профилировщиком.
5. **Нужна ли сортировка событий.** Порядок уже хронологический: encode пишет события в порядке
   препроцессинга. Но сортировка — явный контракт читателя («датасет не подразумевает чужой
   порядок»), она устойчива и на упорядоченном входе стоит O(n) — ~0.4 с. Оставлена; ключ
   `attrgetter`. Тест закрепляет, что равное время сохраняет порядок файла.
6. **Копий убрано:**
   - 4 копии списков на событие (10.9 млн списков);
   - словарь строки на событие (2.73 млн);
   - копия `list()` в `_ints` — 8 на пример.
7. **Отбор контекста:** `select` 0.6 с + `EventStub` в цикле ~2.7 с → `border` 0.18 с (под
   профилировщиком).
8. **`EventStub`:** 2 729 355 → 0 при сборке; `select()` для API и тестов строит их по-прежнему.
9. **Отбор по границе** реализован (`border`, хвост `events[cut:]`).
10. **Сборка массивов:** цикл по событиям с extend ×4 и append ×4 (≈5 с с `np.asarray`) →
    `chain.from_iterable` и `np.array` (≈2.8 с `_ints` под профилировщиком).

    микрозамере одинаковы (0.42 и 0.46 мс на 2729 событий), выигрыш дал отказ от цикла на
    событие.
12. **`Sample.check`:** 3.9 → 0.3 с.
13. **Векторизовано:**
    - покрытие границ;
    - длины ≥ 1;
    - маркеры событий;
    - `positions` внутри событий.

    Анкета (~30 токенов) проверяется прежним обходом.
14. **Повторный проход `n_values`** не убирался: два `(positions == 0).sum()` на пример — 0.02 с

15. **Повторный проход `[UNK]`** не убирался: две суммы numpy на пример — 0.02 с.

17. **Сборка таблицы Arrow:** `from_pylist` ~2.4 с → `_table` 0.23 с; `write_table` (zstd) — 2.0 с
    как было.
18. **Лучший `row_group_samples`** — 32, как есть (раздел 4).
19. **Размер файла:** 73.3 / 68.5 / 61.3 / 57.0 / 51.8 МБ при 8 / 16 / 32 / 64 / 128.
20. **Чтение обучением:** раздел 4; при 32 — 87.6 с на `Source.clients()` 1000 клиентов,

## 6. Не принято и почему

- **Сборка примера прямо из колонок Arrow**, без `TokenizedEvent`, — вторая реализация
  `build_sample` (раздел 7). Не делалась: постановка велит не начинать со сложной
  Arrow-архитектуры, а двух реализаций одного правила проект избегает.
- **Другой `row_group_samples`** — раздел 4.
- **Сокращённый поиск типа события («тип всегда второй токен»).** Не доказуемо:
  - номер ключа `event_type` — 31 при номерах ключей от 5;
  - пары события идут по `key_id`, поэтому место типа зависит от состава события.
- **Отказ от сортировки по времени** — п. 5.
- **Векторный `eligible`** (1.2 с под профилировщиком). Правило периода целей живёт в одной
  функции `targets.eligible`, и вторая его запись разошлась бы на границе (так сказано в самом
  модуле).
- **Сжатие zstd** не менялось: запись со сжатием — 2 с из ~22.
- **Счётчики `n_values` и `[UNK]` при сборке** — выигрыш 0.04 с, а счёт по готовым массивам
  проще проверить.

  Их убирает только сборка примера прямо из колонок Arrow: плоские массивы клиента и смещения,
  тип события, период целей и отбор — массивами numpy. Это архитектурная переделка: вторая
  реализация `build_sample` рядом с той, что нужна `downstream/at_cutoff.py` и тестам.
  Оценочно ещё 2–3× на сборке.
- **Многопроцессность внутри группы** — по клиентам с одним упорядоченным писателем. Не
  делалась.
