# Прямой и обратный проход PRAGMA на CUDA (2026-10-08)

Задача: ускорить шаг обучения PRAGMA (`pack` → проход → потери → backward → нормировка и клип
градиента → AdamW) на CUDA с FlashAttention, не меняя ни одного числа.

Не менялись:
- архитектура и dropout;
- группировка flash (`FLASH_ROWS`, `FLASH_PAD`, `_group_edges`);
- потери, сглаживание меток, вспомогательная цель [USR] и её вес;
- оптимизатор, клип и нормировка градиента;
- `token_budget`, `grad_accum_steps`, `TARGETS_PER_CHUNK`;
- формат и смысл чекпойнта.

**Итог** (scratch: train 1000 клиентов, 531 micro-batch; val 300 клиентов, 179 micro-batch;
RTX 3050 Laptop 4 ГиБ, flash-attn 2.8.3, bf16):

## 1. Путь CUDA (до)

```
pack                   ~35 синхронных переносов CPU→GPU: 23 поля + 12 в трёх VarlenLayout.build
InputEmbedding.embed   события: table(key), table(value), isin маркеров, синусоиды кусков,
                       × маска из одних единиц ([T, d] fp32 читается и пишется лишний раз)
Event Encoder          5 слоёв: LayerNorm → in_proj → flash (1 вызов на слой, ~37k строк,
                       события ≤ 39 токенов) → out_proj → FFN; dated = x[cu_seqlens[:-1]] + calendar
Profile Encoder        1 блок, TimeRoPE; cos/sin в fp32, приводятся к bf16 в каждом rotate
History Encoder        2 блока, вход zeros.index_copy(анкеты).index_copy(события); то же с cos/sin
Голова, счёт           hits_in_pieces: голова по кускам под no_grad + topk(5) → int() ×2 — СИНХРОНИЗАЦИЯ
RecentTypes            nonzero ×3 и torch.tensor(RECENT_DAYS) на устройство — 4 СИНХРОНИЗАЦИИ
mlm_loss               int((targets != IGNORE).sum()) — СИНХРОНИЗАЦИЯ; куски через checkpoint
backward               пересчёт головы в каждом куске (checkpoint)
цикл обучения          float(aux), loss.item() ×2 (окно и Scores.add) сразу после backward —
                       CPU ждёт конца backward, а GPU потом ждёт, пока CPU запустит клип
_foreach_div_, clip    float(norm) — единственная нужная синхронизация (проверка конечности до шага)
AdamW (fused)
```

Повторный счёт:
- голова идёт 3C раз на micro-batch: hits, потери и пересчёт в backward;
- val считает голову дважды: полные логиты и куски `mlm_loss`.

## 3. Внесённые изменения

Каждое проверено отдельно: побайтная сверка с базой в режиме gpu-det (раздел 7) и замер шага.

**B. Счёт top-1/top-5 из кусков потерь** (`src/mlm/model.py`):
- `_piece_loss` после `cross_entropy` берёт `topk(5)` тех же логитов куска под `no_grad` и кладёт
  пару счётчиков-тензоров в список `hits`;
- `forward(logits=False)` складывает их на устройстве;
- отдельный проход головы `hits_in_pieces` удалён вместе с вызовом в тесте; инвариант «счёт
  кусками = счёт по полным логитам» остался в `test_training_speed`.

Почему так безопасно:
- topk стоит после потерь, а пересчёт checkpoint в backward останавливается на последнем
  сохранённом тензоре (`early_stop`), поэтому до topk не доходит;
- граф и случайность не меняются.

Результат:
- голова идёт 2C раз вместо 3C (`Mlm.forward` 14.4 → 9.6 вызова на шаг при C ≈ 4.8);
- CUDA головы в прямом проходе 2.6 → 1.3 мс;
- счёт теперь — `topk` со сравнениями внутри кусков: CUDA `_piece_loss` в прямом проходе 4.76 →
  8.46 мс, то есть ~3.7 мс на шаг (≈0.7 мс на кусок, ~1.7% шага; в отдельном замере `topk` куска
  2048 × 5632 — 1.35 мс). Он остаётся: см. «Отклонено».

**C. Синхронизации:**

| место | на micro-batch до | неизбежна? | после |
|---|---|---|---|
| `pack`: `torch.as_tensor(…, device)` по полям | 23 | нет | 2 асинхронных переноса (E) |
| `VarlenLayout.build`: cu_seqlens, lengths, группы | 12 | нет | 6 асинхронных |
| `mlm_loss`: `int((targets != IGNORE).sum())` | 1 | нет | `count=targets.numel()` — число Python без устройства |
| `hits_in_pieces`: `int(first)`, `int(five)` | 2 | нет | счётчики остаются тензорами (B) |
| RecentTypes: `nonzero` ×3, `torch.tensor(RECENT_DAYS)` | 4 | нет | плотные маски (H) |
| цикл: `float(aux)`, `loss.item()` ×2, `int` ×2 в `Scores.add` | 5 | число нужно, ждать — нет | читаются после нормы градиента, `loss.item()` один раз |
| `float(clip_grad_norm_)` | 1 | **да** — проверка конечности до шага | остаётся |

В шаге инструмента (раздел 2) чтений цикла нет: замер 43.2 = 42 устранимых (23 + 12 + 1 + 2 + 4) +
`float(norm)` + 0.2 служебной синхронизации самого замера; после — 1.2. Пять чтений цикла — в
`train()`: прежде сразу после backward, теперь после нормы.

- Число целей передаётся числом Python: деление на тензор на устройстве округлялось бы иначе.
- Цикл обучения копит выходы проходов окна (`window_outs`). Их числа читаются в `close_window`
  сразу после `float(norm)`, в прежнем порядке сложений Python:
  - `window_loss` — прежняя сумма;
  - `Scores.record` получает уже прочитанный loss (один `.item()` вместо двух);
  - `epoch_aux` — прежний список.
- К этому моменту GPU уже пуст, и чтения стоят микросекунды. Теперь CPU запускает клип, пока GPU
  ещё в backward.
- Окно всегда пусто к моменту `snapshot()`: `max_steps` проверяется сразу после `close_window`, а
  конец эпохи закрывает окно. Поэтому чекпойнт и продолжение не меняются.

**E. `pack` и переносы** (`src/mlm/varlen.py:to_device`):
- массивы одного типа копируются в общий закреплённый буфер, переносятся одним асинхронным
  `to(non_blocking=True)`;
- каждое поле — срез своей формы с выравниванием 16 элементов;
- аллокатор CUDA держит закреплённый буфер до конца переноса;
- на CPU тот же путь без закрепления.

Замеры:

| вариант | 35 мелких массивов |
|---|---|
| по одному полю, обычная память | 2.33 мс |
| по одному полю, закреплённая | 1.06–1.2 мс |
| общий буфер | 0.30 мс |

- `pack` 3.1 → ~1.1 мс на CUDA в отдельном замере; в шаге 4.7 → 2.8 мс.
- `np.concatenate(…, dtype=)` вместо `concatenate().astype()`.
- Поля только для SDPA (`target_inside`, `target_bucket`, `target_row`) стали `cached_property` от
  тензоров устройства. На пути flash они не строятся вовсе, у SDPA — те же значения.

**F. embed без маски из единиц** (`src/embedding/layer.py`):
- `mask=None` на плоском пути flash пропускает умножение `[T, d]` на единицы;
- путь SDPA прежний;
- `embed` 3.05 → 2.67 мс в отдельном замере; в шаге CUDA прямой 2.03 → 1.85, обратный 1.11 →
  0.92 мс.

**G. cos/sin TimeRoPE** (`_activation_type`):
- углы по-прежнему в fp32;
- приводятся к типу autocast один раз на энкодер, а не четырежды в каждом блоке;
- `rotate` получает тензор уже нужного типа, и его `.to` ничего не делает;
- тип берётся из autocast устройства активаций (на CPU-тестах без autocast углы остаются fp32);
- `rotate` прямой 0.365 → 0.322 мс.

**H. RecentTypes без синхронизаций:**
- `nonzero` заменены плотными масками;
- лишнее пишется в запасную ячейку, которая отрезается, или прибавляется нулём;
- счётчики — целые числа в fp32, `amin` от порядка не зависит, поэтому цели те же до бита;
- окна сравниваются с числами Python (7, 30 и 90 представимы точно) — тензор окон не нужен;
- CUDA `RecentTypes.forward` 0.23 → 0.34 мс (плотная работа по всем токенам), но 4 синхронизации
  ушли: время части в шаге с пузырями 1.86 → 0.69 мс.

**D. Голова в val:**
- полный проход головы и куски `mlm_loss` дают одни строки логитов не всегда: на переборе M = 1…6208
  не совпали 258 размеров (cuBLAS берёт другое ядро для другого M);
- val loss из полных логитов поэтому не побайтный — отклонено;
- потоковый проход без полных логитов нарушает контракт полных логитов val
  (`test_training_math.py:572`) и меняет `Detail` (он считается по полным логитам) — отклонено;
- цена дубля: голова 0.33 мс на кусок (проекция 0.06 + умножение на словарь 0.27, отдельный замер),
  273 куска на val — ~0.09 с, меньше 1% прохода val;
- отключение aux в val экономит 0.34 мс на micro-batch (0.6% прохода val) и меняет смысл
  `Predicted.aux` в eval — не сделано.
