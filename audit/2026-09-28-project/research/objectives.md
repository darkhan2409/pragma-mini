# Аудит: самообучение на банковских последовательностях событий — литература, выводы для mini_pragma_v2 и приоритетные эксперименты

Режим был только на чтение. Я не менял ни одного файла, не запускал pytest, конвейер, обучение и ничего на GPU. Все цифры по данным получены небольшими пробами на `.venv/bin/python` по `data/03–08`, для каждой указано, как она посчитана.

## 0. Главное

1. **Нынешняя цель MLM почти не заставляет вектор `[USR]` учитывать время.** Это вывод из кода, а не из эксперимента, поэтому пометка LIKELY.
   - Выход `[USR]` используется только в голове: он склеивается с каждой целью (`src/mlm/model.py:300`, `:428-429`).
   - Для такой цели оптимальный `[USR]` — это «типичные значения полей у этого клиента», то есть распределение без учёта времени.
   - Это объясняет диагностику: `shuffled_content` 0.989 и `partial_50` 0.992 — ожидаемый результат цели, а не сбой обучения.
   - С этим согласуется литература. У MLM-энкодеров CLS-вектор без контрастной или supervised-цели слабый (SBERT: CLS 29.19 против среднего по BERT 54.81). CoLES и NPPR лучше на задачах уровня клиента.
2. **У модели нет «ощущения текущего момента», а для оттока это главный признак.** Проверено в коде (CERTAIN).
   - Время события считается от последнего события клиента (`src/temporal/position.py:93`), `[USR]` стоит в нуле (`src/mlm/model.py:220-221`).
   - Время анкеты при этом считается от cutoff (`position.py:40`). Две системы отсчёта не согласованы.
   - У CatBoost по оттоку признак №1 — `act_days_since_last` (`churn_baseline/README.md`, раздел «Результаты»).
   - Nubank описывает ровно эту проблему и лечит её временем относительно момента прогноза.
3. **Разрешение шкалы времени плохое на всём, что старше месяца.** Посчитано (CERTAIN).
   - При `8·log1p(t/8)` и `rope_base` 10000, `head_dim` 32 последний час занимает 49 из 127 единиц шкалы.
   - Всё старше 30 дней сжато в 25.5 единиц: 30 дней → 101.5, 2 года → 127.0.
   - На давности 180 дней неделя разницы — это 0.305 единицы, то есть не больше 0.3 рад поворота даже на самой быстрой частоте.
4. **Top-1 MLM 0.823 во многом «бесплатный».** Измерено (CERTAIN).
   - Ключи видимы, и справочная таблица «ключ + набор ключей события → самое частое значение» даёт top-1 0.642 на масках val.
   - Даже на целях с маскированием целого события она даёт 0.639.
   - `event_type` почти однозначно определяется набором ключей события.
   - У `currency` в словаре одна категория `KZT`. Это около 4.2% токенов и 3.7% целей.
5. **Шаг оптимизатора почти всегда видит одного клиента.** Измерено (CERTAIN).
   - 45.5% клиентов train дороже `token_budget` 16384, и на них приходится 84% позиций.
   - При `grad_accum_steps` = 1 в среднем выходит около 1.4 клиента на шаг.
   - В таких условиях контрастная цель (CoLES) невозможна без ограничения длины истории.
6. **Без оценки на downstream-задаче ни одно изменение сейчас нельзя оценить.** Это приоритет P0.
   - Литература сходится: вектор сам по себе примерно равен GBDT на ручных признаках, а в сочетании с ними даёт +0.5–2% ROC-AUC.
   - С 142 положительными примерами на test погрешность ROC-AUC около 0.014 (95% ДИ ±0.028), поэтому нужны парные сравнения на одних и тех же строках.

## 2. Общие уроки литературы

- MLM сам по себе даёт хорошие векторы токенов и событий. Для задач уровня клиента выигрывают цели, которые заставляют вектор описывать ближайшее прошлое или будущее: NPPR-PR, NEP, CoLES, HT.
- Вектор без ручных признаков обычно на уровне GBDT. Реальный выигрыш дают сочетание с ручными признаками или совместное обучение (Sber +0.009 AUC, nuFormer +1.25% отн.).
- Время относительно момента прогноза важнее абсолютного времени и времени относительно последнего события.
- Слишком длинная история даёт убывающую отдачу: 256 → 1024 событий дают +0.005 AUC.
- Гибрид генеративной и контрастной целей простой суммой потерь может ухудшить результат (MLEM).

## 3. Что это значит для проекта (факты)

**CERTAIN (прочитано в коде или измерено):**

- **F1. Системы отсчёта времени.** События считаются от последнего события: `position.py:93` — `delta = moments[-1] - moments`. `[USR]` стоит в 0 (`model.py:220-221`). Анкета считается от cutoff (`position.py:40`). Вывод: зазор «cutoff − последнее событие», то есть давность активности, в канал истории не попадает.
- **F2. Шкала времени.** `TIME_SCALE=8` (`position.py:51`), `rope_base` 10000 (`src/history/settings.py:72`), `inv_freq` (`src/history/encoder.py:71-73`). Позиции:

  | давность | позиция |
  |---|---|
  | 1 минута | 17.1 |
  | 1 час | 48.9 |
  | 1 сутки | 74.3 |
  | 1 неделя | 89.9 |
  | 30 дней | 101.5 |
  | 1 год | 121.5 |
  | 2 года | 127.0 |

  9 из 16 частотных пар за весь диапазон поворачиваются меньше чем на π, 6 из 16 — не больше 0.4 рад.
- **F3. Путь градиента в `[USR]`.** Выход `[USR]` используется только в склейке головы: `model.py:300` (`cat[token, event, client]`) и `:429` (`client_vectors[target_client]`).
- **F4. Состав целей MLM.** Три пробы.
  - Проба по `08_masked/val` + `07_batches/val`, каждая 3-я группа строк: 499 клиентов, 410 699 целей. Top-1 справочной таблицы по одному ключу — 0.502. По ключу + набору ключей события — 0.642 (в выборке; это оптимистичная оценка для такой таблицы). По причине маскирования: event 0.639, value 0.637, key 0.654. У модели на val 0.823.
  - Проба по каждой 5-й группе, 258 878 целей: категории 87.8%, числовые корзины 8.4%, куски BPE 3.8%. Самые частые ключи: `event_type` 17.7%, `app_domain` 11.6%, `firebase_screen` 8.2%.
  - Один клиент val, 2721 событие: энтропия `event_type` падает с 1.658 до 0.137 нат, если известен набор ключей события; точность по набору ключей 0.955.
  - `value_vocab.json`: у `currency` только `['KZT']`. По выборке около 61 клиента train (1.34M токенов) на `currency` приходится 4.15% токенов.
  - Там же видно, что события в основном телеметрия приложения: `app_screen` 38.4%, `app_operation` 18.6%, `banner_shown` 6.8%.
  - Для сравнения: словарь 5717 токенов, из них 4096 кусков BPE (72% словаря при 3.8% целей).
- **F5. Упаковка батчей.** По колонкам `07_batches/train`: 182.9M токенов, медиана событий на клиента 1365, 90-й перцентиль 6268. У 45.5% клиентов цена больше 16384, на них 84.3% позиций. Жадная упаковка по отсортированным длинам даёт около 6882 micro-batch'ей, то есть не больше ~1.39 клиента на шаг; настоящая потоковая упаковка может дать меньше. `grad_accum_steps=1` (`src/mlm/settings.py:111`). Обрезано 694 клиента и 1 634 510 событий (`data/05_dataset/train/meta.json`).
- **F6. Лишняя память и счёт в голове.** Полные логиты `[M, словарь]` считаются с градиентом (`model.py:433`) параллельно с кусковой потерей (`:440`). Они живут через весь backward, до `del out` (`train.py:723-738`), и нужны только для `hits()` (`train.py:213`). При лимите 4 ГБ это прямая цена.
- **F7. Диагностике не с чем сравнить.** Косинусы считаются только между клиентом и его вариантом (`src/mlm/diagnostics.py:314-318`). Базы «косинус между разными клиентами» нет, поэтому 0.989 не откалибровано.
- **F8. Промежуточных весов нет.** Сохраняются только `checkpoint.pt` и `best_checkpoint.pt` (`README.md:1044-1047`). Кривую «эпоха → качество на downstream» построить нельзя.
- **F9. Повторы событий.** 41 клиент train, 167 575 событий: уникальных последовательностей токенов внутри клиента 24.0%, на них 41.8% токенов. Календарь прибавляется после энкодера события (`model.py:528`). Значит, при извлечении векторов (eval, без масок) можно считать каждое уникальное событие один раз, и результат не изменится: энкодер события обработает примерно в 2.4 раза меньше токенов.
- **F10. Векторы на момент T технически достижимы.** Окна групп задаются конфигом (`src/preprocessing/settings.py:177-191`, `run.py:101 --config`). Откат анкеты на T уже реализован (`src/preprocessing/profile_state.py:20-33`). Каталоги этапов при этом фиксированы (`data/0N_*/<group>`), нужен отдельный корень — LIKELY.
- **F11. Статистическая мощность.** Test оттока: 142 положительных и 1318 отрицательных. SE ROC-AUC по Hanley–McNeil ≈ 0.0141.

**LIKELY:**

- Сглаживание меток на все 5717 токенов при связанных весах толкает логиты `[PAD]`, `[MASK]` и ключей, которые целью не бывают никогда.
- Dropout 0.1 (`src/event/settings.py:68`, `src/history/settings.py:66`) при 2.4M параметров и ~183M токенов за эпоху, скорее всего, лишний. На это указывает и то, что val loss ниже train, а лучшая эпоха — последняя.
- Для мошенничества на уровне операции двунаправленная история даёт утечку будущего. Векторы по префиксам требуют отдельного прохода на каждую операцию (около 1M на test) или причинного энкодера истории.

## 4. Эксперименты по приоритету

Стандартное A/B-сравнение для P1: два прогона по 3 эпохи (косинусный план на 3 эпохи, один seed). Одна эпоха ≈ 28–29 мин, прогон ≈ 1.5 ч. Затем оценка E0 парным bootstrap на `churn_baseline/reports/eval_rows.parquet`, MLM val в разрезе ключа и причины, диагностика с межклиентской базой. Оговорка: порядок вариантов после 3 эпох может отличаться от порядка после 10.

Две побочные дешёвые правки влияют на цену всех экспериментов.

- **Голова (F6).** Top-k считать внутри кусков потерь под `no_grad` и не строить полные логиты с графом. Это снижает пик памяти и убирает лишнее умножение `[M,3d]×[d,V]`.
- **Извлечение векторов (F9).** Считать каждое уникальное событие один раз: результат тот же, работы энкодеру события примерно в 2.4 раза меньше.

## 5. Чего не делать

- LLM4ES, ESQA и LLM-энкодеры текста (Nemotron-1B, как в PRAGMA): 3B-модели на 4 ГБ не помещаются.
- Размеры PRAGMA-M и L.
- Наивная сумма генеративной и контрастной потерь без подбора λ.
- Выбор вариантов по MLM val loss или top-1: они не заменяют downstream-метрику, и заметная доля top-1 — справочная таблица (F4).
- Ожидать, что один вектор обгонит CatBoost на оттоке (ROC-AUC 0.939). Реалистичная цель — прирост в сочетании с признаками, и он измерим, только если ΔROC-AUC ≳ 0.015–0.02 в парном сравнении.

## 6. Ограничения этого отчёта

- PDF-файлы не читались (нет poppler и pypdf). Цифры CoLES, TabBERT и TabAConvBERT взяты из HTML ar5iv, остальные — из HTML arXiv, через пересказ WebFetch. Таблицы стоит сверить с оригиналами.
- По FATA-Trans, TransactionGPT, Stripe PFM и ESQA прочитаны только аннотации или вторичные источники.
- Сравнение `[USR]` с `[EVT]` в PRAGMA численно не опубликовано.
- Заявление Sber «NEP лучше CoLES и MLM» дано без чисел.
- Время прямого прохода при извлечении векторов не измерено, это оценка.
- Справочная таблица 0.642 посчитана в выборке и завышает то, что можно получить вне её.
