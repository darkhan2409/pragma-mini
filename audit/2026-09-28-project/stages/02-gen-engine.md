# 01b. Генератор — движок, выпуск, память

Часть аудита `audit/2026-09-28-project`, см. `REPORT.md`.

## Сводка аудитора

Как работает: emit.generate_group → generate_dataset режет популяцию на сообщества по 32 клиента, а сообщества — на пачки по chunk_clients//32 = 8 (emit.py:378-387). Пачки уходят в Pool(min(workers, jobs)). В Python 3.14 пул запускается через forkserver (проверено пробой), поэтому каждый воркер сам импортирует модули и лениво строит мир. Внутри пачки run_community симулирует день за днём (_plan_day на клиента → общая очередь → обработчики → month_end). finish пересчитывает balance_after, накладывает дефекты и сериализует payload в JSON. Все строки пачки копятся списком dict и пишутся одним part-файлом. Родитель сверяет sha256 частей и склеивает их в events.parquet: одна row group на пачку.

Замеры по времени создания файлов в data/01_raw (6 воркеров): train 1247 с, val 213.5 с, test 256.9 с, всего около 28.6 мин. Верхняя оценка CPU: около 1 мс на клиенто-день и около 300 мкс на выпущенное событие. На выходной путь (make, дефекты, json.dumps, время строкой, Arrow) уходит около 15 мкс на событие, то есть примерно 5%. Остальное съедает логика симуляции, профиля нет.

Детерминизм и resume после F-1…F-12 по коду держатся. Слабые места:
- буфер вывода пачки занимает 0.56–0.81 ГБ на воркер;
- число воркеров по умолчанию (11) не учитывает RAM;
- Pool навсегда зависает, если воркер убит OOM-killer'ом;
- на val/test параллелизм упирается в 6 задач;
- дрейф черт после жизненных событий мёртв;
- многопроцессный путь и resume не покрыты тестами;
- report.show на реальных группах уводит машину в OOM.

Вердикт: данные корректны и воспроизводимы, но запуск по умолчанию на 7 ГБ WSL небезопасен. Потоковая запись, автоподбор воркеров и ProcessPoolExecutor — правки определённо нужные и дешёвые. Ускорение CPU в 1.2–1.5 раза вероятно, но только после профилирования.

### gen-engine-01. Вся пачка (8 сообществ, до 1.05 млн строк) копится в воркере Python-словарями и затем дублируется в Arrow

- **Вид:** память
- **Серьёзность:** высокая → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** M

**Доказательства.**

emit.py:187-199 — rows[...].extend(result.events) по всем сообществам пачки. emit.py:88-94 — _write делает pa.Table.from_pylist(rows), в этот момент обе копии живут одновременно. engine_month.py:1103-1114 — _row собирает dict из 4 строк, payload через json.dumps.

Проба (tracemalloc, row group 39 train, 40 775 строк): 507 Б на строку в Python (dict плюс свежие строки event_time и payload), 260 Б на строку в Arrow.

Размеры пачек по метаданным parquet: train max 734 158, val max 821 117, test 1 048 576 + 3 181 = 1 051 757 строк. Сообщество, если оценивать по подряд идущим блокам клиентов: медиана 76–100 тыс. строк, максимум 150–177 тыс.

Попутно: Event (observe/envelope.py:55-74) — dataclass без slots. ledger.postings (finance/ledger.py:175) в src никто не читает, только audit/…/checks/money.py:117,173,220.

**Влияние.**

Пик буфера вывода на воркер: train примерно 372 + 191 = 563 МБ, test примерно 533 + 273 = 806 МБ. Это сверх состояния симуляции сообщества (по оценке 0.2–0.3 ГБ у самого тяжёлого) и базовой памяти процесса. 11 воркеров × 0.8–1 ГБ больше 7 ГБ WSL — это и есть наблюдённое «почти исчерпание RAM». Потоковая запись по сообществам сокращает буфер в 5–6 раз, до 140 МБ или меньше.

**Предложение.**

В _run_batch открыть pq.ParquetWriter на part-файл. После каждого run_community писать его строки отдельной row group (или копить RecordBatch'и примерно до 128 тыс. строк) и сразу освобождать Python-строки. Arrow строить поколоночно через pa.array по спискам, а не через from_pylist.

Содержимое и порядок строк не меняются, меняются только байты файла (F-10 уже фиксирует, что sha256 зависит от раскладки).

Дополнительно: Event перевести на @dataclass(slots=True); ledger.postings держать только под флагом аудита.

Временный обход без правки кода: --chunk-clients 64 или 32.

**Как проверить.**

1) Построчный контент-дайджест (client_id, event_time, source, payload) и profile совпадают до и после на 512 клиентах, счётчики манифеста равны. 2) Пиковый RSS воркера (VmHWM из /proc/<pid>/status или ru_maxrss, возвращённый из _run_batch) падает минимум вдвое. 3) Wall time растёт не больше чем на 3%.

**Проверка скептиком: подтверждено.**

Механизм подтверждён. emit.py:187-199: result.events всех сообществ пачки копятся в rows. emit.py:92: pa.Table.from_pylist(rows), в этот момент обе копии живут одновременно. engine_month.py:941-981 (finish): строки _row (1103-1114) строятся, пока жив весь state.events сообщества. Event (observe/envelope.py:55) — @dataclass без slots. Ledger.postings пишется в ledger.py:81,175, а grep по src читателей не находит.

Замер повторил на row group 39 train (40 775 строк, tracemalloc): 506.7 Б на строку в Python и 260.0 Б в Arrow. Метаданные тоже сходятся: row groups train 40 шт. (40 775–734 158), val 6 (652 868–821 117), test 7 (3 181–1 048 576).

Не измерено: полный пик RSS воркера и доля состояния симуляции. «0.8–1 ГБ на воркер» пока только оценка. Поэтому «буфер в 5–6 раз меньше» не означает, что RSS упадёт вдвое.

Серьёзность понижена до medium. Генерация разовая (~29 мин). Обход без правки кода уже есть: --chunk-clients 64/32 меняет только раскладку, данные остаются побайтово равными (audit/2026-09-24-fix/REPORT.md:299).

Поправка к предложению: row group на сообщество не доедет до итогового файла. _merge_parts (emit.py:281-287) читает part целиком и перезаписывает его через writer.write_table, а тот режет таблицу по row_group_size (по умолчанию до 1 Mi строк).

**Второе мнение: подтверждено (серьёзность: средняя).**

Опровергнуть не удалось, механизм проверен по коду. emit.py:187-199: rows["events"].extend(result.events) идёт по всем community_ids пачки. per_batch = chunk_clients // community_size (emit.py:382) = 256 // 32 = 8: community_size 32 взят из params/relationships.py:40 и manifest test. emit.py:88-94: _write строит pa.Table.from_pylist(rows), список rows при этом жив, и в памяти одновременно лежат Python-dict и Arrow. Список освобождается только после возврата из _run_batch. result.events — это dict из _row (engine_month.py:960, 1103-1114): event_time — свежая строка, payload — json.dumps с ensure_ascii=False. Замеры проверил сам. Метаданные parquet: train 40 row group, max 734 158; val 6, max 821 117; test 7 групп [750255, 790361, 1048576, 3181, ...]. Каждая row group — одна пачка, пачка test больше 1 Mi строк порезана на 1 048 576 + 3 181. Проба на 40 000 строк row group 39 train: dict 184 Б, event_time 66 Б, payload 248 Б (3% не-ASCII), итого около 506 Б на строку плюс 8 Б указателя в списке. Arrow t.nbytes/rows = 260 Б. Отсюда 563 МБ для train и около 806 МБ для test сходятся. Поправки: 1) Утверждение «11 воркеров × 0.8-1 ГБ — это и есть наблюдённое почти-исчерпание RAM» правдоподобно, но не доказано. Пик буфера у воркеров наступает в конце пачки и по времени не совпадает, а finish() (engine_month.py:941-981) держит список dict сообщества одновременно с полным состоянием симуляции: Event, payload-dict, ledger. Потоковая запись по сообществам этот пик не убирает. Вклад буфера реальный, но это одна из причин, а не единственная. 2) Побочное замечание про ledger.postings почти ничего не даёт. Те же объекты Posting лежат в by_account и recent (ledger.py:184-187, читаются в :198 и :239), так что без списка postings экономится только 8 Б указателя на проводку. Event без slots (envelope.py:55) подтверждается. 3) Severity снижаю до medium. Генерация разовая, обход без правки кода уже есть: --chunk-clients 32 (одно сообщество на пачку) или меньше --workers. Инвариантность содержимого к размеру чанка заявлена в emit.py:34-37 и :509-511. Предложение (ParquetWriter в _run_batch, row group на сообщество, pa.array по колонкам) корректно: sha256 части считается после записи файла (emit.py:213), и склейка через _merge_parts не ломается.

**Источники:** https://arrow.apache.org/docs/python/generated/pyarrow.parquet.write_table.html

### gen-engine-02. Число воркеров по умолчанию = cpu_count−1 = 11, без учёта RAM и физических ядер

- **Вид:** устройство
- **Серьёзность:** высокая → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** S

**Доказательства.**

emit.py:545-546 — default_workers() = max(1, cpu_count−1). emit.py:614 — --workers по умолчанию берёт это значение.

Пробы среды:
- Python 3.14.4, multiprocessing.get_start_method() = 'forkserver': копирования при записи от родителя нет;
- lscpu: 6 ядер × 2 потока;
- MemTotal 7.0 ГиБ, MemAvailable около 4.5–4.9 ГиБ;
- .wslconfig: memory=8GB, swap=4GB.

README §1 (строки 51-63) не упоминает ни --workers, ни память.

**Влияние.**

Команда из README (python -m src.generator.emit train) поднимает 11 процессов с пиком 0.8–1 ГБ каждый. Итог — либо своп в vhdx с кратным замедлением, либо OOM-kill воркера, который из-за gen-engine-03 превращается в зависание. Сверх 6 процессов прибавка идёт только от SMT; её размер надо измерить (X-03).

**Предложение.**

default_workers = min(os.process_cpu_count() − 1, floor((MemAvailable − 1 ГБ) / бюджет_на_воркер)). MemAvailable читать из /proc/meminfo, без psutil. Бюджет на воркер — константа, измеренная в X-02: сейчас около 1 ГБ, после gen-engine-01 около 0.4–0.5 ГБ. Выбранное число и причину печатать. Описать в README §1.

**Как проверить.**

На текущей машине (около 4.9 ГБ available) по умолчанию выбирается не больше 5–6 воркеров. Прогон 1024 клиентов идёт без свопа (vmstat si/so = 0), MemAvailable не опускается ниже 500 МБ.

**Проверка скептиком: подтверждено с поправками.**

Подтверждено: emit.py:545-546 max(1, cpu_count−1), emit.py:614 default=default_workers(). nproc = 12, MemTotal 7.0 ГиБ, MemAvailable ~4.9 ГБ, start method forkserver (проверил). README:51-59 не описывает ни --workers, ни память.

Поправка:
- 11 процессов поднимаются только на train (40 задач). На val и test Pool ограничен числом задач: min(workers, len(jobs)) = 6 (emit.py:439).
- Бюджет «0.8–1 ГБ на воркер» не измерен, это экстраполяция. Эмпирическое наблюдение пользователя («почти исчерпание RAM при 11») с ней согласуется.

High завышено: пользователь уже работает с 6 воркерами, а правка — S. Medium.

**Источники:** https://docs.python.org/3.14/library/multiprocessing.html

### gen-engine-03. multiprocessing.Pool зависает навсегда, если воркер убит (OOM-killer); память воркеров не сбрасывается

- **Вид:** риск корректности
- **Серьёзность:** средняя → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** S

**Доказательства.**

emit.py:438-444 — with Pool(...) + imap_unordered(_run_batch, jobs), без maxtasksperchild.

CPython gh-66587 (bpo-22393) всё ещё открыт: Pool заменяет умерший процесс, но задача не завершается, и итератор ждёт вечно. ProcessPoolExecutor в той же ситуации поднимает BrokenProcessPool, а с 3.11 поддерживает max_tasks_per_child (несовместим только с fork).

Пул памяти pyarrow — mimalloc (проба).

**Влияние.**

На 7 ГБ при 11 воркерах нехватка памяти — реальный сценарий. Генерация тогда не падает, а висит без вывода и держит память остальных воркеров; видно только застывший счётчик batches.

Вероятно, RSS каждого воркера держится на максимуме его самой крупной пачки до конца прогона: pymalloc и mimalloc не всегда возвращают память ОС.

**Предложение.**

Перейти на concurrent.futures.ProcessPoolExecutor(max_workers, mp_context=get_context('forkserver'), initializer=_worker_init, initargs=..., max_tasks_per_child=1) с обходом через as_completed.

BrokenProcessPool превращать в GenerationError: «воркер убит, вероятно, из-за памяти; продолжите с --resume --workers N−2». Маркеры пачек уже делают resume безопасным.

max_tasks_per_child=1 сбрасывает RSS после каждой пачки. Цена — повторный импорт и построение мира, секунды на пачку длиной в минуты.

**Как проверить.**

X-07: на 64 клиентах убить воркер через SIGKILL посреди прогона. Сейчас ожидается зависание до таймаута, после правки — ошибка за секунды. Затем --resume даёт контент, равный непрерывному прогону.

**Проверка скептиком: подтверждено.**

emit.py:438-444: Pool(...) + imap_unordered без maxtasksperchild и без таймаута. Прочитал https://github.com/python/cpython/issues/66587: issue открыт, фикс не влит, Pool при гибели воркера висит бесконечно.

Часть про RSS, который держится на пике, — правдоподобное предположение, не замер.

Цена max_tasks_per_child=1 не измерена. Каждая пачка заново строит кэши мира через state_cache: product_catalog._build (world/products.py:678), география, мерчанты. «Секунды» — предположение.

Замечание к выбору правки: Pool(maxtasksperchild=1) решает только RSS, но не зависание. ProcessPoolExecutor решает оба. Resume уже безопасен благодаря маркерам (emit.py:419-423).

**Источники:** https://github.com/python/cpython/issues/66587, https://docs.python.org/3.14/library/concurrent.futures.html

### gen-engine-05. Дрейф черт после жизненных событий вычисляется, но нигде не читается

- **Вид:** моделирование
- **Серьёзность:** средняя → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** M

**Доказательства.**

simulate.py:465-472 — для каждого жизненного события вызывается traits.with_shift(event_shift(...)), результат ложится в state.traits. По grep в src state.traits больше нигде не читается.

Все потребители зовут persona.trait(name, ts) (persona.py:107-108). Он берёт persona.traits из draw_traits, где сдвигов нет (traits.py:181-184). Persona заморожена (persona.py:39) и нигде не подменяется.

Поэтому параметры params/traits.py:142-160 на ленту не влияют: job_loss (price_sensitivity +0.10, credit_appetite +0.06), move (merchant_loyalty −0.18), child_birth и остальные, drift_blend_days = 45. Прежние аудиты этого не отмечали.

**Влияние.**

Механизм «жизненное событие → смена поведения через черты» не работает. После потери работы, переезда или рождения ребёнка поведение меняется только через доход, стресс и привычки. В данных меньше нестационарности во времени, а диагностика как раз показывает слабую чувствительность эмбеддинга к временной структуре (shuffled_content 0.989). Связь этих фактов спекулятивна.

Если дрейф оживить, Traits.at() (traits.py:90-115) станет горячим местом: он копирует dict и проходит все сдвиги на каждый вызов trait(), а таких вызовов десятки на клиенто-день.

**Предложение.**

Решить явно, одним из двух способов.

Либо удалить event_shift, with_shift, drift_per_event и state.traits: CLAUDE.md требует удалять неиспользуемую логику.

Либо оживить: держать Traits со сдвигами в ClientState и передавать их в места, где сейчас стоит persona.trait(...). Traits.at тогда предвычислять кусочно (сдвиги известны при подготовке клиента) или кэшировать по дню. Данные при этом изменятся — поднять GENERATOR_VERSION.

**Как проверить.**

Юнит-тест: у клиента с job_loss значение price_sensitivity, прочитанное поведением через 60 дней после события, отличается от базового на ожидаемую дельту. X-06 проверяет, что сдвиг виден в поведении.

**Проверка скептиком: подтверждено.**

simulate.py:465-472: state.traits = traits.with_shift(...). grep по src показывает, что state.traits больше нигде не читается. persona.trait (persona.py:107-108) → persona.traits из draw_traits без сдвигов (traits.py:181-184). Persona frozen (persona.py:39), подмен через replace нет.

История (git show ab0c7a1): прежде state.traits читал только экспорт скрытой правды (строки `final = state.traits.at(...)`, `for shift in state.traits.shifts`). Коммит ab0c7a1 их удалил, и механизм стал мёртвым. Поведение сдвиги не видело никогда.

README и tests дрейф не упоминают. drift_per_event и drift_blend_days (params/traits.py:142,160) на данные не влияют — ловушка для калибровки.

Связь с диагностикой эмбеддинга (shuffled_content 0.989) спекулятивна. Изменения во времени уже несут доход, стресс и привычки.

### gen-engine-08. pytest не проверяет многопроцессный путь, независимость от чанка и resume генератора

- **Вид:** пробел тестов
- **Серьёзность:** средняя → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** S

**Доказательства.**

Все выгрузки в тестах идут с workers=1: tests/test_generator_horizon.py:48-58, test_generator_fraud.py:78-88, test_generator_lifelong.py:61-68. grep по tests/ не находит для генератора ни resume, ни GenerationError, ни _merge_parts, ни chunk_clients.

Проверки воркеров, чанков, порчи частей и resume есть только в audit/2026-09-24-fix/checks/*.py, вне pytest. Отчёт fix, §4: «Многопроцессность при resume… проверялись на одном воркере».

**Влияние.**

Любая правка emit, включая предлагаемые gen-engine-01, 03 и 04, может молча сломать независимость от воркеров и чанка или resume. А генератор — корень всех данных.

**Предложение.**

Быстрый CPU-тест: 8 клиентов, community 4, окно 2 мес., каталог в tmp_path.
1) workers=1 против 2 и chunk 4 против 8 → одинаковый контент-дайджест.
2) Удалить маркер одной пачки → --resume даёт тот же контент и тот же манифест (кроме chunk).
3) Подменить байты части → GenerationError.
4) Пустая пачка склеивается корректно.

**Как проверить.**

Мутационная проверка: тест падает, если в _run_batch переставить сообщества или убрать подпись части. Время теста меньше 15 с, с учётом старта forkserver.
