# 05–06. Датасет и временные позиции

Часть аудита `audit/2026-09-28-project`, см. `REPORT.md`.

## Сводка аудитора

Этап 05 (src/dataset) читает 04_tokenized. Файл событий читается по группам строк (одна группа = один клиент), анкета держится в памяти словарём. События клиента устойчиво сортируются по времени. target_event_mask строится по окну маскирования группы; profile_change и источник вехи целью не бывают. Отбор recent оставляет самый свежий хвост из целых событий, не больше 12000 событий и 58000 токенов. Инварианты проверяются, результат пишется одной строкой на клиента на final_cutoff: samples.parquet (zstd, 32 клиента на группу строк) и meta.json. Этап 06 (src/temporal) перечитывает 05 и добавляет event_time_log = 8·log1p(Δ/8), где Δ — расстояние до ПОСЛЕДНЕГО события, и profile_time_log (давность вехи до cutoff). Затем он переписывает полную копию строки и lineage.json.

Вердикт. Контракты чистые и детерминированные, от утечек защищены хорошо: потеря цели в val/test — ошибка сборки. Память потоковая. По времени этапы дешёвые: 05 ≈ 5.6 мин на train + ~1 мин на val и на test; 06 ≈ 3 мин (по mtime файлов).

Главные слабости:
1. Представление времени (лог-шкала от последнего события + RoPE base 10000 + bf16) почти не различает паузы в истории старше нескольких месяцев. Это совпадает с диагностикой: shuffled_content 0.989, partial_50 0.992.
2. Нет точки среза T, отдельной от окна группы. Без неё churn/fraud-голову нельзя построить без утечки.
3. Разрыв «последнее событие → cutoff» модели не виден.
4. MAX_TOKENS=58000 пропускает 45% клиентов соло-проходами больше бюджета 16384: пиковую память задаёт этот предел.
5. lineage не связывает этапы по содержимому.
6. 06 — избыточная материализация (889 МБ).

### dataset-temporal-02. Нет точки среза T, отдельной от окна группы: churn-голову нельзя честно построить на текущих примерах

- **Вид:** устройство
- **Серьёзность:** высокая → высокая после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** L

**Доказательства.**

- src/dataset/build.py:141 — window = PreprocessingConfig.load(None).windows.get(group).
- build.py:154 — cutoff = window.final_cutoff.
- build.py:156-161 — 04 обязан быть закодирован на тот же cutoff.
- build.py:30-33 — «Второй пример одного клиента не создаётся: срез у группы один».
- src/dataset/run.py:83-86 — есть только --config (context, row_group_samples), cutoff задать нельзя.
- churn_baseline/README.md: T = конец выгрузки − 60 сут (train 2025-11-02, val 2026-01-31, test 2026-06-02), метка по (T, T+60d]. Текущие примеры test содержат события до 2026-08-01, то есть окно метки лежит внутри контекста.
- Fraud в бейзлайне построчный: нужен эмбеддинг на момент каждой транзакции.
- PRAGMA §3: «gather the event history and profile attributes directly preceding the evaluation point».

**Влияние.**

Главную цель проекта — сравнить с CatBoost (churn ROC-AUC 0.939 / PR-AUC 0.618, fraud PR-AUC 0.864) — нельзя выполнить без нового пути данных. Если взять готовые 05-08, окно метки churn окажется в контексте, то есть будет прямая утечка. Анкету на T тоже нужно снять заново на этапах 02-04.

**Предложение.**

Ввести явную точку оценки T (evaluation point), не связанную с окном маскирования:
- 02-04 снимают анкету на T (механизм state_at_event_cutoff уже есть, нужна только передача параметра);
- 05 берёт события < T и не строит целей;
- позиции отсчитываются от T;
- T записывается в meta и lineage.

Для fraud нужны точки оценки на уровне событий или каузальное извлечение.

**Как проверить.**

Тест в духе churn_baseline test_future_does_not_change_features: добавление событий ≥ T и изменения анкеты после T не меняют ни одного байта примера. Затем эксперимент X-04.

**Проверка скептиком: подтверждено.**

build.py:141 (окно из PreprocessingConfig), :154 (cutoff = window.final_cutoff), :156-161 (04 обязан совпасть по cutoff), :30-33 («срез у группы один»). В run.py:83-86 есть только group и --config. churn_baseline/README.md:38,44,46: T = конец − 60 сут, test (2026-06-02, 2026-08-01]. В 05/test/meta.json final_cutoff 2026-07-31T19:00Z, значит окно метки лежит внутри контекста. Это недостающая функция, а не ошибка в существующем коде: известно, что головы ещё нет. Но она блокирует главную цель, а переиспользование 05-08 дало бы прямую утечку. Уточнение для плана: события < T можно отфильтровать из уже готовых 04/05 по event_time. Заново на T нужна прежде всего анкета: Lifelong-вехи после T profile_time_log отвергнет (position.py:130). Зависит ли кодирование событий в 04 от cutoff помимо фильтра, я не проверял.

**Источники:** https://arxiv.org/html/2604.08649v1

### dataset-temporal-01. Лог-шкала от последнего события + RoPE base 10000 + bf16: паузы в старой истории модели почти не видны

- **Вид:** моделирование
- **Серьёзность:** высокая → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** M

**Доказательства.**

Код:
- src/temporal/position.py:65-70 — log_age = 8·log1p(Δ/8).
- position.py:93 — delta = moments[-1] - moments.
- src/history/encoder.py:71-74 — inv_freq = base^(-2i/d), base 10000 (src/history/settings.py:72); при head_dim 32 это 16 частот.
- encoder.py:120 и src/mlm/varlen.py:414-415 — cos/sin приводятся к x.dtype, то есть к bf16 под autocast.

Замеры по data/06_temporal/val (3.97 млн событий):
- последние сутки занимают 74.3 из ~129 единиц шкалы (57%), а событий в них 0.31%;
- 90% событий лежат в полосе [105, 128] (p10 105.0, p99 127.7);
- 240 873 пары соседних событий с паузой ≥1 сут. Если позднее событие старше 180 дней: пауза 1-3 сут даёт медиану Δpos 0.028 (у 99.2% Δpos < 0.1), пауза 7-30 сут — 0.168, пауза ≥30 сут — 0.56. Для сравнения: 1 минута у якоря = 17.1 единицы.

Частоты на диапазоне 0..130:
- пары k=11..15 поворачиваются всего на 0.23 / 0.13 / 0.073 / 0.041 / 0.023 рад, то есть 5 из 16 пар почти не несут позиции;
- проверка на CPU (torch): пауза в 1 сутки на давности 1 год даёт побитово одинаковые bf16 cos/sin у 11 из 16 пар; пауза 7 сут на давности 180 дней — у 3 из 16.

Порядка нет:
- 3.5% событий val имеют то же время, что предыдущее, 40.8% идут в пределах 60 с;
- канала индекса нет, поэтому одновременные события неупорядочены (диагностика shuffled_order = 1.0).

PRAGMA (arXiv 2604.08649, §2.2, §2.3.4) использует ту же формулу и якорь: это точная копия эталона. Но там 6500 событий на пользователя, а здесь плотная лента ~3 события в день за 24-31 мес.

**Влияние.**

Энкодер истории различает время подробно только в последние дни. Паузы, регулярность и тренды старше ~3-6 мес для внимания почти неразличимы. Эмбеддинг вырождается в «мешок событий»: это согласуется с shuffled_content 0.989 и partial_50 0.992.

Признаки оттока из бейзлайна:
- act_gap_max_90 и trend_30_90 выразимы лишь частично: диапазон 30→90 дней занимает ~9 единиц (101.5→110.3);
- тренд за полгода-год уже почти не выразим.

**Предложение.**

1) Добавить канал относительного времени, не зависящий от давности: log1p(Δt_prev/τ) и log1p(Δt_next/τ) на событие (τ≈60 с). Подавать в MLP календаря, то есть 6→8 входов. Это стиль THP/Time2Vec.
2) Разделить головы, как в TO-RoPE split-by-head:
   - половина голов оставляет лог-позицию;
   - половина получает линейное время в сутках, base подобрать так, чтобы длины волн покрывали ~1 ч … ~3 года;
   - при необходимости добавить порядковый индекс для одновременных событий.
3) Поворот делать в fp32: q/k → float → rotate → обратно. Это дёшево.
4) Если лог-шкала остаётся, подобрать rope_base под диапазон 0..130 (например, ~300).

**Как проверить.**

Эксперименты X-01, X-02, X-03. Критерии успеха:
- медиана cosine в shuffled_content ≤ 0.95;
- R² пробы на признаки пауз и давности вырастает на ≥0.1;
- val MLM ухудшается не больше чем на 0.01 nats.

Также нужен юнит-тест: пары событий с паузой 1 сут на давности 1 год различимы по углам хотя бы в N парах частот.

**Проверка скептиком: подтверждено с поправками.**

Механика подтверждена. position.py:65-70 и :93 (якорь moments[-1]). encoder.py:71-74 (inv_freq, base 10000, history/settings.py:72). encoder.py:120 и varlen.py:414-415 приводят cos/sin к x.dtype. Мой пробник по 06_temporal/val (3 972 274 событий) дал: p10/p50/p90/p99 = 105.05/118.25/124.87/127.67; доля позиций <74.3 равна 0.31%; одинаковое время у 3.5%, ≤60 с у 41.2% (у аудитора 40.8%, вероятно из-за границы < против ≤); 240 873 пар с паузой ≥1 сут; при давности >180 дней медиана Δpos 0.028 для 1-3 сут (99.2% <0.1), 0.168 для 7-30 сут, 0.56 для ≥30 сут. Углы 130·inv_freq для k=11..15 равны 0.231/0.13/0.073/0.041/0.023. Проверка на CPU: побитово равные bf16 cos/sin у 11/16 пар (1 сут на давности 365 дней) и у 3/16 (7 сут на давности 180 дней). Поправки: (1) bf16 здесь вторичен. При Δpos=0.022 даже самая быстрая пара поворачивается на ≤0.022 рад, и поворот в fp32 почти ничего не даст: предел задаёт лог-сжатие, а не точность. (2) В PRAGMA 6500 — это порог подвыборки («users with more than 6,500 events are subsampled»), а не типичная длина. Формулу и якорь (последнее событие) я подтвердил по arxiv.org/html/2604.08649v1. (3) Вывод о том, что эмбеддинг вырождается в мешок событий из-за шкалы, не доказан. [USR] усредняет ~2000 событий, а MLM не вознаграждает чувствительность [USR] к порядку, поэтому shuffled_content 0.989 может получиться и при хорошей временной шкале. Это нужно проверить (X-01), а не принимать как certain. Календарь hour/dow/dom частично восстанавливает локальный ритм. Поэтому severity medium, а не high.

**Источники:** https://arxiv.org/html/2604.08649v1, https://arxiv.org/abs/2510.20455, https://arxiv.org/abs/1907.05321, https://arxiv.org/abs/2002.09291

### dataset-temporal-03. Отсчёт от последнего события: разрыв «последнее событие → cutoff» модели не виден, а анкета отсчитывает время от cutoff

- **Вид:** моделирование

| доля > 1 сут | 6.8% | 5.7% | 6.9% |

**Влияние.**

У ~6-7% клиентов (и, вероятно, больше в точке T) тишина в 1 день и в 300 дней до среза неразличима: меняется только содержимое. Для них главный сигнал оттока пропадает. Кроме того, энкодер анкеты и энкодер истории живут в разных системах отсчёта.

Если нужна совместимость с PRAGMA — добавить в слот [USR] скаляр log-разрыва до cutoff.

**Как проверить.**

**Проверка скептиком: подтверждено.**

Календарь: preprocessing/settings.py:75. Мой пробник (разрыв между последним событием и final_cutoff): val >1 сут 5.7%, >7 сут 2.2%, >30 сут 0.34%, максимум 253 д; test 6.9% / 3.0% / 0.47%, максимум 128 д. С аудитом совпадает. Ограничение влияния аудитор назвал честно. В точке T для churn эта информация важнее, потому что длинный разрыв — это как раз уходящие клиенты. Исправление дешёвое. Medium оставляю.

### dataset-temporal-04. MAX_TOKENS=58000 при token_budget=16384: 45% клиентов идут соло-проходом больше бюджета, а половину окна тяжёлых клиентов занимают события приложения

- **Вид:** устройство
- **Серьёзность:** средняя → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** M

**Доказательства.**

Код:
- src/dataset/settings.py:71,80; src/dataset/context.py:116-136.
- src/mlm/inputs.py:333-350: клиент дороже бюджета идёт отдельным проходом (строка 339).
- src/mlm/settings.py:107 — token_budget 16384.

- 4348 из 9556 клиентов (45.5%) дороже 16384 позиций, на них приходится 84.3% всех позиций;

Усечение по meta.json:
- train 694 клиента (7.3%), 1 634 510 событий (6.6%);
- val 134 (9.2%) / 395 504 (9.1%);

Про пределы (проба по 05):
- MAX_EVENTS почти никогда не решает: из примерно 695 усечённых train он сработал у 15, в val у 3, в test у 4;

Состав окна (каждая 4-я группа строк train):
- усечённые клиенты — это 22% токенов;
- в их окне app_screen 28.3%, app_operation 18.2%, banner_shown 5.3%, итого 51.8% (у всех клиентов — 36.6%).

Потеря считается по токенам целей (src/mlm/train.py:728-731). Метки усечения в примере нет, число выброшенных событий лежит только в meta.

**Влияние.**

Размер шага прыгает от 16k до 70k позиций. Это, вероятно, вклад в рост reserved памяти до 4.41 ГиБ и в переливание WDDM (известная проблема 2).

Тяжёлые клиенты (7.3%) дают ~22% целей и доминируют в градиенте. Половина их окна — телеметрия приложения, а финансовая история режется.

Модель не отличает «история обрезана» от «клиент пришёл недавно».

**Предложение.**

- Для train: случайные непрерывные окна или срезы на каждую эпоху с потолком ≈ token_budget; позиции пересчитываются от конца окна (нужен расчёт на лету, finding 07). За несколько эпох все события успевают побыть целями. Для val/test оставить полный свежий хвост.
- Альтернатива: усечение с учётом типа — сначала выбрасывать старую телеметрию (app_screen, app_operation, banner_shown).
- MAX_EVENTS оставить только как защитный предел.
- Добавить явный признак усечения (скаляр или слот) — это известный факт, а не придуманное значение.

**Как проверить.**

X-05: torch.cuda.max_memory_reserved ≤ 3.0 ГиБ без замедления, время эпохи меньше, val loss в пределах +0.02, диагностика partial_* не хуже. X-06 — офлайн-оценка выигрыша по длине финансовой истории.

**Проверка скептиком: подтверждено с поправками.**

Цифры подтверждены пробником по 07_batches/train (cost = n_tokens+profile_n_tokens+n_events+1, как в inputs.py:318-329): 4348/9556 = 45.5% клиентов дороже 16384, на них 84.3% позиций, максимум 69 959, p50/p90/p99 = 13 601/57 714/68 911. Соло-проход: inputs.py:339-348. Усечение по meta: train 694/1 634 510, val 134/395 504, test 199/775 815. Поправки. (1) Предел выше бюджета задан намеренно: dataset/settings.py:73-80 документирует 60k токенов = 2.97 ГиБ. То, что это вызывает рост reserved-памяти, — гипотеза, а не факт. (2) «Модель не отличает обрезанную историю от прихода недавно» верно лишь отчасти: в анкете есть веха bank_registered с давностью от cutoff, и из неё видно, что клиент старше ленты. Явного признака усечения действительно нет. build.py:39-41 утверждает обратное («видно в самой строке»), и это ошибка документации. (3) Долю app_* в окне (51.8%) я не перепроверял.

### dataset-temporal-06. lineage не связывает этапы по содержимому: устаревшие 06/07/08 после пересборки 05 проходят проверку

### dataset-temporal-X-01. Проба временной информации в текущем [USR] (без обучения) (P1)

**Гипотеза.** Текущий [USR] линейно хорошо кодирует состав событий, но плохо — давность и паузы. Если так, finding 01/03 проявляются в эмбеддинге.

**Проверка постановки: постановка корректна.** Не сделано, выполнимо: инференс без grad на 2962 клиентах — минуты, память по пику прохода ≤ обучения. ### dataset-temporal-X-02. A/B представления времени: Δt-канал, якорь на cutoff, разделение голов по времени, день года (P1)

**Гипотеза.** Относительное время, не зависящее от давности, и линейные по времени головы делают паузы и тренды видимыми и снижают инвариантность к перестановке содержимого, не ухудшая MLM.

- D — C плюс split-by-head: 2 головы с лог-якорем, 2 головы с RoPE по суткам (base подобран под длины волн 1 ч…3 года), поворот в fp32;
- E (опционально) — D плюс sin/cos дня года.

Позиции лучше считать на лету (X-07), иначе на каждый вариант пересобирать 06-08 (~10 мин).

- partial_50 ≤ 0.97;
- R² пробы X-01 для y1..y3 выше A на ≥0.1.

**Стоимость.** ~1.5 ч на вариант (3 эпохи × ~29 мин), 4-5 вариантов ≈ 6-8 ч GPU; код M.

**Проверка постановки: постановку нужно исправить.** Направление разумное, дизайн слабый. (1) 3 эпохи с косинусом на 3 далеки от сходимости: на 10-й эпохе val ещё падает, и порог 0.01 nats, вероятно, внутри шума. Нужны два прогона A с разными seed, чтобы оценить разброс. (2) Критерий «shuffled_content ≤ 0.95» не мера качества: чувствительность к перестановке не равна полезности. Основной метрикой взять X-01/X-04. (3) D (2+2 головы при 4 головах) меняет ёмкость.
