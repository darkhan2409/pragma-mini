## Сводка аудитора

Как устроено. Этап 09 разыгрывает одну общую таблицу E[5717×128]: N(0, 1/√d), собственный torch.Generator, seed 42 (src/embedding/layer.py:89-100). MLM-голова берёт логиты скалярным произведением с той же таблицей по всему словарю. ### input-init-01. Связанная голова: softmax по всем 5717 строкам с равномерным сглаживанием — 8.3% вероятности на невозможные классы, 1436 строк схлопнуты в один вектор

- **Вид:** моделирование
- **Серьёзность:** высокая → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** M

**Доказательства.**

Код:
- src/mlm/model.py:300-302 `return self.proj(context) @ weight.t()` — логиты по всей общей таблице: ключи, спецтокены, BPE, значения всех полей.
- src/mlm/model.py:358-361 `F.cross_entropy(..., label_smoothing=smoothing)` — ε/V распределяется на все 5717 классов.
- Та же таблица на входе: model.py:433,441.

Проба 1 (CPU, sdpa, best_checkpoint, 60 val-клиентов с 200–4000 токенами, 3657 целей):
- вне множества значений ключа лежит в среднем 8.31% вероятности. Множество — пары key→value из 07_batches/train плюс [UNK];
- CE без сглаживания: 0.6935 по полному словарю, 0.6062 с маской логитов по ключу;
- top1 0.7905 в обоих случаях.

Проба 2 (все val, fixed masks):
- из 1 244 542 целей ни одна не лежит вне train-множества своего ключа;
- ключей 80, размер множества: медиана 9, максимум 2658.

Обученная таблица:
- 1436 строк без вхождений во входы train (1402 BPE, 32 корзины, [PAD], [MASK]) сошлись к одному вектору: средний попарный cos 0.996, разброс 0.013 вокруг вектора нормы 0.268.

Метрика:
- пол сглаженной CE при ε=0.1 и V=5717 ≈1.19 из итоговой val loss 1.648;
- validation и early stopping считают out.loss со сглаживанием (src/mlm/train.py:393-404).

Эталон PRAGMA тоже сопоставляет с таблицей эмбеддингов (arXiv 2604.08649). Это не отклонение от эталона, а его слабое место на нашем масштабе.

**Влияние.**

- Модель учится отдавать около 10% массы классам, которые при видимом ключе невозможны. Это портит калибровку распределения.
- Каждая строка, которая не бывает целью, на каждом шаге получает со стороны выхода одинаковый градиент −Σ(p−ε/V)·h и тянется к общему аттрактору. Это затирает входную идентичность таких строк (см. input-init-02). Механизм вероятен, сам коллапс измерен.
- Val loss примерно на 72% состоит из пола (1.19 из 1.65), поэтому выбор best и early stopping слабо чувствительны.
- При оценке без переобучения ограничение даёт −0.087 нат CE (−12.6%) при том же top1.

**Предложение.**

1. Построить по 07_batches/train булеву маску кандидатов allowed[key_id → value_ids] плюс [UNK]. Это train-статистика, утечки нет; сборка занимает около 7 с.
2. В _piece_loss и hits выполнять `logits.masked_fill(~allowed[key_of_target], -inf)`. key_of_target = data.key_ids[data.target_token] уже есть в PackedBatch.
3. Сглаживание делать только внутри множества кандидатов, для корзин — соседское (input-init-03).
4. [PAD], [MASK], [EVT], [USR] и строки-ключи никогда не делать кандидатами.
5. Главной метрикой val и early stopping сделать CE без сглаживания по ограниченным логитам.

Альтернатива для A/B: развязать выходную таблицу и держать в ней только строки, которые бывают целями (Chung et al. 2020).

**Как проверить.**

Юнит-тесты:
- логиты вне множества равны −inf, а CE совпадает с CE над подмножеством;
- строка, которая не бывает целью, после шага не получает градиента со стороны выхода. Проверять по .grad таблицы при вход без этой строки.

Проба на обученной модели:
- доля массы вне множества ≈0;
- |row−dead| строк анкеты > 0.5.

A/B-эксперимент input-init-X-02.

**Проверка скептиком: подтверждено с поправками.**

Код подтверждён. Логиты берутся по всей таблице: src/mlm/model.py:300 `self.proj(context) @ weight.t()`. CE со сглаживанием по всем V: model.py:358-361. AdamW с weight_decay=0.01 на всех параметрах: train.py:506-510, settings.py:102. Val считает out.loss со сглаживанием (Scores.add, train.py:215). Коллапс проверил сам по best_checkpoint: 30 заведомо мёртвых строк (корзины credit_limit/credit_utilization/relationship_months, [PAD], ключи profile_holds_*/contracts) дают средний попарный cos 0.998 и норму 0.268±0.0008. Скан 07_batches/train за ~5 с (299 групп, key_ids+value_ids+profile) дал ровно 1436 строк без вхождений: 1402 BPE, 32 корзины, [PAD], [MASK] (к ним ещё 14 ключей). Weight decay 0.01 при lr≤3e-4 такого сжатия нормы не объясняет, значит тянет выходная сторона. PRAGMA тоже использует label smoothing и маскирует только события (arxiv.org/html/2604.08649v1). Что преувеличено: (а) 8.3% массы вне множества — это просто цель сглаживания, которая сама кладёт туда ε·(V−|S|)/V ≈ 10%, а не сбой обучения; (б) −0.087 нат при пост-хок маскировании логитов гарантированы перенормировкой (p_y только растёт) и не говорят, что обучение с маской будет лучше; (в) постоянный пол ~1.19 не меняет ранжирования эпох, так что тезис «early stopping слабо чувствителен» неверен (сглаженная CE почти монотонна по NLL); (г) коллапс строк, которых нет во входах, входу вреда не наносит. Реальный вред — выходное стягивание редко полезных входных строк (возраст и др., см. 02). Это вероятно, но причинно не доказано. Предложение ограничить softmax ключом разумно, но это улучшение дизайна, а не баг.

**Источники:** https://arxiv.org/html/2604.08649v1, https://arxiv.org/abs/2010.12821, https://ar5iv.labs.arxiv.org/html/2302.06375

### input-init-03. Числа кодируются независимыми строками таблицы: порядок выучен только у частых корзин событий, у возраста и редких шкал его нет, величина внутри корзины теряется

- **Вид:** моделирование
- **Серьёзность:** средняя → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** M

**Доказательства.**

Код:
- src/embedding/layer.py:163-165 — у корзины и точного числа есть только своя строка E, числовой компоненты нет.
- transaction_amount: 16 квантильных корзин (src/tokenization/settings.py:231) шириной ×1.4–2.1, например 24820–44000 и 44000–92400.

Проба, |Spearman| первой главной компоненты строк с порядком корзин (обученная таблица / начальная):
- transaction_amount 0.96/0.15;
- amount_or_limit 0.97/0.31;
- balance_after 0.90/0.27;
- principal_outstanding 0.92/0.08;
- installment_no 0.96/0.15; LOO ridge R² 0.97 против 0.27 у случайной таблицы;
- profile_age (64 точных значения) 0.04; cos между соседними = cos между дальними = 0.77; LOO R² 0.00 против 0.42 у случайной таблицы;
- profile_children 0.14;
- profile_declared_income_old 0.19;
- amount_due 0.38;
- rate 0.43.

В fraud-бейзлайне топ признаков — непрерывные отношения сумм: amount_to_max_prev 9.6, amount_to_balance 8.7, amount 7.4 (fraud_baseline/reports/feature_importance.csv:2-7).

**Влияние.**

- Частым корзинам порядок выучить удаётся за счёт объёма. Редким и профильным шкалам — нет, а у возраста его нет вовсе.
- Соседние корзины не делятся статистикой: у хвостовых корзин мало обновлений.
- Тонкая величина суммы внутри корзины (до ×2) модели недоступна, а для fraud-признаков класса amount_to_max_prev это вероятная потеря.

**Предложение.**

1. Упорядоченная параметризация прямо в InputEmbedding (дискретный аналог PLE, Gorishniy et al. 2022): строка k-й корзины ключа = base_key + Σ_{j≤k} Δ_j.
   - Порядок брать из buckets.json и value_vocab.json — это train-артефакты.
   - Так же параметризовать точные числа: profile_age, installment_no, term, children, job_tenure_months.
   - Выход остаётся связанным с теми же составленными строками.
2. Для целей-корзин ввести соседское сглаживание: ε на корзины b±k того же ключа (UniTTab, ур. 4).
3. Позже, отдельным экспериментом: непрерывный канал (PLE/periodic от log-суммы) рядом с id корзины. Для него нужен столбец сырых чисел через этапы 04–07.

**Как проверить.**

- |Spearman(PC1)| ≥ 0.9 для всех числовых ключей, включая profile_age;
- val CE и доля попаданий ±1 корзина на целях-корзинах;
- проба возраста из [USR].

Эксперименты X-05, X-06, X-11.

**Проверка скептиком: подтверждено.**

layer.py:163-165: у числа есть только строка E, числовой компоненты нет. transaction_amount — 16 квантилей (src/tokenization/settings.py:231). Пробой проверил: profile_age |Spearman(PC1)| 0.038 у обученной таблицы против 0.10 у начальной; cos соседних значений 0.771 против 0.775 у удалённых (>20 лет). transaction_amount 0.86 при включённой мёртвой bucket_1; без неё, по аудитору, 0.96. Порядок у частых корзин есть, у возраста нет. Уточнение: потеря величины внутри корзины — дизайн токенизации (этап 04), а не этапа 09. Выгода для fraud предположительна. Упорядоченная параметризация без X-02, вероятно, не спасёт возраст, потому что строки прижаты выходным градиентом.

**Источники:** https://arxiv.org/abs/2203.05556, https://ar5iv.labs.arxiv.org/html/2302.06375

### input-init-04. Бюджет таблицы: 30.7% параметров модели, из них четверть строк мертвы; BPE — 72% строк на ~4.5% токенов

- **Вид:** скорость
- **Серьёзность:** средняя → низкая после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** M

**Доказательства.**

Состав final_vocab: 4096 bpe + 1321 value + 187 bucket + 108 key + 5 специальных = 5717 строк × 128.

Подсчёт по всем 299 группам строк 07_batches/train (182.9 млн токенов событий, 22.98 млн событий):
- 1402 строки BPE ни разу не встречаются, 2213 встречаются меньше 100 раз;
- BPE — 3.98% всех слотов значений событий, примерно 4.5% без маркеров;
- 97.7% токенов стоят на позиции куска 0, максимальная позиция 21.

Мёртвые строки вне BPE:
- 23 корзины: profile_credit_limit, profile_credit_utilization, profile_relationship_months (src/tokenization/settings.py:255,265,269). По README.md:223-227 этих полей в анкете нет;
- 14 ключей: profile_holds_*, profile_contracts_count и другие;
- 9 нулевых корзин;
- [PAD].

Итого 1449 строк = 185 472 параметра = 7.8% модели. BPE vocab_size 4096 задан в src/tokenization/settings.py:308. Строки BPE — 524 288 параметров (22% модели).

**Влияние.**

- 7.8% параметров не получают входного градиента и только добавляют отвлекающие классы в softmax. Все они схлопнуты (input-init-01).
- Большая часть BPE-строк почти не обучена.
- При 2.38M параметров и слабой временной чувствительности эмбеддинга (shuffled_content 0.989) емкость полезнее в энкодере истории: 2 блока = 16.6%.

**Предложение.**

На этапе 03, это не код этапа 09:
- убрать спецификации корзин для полей, не входящих в анкету;
- после обучения BPE оставлять в final_vocab только куски, реально выданные при кодировании train-корпуса (train-статистика);
- попробовать BPE 1024–2048;
- освободившийся бюджет отдать энкодеру истории (X-07).

Это требует пересборки 03→09 по команде пользователя.

**Как проверить.**

- Число строк без вхождений в train = 0 (кроме [MASK]);
- таблица параметров по модулям;
- A/B: val CE на целях без BPE не хуже; время эпохи.

### input-init-X-02. Softmax, ограниченная кандидатами ключа, со сглаживанием внутри множества (P1)

**Гипотеза.** Если убрать невозможные классы из логитов и сглаживания, строки, которые не бывают целями, перестанут схлопываться, а профильная информация сохранится во входе. CE без сглаживания улучшится, top1 не ухудшится.

**Постановка.** Маска allowed[key_id, value_id] строится по 07_batches/train за ≈7 с; плюс [UNK].

В _piece_loss и hits: `logits.masked_fill(~allowed[key_ids[target_token]], -inf)`. label_smoothing нормировать на размер множества: вручную (1−ε)·nll + ε·mean(−logp по кандидатам).

A/B против базы, по 2 эпохи, одинаковые seed'ы и маски эпох.

**Метрика и критерий.** - Val CE без сглаживания по ограниченным логитам (на подвыборке пробы база 0.606): ниже на ≥2σ из X-01 или на ≥0.03 нат;
- top1 не хуже −0.2 п.п.;
- |row−dead| строк анкеты > 0.5;
- age R² из [USR] > 0.1.

**Стоимость.** ≈1 ч GPU на ветку, всего 2 ч; код и тест 2–3 ч.

**Проверка постановки: постановка корректна.** Главный кандидат. Условие честности: базу оценивать той же ограниченной CE без сглаживания, иначе выигрыш тавтологичен (пост-хок маска всегда снижает CE). Множество по train полно: вне него 0 целей из 1.24M val, OOV уже [UNK]. Для BPE-ключей множество до 2658, выигрыш там мал. Добавить контроль: та же ветка без сглаживания (ε=0) с полным softmax — чтобы отделить эффект маски от эффекта сглаживания на коллапс. Память маски [V×V] bool в bf16-пути небольшая. Приоритет P1 оправдан.

**Источники:** https://arxiv.org/abs/2010.12821, https://ar5iv.labs.arxiv.org/html/2302.06375

### input-init-X-07. Перераспределение ёмкости в энкодер истории (P2)

**Гипотеза.** Слабая зависимость [USR] от порядка и старой истории (shuffled_content 0.989, partial_50 0.992) частично вызвана мелкой историей: 2 блока, 16.6% параметров. При этом 7.8% параметров таблицы мертвы.

**Постановка.** init_backbone --history-config {"layers": 3} и {"layers": 4}: +198k параметров на блок. 2 эпохи; смотреть пиковую память, чтобы не выйти за 3.22 GiB.

**Метрика и критерий.** - Val CE без сглаживания;
- диагностика: медиана cos для shuffled_content и partial_50 ниже базы на ≥0.02 при не худшей CE;
- время эпохи.

**Стоимость.** ≈1–1.2 ч GPU на вариант.

**Проверка постановки: постановка корректна.** Выполнимо: блоки истории работают на позициях событий (≤12000), а не токенов, поэтому прирост пиковой памяти мал относительно 2.35 GiB allocated. Но смотреть reserved, спилл WDDM начинается с ~3.22 GiB. Конфаундеры: 2 эпохи недообучения штрафуют бо́льшую модель; падение cos в диагностике (shuffled_content) не есть качество само по себе — нужна downstream-метрика. Тезис «мёртвые параметры таблицы отнимают ёмкость» слабый, эксперимент от него не зависит.

### input-init-X-09. Dropout 0 против 0.1 в backbone (P2)

**Гипотеза.** Режим недообучения: val loss 1.648 < train 1.676, best — последняя эпоха. Dropout 0.1 во всех энкодерах, включая attention dropout, съедает ёмкость маленькой модели.

**Постановка.** init_backbone с --event-config, --profile-config и --history-config {"dropout": 0.0}: dropout зашит в конфиг backbone (backbone.py:333-341). 2 эпохи против базы.

**Метрика и критерий.** - Val CE без сглаживания −2σ;
- разрыв train/val;
- пробы X-03.

**Стоимость.** ≈1 ч GPU.

**Проверка постановки: постановка корректна.** Дёшево, 1 ч. Обоснование ослабить: val < train отчасти объясняется тем, что train считается с dropout и динамическими масками, а val — в eval-режиме на фиксированных масках. Это не прямое доказательство недообучения; сильнее аргумент «best = последняя эпоха». Dropout задаётся в конфигах энкодеров через init_backbone (lineage показывает dropout 0.1 в encoders.event.config). Сравнивать на тех же seed'ах.

### input-init-X-08. Чистка словаря: только встреченные на train токены и BPE 1024–2048 (P3)

**Гипотеза.** Удаление 1449 мёртвых строк и уменьшение BPE не ухудшит CE на целях без BPE и ускорит голову: логиты [M×V] сократятся на 25–55%.

**Постановка.** Этап 03:
- убрать спецификации profile_credit_limit, profile_credit_utilization и profile_relationship_months;
- фильтровать final_vocab по вхождениям в закодированный train.

Варианты BPE vocab_size 1024 и 2048. Пересборка 03→09 и 2 эпохи.

**Метрика и критерий.** - Val CE на целях без BPE не хуже 2σ;
- top1 на BPE-целях;
- время шага и пик памяти.

**Стоимость.** Пересборка 03→09 по команде пользователя (часы CPU); ≈1 ч GPU на вариант; ≈2 ч кода.

**Проверка постановки: постановку нужно исправить.** Дизайн метрики неверен: при смене BPE vocab_size меняется сама единица цели, а число и состав кусков другие, поэтому CE и top1 по BPE-целям несравнимы. Нужна CE на значение (сумма по кускам) или на байт. Пересборка 03→09 длится часы CPU и требует команды пользователя. Фильтр неиспользуемых строк и удаление спецификаций лишних корзин можно сделать отдельно, без смены BPE: это чисто и без конфаундера. P3 корректно.

### input-init-X-10. Схема начальной инициализации: PyTorch default против GPT-2/BERT (P3)

**Гипотеза.** Сейчас инициализация смешанная: xavier на in_proj события, kaiming(a=√5) на остальном, без масштабирования residual. Нормальная 0.02 с 1/√(2L) на выходных проекциях и независимыми seed'ами ускорит начало обучения. Итоговый эффект при глубине ≤5 ожидается малым.

**Постановка.** Своя init-функция в initial_* с обновлением GOLDEN: normal(0, 0.02), out_proj/out/ffn[3] × 1/√(2L), LayerNorm (1, 0), bias 0. 1 эпоха против базы плюс кривая первых 2000 шагов.

**Метрика и критерий.** - Val CE после 1 эпохи;
- шагов до loss < 2.0;
- число клипов нормы градиента.

**Стоимость.** ≈30–40 мин GPU, ≈1 ч кода.

**Проверка постановки: постановка корректна.** Корректно, но ожидаемый эффект мал при глубине ≤5 и 10 эпохах. Потребует перезакрепить GOLDEN (tests/test_backbone.py:49-53). Имеет смысл совместить с исправлением 05 (независимые seed'ы) в одном изменении. P3 верно.

### input-init-X-11. Обучаемая таблица номера куска вместо синусоиды (P3)

**Гипотеза.** Синусоида при PERIOD 10000 различает соседние куски слабо: |P0−P1| = 1.95 при |x| ≈ 19.5, cos(P0, P1) = 0.97. Позиции 0..21 полностью покрывает таблица из 32 строк (4k параметров). Для BPE-целей на позиции >0 порядок кусков — единственный сигнал.

**Постановка.** В InputEmbedding заменить pieces_of на nn.Embedding(32, d), обрезая позицию по 31, с init N(0, 1/√d)·√d. 2 эпохи.

**Метрика и критерий.** top1 и CE на BPE-целях с position > 0 (≈2.3% токенов) без ухудшения общей CE.

**Стоимость.** ≈1 ч GPU, ≈1 ч кода.

**Проверка постановки: постановка корректна.** Затрагивает около 2.3% токенов (позиция >0, max 21 — подтверждено сканом), ожидаемый выигрыш мал. Синусоида уже даёт различимые позиции (|P0−P1|≈1.95 при норме 8), трансформер их использует. Ограничение 32 строками вводит предел длины, которого сейчас нет. Метрику считать только на BPE-целях с позицией >0 и с σ из X-01, иначе шум. P3 верно, можно отложить.
