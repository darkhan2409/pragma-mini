# 10–13. Энкодеры и MLM-голова

Часть аудита `audit/2026-09-28-project`, см. `REPORT.md`.

## Сводка аудитора

Как устроено: InputEmbedding (E[key]·√d + E[value]·√d + синусоида куска) → EventEncoder: 5 блоков nn.TransformerEncoderLayer (pre-norm, GELU, dropout 0.1) внутри одного события, вектор = колонка [EVT] после LayerNorm, к нему прибавляется MLP календаря (6→d→d). ProfileEncoder: 1 Block с TimeRoPE по давности вех до cutoff, вектор из [USR]. HistoryEncoder: 2 Block с TimeRoPE по 8·log1p(Δt/8) до последнего события; вектор анкеты кладётся в слот [USR] (время 0). Голова: concat(токен после события, событие после истории, [USR] после истории) → Linear(3d→d) → скалярное произведение со всей общей таблицей (V=5717), CE с label smoothing 0.1 кусками по 2048 целей с checkpoint. На CUDA все 8 блоков идут через flash_attn_varlen_func по cu_seqlens группами ≤2^17 строк; на CPU — корзины SDPA. Код аккуратный, эквивалентность путей (корзины/посегментно/flash, градиенты, изоляция клиентов) покрыта тестами хорошо; явных ошибок вычислений не нашёл. Главные проблемы — в постановке, а не в арифметике: (1) двунаправленная история без causal-режима — прямой риск утечки для будущих fraud/churn-голов; (2) MLM-цель в основном награждает внутрисобытийную избыточность (ключи видимы при event-маске, среди целей доминируют event_type/app_domain и почти константные поля), а 63% FLOPs и большая часть памяти активаций уходят на 5 слоёв над событиями из 4–5 токенов; (3) softmax по всему словарю со сглаживанием по невозможным токенам; (4) диагностика [USR] не откалибрована (нет межклиентского базового уровня, календарь не переставляется вместе с содержимым), а в самом [USR] 58% дисперсии векторов событий даёт календарь; (5) чекпойнт не хранит конфиг архитектуры — эксперименты с архитектурой небезопасны. Вывод: инженерно надёжно, но архитектура и цель плохо подходят к задаче «вектор клиента для churn/fraud»; нужен downstream-стенд, после него — ребаланс глубины, dropout 0, ограниченный softmax и маскирование без утечки через ключи.

## Находки (16)

### architecture-01. История двунаправленная, causal-режима нет: векторы событий и [USR] видят будущее — прямая утечка для будущих fraud/churn-голов

- **Вид:** утечка
- **Серьёзность:** высокая → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** M

**Доказательства.**

src/mlm/varlen.py:333-340 — flash_attn_varlen_func(..., causal=False) для всех трёх энкодеров; src/history/encoder.py:183-187 — SDPA без is_causal; src/mlm/model.py:572-585 — история клиента [анкета, все события] целиком, наружу x[history_event_slot] и x[history_profile_slot]; model.py:449-460 client_embeddings = тот же проход. fraud_baseline/README.md:44-46: после шага мошенничества идут «алерт антифрода через 1–239 минут, решение, блокировка, обращение, chargeback»; README.md:8 там же планирует «PRAGMA history → client embedding → Fraud Head». README.md:416-418: контекст val/test идёт до конца выгрузки, а churn T = конец группы − 60 дн.

**Влияние.**

Строковая fraud-голова на z_h,i (вектор события после истории) или на [USR], посчитанных по полной истории, увидит последующие алерты/блокировки/chargeback своей же операции — PR-AUC будет завышен и сравнение с CatBoost (0.864) недействительно. [USR], посчитанный по сэмплам 05_dataset (cutoff = конец выгрузки), включает окно (T, T+60d] метки churn.

**Предложение.**

Зафиксировать контракт эмбеддингов до написания голов: churn — [USR] по истории, собранной с cutoff = T (этапы 05–07 с другим final_cutoff; анкета тоже на T); fraud — causal-вариант энкодера истории (causal=True в flash varlen, слот анкеты первым, события хронологически; вектор операции = z_h,i, анкета на момент операции или без неё) либо усечение истории на момент операции для оценочной выборки. Добавить флаг causal в HistoryEncoder/history_block_varlen, не меняя весов.

**Как проверить.**

Тест в tests/ на синтетическом мире: в causal-режиме изменение событий j>i не меняет z_h,i бит в бит (и меняет в двунаправленном). На downstream — сравнить fraud PR-AUC для full-bidirectional vs causal: разница = размер утечки.

**Проверка скептиком: подтверждено с поправками.**

Факт кода подтверждён: varlen.py:333-340 causal=False, history/encoder.py:183-187 SDPA без is_causal, model.py:572-585 слот анкеты + все события. Но это намеренный контракт, а не дефект: tests/test_attention_backends.py:443 прямо закрепляет causal=False, а статья PRAGMA (arxiv 2604.08649) называет History Encoder двунаправленным. Сейчас утечки нет, потому что нет голов. Требование «эмбеддинг по истории строго раньше T / event_time» уже записано в churn_baseline/README.md:169-170 и fraud_baseline/README.md:~224-225, так что новизна только в инструментах. Для churn архитектура вообще ни при чём: достаточно cutoff=T (см. X-01). Для строкового fraud causal-режим действительно нужен, иначе на каждую строку уйдёт отдельный проход. В предложении есть изъян: при causal=True и слоте анкеты первым [USR] видит только себя, и вектор клиента для MLM-головы и churn вырождается. Кроме того, анкета на cutoff сама несёт будущее.

**Второе мнение: подтверждено с поправками (серьёзность: средняя).**

ПОДТВЕРЖДЕНО в коде: внимание везде двунаправленное, causal-режима нет. src/mlm/varlen.py:333-340 — flash_attn_varlen_func(..., causal=False) в общем attend (событие, анкета, история); src/history/encoder.py:183-187 — SDPA только с attn_mask=keys (маска заполнителя), is_causal нет; других вхождений causal/is_causal в src нет (grep). model.py:572-585 — плоская история [USR/анкета, события], наружу x[history_profile_slot], x[history_event_slot]; model.py:449-459 client_embeddings = _encode(data)[2]. Контекст примера = [history_start, final_cutoff) до конца выгрузки (README.md:421-422; src/dataset/build.py:154). fraud_baseline/README.md:8 действительно планирует «PRAGMA history → client embedding → Fraud Head».

ЗАВЫШЕНО: (1) Утечки сейчас нет — голов не существует; это латентный риск контракта будущих голов, а не «certain leakage». Двунаправленность для MLM-предобучения — штатный BERT/PRAGMA-дизайн, не дефект сам по себе. (2) Для churn причина — cutoff выборки (конец выгрузки), а не двунаправленность: [USR] по полной истории содержит окно (T, T+60d] при любой маске внимания; лечится только усечением истории/анкеты на T (05–07 с другим cutoff). (3) Для fraud строковая утечка определяется тем, что в истории лежат события после операции; усечение истории на момент операции устраняет её и при двунаправленном энкодере.

ОШИБКА В ПРЕДЛОЖЕНИИ: слот [USR]/анкеты стоит ПЕРВЫМ в истории клиента (model.py:217-218: history_profile_slot = first_event + arange, history_event_slot = arange + user_of_event + 1). При causal=True [USR] видел бы только себя — клиентский эмбеддинг перестал бы агрегировать события. Кроме того, включать causal «не меняя весов» у модели, обученной двунаправленно, — сдвиг распределения на инференсе; векторы будут деградированы и сравнение с CatBoost несправедливо в обратную сторону. Корректный контракт: эмбеддинг по истории, усечённой на момент метки (T для churn, момент операции для fraud; анкета на тот же cutoff), а causal — только как отдельно обученный вариант. Рекомендация зафиксировать контракт до написания голов — верная; severity medium (обязателен до downstream, но не текущий баг).

**Источники:** https://arxiv.org/html/2604.08649v1

### architecture-02. MLM-цель награждает внутрисобытийную избыточность: при event-маске ключи видимы и выдают тип события, цели доминируют тривиальные поля

- **Вид:** моделирование
- **Серьёзность:** высокая → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** M

**Доказательства.**

README.md:650-652, 664-666 — ключ всегда видим, event-маска 0.10; src/embedding/layer.py:161-165 — E[key] входит в каждый токен, в т.ч. под [MASK]. Проба (val, 12 групп строк через одну четвёртую, 323 912 целей): причины event 32.4% / value 39.9% / key 27.7%; ключи целей: event_type 18.5%, app_domain 10.2%, firebase_screen 8.0%; 44.3% событий val — ровно 4 токена ([EVT]+3 поля, 1 760 816 из 3 972 274). Проба на 83 007 событиях: набор видимых ключей сам по себе даёт event_type с точностью 0.878 (81 разный набор). Модель best_checkpoint на 128 клиентах val (24 817 целей, SDPA fp32): event_type под event-маской top1 0.957; почти константные поля currency 1.000, operation_status 1.000, merchant_country 0.999, merchant_city 1.000, is_subscription 0.997; информативные — transaction_amount 0.393, counterparty 0.408, firebase_screen 0.568, operation 0.603. Top1 по причинам: event 0.775, key 0.868, value 0.864.

**Влияние.**

Градиент в основном учит связи полей внутри события (firebase_screen→app_domain→event_type) и частоты; энкодеру истории почти не нужно моделировать порядок и время — это согласуется с диагностикой (shuffled_content 0.989, partial_50 0.992). Финансово значимые поля (сумма, контрагент, mcc) — единицы процентов целей.

**Предложение.**

(а) Для событий под event-маской скрывать и ключи (key_ids → один служебный id, число токенов сохраняется), а голове подавать эмбеддинг ключа цели как запрос (logits = f([ctx; E[key]])) — событие тогда предсказывается из истории, а не из схемы полей. (б) Веса целей по ключу, например w_k ∝ 1/sqrt(freq_k) с нормировкой к среднему 1, или потолок веса на группу (клиент, ключ) у key-маски. (в) Метрики val по причине и по ключу (в Scores). Это пересекается с этапом 08 — согласовать с его аудитом.

**Как проверить.**

Эксперимент architecture-X-05: val NLL по причинам и по трудным ключам; центрированный cosine shuffled_content должен заметно упасть (выше чувствительность ко времени); churn-проба из architecture-X-01 не хуже базовой.

**Проверка скептиком: подтверждено с поправками.**

Механизм подтверждён: embedding/layer.py:161-165 — E[key] и синусоида номера куска входят в каждый токен, и под маской тоже. Моя проба совпала с аудитом: причины в val event 0.324 / value 0.399 / key 0.277 на 323 912 целях; 44.3% настоящих событий val имеют длину ровно 4 токена, медиана 5, максимум 37 (из 6.15M строк 3.97M — настоящие события, остальные — заполнитель с длиной 0). Упущено: утекает не только ключ, но и positions, то есть число BPE-кусков скрытого значения. Однако видимый ключ — замысел README (README ~651: «Ключ остаётся видимым — предсказывается значение») и эталона PRAGMA (там тоже 15/10/10 и видимые ключи). Top1 по ключам на чекпойнте я не перепроверял. Связь с 0.989 в shuffled_content — гипотеза. Итог: это исследовательская гипотеза о цели обучения, а не ошибка; пересекается с этапом 08.

**Источники:** https://ar5iv.labs.arxiv.org/html/2302.06375

### architecture-05. Диагностика [USR] не откалибрована: нет межклиентского уровня, доля внимания «на события» ≈ равномерной, shuffled_content не двигает календарь

- **Вид:** устройство
- **Серьёзность:** средняя → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** S

**Доказательства.**

src/mlm/diagnostics.py:219-225 — cosine только клиента со своим вариантом; :104-105 и :87-88 — shuffled_content переставляет содержимое, а calendar=client.calendar[times] остаётся в слоте; :213-214 — доли [USR]→[USR] и [USR]→события. При равномерном внимании доля на события = L/(L+1) = 99.95% при L=2210 — это и есть наблюдённые 97–99.99%. Моя проба (60 клиентов val, 150–900 событий, медиана 224.5): межклиентский cosine [USR] p10/p50/p90 = 0.137/0.363/0.633; shuffled_content — свой cosine 0.948/0.98/0.99, центрированный 0.965, retrieval@1 = 0.98; partial_50 retrieval@1 = 1.00; participation ratio [USR] 15.6, среднего векторов событий 4.5. Внимание (40 клиентов): в блоке 0 две головы держат ~45% массы на 1% событий (нормированная энтропия 0.40–0.42), блок 1 почти равномерный (0.71–0.89); доля 10% самых свежих событий 0.07–0.14 — предпочтения свежести нет. Обнуление event_time_log меняет [USR] до cosine 0.960 (медиана), обнуление календаря — до 0.952.

**Влияние.**

Число 0.989 само по себе ничего не говорит: вариант остаётся ближе к себе, чем к 98% других клиентов, но сдвиг составляет всего ~3% типичного межклиентского расстояния. Вывод «зависит от анкеты и состава событий» верен качественно, но количественно его не измерить; равномерное усреднение не отличается от «внимания к событиям».

**Предложение.**

Добавить в отчёт: межклиентский cosine (сырой и центрированный), retrieval@1 варианта среди оригиналов, нормированную энтропию внимания [USR] и массу по возрастным корзинам; вариант shuffled_rows_with_calendar — переставить содержимое вместе с календарём, оставив моменты времени (изолирует TimeRoPE). Сравнивать с тем же на начальных весах.

**Как проверить.**

Повторить диагностику на best_checkpoint: при равномерном внимании энтропия ≈1; retrieval@1 для no_profile и no_events покажет, остаётся ли клиент узнаваемым.

**Проверка скептиком: подтверждено.**

diagnostics.py:219-225 — cosine только пары клиент/свой вариант, межклиентской базы нет. diagnostics.py:213-214 — доли внимания на [USR] и на события без равномерной базы L/(L+1). diagnostics.py:104-105 и 87-88: shuffled_content оставляет calendar и event_time_log в слоте. Моя CPU-проба показала, что календарь даёт ~59% дисперсии вектора события (см. architecture-06), значит перестановка содержимого не трогает большую часть представления события. При почти равномерном внимании [USR] инвариантен к перестановке и сам по себе. Отсюда 0.989 без калибровки неинтерпретируемо. Межклиентские числа аудитора (0.363 и т.д.) без GPU-прогона не проверял.

### architecture-08. Полные логиты [M, V] считаются в forward с графом только ради top1/top5 — лишний проход головы и до ~160 МБ на пике

- **Вид:** память
- **Серьёзность:** средняя → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** S

**Доказательства.**

src/mlm/model.py:431-433 — logits = self.head(...) по всем целям, под autocast и с requires_grad; model.py:440-443 — потери отдельно, кусками с checkpoint (голова считается ещё раз и третий раз в backward); train.py:723-738 — out живёт до del после backward; README.md:1122-1124 это фиксирует. Доля целей в train 24.6% (45.0M/182.9M) → клиент в 58 000 токенов даёт ~14k целей → логиты 14k×5717×2 Б ≈ 160 МБ bf16.

**Влияние.**

До ~5% памяти карты занято во время backward самого тяжёлого шага (известная проблема: пик reserved 4.41 ГиБ > 3.22 ГиБ); лишняя матричная операция головы ≈4% FLOPs шага.

**Предложение.**

Считать top-k внутри цикла кусков mlm_loss под torch.no_grad (или отдельным проходом по кускам без графа) и возвращать только индексы top-5 (и top_probs для отчёта этапа 13); Predicted.logits убрать.

**Как проверить.**

Поэтому train > val (история чекпойнта 1.972/1.804 … 1.675/1.648) не доказывает недообучение. Плато в эпохах 8–10 объясняется и LR → 1e-5. Оценка памяти масок (~768 Б на токен на слой, ≈0.22 ГБ на 58k×5) правдоподобна: native_dropout хранит bool-маску, flash маску не хранит. Эксперимент дешёвый и разумный, но утверждение «явное недообучение» не подтверждено.

### architecture-X-01. Downstream-стенд эмбеддингов (обязательное условие для всех архитектурных решений) (P1)

**Гипотеза.** Качество вектора клиента не следует из MLM loss; без стенда нельзя выбирать архитектуру. Ожидание: замороженный [USR] уступает CatBoost churn, конкатенация [USR] + центрированное среднее z_h,i + вектор анкеты лучше одного [USR].

Для best_checkpoint (с сохранёнными конфигами, см. architecture-07) посчитать в eval: [USR], профиль до истории, среднее z_h,i (центрированное по среднему val), среднее с весом exp(−возраст/30 дн.) и конкатенацию. Логистическая регрессия (L-BFGS, как в PRAGMA) и CatBoost на эмбеддингах: обучение на val-клиентах, оценка на test. Отдельно — CatBoost-признаки + эмбеддинг.

**Стоимость.** Код M (1–2 дня: cutoff-T сборка, экспорт, проба). Прогон: сборка 05–07 для двух групп на CPU (оценка 10–20 мин), эмбеддинги ~3k клиентов на GPU ~5 мин, проба — секунды.

Анкету на T можно восстановить через profile_moment (audit/2026-09-24-fix/REPORT-split5.md, src/preprocessing/profile_state.py), но сборка 04–07 с cutoff=T требует кода (сейчас окна берутся из DATASETS/group_window) и отдельного каталога, чтобы не затереть data/05-07. Протокол можно улучшить: обучать пробу не на 1462 val-клиентах, а как CatBoost — на train-строках (churn_baseline/reports/train_rows.parquet, T train = 2025-11-02); val — ранняя остановка, test — оценка. Сравнивать парно на тех же eval_rows (DeLong/bootstrap). Для fraud нужен causal-режим или усечение (см. X-11). По ресурсам выполнимо: CPU-сборка групп плюс GPU-эмбеддинги по одному клиенту.

Моя проба воспроизвела базу: ~59% дисперсии, нормы 11.1 и 13.6, так что стартовая точка измерена. Вариант (в) — календарь токеном внутри события — меняет длину событий и память энкодера события, его стоит оценить в X-09.

### architecture-X-07. Время: привязка к cutoff T и двухмасштабный TimeRoPE / порядковый канал (P2)

**Гипотеза.** Логарифмическая шкала от последнего события лишает старую историю порядка; линейная шкала дней до T на части пар частот (или порядковый номер) даст модели структуру старых событий и давность активности.

**Постановка.** (а) event_time_log и [USR] от cutoff T (этап 06, пересборка 06–07); (б) 8 из 16 пар частот головы — на днях до T с base 10000, остальные — как сейчас; (в) вариант с порядковым номером. 2 эпохи каждый.

**Метрика и критерий.** Чувствительность [USR] к shuffled_content и к обнулению времени (центрированный cosine) растёт; NLL event-маски не хуже; churn-проба X-01.

**Стоимость.** Код M, пересборка 06–07 на CPU (оценка десятки минут), ~1 ч GPU на вариант.

**Проверка постановки: постановка корректна.** Для MLM на train почти ничего не даст: разрыв последнего события до cutoff — медиана часы. Эффект ожидается только в churn с cutoff=T, поэтому ставить после X-01 и оценивать им же. Вариант (а) требует изменения этапа 06 (time_log от cutoff) и пересборки 06–07 (848 МБ + 792 МБ на диске; место и RAM проверить, писать в отдельный каталог). Вариант (б) с линейной шкалой дней заденет всё сравнение TimeRoPE, включая анкету; лучше менять только history. Нужен тест на инвариантность к сдвигу (architecture-15) до изменений.

**Источники:** https://arxiv.org/abs/2310.13818

### architecture-X-08. Вспомогательная цель уровня клиента для [USR] (P2)

**Гипотеза.** MLM не обучает [USR] сводить клиента; контрастивная (CoLES) или next-period (NPPR) цель улучшит замороженный эмбеддинг для churn.

**Постановка.** Вариант A: два случайных временных среза клиента (по 50–70% событий) за один проход; InfoNCE по [USR] с очередью 4096 detached-векторов (в шаге обычно один клиент — 85.6% micro-batch'ей), вес 0.1 к MLM. Вариант B: для случайного t = T−30 дн. — BCE-предсказание мультихот-гистограммы event_type в (t, T] из [USR] на t (только train-клиенты, окно в пределах train). 2 эпохи.

**Метрика и критерий.** PR-AUC churn-пробы X-01 выше базы на ≥0.02; MLM NLL хуже не более чем на 2%.

**Стоимость.** Код L (2–3 дня), ~1.5 ч GPU на вариант.

**Проверка постановки: постановка корректна.** Идея обоснована, но по железу рискованна. Два среза по 50–70% в одном проходе дают 100–140% токенов клиента, а самый длинный клиент уже держит пик 2.35 ГиБ из 3.22 — на длинных клиентах нужен предел токенов среза. Очередь detached-векторов без momentum-энкодера (в отличие от MoCo) устаревает при LR 3e-4, и при одном клиенте на шаг это важно: нужен momentum-энкодер или маленькая очередь. Вариант B (next-period по train-окну) без утечки и дешевле — начинать с него. Ссылки поправить: 2401.01641 — не NPPR, 2408.09995 — Yugay и Zaytsev, а не MLEM.

**Источники:** https://arxiv.org/html/2002.08232v3, https://arxiv.org/html/2401.01641, https://arxiv.org/abs/2408.09995

### architecture-X-10. Плотное внимание по корзинам длины для событий против flash varlen (P2)

**Гипотеза.** Для сегментов длиной 4–37 плотный SDPA/bmm по корзинам 4/8/16/37 быстрее ~130 вызовов flash на шаг с почти пустыми тайлами.

**Постановка.** Микробенчмарк энкодера события (5 слоёв, d 128, bf16) fwd+bwd на токенах самого длинного клиента: текущий путь против корзин с маской; CUDA events, 20 повторов после прогрева.

**Метрика и критерий.** Время fwd+bwd энкодера события; принять, если быстрее на ≥20% при max|Δ| выходов в пределах bf16 (1e-2).

**Стоимость.** Код S, ~20 мин GPU.

**Проверка постановки: постановка корректна.** Микробенчмарк выполним, ~20 мин. Путь по корзинам уже есть (Model._events через nn.TransformerEncoderLayer и SDPA), но он режет события на порции по events_per_chunk=512 и сам даёт много запусков, так что сравнение с ним нечестно; нужна отдельная плотная реализация [E,H,L,L] по корзинам. Ожидаемый выигрыш мал (внимание внутри событий ~0.6% FLOPs), ~30% простоя из-за загрузки данных важнее. Приоритет P3.

### architecture-X-11. Causal-история для строкового fraud и оценка утечки двунаправленной версии (P2)

**Гипотеза.** Вектор операции из двунаправленной истории несёт последующие алерты/блокировки; causal-вариант даст честную оценку.

**Постановка.** Флаг causal в history_block_varlen (causal=True); fine-tune лучшего чекпойнта на 1 эпоху в causal-режиме; на val/test: z_h,i операций purchase/transfer_out → логистическая регрессия/CatBoost; сравнить с тем же на двунаправленной модели.

**Метрика и критерий.** PR-AUC fraud (causal) против CatBoost 0.864; разница bidirectional − causal = размер утечки (ожидается существенной).

**Стоимость.** Код M, fine-tune ~30 мин + извлечение векторов ~10 мин GPU.

**Проверка постановки: постановку нужно исправить.** Дизайн с изъянами. (1) При causal=True и слоте анкеты первым [USR] видит только себя, и дообучение MLM с головой на client-векторе меняет задачу; [USR] нужно ставить последним или убрать из головы. (2) Анкета на cutoff в слоте 0 — сама утечка будущего для строк внутри окна. (3) «bidirectional − causal = размер утечки» смешивает утечку с разницей в качестве представлений. Честнее контроль: двунаправленная модель на истории, усечённой до event_time, для подвыборки 1–2 тыс. строк (по проходу на строку, выполнимо) против causal на тех же строках. (4) 1 эпоха fine-tune ≈30 мин плюс извлечение z_h,i на 887k строк val — много проходов по клиентам, но выполнимо. Оценивать на eval_rows.parquet fraud_baseline.

**Источники:** https://arxiv.org/html/2507.23267v1

### architecture-X-12. Голова в стиле BERT (dense+GELU+LN) и SwiGLU в FFN (P3)

**Гипотеза.** Нелинейная голова и GLU-FFN дают небольшой выигрыш NLL при том же числе параметров.

**Постановка.** Mlm: Linear(3d→d)→GELU→LN→@E^T+bias; отдельно FFN SwiGLU с ff=2/3·512 в Block и varlen-слоях. 2 эпохи каждый, после X-02..X-04.

**Метрика и критерий.** Val NLL лучше на ≥0.5% при том же времени эпохи ±5%.

**Стоимость.** Код S, ~1 ч GPU на вариант.

**Проверка постановки: постановка корректна.** Корректно и выполнимо, но низкая ценность до появления стенда X-01. Порог ≥0.5% NLL без оценки шума между seed не интерпретируем. P3 оправдан.
