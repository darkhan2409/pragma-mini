# Добор: вес клиентов в loss и метрике

Часть аудита `audit/2026-09-28-project`, см. `REPORT.md`.

## Вопрос критика полноты

Никто не разобрал, как в loss и в val-метрике взвешены клиенты. Градиент окна делится на число целей (src/mlm/train.py:640-645), val_loss — среднее по всем целям группы (train.py:374-410, docstring validate). Поэтому вес клиента пропорционален длине его истории. Замерил по data/05_dataset/train/samples.parquet (сумма event_lengths по row group): 9556 клиентов, 22.98M событий, 182.9M токенов; нижние 50% клиентов дают 12.7% токенов, верхние 10% — 29.8%; перцентили числа событий p5=107, p10=205, p50=1365; 437 клиентов меньше чем со 100 событиями. Диагностика эмбеддинга по умолчанию отбрасывает клиентов меньше чем со 100 событиями (src/mlm/diagnostics.py:280, 343). Как раз короткие истории (новые и уходящие клиенты) важны для churn. Не предложены: A/B весов «на клиента» против «на цель» (или sqrt-перевзвешивание) и стратификация val-метрик и будущих downstream-метрик по бинам длины истории.

**Почему:** Выбор чекпойнта и сама цель обучения смещены к тяжёлым клиентам с 64% телеметрии. Качество эмбеддинга коротких историй не измеряется нигде, а для оттока и холодного старта оно ключевое.

**Где смотреть:** src/mlm/train.py:374-410, 630-660; src/mlm/model.py:305-345 (mlm_loss, среднее по целям); src/mlm/diagnostics.py:239-294; data/05_dataset/*/samples.parquet

## Сводка аудитора

Как устроено. mlm_loss возвращает среднее по целям micro-batch (model.py:333-345). train() делает backward по сумме (train.py:728-731) и делит градиент на число целей ОКНА (639-645). При grad_accum_steps=1 окно совпадает с micro-batch. micro-batch собирается жадно по бюджету 16384 позиций в порядке файла (inputs.py:333-358). Файл по окнам в 2048 клиентов отсортирован по длине (batching/temporal.py:116-133), и перемешивания нет. val_loss — глобальное среднее по целям последних трёх месяцев val (train.py:374-408), по нему выбирается лучший чекпойнт и работает early stopping (758-771).

Моя симуляция упаковки даёт ровно 6876 шагов, как в чекпойнте. Из них 85.6% шагов — один клиент. Поэтому исходная посылка GAP верна только для val_loss. Фактический градиент взвешен «на шаг»: клиенты с <1000 событий получают 21.5% веса, а в val_loss у них 7.9%. Клиенты с ≥3000 событий получают 40.9% против 72.1%. Цель обучения и метрика выбора взвешивают клиентов по-разному, и ни одна из схем не выбрана сознательно. Вес градиента — побочный эффект token_budget и порядка файла. Короткие истории, где лежат 70–78% будущих churn-позитивов, нигде не измеряются: ни в val, ни в диагностике (min_events 100), ни в протоколе downstream.

Вердикт: механика окна верна и покрыта тестами. Эпохальное взвешивание, наблюдаемость и стратификация отсутствуют. Это нужно исправлять до сравнения PRAGMA+Head с CatBoost.

### gap-client-weighting-loss-metric-01. Фактический вес клиента в градиенте — «на шаг», а не «на цель»: 85.6% шагов содержат одного клиента

- **Вид:** устройство
- **Серьёзность:** высокая → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** S

**Доказательства.**

train.py:639-645 делит градиент окна на window_targets. settings.py:107,111: token_budget=16384, grad_accum_steps=1, то есть окно = один micro-batch. inputs.py:333-358: жадная упаковка в порядке файла.

Проба (read-only, 07_batches/train n_tokens/profile_n_tokens/n_events + повтор micro_batches): 6876 micro-batch — ровно столько шагов на эпоху в history best_checkpoint.pt (step 6876·k). Из них 5887 одиночных (85.6%), у 4348 клиентов (45.5%) cost > бюджета, в среднем 1.39 клиента на шаг.

Эффективный вес клиента w_c = t_c / T_step(c); t_c — цели из 08_masked/train как прокси масок эпохи. Доли по бинам n_events [<300 | 300–1k | 1k–3k | ≥3k]:
- фактический градиент: 2.7 / 18.8 / 37.7 / 40.9%;
- «на цель»: 1.4 / 8.1 / 25.3 / 65.2%;
- «на клиента»: 16.5 / 26.4 / 27.7 / 29.4%.
Нижние 50% клиентов получают 30.5% веса против 13.7% «на цель».

Документация говорит о равенстве целей только внутри окна: model.py:75-76 («цель одного клиента весит столько же, сколько цель другого»), train.py:54-57, README:1012-1016. Тесты test_training_math.py:150-333 проверяют только эквивалентность внутри окна.

**Влияние.**

Оптимизируемая цель не описана нигде. Она лежит посередине между «на цель» и «на клиента». Клиент тяжелее 16384 позиций получает ровно один голос в эпоху. Энкодер анкеты и [USR] на 85.6% шагов получают градиент от одного клиента. Рассуждения «обучение доминируют тяжёлые клиенты» (в том числе исходная посылка GAP) верны лишь наполовину: градиент примерно вдвое менее смещён к тяжёлым, чем val_loss.

**Предложение.**

1) Дописать в README §14 и комментарии model.py/train.py фактическое правило: равенство целей внутри окна, равенство шагов между окнами, одиночный шаг для клиента дороже бюджета.
2) В close_window копить доли веса по бинам n_events (Σ t_c/T_window по клиентам окна; клиентов даёт список clients) и писать их в history эпохи.
3) Схему взвешивания выбирать явно (finding 02, X-02).

**Как проверить.**

CPU-тест на синтетическом мире: логируемые доли по бинам равны ручному Σ t_c/T_window при token_budget 14 и 1000. Повтор симуляции на реальных размерах даёт 6876 шагов.

**Проверка скептиком: подтверждено.**

Код: train.py:639-645 делит градиент на window_targets; settings.py:107,111 token_budget 16384, grad_accum_steps 1; inputs.py:333-358 жадная упаковка; inputs.py:227-236 порядок файла. Повторил симуляцию по 07_batches/train (cost = n_tokens+profile_n_tokens+n_events+1, inputs.py:330): 6876 micro-batch (= step 6876 на эпоху в history best_checkpoint.pt), 5887 одиночных (85.6%), 4348 клиентов дороже бюджета, 1.39 клиента на шаг. Цели по 08_masked/train (44.6M): доли по бинам <300/300-1k/1k-3k/>=3k — шаг 2.7/18.8/37.7/40.9, на цель 1.4/8.1/25.3/65.2, на клиента 16.5/26.4/27.7/29.4; нижние 50% — 30.5% против 13.7%. Все числа совпали. Смягчение: «цель не описана нигде» преувеличено — train.py:54-57 и README:1012-1014 прямо говорят «градиент среднего по целям окна», равенство шагов из этого следует, хотя явно не сказано. Это свойство дизайна, а не ошибка; влияние на качество не измерено, поэтому high -> medium.

### gap-client-weighting-loss-metric-02. Вес клиентов в цели обучения — побочный эффект token_budget, порядка файла и grad_accum

- **Вид:** устройство
- **Серьёзность:** высокая → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** M

**Доказательства.**

Симуляция на реальных размерах train и целях 08_masked/train. Доля градиента у клиентов с <1000 событий:
- файл как есть, token_budget 8192 / 16384 / 32768 / 65536: 33.0 / 21.5 / 11.8 / 7.9%;
- перемешанный порядок, accum 1: 31.0%;
- перемешанный порядок, accum 8: 10.8%; accum 32: 9.8%;
- предел «на цель»: 9.5%.
При текущей сортировке accum 8 почти ничего не меняет (≈21.8%): соседи по окну одной длины.

token_budget объявлен как предел памяти (settings.py:104-107) и остаётся главным рычагом против известной проблемы WDDM-spill.

Перевзвешивание целей внутри mlm_loss с нормировкой на сумму весов окна сокращается в одиночных окнах: вес постоянен внутри клиента. «sqrt-взвешивание», сделанное в лоб, ничего не изменит в 85.6% шагов.

Число целей клиента зашумлено key-маскированием (choose.py:171-179): targets/token по клиентам p5–p95 = 0.18–0.336, доля key-целей у клиента p95 = 0.53.

**Влияние.**

Любая правка памяти или пропускной способности меняет цель обучения молча: смена token_budget, введение shuffle, grad_accum. A/B таких правок смешаны с эффектом перевзвешивания. Сравнение прогонов с разным бюджетом некорректно.

**Предложение.**

Развязать вес и упаковку:
1) Вес цели u = e_c^(α−1). Здесь e_c — число допустимых значений клиента в окне целей (детерминировано, без шума маски), α — одно поле конфига: 1 = «на цель», 0 = «на клиента», 0.5 = sqrt.
2) Градиент окна делить на постоянную K вместо собственной суммы окна. K — средняя Σu на окно, посчитанная до обучения по размерам, как horizon().
3) Клип при постоянной K начнёт уравнивать тяжёлые шаги, поэтому нужен лог нормы (finding 05) и при необходимости пересмотр max_grad_norm.
Старое поведение не держать отдельным режимом: после X-02 оставить одну схему.

**Как проверить.**

CPU-тест: вектор суммарного веса клиентов за эпоху (чистая функция от размеров и e_c) совпадает при token_budget ∈ {14, 1000} и grad_accum_steps ∈ {1, 5}. Для α=1 градиент равен градиенту глобального среднего по целям (аналог test_training_math.py:150).

**Проверка скептиком: подтверждено.**

Симуляция повторена: доля <1000 событий при бюджетах 8192/16384/32768/65536 — 33.0/21.5/11.9/8.0% (у аудитора 11.8/7.9 — округление); перемешанный порядок, accum 1 — 31.0%; перемешанный, accum 8 — 10.7%; файл, accum 8 — 21.7%; на цель — 9.5%. Вывод о сокращении перевзвешивания внутри одноклиентного окна при нормировке на сумму весов окна верен. Шум числа целей: targets/n_tokens p5/p50/p95 = 0.180/0.238/0.336 (моя проба). Ключ маски привязан к клиенту (choose.py:158-161), поэтому порядок чтения маски не меняет. Оговорка: при AdamW постоянный множитель шага не сокращается точно, как у SGD, но относительный вес шагов через первый момент сохраняется, так что вывод в силе. Severity medium: связь с token_budget реальна, но ущерб качеству пока гипотеза.

**Источники:** src/mlm/settings.py:104-111, src/mlm/train.py:639-645, src/masking/choose.py:171-179, https://arxiv.org/html/2604.08649v1

### gap-client-weighting-loss-metric-03. val_loss (лучший чекпойнт и early stopping) почти не видит коротких историй и уходящих клиентов

- **Вид:** моделирование
- **Серьёзность:** высокая → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** S

**Доказательства.**

train.py:374-408: Scores — сумма потерь / число целей всей группы. train.py:758-771: улучшение считается только по val_loss. README:987-991.

Цели val лежат только в [2026-01-01, 2026-04-01) (lineage.json windows.val, README §5). Проба по 08_masked/val, доля целей по бинам n_events [<100 | 100–300 | 300–1k | 1k–3k | ≥3k] — 0.2 / 1.1 / 6.6 / 19.9 / 72.1% при долях клиентов 3.4 / 9.8 / 25.9 / 27.2 / 33.7%. Верхние 10% клиентов дают 32.6% метрики. ESS весов — 619 клиентов из 1462.

Склейка с churn_baseline/reports/eval_rows.parquet: 140 val-клиентов с churn=1 (9.6%) дают 0.83% целей val (медиана 55 целей против 608 у churn=0).

В последнем прогоне best = последняя эпоха (history: 1.6489 → 1.6481), поэтому выбор эпохи пока ничего не решил.

**Влияние.**

Выбор чекпойнта и остановка оптимизируют качество MLM тяжёлых активных клиентов. Цель обучения взвешена иначе (finding 01). Когда появится патience-остановка или сравнение прогонов, решение будет приниматься без когорты оттока. val_top1 0.8234 — по сути точность клиентов с ≥1000 событий.

**Предложение.**

В validate считать поцелевую CE из out.logits.float() кусками по TARGETS_PER_CHUNK с тем же label_smoothing и складывать через index_add по out.client. Клиенту приписывать бин по clients[i].n_events.

В history и строку эпохи писать:
- по бинам [0,100), [100,300), [300,1000), [1000,3000), [3000,∞): loss, top1, targets, clients;
- macro val loss (среднее поклиентных средних).

Критерий выбора пока не менять. Решение (per-target / macro / худший бин в духе group DRO) принимать по X-01 и X-02.

**Как проверить.**

Тест-инвариант: Σ loss_sum по бинам / Σ targets == val_loss (допуск float). macro совпадает с ручным поклиентным средним на синтетическом мире. Клиент без целей не входит ни в один бин. Время validate растёт не больше чем на 10%.

**Проверка скептиком: подтверждено.**

validate (train.py:374-408) и Scores.add (train.py:203-218) усредняют по всем целям группы; выбор лучшей эпохи только по val_loss (train.py:~758-771). Окно целей val [2025-12-31T19Z, 2026-03-31T19Z] по 08_masked/val/lineage.json. Проба: доли целей по бинам <100/100-300/300-1k/1k-3k/>=3k — 0.2/1.1/6.6/19.9/72.1% при долях клиентов 3.4/9.8/25.9/27.2/33.7%; ESS 619 из 1462; верхние 10% — 32.5%; churn=1 — 0.83% целей, медиана 55 против 608.5. Всё совпало. Оговорка: малое число целей у ушедших клиентов задано самим окном целей (последние 3 месяца, а они молчат после T), поэтому macro-метрика по ним будет шумной (~55 целей). В history best = эпоха 10, early stopping не сработал ни разу, поэтому решений метрика пока не исказила: high -> medium.

**Источники:** src/mlm/train.py:374-408, src/mlm/train.py:758-771, README.md:987-996, https://arxiv.org/abs/1911.08731

### gap-client-weighting-loss-metric-04. Порядок клиентов фиксирован и отсортирован по длине: каждая эпоха — одинаковая «пила» от коротких к длинным

- **Вид:** устройство
- **Серьёзность:** средняя → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** S

**Доказательства.**

Порядок формируется так:
- batching/temporal.py:93-133: окна по 32×64 = 2048 клиентов, сортировка по (длина, client_id) (settings.py:46,56);
- inputs.py:227-236: клиенты идут в порядке файла;
- train.py:698,706: от эпохи к эпохе меняется только seed маски (for_epoch, 243-253), shuffle нет.

Проба: все 5 окон train монотонны по n_tokens (от 6–13 до 58000). Шагов на окно [1476, 1491, 1470, 1470, 969], из них одиночных [1263, 1284, 1261, 1256, 823]. Окно = ~210 упакованных шагов коротких клиентов, затем ~1260 одноклиентных шагов растущей длины. Каждая эпоха, а значит каждая validation и каждый чекпойнт, заканчивается самыми длинными клиентами окна 4 (до 58000 токенов).

README:596-602 говорит, что порядок строк «смысла не несёт». Для SGD он смысл несёт.

horizon() (train.py:275-296) считает шаги по порядку файла.

**Влияние.**

Поток градиента не i.i.d. и повторяется каждую эпоху. Это incremental gradient со структурированным порядком — даже не shuffle-once, который в анализе Mishchenko et al. 2020 практически достаточен. Моменты AdamW подстраиваются под блоки режимов. Эффект на качество не измерен (likely), при min LR в конце он слабее.

**Предложение.**

Детерминированная перестановка порядка групп строк на каждую эпоху: seed = stable_hash("order", seed, epoch). Опционально — перемешивание внутри буфера из 2–4 групп. Потоковость сохраняется, группы остаются однородными по длине, упаковка не хуже.

horizon() обязан считать micro-batch'и по порядку каждой эпохи плана. resume уже пропускает micro-batch'и детерминированно.

Вводить только вместе с развязкой веса (finding 02): при нормировке на окно перемешивание само меняет долю клиентов <300 событий с 2.7% до 8.3%.

**Как проверить.**

Тесты:
- одна и та же эпоха даёт одинаковый порядок, соседние эпохи — разный;
- resume посреди эпохи даёт тот же поток (test_checkpoint_resume);
- horizon равен фактическому числу шагов.
Эффект на качество — X-03.

**Проверка скептиком: подтверждено.**

batching settings.py:46,56 — 32×64 = 2048; README:594-602 — сортировка внутри окна. Проба: все 5 окон train монотонны по n_tokens и заканчиваются на 58000; шагов на окно 1476/1491/1470/1470/969, одиночных 1263/1284/1261/1256/823. Порядок не меняется между эпохами: train.py:698 создаёт Source с одним for_epoch(masking), inputs.py:227-236 идёт в порядке файла. horizon (train.py:275-296) считает шаги по порядку файла. Перестановка групп реализуема без изменения масок: seed маски клиентский (choose.py:158). Фраза README «смысла не несёт» относится к семантике данных, а не к SGD, так что это натяжка, но проблема реальна. Эффект на качество не измерен.

**Источники:** src/batching/temporal.py:93-133, src/batching/settings.py:46-56, src/mlm/inputs.py:227-236, src/mlm/train.py:275-296, src/mlm/train.py:692-706, README.md:596-602, https://arxiv.org/abs/2006.05988

### gap-client-weighting-loss-metric-06. Диагностика эмбеддинга по умолчанию не содержит коротких историй и не стратифицирована

- **Вид:** моделирование
- **Серьёзность:** средняя → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** S

**Доказательства.**

diagnostics.py:
- :280 — фильтр n_events >= min_events, :343 — по умолчанию 100;

**Постановка.** Когда появится сборка примеров с cutoff = T (события строго до T, анкета на T): эмбеддинги [USR] для строк churn_baseline eval_rows и train_rows, logistic regression на train_rows.

Оценка на val/test по бинам числа событий до T: [0,300), [300,1000), [1000,3000), [3000,∞). Парный bootstrap с перевыборкой клиентов против score baseline. Опорные модели — «только −n_events» и «только анкета». Для fraud то же с bootstrap по клиентам.

**Метрика и критерий.** ROC-AUC и PR-AUC по бинам с 95% доверительным интервалом. Решение о полезности эмбеддинга принимать по бинам <1000 событий, а не по pooled.

**Стоимость.** Голова на CPU — минуты. Извлечение эмбеддингов — один проход val/test (оценка 5–10 мин GPU). Заблокировано отсутствием датасета на cutoff T.

**Проверка постановки: постановка корректна.** Правильный главный критерий; заблокирован отсутствием датасета с cutoff T (churn_baseline/README.md:167-168 этого требует). Бины >=1000 стоит объединить: в >=3000 только 9/23 позитивов. Для churn строка = клиент, поэтому bootstrap по строкам уже кластерный; для fraud нужен кластерный по клиентам. Паровое сравнение по score уже заявлено (churn_baseline/README.md:166). Учесть, что train_rows — клиенты, чьё окно target видел pretraining. CPU-часть дешёвая; извлечение эмбеддингов — один проход val/test.
