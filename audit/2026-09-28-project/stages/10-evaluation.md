# Оценка и диагностика эмбеддингов

Часть аудита `audit/2026-09-28-project`, см. `REPORT.md`.

## Сводка аудитора

Сейчас представление клиента проверяет только src/mlm/diagnostics.py. На выборке val он берёт [USR] после энкодера истории на конечном cutoff группы, строит 6 вариантов клиента (абляции) и печатает cosine/L2 и долю внимания [USR]. Механика верная и покрыта тестами (tests/test_client_embedding.py): инвариантность к порядку строк, строка внимания совпадает с реальным выходом. Этап 13 (build.py/report.py) даёт разбор по целям, но только на начальных весах. Пути «чекпойнт → эмбеддинг строго до T/event_time → голова → парное сравнение на eval_rows» нет совсем: нет кода среза, голов, статистики и экспорта векторов. Строительные блоки для него уже есть: Group.history(cid, cutoff) с откатом анкеты, build_sample, time_log.

Что показали read-only пробы:
- Главный сигнал churn — давность. Одна act_days_since_last даёт на test ROC 0.929 / PR 0.529, полный CatBoost — 0.939 / 0.618. Давность до T во вход PRAGMA не попадает по построению.
- Мощность сравнения мала: 95% CI PR-AUC для churn на test ±0.08; у fraud позитивы есть только у 96 клиентов test.
- Абляции no_events и no_profile вне распределения: в train 0 таких клиентов. Косинусы печатаются без межклиентской шкалы.
- Коллапса эмбеддинга нет: на 48 клиентах эффективный ранг 29.9.
- Фрод-протокол с точным срезом на каждую строку осуществим, если переиспользовать векторы энкодера события: он считает каждое событие отдельно.

Вердикт: как механика диагностика корректна, но ответить «полезен ли эмбеддинг» она не может. Downstream-оценка не готова.

## Находки (14)

### evaluation-01. Нет пути «чекпойнт → эмбеддинг на T → голова → сравнение с baseline»

- **Вид:** устройство
- **Серьёзность:** критичная → высокая после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** L

**Доказательства.**

grep 'churn|downstream' по src/ и tests/ находит только файлы генератора. diagnostics.py:262-317 считает эмбеддинги только в памяти, только на final_cutoff группы и никуда их не пишет. build.py:108-114 и model.py:738-784: load_model без чекпойнта. Этапы 11/12 работают только на начальных весах (README.md:1153-1158). churn_baseline/README.md:161-172 и fraud_baseline/README.md:204-217 требуют эмбеддинг по истории строго до T / event_time строки и оценку ровно на eval_rows. Нужные примитивы уже есть: preprocessing/read.py:256-340 Group.history(client_id, cutoff) — события < cutoff и анкета с откатом на любой cutoff ≤ as_of; dataset/sample.py:262 build_sample; temporal/position.py:93 time_log.

**Влияние.**

Цель проекта (эмбеддинг [USR] для churn/fraud против CatBoost) сейчас не измеряется ничем. Все выводы по diagnostics косвенные.

**Предложение.**

Этап 15 `src/downstream/`.
(1) embed.py.
- Вход: train_rows/eval_rows baseline; sha256 сверяется с их metrics.json.
- Для строки: Group.history(cid, T) → encode_event/encode_profile на замороженном словаре → build_sample с окном final_cutoff=T и политикой recent → time_log/profile_time_log → pack пачками по token_budget → model.client_embeddings (flash bf16, eval).
- Выход parquet: ключ строки, usr[128], last_evt[128], mean_evt[128], log_gap_any.
(2) probe.py: логрег (L2, C по 5-fold CV на train), kNN, CatBoost на эмбеддинге, CatBoost(признаки baseline + PCA эмбеддинга). Порог — max-F1 на val, как у baseline.
(3) compare.py: парный кластерный bootstrap и DeLong.
Test считается один раз, по заранее записанному списку вариантов.

**Как проверить.**

Тесты из evaluation-11. Эмбеддинг на T = final_cutoff побитно совпадает с diagnostics.embeddings. compare.py на score baseline воспроизводит его metrics.json.

**Проверка скептиком: подтверждено.**

Проверено. diagnostics.py:262-317: эмбеддинги считаются только в памяти, по клиентам из 07_batches, то есть на final_cutoff группы. build.py:108-114: load_model вызывается без чекпойнта. В src/ и tests/ нет downstream-кода: grep 'churn|downstream' находит только src/generator. Примитив Group.history(client_id, cutoff) с откатом анкеты через profile_at есть (read.py:256-338). Оба README baseline требуют строгого среза: churn_baseline/README.md:161-173, fraud_baseline/README.md:204-217. Серьёзность снижена до high: это известный и ещё не начатый этап (в постановке сказано, что головы не существуют), а не дефект кода. Правка к валидации: «побитное совпадение с diagnostics.embeddings» верно только при том же бэкенде (SDPA fp32) и той же упаковке по одному клиенту. Для пути flash bf16 с пачками по бюджету нужен allclose.

**Источники:** https://arxiv.org/html/2604.08649v1

### evaluation-02. Эмбеддинг не знает «сейчас»: давность от последнего события до T или до операции не видна

- **Вид:** моделирование
- **Серьёзность:** высокая → высокая после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** S

**Доказательства.**

Как устроен вход:
- temporal/position.py:93 — delta = moments[-1] − moments, отсчёт от последнего события.
- model.py:220-221 — слот [USR] на позиции 0, то есть в момент последнего события (README.md:872).
- calendar.py:92-96 — только час, день недели и день месяца; месяца и года нет.
- С T связаны только profile_time_log вех, возраст и стаж.
Пробы:
- val, T=2026-01-31, 02_preprocessed, 1434 строки churn: давность последнего события любого типа до T — p50 0.47 д, p90 5.5 д; у churn=1 медиана 3.5 д. Одна эта величина даёт ROC 0.80 / PR 0.34.
- act_days_since_last (топ-1 важности baseline) одна даёт на test ROC 0.929 / PR 0.529 при 0.939 / 0.618 у полного CatBoost на 116 признаках.
- Давность собственных действий относительно последнего события модель видит (разница с давностью до T: p50 0, p90 43.6 д). Не видит она только кусок «последнее событие → T».
Во фроде в топе baseline txn/mcc/counterparty_hours_since_prev. В PRAGMA (arXiv 2604.08649) та же привязка: log-секунды до последнего события истории.

**Влияние.**

Голова на одном [USR] структурно теряет главный сигнал churn и часть сигнала fraud. Сравнение с CatBoost будет занижено из-за входа, а не из-за качества представления.

**Предложение.**

Сразу: подавать в голову скаляры log1p((T − t_last)/8) и давности по source из той же ленты — это часть входа PRAGMA на T — и отчитывать «эмб.» и «эмб. + gap» отдельно. В diagnostics добавить вариант idle_Δ: все события сдвинуты на Δ назад относительно T; позиционная часть сейчас к этому инвариантна. Долгосрочно: привязать TimeRoPE к cutoff (event_time_log = 8·log1p((T−t_i)/8), [USR] в T) и переобучить (X-04).

**Как проверить.**

X-01/X-04: ΔPR-AUC (эмб.+gap − эмб.) на test с парным CI. idle_30d после исправления сдвигает эмбеддинг больше медианного межклиентского расстояния × 0.1.

**Проверка скептиком: подтверждено.**

position.py:93: delta = moments[-1] − moments. model.py:217-218: слот анкеты [USR] стоит на позиции 0, в момент последнего события (README.md:872). calendar.py:92-104: только час, день недели и день месяца. profile_time_log отсчитывается от cutoff (position.py:108-136, temporal/build.py:103). Пробой по churn_baseline/data/test/features.parquet воспроизвёл act_days_since_last: ROC 0.929 / PR 0.529 против 0.939 / 0.618 у полного CatBoost. Уточнения: (1) косвенный путь есть. Источник вехи first_* лежит в ленте с давностью до t_last, а сама веха лежит в анкете с давностью до T (README.md:229-240, generator/profile.py:96-101). Разность в принципе можно вывести, но только внутри логарифмов и через разные энкодеры, и стимула учить её у MLM нет. (2) Та же привязка к последнему событию есть в самой PRAGMA (arXiv 2604.08649 подтверждает «log-seconds to last event»). Это паритет с эталоном, а не ошибка, но для churn потеря реальна. Число ROC 0.80 / PR 0.34 для давности любого события на val я не перепроверял.

**Источники:** https://arxiv.org/html/2604.08649v1

### evaluation-05. Фрод: срез на каждую строку осуществим, если переиспользовать векторы событий; дневные снимки теряют пробы того же дня

- **Вид:** устройство
- **Серьёзность:** высокая → высокая после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** M

**Доказательства.**

fraud_baseline/README.md:216-217 требует эмбеддинг строго до event_time.
- Энкодер истории двунаправленный (varlen.py:339 causal=False): выходы полного прохода для строк брать нельзя, они видят саму операцию и алерты после неё.
- Энкодер события считает каждое событие отдельно: model.py:504-533, внимание по cu_seqlens событий, dated = x[EVT] + calendar (строка 528). Вектор события от среза не зависит.
Проба eval_rows:
- val: 886,625 строк, 304,868 клиенто-дней, 85,819 клиенто-недель; 279 позитивов в 90 клиенто-днях у 77 клиентов.
- test: 1,014,958 строк, 341,677 клиенто-дней, 97,399 клиенто-недель; 355 позитивов в 116 клиенто-днях у 96 клиентов.
Позитивы идут пачками, около 3 на клиенто-день (probe → strike).

**Влияние.**

Полный проход на каждую строку или клиенто-день стоит O(строк × длина) через 5 блоков события — часы или сутки. Недельные и дневные снимки не видят проб текущего дня — самый ценный сигнал.

**Предложение.**

Точный снимок на каждую строку:
1. Один проход энкодера события по всей ленте клиента; dated [n, 128] держится на GPU.
2. Для строки: префикс событий < event_time (хвост recent ≤ 12000 событий / 58000 токенов).
3. Позиции пересчитываются от последнего события префикса; анкета — на момент строки, кэш по клиенто-дню.
4. Заново считаются только энкодер анкеты и 2 блока истории; префиксы клиента идут одной varlen-пачкой.
Грубая оценка без замера: для val Σn² ≈ 2.2e12 пар, ≈2e15 FLOP внимания — минуты или десятки минут на RTX 3050 против часов без кэша.

**Как проверить.**

Тест: путь с кэшем = model.client_embeddings на клиенте, срезанном по event_time (fp32 SDPA, allclose). Замер времени на 50 клиентах val до полного прогона.

**Проверка скептиком: подтверждено с поправками.**

Верно: энкодер события считает каждое событие независимо от среза (model.py:504-533; dated = x[EVT] + calendar). Энкодер истории двунаправленный, поэтому полный проход для строк фрода не годится. Кэш dated плюс пересчёт анкеты и двух блоков истории — правильная схема. Оценка стоимости занижена. Моя проба по 01_raw/val (события строго раньше event_time каждой из 886,625 строк, кэп 12000): Σprefix = 2.09e9 слотов истории, Σprefix² = 1.06e13 пар, медиана префикса 1416, p90 5723. У аудитора Σn² ≈ 2.2e12, это примерно в 5 раз меньше. Для сравнения: эпоха обучения прогоняет около 25M слотов истории. Одна val — это около 84 такого объёма, пусть только прямой проход через 2 блока, плюс квадратичное внимание. Реалистично часы на val+test+train_rows, а не «минуты или десятки минут» (сам замер времени не проводил). Кэп на последние K событий резко снижает стоимость: при K=1024 Σ=7.3e8 и Σ²=6.8e11, при K=2048 Σ=1.16e9 и Σ²=2.0e12.

### evaluation-03. Мощность сравнения мала, а парной и кластерной статистики нет

- **Вид:** процесс
- **Серьёзность:** высокая → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** M

**Доказательства.**

churn_baseline/churn/train.py:74-89 и fraud_baseline/fraud/train.py:67-84 выдают точечные метрики без CI. eval_rows только хранят score.
Пробы, bootstrap 2000:
- churn test (1460 строк, 142 позитива): PR-AUC 0.618, CI [0.542, 0.701]; ROC CI [0.921, 0.955].
- Парный ΔPR (полный CatBoost − одна давность) = [0.029, 0.151]: ширина 0.12 против 0.16 у непарного. Весь baseline лишь на +0.089 PR и ≈+0.01 ROC выше одной давности.
- fraud test: 355 позитивов у 96 клиентов в 116 клиенто-днях. Кластерный по клиентам bootstrap PR-AUC даёт [0.816, 0.902], построчный — [0.832, 0.892], на 43% уже.
- Порог F1 выбирается на val (140 и 279 позитивов).
EBES (arXiv 2410.03399): Monte-Carlo CV на 20 seed и Mann–Whitney с поправкой Holm–Bonferroni.

**Влияние.**

Разница PRAGMA и baseline меньше ~0.06 PR-AUC на churn неотличима от шума. Построчный bootstrap во фроде даёт ложную значимость. Много вариантов голов на одном test — подгонка к test.

**Предложение.**

compare.py:
- Парный bootstrap с ресэмплингом клиентов (2000 повторов) для ΔPR-AUC и ΔROC-AUC, DeLong для ROC.
- Основная метрика — PR-AUC; F1 при пороге с val — вторичная.
- ≥5 seed на голову.
- Мульти-T строки churn для клиентов val/test: предобучение их не видело (X-08).
- Реестр вариантов; выбор по CV на train, test — один раз.

**Как проверить.**

compare.py на score baseline против score «только давность» воспроизводит CI [0.029, 0.151]. На мульти-T ширина CI уменьшается (X-08).

**Проверка скептиком: подтверждено.**

churn/train.py:74-89 и fraud/train.py:67-84: только точечные метрики, CI нет. Мой bootstrap (2000 повторов, seed 0) по eval_rows и features test: CI PR-AUC полного CatBoost [0.538, 0.695], парный ΔPR (полный − act_days_since_last) [0.030, 0.148]. Это совпадает с аудитором. Фрод-кластеры: позитивы у 96 клиентов test и 77 val, по клиенто-дням UTC 118 и 94 (у аудитора 116 и 90, вероятно по местному дню). EBES (arXiv 2410.03399) проверен: Monte-Carlo CV на 20 seed, Mann–Whitney с поправкой Holm–Bonferroni. Серьёзность medium: сравнения ещё нет, а порог «0.06» относится к паре с давностью. У PRAGMA+голова против baseline корреляция score, вероятно, иная, и ширина CI другая.

**Источники:** https://arxiv.org/html/2410.03399v1

### evaluation-04. [USR] получает от MLM только избыточный градиентный канал

- **Вид:** моделирование
- **Серьёзность:** высокая → средняя после проверки
- **Уверенность аудитора:** вероятно
- **Цена исправления:** S

**Доказательства.**

model.py:428-433: голова получает [token; event; client]. model.py:583-585: выход слота [USR] последнего блока истории используется только в client_rows головы. Векторы событий после энкодера истории уже видят все события и слот анкеты (varlen.py:339 causal=False), поэтому для MLM канал client избыточен (это следует из архитектуры).
Проба весов best_checkpoint: ||W||_F блоков head.proj — client 5.54, token 10.12, event 8.25.
Литература: MLM-подобные цели лучше на локальных задачах и слабее на глобальных, чем контрастивные (arXiv 2408.09995, 44 датасета). PRAGMA для linear probe берёт [USR], последний [EVT] или оба.

**Влияние.**

[USR] может оказаться слабо обученным побочным вектором. Тогда downstream на нём занизит пользу модели, хотя информация есть в векторах событий.

**Предложение.**

X-03: обнулить или перемешать client-канал на val и измерить Δloss по ключам. В пробах сравнивать [USR], последний [EVT], среднее событий после истории и их конкатенацию. Если [USR] слабый — добавить клиентскую цель: CoLES random slices на [USR] (X-09) или предсказание части целей key-маскирования только из [USR].

**Как проверить.**

X-03: Δ val loss при перемешанном [USR] < 0.01 nats — [USR] не используется. X-01: PR-AUC пробы last_evt/mean_evt против usr с парным CI.

**Проверка скептиком: подтверждено с поправками.**

Верно: голова берёт cat[token, event, client] (model.py:300). Выход [USR] последнего блока идёт только в client_rows (model.py:428-433), история двунаправленная (varlen.py:339 causal=False). Нормы блоков head.proj перепроверил на best_checkpoint: token 10.12, event 8.25, client 5.54. Но это скорее довод против тезиса об «избыточности»: client-блок по норме составляет около 55% token-блока и явно используется. Избыточность остаётся гипотезой, её проверяет X-03. Правка по ссылке: arXiv 2408.09995 (CMLM) использует 4 датасета (Rosbank churn, Sber gender/age, DataFusion), а не 44. Вывод «генеративное лучше на локальных задачах, контрастивное — на глобальных» в статье есть.

**Источники:** https://arxiv.org/html/2408.09995v1, https://arxiv.org/html/2604.08649v1

### evaluation-06. Абляции no_events/no_profile вне распределения; косинусы без шкалы

- **Вид:** риск корректности
- **Серьёзность:** средняя → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** S

**Доказательства.**

diagnostics.py:101-123 — варианты no_events и no_profile. В data/04_tokenized/train/meta.json clients_with_empty_profile = 0; клиентов без событий в 07_batches всех групп 0. Модель ни того ни другого не видела.
diagnostics.py:314-319 — только cos/L2 к собственному оригиналу, без межклиентской шкалы. norm_full почти константа из-за финального LayerNorm (history/encoder.py:226,258).
CPU-проба: best_checkpoint, SDPA fp32, 48 клиентов val, медиана 602 события, row groups 6/10/14/18, 38 с.
- Межклиентский cos: raw median 0.42 (p10 0.17, p90 0.71), центрированный −0.07.
- Эффективный ранг 29.9 из ≤ 47, PC1 13.9% — коллапса нет.
- Центрированный cos / retrieval@1 по вариантам: partial_50 0.981 / 0.98; shuffled_content 0.968 / 1.00; no_profile 0.142 / 0.12; no_events 0.492 / 0.48.
- Калибровка мешком токенов (log-count value_ids) на тех же клиентах: partial_50 — centered cos 0.79, retrieval 0.90.

**Влияние.**

0.58 и 0.48 — реакция на невиданный вход. Вывод «эмбеддинг определяется анкетой» может быть артефактом. Вывод о слабой зависимости от старой половины истории калибровкой подтверждается: эмбеддинг инвариантнее простого счётчика.

**Предложение.**

В diagnose:
- межклиентская шкала: raw и центрированный cos, медиана попарных L2;
- нормированное смещение ||e−e'|| / median ||e_i−e_j||;
- retrieval@1 и MRR;

### evaluation-X-03. Использует ли MLM-голова [USR]: абляция client-канала на val (P1)

**Гипотеза.** Канал client избыточен при векторах событий после истории, поэтому замена [USR] почти не меняет val loss.

**Постановка.** validate() на val с фиксированной маской; client_rows в голове заменяется на (a) нули, (b) средний [USR] micro-batch, (c) [USR] другого клиента (перестановка внутри micro-batch). Флаг или хук только для диагностики. Δ loss, NLL и top1 — всего и по key_id.

**Метрика и критерий.** Δ val loss. < 0.01 nats — [USR] MLM не нужен: брать mean/last_evt и/или вводить клиентскую цель. > 0.05 — канал используется.

**Стоимость.** 3 прохода val ≈ 3 × (2–4) мин (val 31M токенов ≈ 1/6 train, прямой проход; оценка). Код S.

**Проверка постановки: постановка корректна.** Дёшево: прямой проход val с фиксированными масками 08_masked; оценка 2–4 мин на вариант правдоподобна. Нужен диагностический хук на client_rows без изменения обучения. Замена client_rows в голове проверяет только канал финального [USR]: промежуточные слои, где события видят слот анкеты, остаются. Это надо явно оговорить. Пороги 0.01/0.05 nats произвольны, лучше отчитывать Δ по ключам. Вариант (b), средний [USR], — хороший контроль сдвига распределения.

**Источники:** evaluation-04, evaluation-07

### evaluation-X-04. Якорь времени в T (P2)

**Гипотеза.** Давность до T — главный сигнал churn; её отсутствие во входе стоит заметную часть PR-AUC.

**Постановка.** (a) Дёшево: в X-01 сравнить эмб. и эмб. + log_gap_any (+ давность последнего события каждого source).
(b) Дорого: event_time_log = 8·log1p((cutoff − t)/8), слот [USR] в cutoff; пересборка 06–09, init_backbone и 10 эпох обучения, затем повтор X-01 и diagnostics idle_30d.

**Метрика и критерий.** Test ΔPR-AUC churn, парный CI. (b) принимается, если нижняя граница CI ΔPR (эмб. новой модели − эмб. старой) > 0 при сопоставимом val NLL.

**Стоимость.** (a) секунды. (b) пересборка 06–09 (минуты — десятки минут) + ≈ 5 ч обучения + 30 мин оценки.

**Проверка постановки: постановка корректна.** (a) Бесплатно и правильно. (b) Около 5 ч обучения плюс пересборка 06–09 — осуществимо, но одна пара моделей по одному seed не отделяет эффект якоря от разброса обучения; нужны ≥2 seed или хотя бы оценка seed-вариации головы. Вариант idle_Δ в diagnostics не строго инвариантен и сейчас: сдвиг на 30 дней меняет день недели и день месяца в календаре. Брать Δ, кратный 7 дням, и учитывать день месяца.

**Источники:** evaluation-02

### evaluation-X-05. Кривая «MLM против downstream» по эпохам (P2)

**Гипотеза.** val MLM loss монотонно связан с полезностью эмбеддинга; если нет, чекпойнт надо выбирать по пробе.

**Постановка.** При следующем обучении сохранять веса каждой эпохи (evaluation-08). Для начальных весов и эпох 1–10 считать: val loss и NLL, top1 по ключам, RankMe на 1000 val-клиентах, churn-пробу (train-CV PR-AUC; val PR-AUC).

**Метрика и критерий.** Spearman ρ(val_loss, PR-AUC пробы) по 11 точкам. |ρ| < 0.7 или пик пробы до последней эпохи — выбирать чекпойнт по пробе.

**Стоимость.** ≈ 5 ч обучения (только если переобучение и так планируется) + 11 × ~15 мин embed+probe (≈ 3 ч; на подвыборке 3000 train-клиентов ≈ 1 ч).

**Проверка постановки: постановку нужно исправить.** Сохранять веса каждой эпохи дёшево и полезно (evaluation-08). Метрика слабая: в одном прогоне и val_loss, и проба монотонно улучшаются с эпохой, поэтому высокий Spearman по 11 точкам получится почти автоматически и ничего не докажет. Лучше смотреть argmax пробы относительно последней эпохи и Δ пробы между соседними эпохами с CI, а связь MLM и downstream проверять между разными конфигурациями или seed. Стоимость: около 5 ч обучения плюс 11 × embed+probe. Оправдано, только если переобучение уже запланировано.

**Источники:** evaluation-08, evaluation-07

### evaluation-X-06. Diagnostics v2: шкала, retrieval, swap-абляции, внимание по давности (P2)

**Гипотеза.** После калибровки вклад анкеты против событий и свежей истории против старой отличается от чтения по OOD-абляциям.

**Постановка.** best_checkpoint, 1000 клиентов val (выбор по sizes, evaluation-09).
- Межклиентский raw и центрированный cos; нормированное смещение; retrieval@1; RankMe.
- Swap анкеты и событий с клиентом той же децили длины; idle_30d.
- Масса внимания [USR] по корзинам давности.
- BoW-калибровка.

**Метрика и критерий.** Нормированное смещение по вариантам. Вывод «эмбеддинг = анкета» принимается, только если swap анкеты сдвигает сильнее swap событий.

**Стоимость.** GPU ≈ 10–20 мин; код S–M.

**Проверка постановки: постановка корректна.** Осуществимо: 1000 клиентов val при выборе по sizes(). Для каждого варианта нужен отдельный проход по одному клиенту в SDPA fp32 (diagnostics.embeddings). На CPU это медленно, на GPU flash bf16 — минуты. Swap-абляции in-distribution — правильная замена no_events/no_profile. Swap событий с клиентом той же децили длины меняет и календарь, и t_last — это ожидаемо. Про idle_Δ и календарь — см. X-04.

**Источники:** evaluation-06, evaluation-12, evaluation-09

### evaluation-X-07. Фрод-гибрид: точные снимки на строку с кэшем векторов событий (P2)

**Гипотеза.** Контекст клиента из PRAGMA добавляет PR-AUC к признакам операции сверх ручных признаков истории.

**Постановка.** 1. Снимки строго до event_time по схеме evaluation-05 для val и test (все строки) и для train_rows (527k).
2. CatBoost(признаки baseline + PCA-16 usr + PCA-16 last_evt + log_gap) против baseline; ранняя остановка по подвыборке val (evaluation-14).
3. Контроль: моменты округлены до минуты (evaluation-10).
4. Кластерный bootstrap по клиентам.

**Метрика и критерий.** Нижняя граница кластерного CI ΔPR-AUC test > 0. |Δ| между исходными и округлёнными моментами — внутри CI.

**Стоимость.** Эмбеддинги ≈ 0.5–1.5 ч (оценка, не замер). CatBoost 2–4 обучения × ~10 мин с подвыборкой eval (28 мин как сейчас). Код L.

**Проверка постановки: постановка корректна.** Схема верна, но затраты сильно занижены. Моя проба по 01_raw/val (префикс строго раньше event_time, кэп 12000): Σ префиксов 2.09e9 слотов истории, Σ квадратов 1.06e13 пар — около 84 эпох обучения по слотам истории, пусть и только прямой проход через 2 блока. На val+test+train_rows (527k) это скорее часы, чем 0.5–1.5 ч; замера нет. Лучше так: (1) кэп на последние K событий, при K=1024 Σ=7.3e8 и Σ²=6.8e11; сначала проверить на подвыборке, что cos с полным префиксом ≥0.99 и метрика не меняется; (2) один эмбеддинг на уникальный (клиент, число событий до строки) — строки одного момента делят префикс; (3) префиксы собирать индексами на GPU из кэша dated, без Python-pack на каждую строку. Profile_at на 305k клиенто-дней не замерен и может стать узким местом CPU.

**Источники:** evaluation-05, evaluation-10, evaluation-14, evaluation-03

### evaluation-X-08. Мульти-T churn для мощности (P3)

**Гипотеза.** Несколько T на клиента val/test сужают CI парной разницы без утечки: эти клиенты не видны предобучению.

**Постановка.** T_k = конец выгрузки − 60 д − 30·k д, k = 0…4, для val и test. Строки baseline на каждом T (параметр T в churn.build) и эмбеддинги на тех же T. Головы учатся на train при T = 2025-11-02. Кластерный bootstrap по клиентам.

**Метрика и критерий.** Ширина 95% CI ΔPR-AUC уменьшается ≥ 30% относительно одного T.

**Стоимость.** Сборка baseline 5 × ≈ 4 мин (на все группы); эмбеддинги val+test 5 × ≈ 3 мин; обучение голов — минуты. Код S в churn_baseline.

**Проверка постановки: постановка корректна.** Идея верна: клиентов val/test предобучение не видело. Параметра T в churn.build нет: build(group, …) в churn_baseline/churn/build.py:23, T фиксирован в config.cutoff (config.py:47-53), нужна правка кода. Метки одного клиента на разных T_k сильно коррелированы, отток почти поглощающий, а доля позитивов меняется с T. Кластерный bootstrap обязателен, и сужение CI на 30% не гарантировано. Голова с одного T train на нескольких T_k test — дополнительный сдвиг распределения по сезону.

**Источники:** evaluation-03

### evaluation-X-09. Контрастивная вспомогательная цель на [USR] (CoLES random slices) (P3)

**Гипотеза.** MLM даёт слабый глобальный сигнал; InfoNCE на [USR] двух срезов одного клиента улучшит глобальные задачи при небольшой потере MLM.

**Постановка.** Добавить к MLM InfoNCE по micro-batch (два случайных подотрезка клиента), λ ∈ {0.1, 0.5}; 10 эпох. Сравнить X-01, X-03 и метрики MLM по ключам с текущей моделью.

**Метрика и критерий.** Нижняя граница CI ΔPR-AUC churn test > 0 при росте val NLL ≤ 2%.

**Стоимость.** Код M; ≈ 5 ч обучения на каждое значение λ.

**Проверка постановки: постановку нужно исправить.** В заявленном виде неосуществимо. InfoNCE по micro-batch требует многих клиентов в проходе, а token_budget 16384 (settings.py:107), тогда как средний клиент пула val стоит около 24.7k позиций: 30.88M токенов / 1413 плюс события (cost, inputs.py:318-331). Большинство micro-batch содержат одного клиента, негативов нет. Нужны короткие срезы (например, ≤256–512 событий на срез), чтобы в проход влезали десятки клиентов, или очередь или memory bank [USR] через шаги (MoCo). Двойной проход срезов на 4 ГБ VRAM под WDDM рискован. Около 5 ч на каждое λ — только после X-01/X-03.

**Источники:** evaluation-04
