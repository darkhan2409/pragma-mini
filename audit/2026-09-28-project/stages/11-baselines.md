# Бейзлайны churn и fraud

Часть аудита `audit/2026-09-28-project`, см. `REPORT.md`.

## Сводка аудитора

Оба проекта изолированы и только читают data/01_raw. churn: одна точка T = конец группы − 60 сут на клиента (config.py:47-53). Популяция — клиенты хотя бы с одним собственным действием до T. 116 признаков строго раньше T, анкета откатывается на T. CatBoost с фиксированными PARAMS, ранняя остановка и порог max-F1 на val. fraud: строки purchase и transfer_out с 2024-04-01; метка получается повтором генератора со сверкой хешей лент; в train берётся 1/10 негативов с весом 10; 64 признака на момент операции; обучение CatBoost занимает 27.9 мин. С данными и утечками всё чисто: признаки строго раньше T или t_i, исход операции и следы сериализации исключены, тесты «будущее не меняет признаков» есть. Главные слабости — в честности и статистической силе будущего сравнения с PRAGMA, а не в коде. (1) Протокол PRAGMA+Head на тех же строках сейчас невыполним: у датасета PRAGMA один cutoff на группу, для fraud нужен cutoff на каждую строку, а вход головы не определён. (2) Нет доверительных интервалов; строки fraud кластеризованы по клиентам: 355 позитивов test приходятся на 96 клиентов. (3) Метка churn почти вся о продолжении уже идущей тишины: 105 из 142 позитивов test молчат больше 30 дней. (4) Высокий ROC fraud держится на детерминированных правилах генератора: доля суммы от доступных средств, равномерный час эпизода, канал ecom, вход за 4 минуты до операции. Это не утечка метки, но потолок бенчмарка. (5) CatBoost fraud идёт на настройках по умолчанию с тяжёлыми CTR-комбинациями. Вердикт: реализация аккуратная, как точка отсчёта годится. Для сравнения с PRAGMA нужны протокол, CI и контроль артефактов.

## Находки (14)

### baselines-01. Протокол сравнения PRAGMA+Head «на тех же строках» не определён и на текущей инфраструктуре невыполним

- **Вид:** устройство
- **Серьёзность:** высокая → высокая после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** M

**Доказательства.**

Датасет PRAGMA строит один срез на группу: src/dataset/build.py:30-33 («срез у группы один — её конечный cutoff»), :153-160 (events_cutoff обязан совпасть с window.final_cutoff). src/preprocessing/settings.py:186-191: final_cutoff train/val/test = 2026-01-01 / 2026-04-01 / 2026-08-01, а T для churn = 2025-11-02 / 2026-01-31 / 2026-06-02 (churn README:42-46). В fraud README:216-217 сказано: «эмбеддинг ... строго раньше event_time строки». Строк оценки 886 625 (val) + 1 014 958 (test). Эмбеддинг истории до t операции не знает (сумма, канал, мерчант), а вход головы в README не задан. Исход самой операции нужно маскировать и на стороне PRAGMA: в выборке RAW row group 0 val около 40% помеченных строк отклонены (decline_reason), у легитимных около 2%. Проба (eval_rows test): случайная подвыборка 1/100 негативов с весом 100 даёт AP baseline 0.8716±0.0254 против полного 0.8637, 1/20 — 0.8684±0.0147. Стратификация «все помеченные + все негативы со score≥1e-3 (7 995) + 1/100 остальных», около 18.5 тыс. строк, воспроизводит AP 0.8637 (sd<0.0005).

**Влияние.**

Без протокола PRAGMA+Head либо нельзя посчитать (эмбеддинг на каждую строку ≈1.9 млн прямых проходов, по грубой оценке из 28 мин на эпоху — десятки часов на RTX 3050, спекулятивно), либо посчитают несопоставимо: на конечный cutoff группы, то есть с будущим; без текущей операции; с её status и balance_after. Сравнение с CatBoost тогда ничего не доказывает.

**Предложение.**

Добавить в оба README раздел «Протокол PRAGMA+Head». (1) churn: отдельная сборка этапов 02→06 с final_cutoff = T группы (словарь тот же, train-only), эмбеддинг [USR] по истории < T. (2) fraud: голова получает эмбеддинг истории < t и текущую операцию как последнее событие; status, decline_reason и balance_after этой операции маскируются. Альтернатива — эмбеддинг плюс только операционные признаки из _operation. (3) Зафиксировать файл eval_subset.parquet (raw_row, weight): все помеченные строки, негативы из страты по score baseline, случайная страта 1/50–1/100 с весами Хорвица–Томпсона. На нём считать обе модели; полные метрики baseline оставить для контроля. (4) Три плеча: CatBoost(признаки), Head(эмбеддинг + операция), CatBoost(признаки + эмбеддинг).

**Как проверить.**

Взвешенные AP и ROC baseline на eval_subset совпадают с полными в пределах 0.002 на 20 повторных розыгрышах случайной страты. Тест: для каждой строки подвыборки cutoff эмбеддинга < event_time, текущая операция без status, decline_reason и balance_after.

**Проверка скептиком: подтверждено.**

Проверено. Срез один на группу: src/dataset/build.py:30-33, 153-160 (events_cutoff обязан совпасть с window.final_cutoff). Окна групп: src/preprocessing/settings.py:185-190. Эмбеддинг на T или на t строки текущими этапами получить нельзя. Анкета и позиции времени считаются от final_cutoff, поэтому простое обрезание событий в памяти будущее анкеты не уберёт. Моя проба по RAW val row group 0: у 61 fraud-строки доля declined 0.393; у 4 844 случайных легитимных операций 0.020. Требование маскировать исход операции верно. Оговорки. (1) Проба стратификации «sd<0.0005» для baseline тавтологична: все негативы с высоким score baseline попадают в выборку детерминированно. Для второй модели разброс будет определяться её сильными негативами из случайной страты, и эта оценка ещё не сделана. (2) Число «десятки часов» спекулятивно. Дешевле считать эмбеддинг на начало суток или недели строго раньше t и отдать голове операционные и внутридневные признаки: проходов тогда столько, сколько пар (клиент, день). Цена такого решения: шаги эпизода идут через 2–180 мин (params/fraud.py:90), и пробы того же дня эмбеддинг не увидит.

**Источники:** fraud_baseline/README.md:204-217, churn_baseline/README.md:161-173, src/dataset/build.py:30-33, src/preprocessing/settings.py:177-191

### baselines-02. Метрики без доверительных интервалов; для кластеризованных строк fraud предложен DeLong

- **Вид:** риск корректности
- **Серьёзность:** высокая → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** S

**Доказательства.**

churn/train.py:74-89 и fraud/train.py:67-83 считают только точечные значения; в metrics.json CI нет. churn README:166 предлагает «bootstrap, DeLong» для парного сравнения, но DeLong применим только к ROC-AUC и предполагает независимые объекты. Мои пробы по reports/eval_rows.parquet (sklearn, 2000 бутстрепов по строкам): churn test ROC 0.939 [0.922, 0.955], PR-AUC 0.618 [0.537, 0.701]; val PR-AUC [0.558, 0.721]. fraud test: 355 позитивов у 96 клиентов (в среднем 3.7, максимум 13), в val у 77 клиентов. Кластерный бутстреп по клиентам (300 повторов, взвешенный AP на предсортированных скорах) даёт PR-AUC 0.864 [0.816, 0.901], sd 0.022.

**Влияние.**

Ширина 95% CI для PR-AUC — около 0.16 (churn) и 0.085 (fraud). Разницы PRAGMA vs CatBoost порядка 0.02–0.05 без парного кластерного теста неотличимы от шума. Построчный бутстреп или DeLong для fraud завысят уверенность: эффективный размер около 96 клиентов, а не 355 строк.

**Предложение.**

Добавить в train.py обоих проектов clustered bootstrap по client_id (B≥1000) для ROC-AUC, PR-AUC и F1 при фиксированном пороге. Добавить модуль парного сравнения compare.py (eval_rows с двумя score → CI разности). Для ROC — кластерный вариант DeLong по Obuchowski (1997). Первичной метрикой fraud сделать PR-AUC (Saito & Rehmsmeier 2015), а не ROC 0.996.

**Как проверить.**

Тест на синтетике: при двух одинаковых score CI разности содержит 0 и имеет нулевую ширину. При кластерах CI шире построчного. Числа CI попадают в metrics.json.

**Проверка скептиком: подтверждено с поправками.**

Точечные метрики без CI подтверждаются: churn/train.py:74-89, fraud/train.py:67-83. Мой бутстреп churn test (1000 повторов): PR [0.539, 0.704], ROC [0.921, 0.955], совпадает с аудитом. Кластерность fraud подтверждена: test — 355 позитивов у 96 клиентов (среднее 3.70, максимум 13), val — 279 у 77. Мой кластерный бутстреп (200 повторов): AP 0.863 [0.828, 0.906], sd 0.020. Построчный пуассоновский бутстреп даёт sd 0.017 [0.831, 0.897], то есть только примерно на 15–20% уже. Тезис «эффективный размер ~96 клиентов» и сильное завышение уверенности преувеличены. Для churn строка = клиент, поэтому DeLong для ROC там корректен (README:166).

**Второе мнение: подтверждено с поправками (серьёзность: средняя).**

ПОДТВЕРЖДЕНО: churn_baseline/churn/train.py:74-89 и fraud_baseline/fraud/train.py:67-83 считают только точечные roc_auc/pr_auc/f1, в обоих reports/metrics.json CI нет, grep по bootstrap/DeLong/доверит. в *.py пуст. Числа повторил своими пробами по reports/eval_rows.parquet: churn test, построчный бутстреп 1000 повторов: ROC [0.920, 0.954], PR-AUC [0.538, 0.699]. fraud: test 355 позитивов у 96 клиентов (в среднем 3.70, максимум 13), val 279 у 77 клиентов. Кластерный бутстреп по client_id (200 повторов, взвешенный AP на предсортированных скорах, точечное значение совпало: 0.8637): [0.822, 0.896], sd 0.020. ИСПРАВЛЕНИЯ: (1) Заголовок неточен. DeLong предложен только в churn_baseline/README.md:166, а там по одной строке на клиента: в eval_rows дублей client_id 0, check_groups train.py:58 это требует. Значит, объекты независимы, и для ROC DeLong там корректен (для PR-AUC нет). В fraud_baseline/README.md:211 написано только «для парного сравнения», DeLong не назван. (2) «Эффективный размер около 96 клиентов, а не 355 строк» — преувеличение. Построчный бутстреп fraud дал sd 0.0156 против кластерного 0.0199, то есть эффект дизайна по дисперсии около 1.6: эффективно примерно 220 позитивов, а не 96. Построчный CI занижает ширину умеренно, не в разы. (3) Вывод «разницы 0.02–0.05 неотличимы от шума» по ширине маргинальных CI не следует. При парном сравнении на тех же строках скоры коррелированы, и CI разности обычно уже маргинальных. Значимость надо оценивать парным (кластерным для fraud) бутстрепом разности, как и сказано в proposal. Серьёзность снижаю до medium: головы PRAGMA пока нет, сравнения не проводились, так что это пробел методики будущего сравнения, а не ошибка в уже полученных результатах. Само предложение (кластерный парный бутстреп, PR-AUC как первичная метрика fraud) обосновано.

**Источники:** https://journals.plos.org/plosone/article?id=10.1371%2Fjournal.pone.0118432, https://dx.doi.org/10.2307/2533958

### baselines-03. Метрика churn почти вся о продолжении уже идущей тишины; один признак давности почти равен CatBoost

- **Вид:** моделирование
- **Серьёзность:** высокая → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** S

**Доказательства.**

Проба по data/<group>/features.parquet и eval_rows. Один признак act_days_since_last даёт: train ROC 0.936 / PR 0.526, val 0.935 / 0.556, test 0.929 / 0.529. У CatBoost на test 0.939 / 0.618. Доля churn по давности последнего действия (test): ≤1 дня 0.001, 7–14 дней 0.062, 14–30 — 0.268, 30–60 — 0.476, >90 — 0.559. Молчат больше 30 дней на момент T 98 из 140 позитивов val и 105 из 142 test. Срез «начало оттока» (act_days_since_last≤30), test: 1259 строк и 37 позитивов; CatBoost ROC 0.896 [0.851, 0.936], PR 0.363 [0.212, 0.522]; одна давность — PR 0.214. Причина по коду: популяция требует лишь одно действие до T за всю историю (target.py:163, build.py:232). Паузы генератора длятся 60–380 дней (params/lifecycle.py:79-86).

**Влияние.**

ROC 0.94 сжат к потолку, и сравнение PRAGMA с CatBoost будет в основном о том, кто лучше читает давность. Содержательная задача — предсказать начало паузы — опирается на 37 позитивов test с CI шириной около 0.3 по PR-AUC. Односнимочный протокол не может её различить.

**Предложение.**

Добавить в отчёт обязательный срез «активные ≤30 дней до T» и эталон «только давность» (act_days_since_last), с CI. Рассмотреть основную популяцию «действие за последние 30 дней» либо отдельную цель «начало оттока». Позитивы для неё набирать мультиснапшотами (baselines-04).

**Как проверить.**

В metrics.json есть срезы all, active_90 и onset_30 с CI и эталон по давности. Прирост модели над эталоном виден отдельно.

**Проверка скептиком: подтверждено с поправками.**

Числа воспроизведены моей пробой. Давность отдельно: train 0.936/0.526, val 0.935/0.556, test 0.929/0.529. Доли churn по корзинам давности совпадают (0.001 / 0.062 / 0.268 / 0.476 / 0.559). Молчат >30 дней 98 и 105 позитивов. Onset test: 1259 строк, 37 позитивов, CatBoost PR 0.363, ROC 0.896; давность PR 0.214. Поправки: (1) по ROC давность почти равна CatBoost, но по PR разрыв 0.09 (0.529 против 0.618), так что «почти равен» верно только для ROC. (2) Ссылки неверны: target.py:163 и build.py:232 не существуют (файлы 44 и 123 строки). Правильно target.py:34-39 и build.py:61. (3) Паузы генератора 25–380 дней, а не 60–380 (params/lifecycle.py:79-86: cards_only 25–150, app_only 30–180). (4) Частичный срез уже есть: active_90_days (train.py:46-48, 119-122). Среза onset и эталона по давности нет.

**Источники:** churn_baseline/churn/train.py:46-48, churn_baseline/churn/target.py:150-168

### baselines-04. churn: один снимок на клиента — мало данных для обучения и сезонный сдвиг между группами

- **Вид:** моделирование
- **Серьёзность:** средняя → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** M

**Доказательства.**

config.py:47-53: cutoff = period_end − 60 сут; build.py:202 — одна точка T на группу. Train: 9 339 строк и 776 позитивов (meta.json). Окна target: train 2025-11-02 → 2026-01-01 (ноябрь–декабрь), val 2026-01-31 → 2026-04-01, test 2026-06-02 → 2026-08-01 (README:42-46). Доля churn: 8.3% / 9.8% / 9.7%. История train покрывает 2024-01-01 … 2026-01-01, а используется одна точка.

**Влияние.**

Около 780 позитивов ограничивают и CatBoost, и будущую голову PRAGMA. Модель видит одну сезонную точку, а оценивается на других. Причина разницы 8.3% vs 9.7% (сезон или состав группы) не проверена — это спекулятивно. Прирост качества от мультиснапшотов вероятен, но не измерен.

**Предложение.**

Для train строить ежемесячные T_k с 2024-04-01 (прогрев 90 дней) до 2025-11-02, около 20 снимков и порядка 150–180 тыс. строк. Популяция и признаки на каждое T_k — тем же кодом, cutoff как параметр. Ранняя остановка по val на единственном вне-временном T. Для оценки оставить один T, чтобы eval_rows не менялись. Все окна target train кончаются до 2026-01-01, раньше T val, так что утечки по времени нет. Для головы PRAGMA понадобятся эмбеддинги на каждый T_k.

**Как проверить.**

Эксперимент baselines-X-05: парный кластерный бутстреп ΔPR-AUC test и среза onset против текущей модели. Проверить, что doля churn по месяцам T_k объясняет разницу 8.3% vs 9.7%.

**Проверка скептиком: подтверждено.**

config.py:47-53 — T = period_end − 60 d. Одна точка на группу: build.py:31 (moment = cutoff(group)), не :202. meta.json train: population 9339, churn_1 776, rate 0.083. Доли 9.8% и 9.7% — README:145-147. Причина разницы (сезон или состав) не проверена, аудитор честно называет это спекуляцией. Не учтено: для головы PRAGMA мультиснапшоты означают отдельную сборку 02→06 и инференс на каждый T_k. Это главная цена, а не 60 строк кода baseline.

**Источники:** churn_baseline/churn/config.py:47-53, churn_baseline/churn/build.py:202

### baselines-05. Высокий ROC fraud держится на детерминированных правилах генератора (не утечка метки, но потолок бенчмарка)

- **Вид:** утечка
- **Серьёзность:** высокая → средняя после проверки
- **Уверенность аудитора:** точно
- **Цена исправления:** M

**Доказательства.**

Код генератора и пробы по fraud_baseline/data/val/features.parquet + labels.parquet. (a) Сумма удара = max(5000, max(50000, balance+credit_limit)·U(0.25, 0.95)) (engine_products.py:1073-1076, params/fraud.py:81): amount_to_balance≥0.25 у 98.7% ударов val против 16.8% негативов; признак на 3-м месте. (b) Час начала эпизода равномерен (life/fraud.py:82), шаги идут через целые минуты (:91, :113). Доля ночи 0–5 ч местного: у fraud 22.9% (val) и 24.8% (test), у негативов 1.4%; в 2–3 ч отношение частот ≈30×; hour на 9-м месте. (c) Мошеннический перевод всегда channel=ecom и без сессии (engine_products.py:982); у легитимных transfer_out в val app 27 950 и ecom 50 048; мошеннических покупок через qr нет (67 842 легитимных qr); channel на 2-м месте. (d) Захват доступа (ATO): вход ровно за 4 мин до удара (engine_products.py:975). login_hours_since_prev = 4/60 у 20 из 86 мошеннических переводов val против 128 из 77 998 легитимных. (e) Получатель cp_fraud_{hash(client, day)} (:977): повтор получателя в пределах 3 ч у 66% ударов-переводов против 0.4% легитимных. (f) Все шаги мошенника приходятся на second==0 (100% против ~7%). Baseline это исключил, но PRAGMA видит секунды: event_time_log (README:487-499), дробный час календаря (preprocessing/calendar.py).

### baselines-X-01. Кластерные CI и парное сравнение на текущих eval_rows (P1)

**Гипотеза.** При нынешнем объёме оценки минимально различимая разница PR-AUC составляет около 0.05 (churn) и 0.03 (fraud). Тогда без парного кластерного теста сравнение с PRAGMA неинформативно.

Мощность по симуляции: к score baseline добавлять шум, контролируемый через rank-корреляцию 0.8–0.95, и искать Δ, при которой CI разности исключает 0 в 80% повторов. Данные: только reports/eval_rows.parquet и data/<g>/features.parquet (для среза onset).

**Метрика и критерий.** Ширина CI и минимально различимая ΔPR-AUC. Решение: если MDE > 0.05, обязательны мультиснапшоты (X-05) и срезы.

**Стоимость.** ≤5 мин CPU, около 150 строк кода; RAM <300 МБ

**Проверка постановки: постановка корректна.** Корректно и дёшево: только CPU, eval_rows около 140 МБ в pandas. Не сделано, кроме разовых проб аудитора и моих. Для churn кластер = строка, отдельной кластеризации не нужно. Для fraud парный бутстреп с одинаковыми клиентами в обеих моделях обязателен. Моя проба: кластерная sd AP 0.020, построчная 0.017, так что выигрыш от кластеризации умеренный. MDE лучше оценивать через шум в logit-пространстве с контролем rank-корреляции. ### baselines-X-02. Ускорение CatBoost fraud без потери качества (P1)

**Гипотеза.** Основное время уходит на CTR-комбинации (max_ctr_complexity=4) и CTR для категорий с малой кардинальностью. Конфигурация max_ctr_complexity=1 + one_hot_max_size=32 + lr 0.1 + урезанный eval set сокращает обучение в 3–5 раз при |ΔPR-AUC| ≤ 0.01.

**Постановка.** Прогоны на тех же data/<g>/features.parquet. A — текущие PARAMS (эталон 27.9 мин). B — A + max_ctr_complexity=1, one_hot_max_size=32. C — B + learning_rate=0.1, iterations 3000. D — C + eval set из всех позитивов val и 1/10 негативов (детерминированный хеш raw_row) с весом 10, eval_metric='PRAUC:use_weights=true', metric_period=25; порог и отчёт — на полном val. E — D с категориями как pandas.Categorical и сохранённым квантованным Pool. F (опционально, при свободной GPU) — D с task_type=GPU. Везде thread_count=8, test грузится после fit, замер через /usr/bin/time -v.

**Метрика и критерий.** Время на стене и пик RSS; test PR-AUC и ROC с кластерным CI. Решение: принять самую быструю конфигурацию с |ΔPR-AUC test| ≤ 0.01, CI которой перекрывается с эталоном, и пиком RSS ≤ 3 ГБ.

**Стоимость.** ≈1.5–2 ч CPU на всё: A уже есть, B–E по 5–15 мин (оценка); правка train.py около 30 строк

**Проверка постановки: постановка корректна.** Выполнимо на CPU, но каждый прогон с текущими PARAMS занимает около 28 мин и 4.7 ГБ пика при ~4.9 ГБ свободных. Запускать строго по одному, когда параллельно ничего не идёт, и начинать с B и D, которые уменьшают память. Конфаундеры: при lr 0.1 меняется число деревьев, поэтому сравнивать надо и время на итерацию, и итоговое качество. PRAUC:use_weights=true на прореженном val меняет критерий остановки. Детерминизм проверять при фиксированном thread_count. GPU исключить: карта занята обучением PRAGMA, 4 ГБ под WSL.

**Источники:** https://catboost.ai/docs/en/concepts/speed-up-training, https://catboost.ai/docs/en/references/training-parameters/ctr

### baselines-X-04. Взвешенная подвыборка оценки fraud для PRAGMA+Head (P1)

**Гипотеза.** Стратифицированная подвыборка из 20–30 тыс. строк с весами Хорвица–Томпсона даёт несмещённые PR-AUC и ROC с разбросом ≤ 0.01 для обеих моделей и делает построчный эмбеддинг PRAGMA посильным.

**Постановка.** Страты: все помеченные строки (с false_positive); все негативы клиентов с позитивами в ±48 ч от шага эпизода; негативы со score baseline ≥ 1e-3 (в test 7 995); случайная 1/50 остальных с весом 50. Файл eval_subset.parquet (group, raw_row, weight, stratum). На 20 повторных розыгрышах случайной страты сравнить взвешенные AP и ROC baseline с полными. Чтобы оценить разброс для модели, чьи сильные негативы вне страты, подставить в роль второй модели baseline с шумом. Моя проба: чисто случайная 1/100 даёт sd 0.025, а score-страта воспроизводит AP 0.8637 точно.

**Метрика и критерий.** |AP_subset − AP_full| ≤ 0.005 и sd ≤ 0.01 для baseline и для зашумлённой модели. Решение: зафиксировать подвыборку как объект сравнения.

**Стоимость.** ≤10 мин CPU по eval_rows, около 80 строк кода

**Проверка постановки: постановку нужно исправить.** Идея подвыборки с весами Хорвица–Томпсона верна, но дизайн страт смещён в пользу baseline. Страта «score baseline ≥1e-3» воспроизводит AP baseline тривиально, потому что все её сильные негативы входят с весом 1. У PRAGMA сильные негативы, которых baseline не считает подозрительными, попадут только в случайную страту с весом 50–100. Её AP будет иметь большую дисперсию и может выглядеть хуже или лучше случайно. Лучше дизайн, независимый от моделей: все помеченные строки + все операции клиентов с позитивами + кластерная выборка клиентов (все их операции) с весом по клиенту, либо страты по времени и типу. Вариант с зашумлённым baseline как второй моделью недооценивает проблему: шум коррелирован с исходным score. Кроме того, взвешенный AP — отношение оценок: он состоятелен, но не несмещён.

**Гипотеза.** Построчный PR-AUC переоценивает длинные эпизоды. Метрика «эпизод пойман до первого удара» лучше различает модели, у которых разная полнота на пробах (сейчас пробы 86/138 против ударов 184/217 на test).

**Постановка.** episode_id — из повтора (baselines-07) либо реконструкцией по (client_id, episode_kind, разрыв ≤ 180 мин) из labels.parquet. Метрики: доля эпизодов с хотя бы одним флагом, доля пойманных до первого удара, медианный номер шага первой поимки, полнота при precision ≥ 0.9, полнота при 1 и 5 алертах на 10 тыс. операций.

**Метрика и критерий.** Числа по baseline с кластерным CI; тот же расчёт затем для PRAGMA+Head. Решение: включить в основной отчёт сравнения.

**Стоимость.** ≤15 мин CPU по eval_rows и labels (без нового повтора); код около 100 строк

**Проверка постановки: постановка корректна.** Выполнимо по eval_rows + labels.parquet: там есть step_kind, episode_kind и raw_row. Реконструкция эпизода по разрыву ≤180 мин согласуется с step_gap_minutes (2, 180) в params/fraud.py:90. Эпизодов на клиента не больше 3, и начинаются они в случайные дни (life/fraud.py:75-82), так что склейка двух эпизодов маловероятна, но её стоит проверить. Строки false_positive из эпизодов fraud исключить. При ~96 клиентах с позитивами метрики эпизода будут шумными, CI обязателен.

### baselines-X-10. Гибрид: CatBoost + эмбеддинг PRAGMA (P2)

**Гипотеза.** Эмбеддинг [USR] даёт прирост поверх ручных признаков (главный практический вопрос), даже если голова на одном эмбеддинге проигрывает CatBoost.

**Постановка.** После реализации протокола из baselines-01: к признакам churn добавить d=128 координат эмбеддинга на T (или PCA-32); к признакам fraud — эмбеддинг истории < t на подвыборке X-04. Обучение на тех же строках, те же PARAMS и подбор из X-07. Парный кластерный бутстреп против baseline.

**Метрика и критерий.** ΔPR-AUC test (all и onset для churn; подвыборка с весами для fraud) с CI, не содержащим 0 → эмбеддинг несёт новую информацию.

**Стоимость.** Зависит от вычисления эмбеддингов: churn около 11 тыс. клиентов × один cutoff — оценочно десятки минут на GPU; CatBoost 1–10 мин

**Проверка постановки: постановка корректна.** Главный практический эксперимент, но он зависит от протокола baselines-01. Для churn нужна пересборка 02→06 с cutoff = T каждой группы и инференс на ~12.2k клиентов. Forward-only, по грубой оценке, заметно дешевле эпохи в 28 мин, но это не измерено. Для fraud — только на подвыборке с исправленным дизайном X-04 или с эмбеддингом на начало суток. PCA-32 стоит обучать только на train. Ссылку arXiv 2604.08649 я не проверял.

**Источники:** https://arxiv.org/abs/2604.08649

### baselines-X-09. CatBoost на информации, доступной PRAGMA (P3)

**Гипотеза.** Асимметрия информации (ID-признаки, полная история против MAX_EVENTS и MAX_TOKENS) меняет метрики baseline меньше, чем ширина CI.

**Постановка.** churn: убрать cards_nunique_90, contracts_nunique_90, products_nunique_90, app_sessions_*; все признаки «за всю историю» считать по последним N событиям клиента до T, где N — как в 05_dataset (12 000 событий или 58 000 токенов). fraud: то же для новизны и amount_to_max_prev. Переобучить и сравнить парно.

**Метрика и критерий.** ΔPR-AUC и ΔROC test с кластерным CI. Решение: если Δ вне CI — сравнивать PRAGMA с этой ограниченной версией как с главным плечом.

**Стоимость.** churn около 10 мин, fraud около 30 мин (конфигурация X-02); код около 50 строк

**Проверка постановки: постановка корректна.** Корректно, P3 оправдан. Точно эмулировать MAX_TOKENS в baseline трудно: нужен счёт токенов на событие из 04_tokenized, а baseline изолирован от src. Приближение через последние N событий префикса до t достаточно. Для fraud важна длина префикса на момент строки, а не полной ленты: доля усечённых строк ниже 16.4%. На fraud требуется конфигурация X-02.
