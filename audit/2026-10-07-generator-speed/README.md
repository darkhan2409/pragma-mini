# Скорость Generator 1.0.1 (2026-10-07)

Задача: найти, где генератор тратит время, и ускорить его, не меняя ни семантики, ни байтов
выгрузки.

**Итог:**

- выгрузка того же seed и конфига **побайтно та же** — все четыре таблицы, sha256 файлов;
- на 1000 клиентах генерация быстрее в **1.68×** при воркерах по умолчанию (209 → 124 с) и в
  **1.84×** при 8 воркерах (114 с);
- `GENERATOR_VERSION` не поднята: байты выгрузки не изменились.

Замеры воспроизводит `bench.py` (пишет только в каталог из `--out`):

```bash
.venv/bin/python audit/2026-10-07-generator-speed/bench.py run --out <scratch> --workers 7 --chunk 256 --hash
.venv/bin/python audit/2026-10-07-generator-speed/bench.py profile --out <scratch> --batch 0
.venv/bin/python audit/2026-10-07-generator-speed/bench.py stats --out <scratch> --batch 0
```

Код «до» мерился со снимка коммита 1e973be: `PYTHONPATH=<снимок>`; в записи прогона есть поле
`code`, откуда загружен генератор.

## Условия замера

- **Машина:**
  - процессор AMD Ryzen 5 6600H: 6 физических ядер, 12 потоков SMT;
  - 7 ГиБ RAM, своп 4 ГиБ;
  - WSL2;
  - scratch в `/tmp` (tmpfs, то есть в памяти).
- **Выгрузка:**
  - 1000 клиентов, seed 11, world_seed 42;
  - окно train: 2024-01-01 → 2026-01-01, `registration_end` 2026-01-01;
  - `chunk_clients` 256.
- **Объём:** 2 729 355 событий, 1000 строк анкеты, 3552 перехода и 96 713 недельных снимков truth.
- **Разброс:** повторы одного прогона на этой машине расходятся до ±15%. Прогоны, на которые
  пришлась сторонняя нагрузка, помечены.

## 2. Внесённые оптимизации

**O1. Задание воркера — одно сообщество, а не пачка** (`emit.py`).
- **Как было.** Пачка из `chunk_clients` клиентов задавала и задание воркера, и раскладку
  итогового файла (одна группа строк на пачку). На 1000 клиентах это 4 задания, на val и test —
  по 6. Ядра простаивали, а самая долгая пачка задерживала конец.
- **Как стало.** Задание — сообщество из 32 клиентов. Склейка собирает части пачки по порядку в
  одну таблицу и пишет её одной группой строк, как раньше.
- **Почему безопасно:**
  - клиент зависит только от своего сообщества (`test_generator_prefix`);
  - кэши воркера — чистые функции;
  - состав и порядок строк каждой группы строк те же, параметры записи те же, поэтому байты
    файла те же.
- **Целостность** не ослаблена: каждая часть подписана sha256 в маркере задания, при склейке
  подпись сверяется. В карточке прогона появилось поле `job: community`, поэтому черновик
  прежнего формата `--resume` не продолжает.
- **Память:** пик воркера 0.33–0.36 ГиБ (было до 1 ГиБ на пачку в 256 клиентов).

**O2. Подбор продуктов** (`behaviour/adoption.py`).
- **Требования версии.** Условия eligibility разбираются один раз на версию (`_requirements`)
  вместо примерно 12 `dict.get` с `int()` на каждый из 7.3 млн вызовов. Порядок проверок и точка
  ошибки о неизвестном условии те же.
- **Вызов `catalog()`** — один раз в проверках дебетовых карт и кредитов, а не дважды на каждый
  удерживаемый продукт.
- **Общая для момента часть** — продаётся ли продукт, версия, базовый вес, кривая принятия,
  возраст версии — кэшируется на один момент (`_offerable`). План дня всех клиентов сообщества
  спрашивает её на полночь. Вес по-прежнему умножается на кривую после проверки базового веса,
  поэтому операции с плавающей точкой те же.

**O3. Множитель категории на день** (`life/calendar.py`).
- `category_factor` зависит только от категории, даты и региона при тех же параметрах. Карта
  праздников фиксирована (2017–2030).
- Кэш живёт один день и сбрасывается со сменой объекта параметров.

**O4. Ключевые розыгрыши** (`rng.py`).
- `state_key` без повторных `int()` и `str()`: значения уже приведены в `configure`.
- Упаковка ключа и номера розыгрыша — те же `<Nq` и `<q`, но форматы `struct` разобраны заранее.
- Микрозамер: `keyed_rng` вместе с `random()` быстрее на 13%, `state_key` — на 20%.

**Проверка после каждой правки** — эталон 96 клиентов и 2 пачки, затем выгрузка на 1000 клиентов.
Файлы всех четырёх таблиц совпали побайтно; логический хеш строк тоже.

нельзя; первый прогон «после, 7 воркеров» (157 с) — тоже выброс.

**Чистая пара на 2 воркерах:** 295 → 265 с, то есть ускорение кода (O2–O4) около 10%. Остальное
на 1000 клиентах даёт O1.

**Оценка на полном наборе** (по пропускной способности): train, 8500 клиентов, около 20 → 16 мин;
val и test — около 1.4×. На train пачек и раньше было 34, и простой там меньше.

**Воркеры.**
- Своп ни в одном прогоне не рос.
- Пик воркера 0.33–0.36 ГиБ, а `WORKER_MEMORY` закладывает 512 МиБ — оценка с запасом.
- Пик главного процесса при склейке — 0.9–1.1 ГиБ при `chunk_clients` 256 (1.76 ГиБ при 1024);
  это примерно `MEMORY_RESERVE` (1 ГиБ).
- `default_workers()` на этой машине даёт 7. Сверх 6 физических ядер прирост небольшой
  (7 → 124 с, 8 → 114 с, 12 → 110 с при 3.7 ГиБ) и в пределах разброса, поэтому формула не
  менялась.

**`chunk_clients`.** Теперь он задаёт только раскладку итогового файла, а не параллелизм.
- 512 и 1024 не быстрее 256: 122 и 142 с против 124 с.
- Байты файла другие, хотя строки те же.
- Пик главного процесса при склейке растёт.

Лучший — 256, по умолчанию.

## 4. Burn-in, день, очередь

**Burn-in** — пачка 0:
- проходили его 217 клиентов из 256, в среднем 908 шагов;
- полный (1095 дней) — у 133 клиентов;
- 2.1 с из 166 с, из них `_step` — 1.9 с; 1.3–1.5% времени.

Переделывать его нет смысла.

**День клиента** — пачка 0, 187 136 клиент-дней:
- пустых 6.1% — все до прихода клиента в банк, это ранний выход и дёшево;
- в среднем 4.63 действия на клиент-день.

Ежедневные действия, которые почти всегда ничего не меняют:
- **`tariff_check`** — каждый клиент-день, 175 766 действий, 21% всех действий очереди; меняет
  что-то только в дни смены версии тарифа и принудительной миграции;
- **`adoption`** — 0.85 на клиент-день и около 15% времени: подбор продуктов при исполнении,
  хотя заявка подаётся редко;
- **`loan_check`** — по каждому кредиту каждый день;
- **`bill_sweep`**, **`support_check`**.

**Кандидаты на расписание по событиям** — `tariff_check` (по датам версий каталога) и, возможно,
`loan_check`.
- Розыгрыш у них привязан к паре «клиент, день», поэтому пропуск пустых дней не сдвигает
  розыгрыши других дней.
- Нужно доказать, что в пропущенные дни обработчик ничего не делает.
- Это отдельное решение. У `adoption` порядок розыгрышей внутри обработчика зависит от пула
  кандидатов, поэтому без изменения выхода её не перевести.

**Очередь** — пачка 0:
- в среднем 139 действий на сообщество в день, p50 — 136, p90 — 173, p99 — 212;
- хвост пересортировывался 60 раз за всю пачку, длина хвоста в среднем 80;
- сортировка — меньше 2% времени.

Дешевле структура не нужна: сейчас выигрыш был бы в пределах шума, а риск сдвинуть устойчивый
порядок при равных `(ts, ordinal, order)` реален.

## 5. Отклонено

| что | почему |
|---|---|
| сменить `chunk_clients` по умолчанию | байты файла другие, скорости нет |
| склейка частей по ходу генерации | выигрыш 3–4%, усложняет `emit` |
| переделка burn-in | 1.5% времени |
| расписание по событиям для ежедневных проверок | архитектурное решение, нужно доказательство равенства выхода |
| другая структура очереди | сортировка меньше 2% |
| сменить `default_workers` | 8 против 7 в пределах разброса на этой машине |

## 6. Проверки

- **Тесты** (CPU; CUDA-тестов в этой среде нет):
  - корневой `pytest` — 744 пройдено, ноль пропущено;
  - `churn_baseline` — 169 пройдено.

  Одно падение, `test_vocab_fit_and_encoding_read_the_same_cutoff`, было из-за потокового
  чтения fit. Шпион стоял на `Group.history`, а поток её не вызывает. Шпион перенесён на
  `Group._build`, общий путь обоих чтений; инвариант «fit и кодирование на одном cutoff»
  проверяется так же.
- **Префикс на 1000 клиентах** (`audit/2026-10-06-generator-v1/diagnose.py prefix`, seed 11):
  выгрузка до 2026-03-01 против выгрузки до 2026-09-01 — разошлись 0 из 973 клиентов по событиям,
  0 из 914 по переходам truth, 0 из 973 по недельным снимкам, 0 из 973 по датированным фактам
  анкеты. `MAX_DIVERGED = 0`.
- **Равенство выгрузки:** во всех прогонах с `chunk_clients` 256 при 1, 2, 4, 6, 7, 8 и 12
  воркерах sha256 всех четырёх файлов те же, что у кода до правок.

**Можно ли считать ускоренную реализацию эквивалентной 1.0.1:** да. Байты выгрузки при том же
seed и конфиге те же, `GENERATOR_VERSION` не менялась.

```
SAFE SPEEDUP:
1.7x (воркеры по умолчанию; 1.8x при 8 воркерах)

SEMANTICS CHANGED:
NO
```
