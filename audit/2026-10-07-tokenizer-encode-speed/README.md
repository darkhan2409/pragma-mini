# Скорость encode токенизатора (2026-10-07)

Задача: ускорить `python -m src.tokenization.run encode <group>`, не меняя ни одного токена,
номера, позиции, календаря, пометки источника вехи, времени анкеты, порядка событий и поведения
на ошибках.

**Итог:**

- encode группы на 1000 клиентах быстрее в **2.3×**: 111.6 → 48.0 с (среднее двух прогонов);
- процессорного времени в **4.9×** меньше: 257 → 52 с;

  раскладка по группам строк та же: одна группа строк на клиента.

Побочно ускорился и fit (он читает историю тем же `Group._build`): 81.1 → 57.3 с; все семь
артефактов словаря и полный слепок `FitStatistics` те же.

## 1. Как encode устроен

```
02_preprocessed/<group>/events.parquet + 01_raw/<group>/profile.parquet + 03_vocab
  → FrozenArtifacts.load, check_vocab
  → Group(group); для каждого client_id анкеты: history(client_id, final_cutoff)
      → events_table: read_row_groups всей группы строк клиента → slice
      → _build: to_pylist всех 62 колонок → отбор < cutoff → календарь
               → event_values (model_event) → ClientEvent; profile_at; проверка вех
  → encode_event(event.model_values()) → EncodedRecord → словарь строки
  → from_pylist по клиенту → TableWriter.write (одна группа строк на клиента)
  → encode_profile → from_pylist одной строки → TableWriter.write
  → meta.json
```

Кодирование значения по виду ключа:
- **категория** — `value_text` → номер значения;
- **число** — шкала ключа (у `split_by` — отбор по условию на каждый вызов) → перебор `locate`;
- **текст** — `normalize_text` → BPE → `piece_id` по кускам, с проверкой предела кусков.

## 3. Повторное чтение групп строк — подтверждено

- **До:** `history` по одному клиенту читает всю группу строк клиента (`read_row_groups`), чтобы
  взять его срез. 1000 клиентов — 1000 чтений групп строк, каждая из 17 групп раскрывается
  ~64 раза. Это 18.7 с стены и большая часть лишнего CPU: распаковка многопоточная, отсюда
  CPU 257 с при 112 с стены.
- **После:** `Group.histories(cutoff)` — тот же потоковый читатель, что у fit (аудит
  `2026-10-07-tokenizer-fit-speed`, F1). Второго механизма нет. 17 курсоров `iter_batches`
  читают каждую группу строк ровно один раз, плюс прежний индекс клиентов по колонке
  `client_id`: 17 чтений одной колонки.
- **Целостность:** клиенты и их истории те же и в том же порядке.
  - Клиент на границе групп строк собирается целиком.
  - Лента, где клиенты внутри группы строк не по возрастанию, идёт прежним путём `history`.
  - Клиент ленты без анкеты в группу не попадает, как и раньше.

## 4. Внесённые изменения

**E1. Потоковое чтение** (`tokenization/transform.py`).
- `encode_group` берёт истории из `source.histories(cutoff)` в порядке `client_ids`.
- Ошибка чтения по-прежнему оборачивается в `TransformError("клиент <id>: …")` с тем же id.

**E2. Сборка истории по колонкам** (`preprocessing/read.py`, общий путь encode и fit).
- **Как.** `_build` переводит в Python только `event_time`, `client_id`, `source`, `type` и
  `lifelong_source`. Значения событий собираются по колонкам проекции: только непустые ячейки
  (`is_valid` → номера строк, `drop_null` → значения). Ключ поля ищется один раз на пару
  (поле, источник) в колонке.
- **Порядок ключей тот же**, что у `event_values`: тип первым (даже пустой), затем поля в порядке
  `SEMANTIC_PAYLOAD_FIELDS`, затем изменение профиля (`values.update(changed)`); заметки — в
  порядке строк.
- **Ошибки.** Ошибку данных воспроизводит прежний построчный разбор
  (`client_events_by_rows`, он же эталон в тесте). При `ValueError`/`KeyError` в колоночной
  сборке разбор повторяется построчно: какую строку и какое поле назвать первыми, решает он.
- **Откат анкеты** получает только строки с `event_time >= cutoff`, в порядке ленты.
  `profile_at` и сам смотрит только на них.
- **Короткий путь финального cutoff.** Если у колонки `event_time` нет пустых значений и её
  максимум раньше cutoff, вся лента клиента — события, а откатывать нечего. Отбор построчно не
  нужен. Это проверка по данным клиента, а не допущение о ленте: на любом другом cutoff и на
  любой ленте работает общий путь. Пустое время, как и раньше, падает на сравнении.

**E3. Без копии `model_values()`** (`tokenization/encode.py`).
- `encode_event` передаёт `event.values`: `encode_values` в них только смотрит.
- Тест закрепляет, что значения событий после кодирования те же.

**E4. Запас разобранных текстов** (`encode.py`, поле `FrozenArtifacts.texts`).
- Сырой текст → кортеж глобальных номеров кусков (или `None` — пусто после нормализации).
  `normalize_text` и BPE — чистые функции строки, словарь заморожен.
- Ограничен 65 536 строками; переполненный запас начинается заново, ответ от этого не зависит.
- На промахе предел кусков проверяется **до** перевода кусков в номера, как раньше. На попадании
  предел проверяется заново на каждом значении: предел может быть другим.
- Без BPE путь прежний: `[UNK]` для непустого текста, без запаса.

**E5. Шкалы, подготовленные заранее** (`numeric.Scale`, `FrozenArtifacts._scales`).
- Ключ → `(split_by, {условие: Scale})` строится один раз; отбора `when` на каждый вызов нет.
- В сплошной шкале обычный диапазон ищется `bisect_right` по нижним границам. Сплошная значит:
  первый открыт снизу, последний сверху, каждый начинается там, где кончился предыдущий, и
  границы не убывают. Тогда значение лежит в последнем диапазоне с `minimum <= значения`, и это
  тот же первый диапазон, который нашёл бы перебор.
- Нулевой диапазон проверяется первым, как раньше.
- Шкала не сплошная — перебор `locate` как есть.
- Проверка числа (NaN, бесконечность, не число) — та же функция и тот же текст ошибки.

**E6. Мелочи кодирования без смены результата.**
- Готовая таблица ключа: `encoders` (`key → (key_id, kind)`) строится один раз вместо
  `key_id` и `kind` на каждое значение.
- `categorical_id` без `{}` на каждый вызов.
- Строковая категория записывается сама собой: `value_text(str) == str`.
- `EncodedRecord.add`: один кусок — три `append`, несколько — `extend`.
- `n_values` и подсчёт `[UNK]` — `list.count`.
- `[UNK]` берётся один раз на группу.
- `check()`:
  - все позиции содержимого нулевые → обе ветки проверки заведомо проходят, обход пропускается;
  - иначе — прежний обход с тем же текстом ошибки.
- Сортировка пар по `key_id`: `list.sort` с `itemgetter(0)` (тот же устойчивый порядок).

**E7. Запись колонками** (`transform.py`).
- Строки клиента копятся колонками и пишутся `pa.Table.from_pydict`. Это то, что `from_pylist`
  делает внутри, но без словаря на строку.
- Одна группа строк на клиента — как раньше.

## 6. Ответы по пунктам

1. **Время encode до.**
   - Train (1000 клиентов, 2.73 млн событий): 111.6 с.
   - Пара «до/после» подряд на батарее (частота ниже): 198.7 → 87.2 с — то же 2.28×, выдача та же.
   - Val и test отдельно не мерились: scratch-выгрузка одна. Encode линеен по событиям, поэтому
     на группу в 1500 клиентов — около 2.8 мин до и 1.2 мин после.
2. **Главные узкие места до:**
   - сборка истории — 42 с;
   - кодирование значений — 38 с;
   - повторное чтение групп строк — 19 с;
   - `from_pylist` и запись — 9 с.
3. **Чтения групп строк ленты:** 1000 → 17 (плюс 17 чтений колонки `client_id` для индекса до и
   после).
4. **Повторное чтение по клиентам** подтвердилось: каждая группа строк раскрывалась ~64 раза.
5. **Читатель** — `Group.histories(cutoff)`: потоковый, с курсорами по группам строк, тот же, что
   у fit.
6. **Таблицы Arrow.**
   - Выдача: 2000 → 2000 (по таблице events и profile на клиента), но колонками, без 2.73 млн
     словарей строк.
   - Чтение: 1000 таблиц всей группы строк → ~1350 кусков по ≤2048 строк и 1000 склеек
     клиента.
7. **Записи parquet:** 2000 → 2000; раскладка и байты те же.
8. **Лучший размер пачки записи** — 1 клиент. Таблица выше: пачки не ускоряют и расходуют память.
9. **Пик RSS:** 0.58 → 0.44–0.46 ГиБ. Вся группа в памяти не копится: истории идут по одной, на
   курсоры около 300 МиБ.
10. **Объекты Python:**
    - `ClientEvent`: 2.73 млн → 2.73 млн (это контракт `ClientHistory`);
    - словари строк ленты на 62 ключа: 2.73 млн → 0 (только строки позже cutoff для отката, в
      этой группе 0);
    - копии `model_values`: 2.73 млн → 0;
    - словари строк выдачи: 2.73 млн → 0.
11. **Копия `model_values` убрана**; тест — `test_encoding_only_reads_the_values_of_events`.
12. **Вызовы BPE:** 841 770 → 8 502; `normalize_text` — тоже 8 502.
13. **Попадания в запас BPE:** 99.0% (8 502 разных строк на 841 770 значений). Запас в 65 536
    строк держит все тексты этой группы; память — порядка мегабайта.
14. **Время BPE:** 4.9 + 0.65 с (`pieces` + `normalize_text`) → 0.18 + 0.02 с.
15. **Поиск числового диапазона:** `bucket_id` — 7.9 → 1.6 с на 1.98 млн вызовов (таймеры).
16. **Шкалы подготовлены заранее** — да. Двоичный поиск тоже, с перебором для несплошной
    шкалы. Свойство проверено тестом на 25 тыс. пар (шкала, значение): вокруг границ, ноль, −0.0,
    отрицательные, большие, повторяющиеся границы, bool, строка-число, NaN, бесконечности.
17. **`EncodedRecord.add`** ускорен (E6).
18. **Лишние проходы по массивам записи** убраны: `n_values`, `[UNK]` и обход `check` в типичном
    случае. Сама проверка `check()` осталась.
19. **Короткий путь финального cutoff доказан** по построению: максимум < cutoff ⇒ каждая строка <
    cutoff. Допущения о ленте нет.
    - Вариант «cutoff равен `period_end` ленты» не используется. Здесь он верен (`period_end`

      дешевле и верна на любой ленте.
    - Отдельный короткий путь `profile_at` не нужен: без строк позже cutoff откат стоит 0.04 с на
      1000 клиентов.
20. **Использован:** да, у всех 1000 клиентов этой группы.
21. **Последовательный train/val/test** — замер на трёх копиях train (по 1000 клиентов): 3 × 48 ≈
    143 с.
22. **Параллельные группы:** три процесса на трёх копиях train вместе — 67.7 с.
    - В это время входит ~10 с подсчёта отпечатков после encode в каждом процессе; сам encode —
      57–59 с на процесс.
    - Память: 3 × 0.45 ГиБ.
    - Две копии вместе: 67.6 с (encode 57.7–58.4 с на процесс) против ~96 с по очереди.
    - Диск: выдача ~76 МБ на 1000 клиентов, запись на tmpfs узким местом не была; на SSD её
      объём тот же.

      времени encode: оно определяется train.

## 7. Не принято и почему

- **Пачки клиентов в одной группе строк** — раздел 5.
- **Плоские `ListArray.from_arrays` вместо списков** при сборке таблицы: микрозамер медленнее
  (0.050 против 0.035 с на 175 тыс. строк). Оставлен `from_pydict`.
- **Повторная нормализация текста не убиралась.**
  - Значение текстового ключа в ленте — исходная запись. Нормализованная копия в
    препроцессинге живёт отдельно и в историю не идёт, так что контракта «текст уже
    нормализован» нет.
  - После запаса `normalize_text` вызывается 8.5 тыс. раз за 0.02 с, убирать её незачем.
  - Края (NFKC-лигатура, NBSP, табуляция, перевод строки, двойные пробелы, кириллица и
    казахские буквы с casefold, пустая строка и одни пробелы) проверены тестом запаса против
    разбора заново.
- **BPE пачкой (`encode_batch`)** — после запаса 8.5 тыс. вызовов на 0.18 с.
- **Без сортировки по `key_id`.** Порядок ключей словаря значений — порядок проекции, а не
  `key_id`, так что сортировка нужна. Она стоит ~0.3 с: 2.7 млн сортировок по ~7 элементов.
- **Векторный календарь.** 4 с (8%).
  - Перевод в пояс банка — `astimezone` по `zoneinfo` на каждый момент.
  - Перевод средствами Arrow опирается на свою базу поясов, и её совпадение с `zoneinfo`
    (Алматы меняла смещение 2024-03-01) не доказано. Не трогался.
- **Короткий путь `profile_at`** — 0.04 с, незачем.
- **Сжатие.** zstd не менялся: запись вместе со сжатием — 3 с из 48, смена кодека меняла бы
  договор хранения ради ≤6%.
- **Многопроцессность внутри группы** не делалась. Оценка — раздел 9.

## 8. Проверки

- **Полный `pytest`:** 754 пройдено из 754 собранных, ни одного падения и ни одного пропуска.
  В том числе 10 новых.
- **Новый `tests/test_tokenizer_encode.py`** (10 тестов, ~5 с, мир генератора 12 клиентов до
  конца окна train):
  - одна группа строк закодированной ленты — один клиент;
  - клиент, разрезанный границей группы строк, кодируется целиком;
  - лента без порядка клиентов идёт прежним путём и даёт то же;
  - клиенты ленты без анкеты (в середине и в конце) в группу не попадают;
  - кодирование не меняет значения событий;
  - колоночная сборка событий даёт то же, что построчный разбор: значения с порядком ключей,
    календарь, пометки, заметки неразобранных изменений профиля;
  - ошибка данных (поле без смысла у источника) та же, что у построчного разбора;
  - `Scale.locate` совпадает с `locate` на 400 шкалах любого вида;

    записи, неизвестный ключ;
  - запас текстов отвечает так же, как разбор заново: запас на 7 строк переполняется на ходу,
    предел 256/1/256, в том числе на значении из запаса.

  Тесты проверены поломками на копии кода — каждая ловится своим тестом:
  - `bisect_left`;
  - предел только на промахе;
  - обратный порядок полей;
  - пачка по 5 клиентов;
  - потерянные заметки.
- **Истории всех 1000 клиентов** (хеш событий со значениями и порядком ключей, календаря, анкеты,

- **Python на значение.** `encode_event` — ~0.85 мкс на значение (19.2 млн значений), сборка
  истории — ~4.6 мкс на событие (из них 1.5 мкс календарь).
  - Ещё вдвое на одном ядре — только векторным кодированием прямо из колонок Arrow (номера
    категорий и диапазонов — таблицами numpy). Это архитектурная переделка `encode_values` и
    контракта `ClientEvent`.
