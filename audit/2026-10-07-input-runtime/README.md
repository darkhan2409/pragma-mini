# Подготовка входа модели при обучении (2026-10-07)

Задача: сократить ожидание данных и работу CPU между `samples.parquet` и началом прямого прохода
PRAGMA, не меняя ни одного числа входа. Не меняются:
- маска и порядок и число розыгрышей;
- время событий и анкеты;
- порядок клиентов;
- границы micro-batch;
- тензоры модели.

Сама модель, её внимание, loss и оптимизатор не трогались.

**Итог** (train scratch, 1000 клиентов, 548 micro-batch; val 300 клиентов; RTX 3050 Laptop 4 ГиБ,
flash-attn, bf16):

|---|---|---|---|
| подготовка входа без модели (CPU, эпоха train) | 88.5–90.9 с | 21.6 с | **4.1×** |
| то же на micro-batch | 161.5 мс | 39.4 мс | |
| первая порция с одним процессом подготовки | 4.2 с | 2.0 с | |
| `pack` на micro-batch | 6.7 мс | 3.5 мс | 1.9× |
| эпоха целиком: train + val | 195.8 с | 175.0 с | **1.12×** |
| — train | 151.5 с | 143.5 с | |
| — ожидание данных в train | 11.9 с (7.9%) | 9.0 с (6.2%) | |
| — val | 37.4 с | 28.8 с | 1.3× |

- Обучение и раньше упиралось в GPU, а не во вход: один процесс подготовки успевал за шагом
  (~250 мс на micro-batch при ~160 мс подготовки). Поэтому эпоха ускорилась меньше, чем
  подготовка.
- Выигрыш эпохи — это:
  - старт: до первого шага;
  - val: там только прямой проход, и он упирался во вход;
  - CPU, освобождённый от подготовки.
- Вход модели **тот же побайтно** — клиенты, их маски и время, границы micro-batch, тензоры
  `pack` с раскладками.
- Val той же модели даёт **те же** loss, top-1, top-5, число целей и разбивку по механизму, ключу
  и длине истории.

Замеры воспроизводит `bench.py`. Он работает в раскладке data/ во временном каталоге `--root`;
настоящий data/ не трогается. Код «до» — снимок рабочего дерева перед правками, через
`PYTHONPATH`.

```bash
.venv/bin/python audit/2026-10-07-input-runtime/bench.py setup --root <scratch> --vocab <03_vocab> --train <05_dataset/train>
.venv/bin/python audit/2026-10-07-input-runtime/bench.py loader --root <scratch> [--workers N] [--ahead K] [--timers]
.venv/bin/python audit/2026-10-07-input-runtime/bench.py digest --root <scratch> --group train|val [--workers N]
.venv/bin/python audit/2026-10-07-input-runtime/bench.py pack --root <scratch> --limit 100 --digest
.venv/bin/python audit/2026-10-07-input-runtime/bench.py train --root <scratch> --label <имя> --steps 60|0 [--workers N] [--ahead K] [--device cpu]
.venv/bin/python audit/2026-10-07-input-runtime/bench.py validate --root <scratch> --checkpoint <checkpoint.pt> --label <имя>
```

**Окружение в scratch** (`setup`):
- train — набор из аудита dataset (1000 клиентов, побайтно равный выдаче кода до правок);
- val — 300 клиентов окна val той же цепочкой: генератор 1.0.1, seed val, препроцессинг,
  encode словарём train, набор;
- веса 06 и 07 — розыгрыш по seed конвейера, как `python -m src.embedding.run` и
  `src.mlm.init_backbone`;
- обучение — `train()` с `--out` в scratch: `--max-steps` для мини-прогонов, без него — полная
  эпоха с val.

## 1. Цепочка (до)

```
samples.parquet (группа строк, 32 клиента)
  → TemporalGroup.row_group: read_row_group → _with_time:
      to_pylist(event_time), на каждого клиента: datetime → replace(tz) → datetime64 → log_age
      → float32 → .tolist(); то же для анкеты; check/check_profile — циклом Python
      → pa.array(списки) → append_column
  → Source.batch: Table.to_pylist() — словарь на клиента, списки чисел Python
  → choose: values_of (разбор окон событий, Value на каждое значение),
            розыгрыш событий, ключей, значения (value_chance + blake2b на каждое из 18 млн
            значений), [UNK]; затем values_of второй раз (все события) для порчи контекста
  → apply: list(value_ids), labels/reason/taken по ширине строки, цикл по токенам
  → Client: np.asarray из списков
  → Prefetch (процесс DataLoader) → pickle → главный процесс
  → micro_batches → pack: concatenate → VarlenLayout.build ×3 (группы flash И корзины SDPA:
      матрицы index/mask и их копирование на GPU) → torch.as_tensor(..., device)
```

**Переходы между представлениями (до):**
- Arrow → Python:
  - `to_pylist` времени в `_with_time`;
  - `to_pylist` всей группы строк в `Source.batch`.
- Python → numpy:
  - время в `_utc_naive`;
  - `_ints` и `np.asarray` при сборке `Client`.
- numpy → Python: `.tolist()` времени, затем снова `pa.array`.
- numpy → torch → GPU: `pack`, `torch.as_tensor(..., device)` — синхронная копия из обычной
  памяти.
- Процесс → процесс: `Prefetch` отдаёт `list[Client]` через pickle.

## 3. Внесённые изменения

**R1. Время всей группы строк массивами** (`temporal/samples.py`, `temporal/position.py`).
- Колонка `list<timestamp>` → плоские целые микросекунды UTC и границы клиентов, без
  `datetime` на момент.
- Расстояние до точки отсчёта — целыми микросекундами.
- `log_age` считается **по свежему массиву каждого клиента**, как прежде. Поэтому float32 те
  же до бита, независимо от выравнивания и пути SIMD.
- Колонка позиций — `ListArray` из тех же границ.
- Проверки (`checks_hold`) векторно:
  - конечность;
  - неотрицательность;
  - невозрастание внутри клиента;
  - ноль у последнего при `last_event`;
  - у анкеты: ноль у недатированного, положительное у вехи.
- Что-то не сошлось — прежний обход по клиентам (`time_log` + `check`) называет ошибку.

**R2. Один разбор значений** (`masking/choose.py`).
- `_parse` разбирает окна всех событий разом, массивами (событие, ключ, начало, длина), в том
  же порядке, что прежний обход.
- Значения целей и значения вне целей для порчи контекста — части одного разбора: второго нет.
- Строку, которую массивами не разобрать, разбирает прежний обход — в прежнем порядке шагов,
  чтобы ошибка была та же.
- `values_of` (API, тесты) — тот же список `Value`.

**R3. Розыгрыши пачкой** (`generator/rng.py`, `KeyedRandom.randoms`).
- n чисел подряд — те же, что n вызовов `random()`:
  - тот же blake2b тех же байтов: состояние с поданным префиксом копируется, номер
    дописывается;
  - `uint64 → double` с тем же округлением, деление на 2⁶⁴ точное.
- Потоки, их ключи, число и порядок розыгрышей не менялись:
  - событие — каждое допустимое, даже без значений;
  - ключ — по возрастанию;
  - значение — каждое;
  - `[UNK]` — каждое выбранное;
  - порча — по вхождениям ключа.
- `random()` не менялся.

**R4. Вероятности value массивом** (`masking/weights.py`, `ValueWeights.probabilities`).
- Формула та же и в том же порядке: `((value_probability · scale) · key_weight) ·
  value_weight`, затем границы `min`/`max`.
- Значение из одного куска ищется в отсортированных кодах (ключ, токен), из нескольких — прежний
  `probability` по одному.
- Нечисловой вес идёт по одному: у `min`/`max` Python и numpy NaN ведёт себя по-разному.

**R5. Выбор массивами, объекты по требованию** (`masking/choose.py`).
- `Selection` хранит массивы:
  - допустимые значения;
  - номера выбранных;
  - код причины;
  - `[UNK]`;
  - испорченный контекст.
- `values`, `choices`, `corrupted` — те же объекты `Value` и `Choice`, но строятся при обращении:
  их читают отчёт маскирования и тесты. Источник обучения их не строит.

**R6. Маска массивами** (`masking/apply.py`, `apply_selection`).
- `value_ids` и `labels` — int64, как и раньше после `_ints`.
- `reason` — список строк, собранный одним `_REASON_NAMES[codes].tolist()`. Это те же объекты
  строк, что `Choice.reason`, поэтому разбивка val и pickle не меняются.
- Выход за строку или наложение — прежний `apply` по спискам называет ошибку.
- `apply(…, choices, …, corrupted)` для API и тестов — без изменений.

**R7. Строки группы колонками** (`mlm/inputs.py`, `_rows`).
- Колонка-список чисел → срезы массива numpy по её границам, без числа Python на токен.
- Массив колонки — своя записываемая копия, как и прежние массивы `Client`, а не буфер Arrow
  только для чтения. Первый прогон полного `pytest` поймал это предупреждением torch; тест
  закрепляет записываемость.
- `event_time` остаётся списком `datetime`: его читают оценка на T и диагностика.
- Колонки с пустыми местами идут через `to_pylist`, как раньше.

**R8. Корзины раскладки — по требованию** (`mlm/varlen.py`).
- Путь flash берёт только группы и `cu_seqlens`.
- Матрицы корзин (`index`, `mask`) и их копирование на устройство строятся при первом
  обращении к `layout.buckets`, то есть только на пути корзин (SDPA, `auto` без autocast).
- `bucket_of` и `row_of` — по-прежнему numpy, считаются дёшево: от них `target_bucket` и
  `target_row` в `pack`.
- Сами корзины не меняются: тест сверяет их с прежней сборкой.

## 5. Ответы по пунктам

1. **Время подготовки входа до:** 88.5–90.9 с на эпоху train (1000 клиентов) без модели,
   161.5 мс на micro-batch.
2. **Ожидание данных до:** 3.4% шага в установившемся режиме, 7.9% train-времени эпохи вместе со
   стартом.
3. **Загрузка GPU до:** 73.6% за эпоху с val, 86.8% на 60 шагах train.
4. **Главные узкие места:**
   - маска — 78%: два разбора значений, 18 млн `value_chance` и розыгрышей по одному;
   - время — 11%;
   - `to_pylist` — 8%.

    - 22.4 МиБ на группу строк из 32 клиентов — и до, и после;
    - pickle в процессе подготовки — 0.08–0.09 с на группу;

    Изменений не потребовала.

## 6. Не принято и почему

- **Persistent workers.** Источник эпохи несёт свой seed маски (`for_epoch`), и `Prefetch`
  создаётся заново на эпоху. Процесс, переживший эпоху, рисковал бы маской прошлой эпохи, а
  старт процесса теперь ~2 с на эпоху.
- **Закреплённая память и `non_blocking`.** Копирование на GPU — ~1 мс на micro-batch, шаг
  ~247 мс.
- **Кэш длин `Source.sizes()`** — один вызов за прогон.
- **Отказ от `reason` в train.** Выигрыш ~0.3 с на эпоху, а тип поля `Client` пришлось бы менять
  у val и диагностики.
- **Отказ от `event_time` в train** — то же: ~1.5 с на эпоху в процессе подготовки,
  параллельно GPU.
- **`int32` вместо `int64` в `Client`.** Контракт `pack` и эмбеддингов — `int64`; перевод
  делается один раз при сборке `Client`.
- **`micro_batches`** — доли процента, не трогался.
- **Модель, flash-группировка (`FLASH_PAD`, `FLASH_ROWS`), dropout** — вне задачи.
- **Переключатели `restricted_softmax`, `recency_embedding`, `hide_event_keys`,
  `shuffle_row_groups`** из постановки в коде больше нет: удалены раньше с их кодом.
  `Source.order` по-прежнему задаёт порядок групп строк, и тест проверяет его при нескольких
  процессах.

## 7. Что осталось

- **Обучение упирается в GPU:** прямой и обратный проход ~247 мс на micro-batch при подготовке
  ~39 мс. Дальше ускорять эпоху может только модель — это следующий отдельный этап.
- **В подготовке:**
  - розыгрыши blake2b — ~12 с на эпоху, 18–20 млн чисел; меньше их не станет без смены
    генератора случайности, а это смена маски;
  - `event_time` как `datetime` — ~3 с.
- **Val** упирается во вход сильнее, чем train: 18–29 с на 300 клиентов, из них ~30% —
  прямой проход.
