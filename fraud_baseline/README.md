# fraud_baseline

Обычная табличная модель мошенничества на уровне операции, на CatBoost. Это точка отсчёта для
честного сравнения:

```
обычные признаки → CatBoost                     (этот проект)
PRAGMA history → client embedding → Fraud Head  (не оценивается)
```

Проект изолирован от PRAGMA и от `churn_baseline`:
- код PRAGMA не используется;
- признаки строятся только из выгрузки генератора `data/01_raw/<group>/`, её он только читает;
- все датасеты, модели и отчёты лежат внутри `fraud_baseline/`;
- своё окружение `.venv` и свои тесты.

Код генератора (`src.generator`) импортирует один файл — `fraud/replay.py`, только ради target
(см. ниже).

PRAGMA фрод на уровне операции не оценивает: вектор нужен на момент каждой операции строго до неё,
а история в модели двунаправленная (README PRAGMA, раздел 13). Сравнивать этот бейзлайн пока не с
чем.

## Разбиение

- Своего разбиения нет: группы — ровно группы выгрузки PRAGMA.
- Строка группы — операция клиента этой группы: операции train-клиентов идут в train, val-клиентов
  — в val, test-клиентов — в test.
- Обучение проверяет, что клиенты групп не пересекаются.

| группа | строки | роль |
|---|---|---|
| train | все позитивы и 1 из 10 отрицательных, вес 10 | обучение |
| val | все | ранняя остановка и выбор порога F1 |
| test | все | одна финальная оценка при пороге с val |

## Где fraud target

**Явной метки в выгрузке нет.**
- В payload нет поля «мошенничество».
- В `truth/` выгрузки (с генератора V1) — только отношения с банком (`states`, `transitions`);
  меток мошенничества там нет.
- Состояние эпизода живёт только в памяти генератора (`src/generator/life/fraud.py`,
  `engine_products.py`).
- На ленте мошенническая операция — это обычная `purchase` или `transfer_out`. Target существует
  только для этих двух типов.

Как генератор делает мошенничество:
- **Эпизоды на клиента.** Их виды:
  - card_compromise, unusual_purchase — покупки;
  - suspicious_transfer, social_engineering, account_takeover — переводы; у account_takeover
    перед ударом идёт вход с нового устройства;
  - false_positive — **легитимная** подозрительная покупка самого клиента.
- **Шаги эпизода:** probe (мелкие онлайн-пробы) и strike (крупное списание).
- **После шага, если эпизод обнаружен:** алерт антифрода через 1–239 минут, решение, блокировка,
  обращение, chargeback, перевыпуск.

**Метка берётся повторным прогоном генератора** (`python -m fraud.replay <group>`):
1. **Настройки группы.** Группа прогоняется тем же генератором с теми же seed, окном, последним
   приходом в банк (`registration_end`) и параметрами. Версия генератора, `generation_config_sha256`,
   seed, `world_seed`, число клиентов и `registration_end` сверяются с manifest выгрузки.
2. **Перехват, без правки файлов генератора.** В процессах подменяются
   `engine_products._fraud_purchase`, `_fraud_transfer` и `engine_month._row`. Каждая строка,
   которую выдал шаг мошенничества, помечается видом эпизода и шага.
3. **Сверка всей ленты.** Хеш ленты **каждого** клиента в повторе обязан совпасть с хешем его строк
   в RAW. Каждая помеченная строка обязана найти ровно одну строку RAW с теми же `client_id`,
   строкой времени, `source` и `payload`. Иначе меток нет.
4. **Независимая сверка.** Помеченные строки сравниваются со следами сериализации мошеннического
   пути в RAW: у покупки `card_id` идёт сразу за `channel`, у перевода нет `transfer_id` при
   заполненном `account_id`. Эти следы используются только для проверки и в признаки не идут.

```
fraud = 1   шаг мошенничества (probe или strike) любого вида, кроме false_positive
fraud = 0   любая другая операция, включая шаг false_positive — трудный отрицательный пример
```

Сверка повтора пишется в `reports/replay_check.json`: по группе — клиенты, совпали ли их ленты с
RAW, сколько строк помечено, fraud=1, false_positive, probe / strike и время повтора, и сошлись ли
помеченные строки со следами в RAW один к одному. Строки выгрузки считаются с 2024-01-01, в
датасет идут строки с 2024-04-01.

## Строки датасета

- Строки — `purchase` с `reason=purchase` и `transfer_out` клиента группы, одобренные и
  отклонённые.
  - Подписки и страховые списания — автоматические, мошенник их не делает. Остальные типы target не
    имеют.
- Время строки — не раньше 2024-04-01 (местное): так окна истории до 90 дней наблюдаются целиком.
  Выгрузка начинается 2024-01-01.
- В train берутся все помеченные строки (fraud и false_positive) и детерминированная 1 из 10
  прочих строк, по хешу `raw_row`, с весом 10. Иначе 5,4 млн строк не помещаются в память.
  val и test — полностью.

## Момент решения и защита от утечки

Момент решения — время операции. Признаки (`fraud/features.py`, полный список в
`reports/features.md`):

- **Сама операция — то, что известно при авторизации:**
  - тип;
  - канал;
  - онлайн;
  - сумма;
  - валюта;
  - страна, MCC, категория и название мерчанта;
  - город мерчанта против города клиента;
  - перевод между своими счетами;
  - час, день недели, число.
- **История клиента строго раньше операции.** Окно «за w» — `t_i − w ≤ t < t_i`. Событие в тот же
  момент в историю не входит.
  - операции за 1 ч / 1 / 7 / 30 / 90 дней: число и суммы;
  - прошлые отказы;
  - онлайн и зарубежные операции;
  - сумма относительно средней и наибольшей прошлой, z-оценка;
  - новизна: MCC, мерчант, страна, получатель перевода;
  - входы в приложение, неудачные входы, входы с нового устройства;
  - доходы;
  - остаток повседневного счёта до операции и сумма / остаток;
  - прошлые алерты и блокировки антифрода.
- **Анкета на момент операции:** поля откатываются по `profile_change`, возраст считается на дату
  операции, давность вех.

**Исключено:**
- исход самой операции: `status`, `decline_reason`, `balance_after`;
- всё, что после неё: алерты, решения, блокировки, обращения, chargeback, перевыпуск;
- следы генератора:
  - есть ли `transfer_id`, `card_id`, `account_id`, `session_id`;
  - порядок ключей payload;
  - секунды и минуты времени: шаги мошенника стоят на целых секундах от целого часа;
  - «круглость» суммы: суммы мошенника округлены до 100;
- идентификаторы: получатель перевода используется только как новизна.
- Остаток до операции берётся по повседневным операциям клиента, а не по `account_id` самой строки:
  у отказов генератора `account_id` бывает пустым, и его присутствие выдавало бы шаг мошенника.

Тесты (`tests/test_features.py`):
- исход самой операции, будущие события и события того же момента не меняют ни одного признака;
- строка со следами генератора — без `transfer_id`, со счётом, на 17 мин 43 с позже — отличается
  от обычной только давностью прошлых событий;
- в именах признаков нет запрещённых полей.

## Модель и оценка

- CatBoost: `Logloss` с весами строк, `eval_metric=PRAUC`, до 3000 деревьев, `learning_rate` 0.05,
  глубина 6.
- Ранняя остановка по val (300 итераций), `random_seed=42`, 8 потоков.
- Порог — наибольший F1 на val. Test оценивается один раз при этом пороге.
- Метрики на val и test целиком и отдельно по типу операции. Для строк false_positive — сколько из
  них модель подняла выше порога.

## Для сравнения с PRAGMA + Fraud Head

- `reports/eval_rows.parquet` — точный список объектов оценки:
  `group, client_id, event_time, raw_row, type, fraud, score` для val и test.
  - `raw_row` — номер строки в `data/01_raw/<group>/events.parquet`: пара `(client_id, event_time)`
    у операций одного момента может повторяться.
  - PRAGMA + Head оценивается **на этих же строках**.
- `score` — прогноз baseline для парного сравнения.
- `reports/train_rows.parquet` — строки обучения с весами.
- `reports/metrics.json` хранит sha256 обоих файлов и `events_sha256` выгрузки каждой группы.
- Оба файла в git не входят, как `data/` и `models/`. Их пишет `fraud.train`, а
  совпадение с исходными проверяется по sha256 из `metrics.json`.
- **Эмбеддинг клиента для строки должен считаться по истории строго раньше `event_time` строки.**
  Эмбеддинг на конечный cutoff группы видел бы и саму операцию, и алерты после неё.

## Файлы

```
fraud/
  config.py    пути, группы, начало строк, прореживание
  raw.py       чтение выгрузки блоками целых клиентов
  replay.py    повтор генератора → помеченные строки
  labels.py    помеченные строки → номера строк RAW, сверка лент
  features.py  признаки на момент операции
  build.py     строки группы
  train.py     обучение и оценка
tests/           синтетические выгрузки во временном каталоге; data/ не читают
data/<group>/    labels.parquet, features.parquet, meta.json
models/          catboost.cbm
reports/         features.md, replay_check.json, target_distribution.json, metrics.json,
                 feature_importance.csv, eval_rows.parquet, train_rows.parquet
```

## Воспроизведение

```bash
cd fraud_baseline
python3.14 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python -m pytest
for g in val test train; do .venv/bin/python -m fraud.replay $g --workers 6; done
for g in val test train; do .venv/bin/python -m fraud.build $g; done
.venv/bin/python -m fraud.train
```
