# mini-PRAGMA v2

Синтетический генератор истории банковских клиентов, повторяющий **структуру и типичные дефекты реальных данных HCB**. Цель: написать preprocessing и модель на синтетике и переключить их на реальные данные без смены архитектуры.

```
Persona (скрытая)
   ↓
Mixture assignment          сценарии активности и кредитного стресса
   ↓
Behavior trajectory         кусочно-линейные кривые по дням
   ↓
7 наблюдаемых потоков       + дефекты наблюдения
   ↓
Единая лента событий        client_id | ts | event_type | payload
```

## Общий контракт события

```
client_id | ts | event_type | payload
```

Плюс `seq`: порядковый номер в ленте клиента. Он нужен только для детерминированного tie-break при совпадающих `ts` и информации не несёт.

## Семь потоков

| Поток | Строка | Поля |
|---|---|---|
| `profile` | клиент × месяц | 20 полей HCB: age, gender, family_status, children, education, region, housing_type, pensioner, income_type, declared_income, industry, salary_day, relationship_months, contracts_count, active_contracts, holds_credit_card, holds_debit_card, holds_deposit, credit_limit, credit_utilization |
| `transactions` | покупка или зачисление | amount, direction, mcc, merchant_city, merchant_country, is_online, is_subscription |
| `product_events` | открытие договора | product_type, amount_or_limit, term, product_subtype, timestamp_quality |
| `communications` | отправка банка | channel, template, day_of_week, hour, delivered |
| `app_screens` | экран приложения | session_id, firebase_screen, product, funnel_stage, reject_reason |
| `app_operations` | операция | domain, operation, status |
| `banners` | показ или клик | slot, offer, action = `shown` \| `clicked` |

Служебные таблицы: `source_coverage` (доступность источника и появление в нём клиента), `timeline` (единая лента, payload в JSON), `labels` (`product_open_90d`).

**Валюты в транзакциях нет** сознательно: V1 работает в одной валюте.
**Двух флагов у баннера нет** сознательно: одна строка на действие.

## Имитируемые дефекты

| Дефект | Как проявляется |
|---|---|
| `availability_start` | Источники подключены в разные даты: реестр договоров с 2018-01, транзакции с начала истории, баннеры с 2024-08, экраны с 2024-12-16, коммуникации с 2024-12-22 |
| `client_first_seen_in_source` | Приложение установлено не сразу и не всеми (~16% не пользуются), согласие на связь дано позже (~8% без согласия) |
| `timestamp_quality` | `exact` у карт, `date_only` у кредитов, депозитов и страховок: время потеряно, событие лежит в полночь |
| Пропуски профиля | Структурные (нет отрасли у пенсионера, нет лимита без карты), сегментные (у части клиентов блок пуст всегда), помесячные (источник блока отваливается на месяц) |
| Редкие категории | Длинный хвост MCC, шаблонов, экранов, операций, городов, стран; GA4 отдаёт `(not set)` |
| Совпадающие `ts` | Баннер делит момент с экраном, договоры без времени падают в полночь: около 15% соседних событий ленты имеют равный `ts` |
| Детерминированный tie-break | Порядок при равном `ts` задаётся приоритетом типа события, затем позицией в своём потоке; результат фиксируется в `seq` |
| Разные даты старта потоков | Реестр договоров содержит контракты старше окна наблюдения |

Скрытые поля (`activity`, `credit_need`, `risk`, `push_reachable`, кампания, факт клика, сценарий траектории) в RAW не пишутся никогда. Это проверяется тестом.

## Горизонт

| Граница | Значение |
|---|---|
| `HISTORY_START` | 2024-06-01 |
| `FEATURE_END` | 2026-06-01, момент среза «как есть» |
| `LABEL_END` | 2026-08-30, окно метки 90 дней |

В RAW попадают только события строго раньше `FEATURE_END`. Профиль на cutoff это последний месячный снимок раньше среза.

## Бюджеты последовательности

Два **разных** параметра, они лежат в `config.py` и в манифесте:

- `MAX_TOKENS_PER_EVENT = 12` — сколько токенов занимает одно событие (`event_type` + поля payload) в Event Encoder.
- `MAX_EVENTS_PER_HISTORY = 4096` — сколько событий History Encoder читает из ленты клиента.

Генератор их к RAW не применяет: история хранится целиком. Значения передаются в preprocessing, чтобы лимиты совпадали на синтетике и на реальных данных.

## Детерминизм

Случайность события выводится хэшем его идентичности `(namespace, client_id, day, index_in_day, component)`. Следствия:

- один seed даёт побайтово одинаковый датасет при любом числе воркеров;
- изменение числа событий в один день не меняет другие дни;
- продление горизонта не меняет префикс истории;
- смена владения меняет выбор кампании, но не время отправки.

## Preprocessing

RAW → проверенные месячные as-of примеры → сплиты → bucketization → статистические artifacts.
Токенов, словаря и маскирования здесь нет: это отдельный слой, см. «Tokenizer».

```bash
venv\Scripts\python -m src.preprocessing.run --raw data/raw/smoke --name smoke
```

### Пример

Пример это пара `(client_id, cutoff)`, где `cutoff` это начало следующего месяца: срез за май 2026 имеет `cutoff = 2026-06-01`. В историю входят события строго раньше `cutoff`, профиль это последний снимок строго раньше `cutoff`.

Кандидат становится примером, если от `max(HISTORY_START, first_seen[transactions])` прошло не меньше 90 дней, есть хотя бы одно событие и есть снимок профиля. Иначе в `cutoff_index.parquet` записывается причина: `no_transactions_coverage`, `insufficient_observation`, `no_events`, `no_profile_snapshot` или `unused_combination`.

Используются только полные месяцы до границы RAW из манифеста: 24 месяца, `cutoff` от 2024-07-01 до 2026-06-01. Правило 90 дней отсекает первые два, поэтому реально примеры начинаются с `cutoff = 2024-09-01`.

### Сплиты

Группа клиента это SHA-256 от `"{seed}:{client_id}"`: 80% train, 10% val, 10% test. Python `hash()` не используется, добавление клиентов не переселяет существующих. Последний полный месяц это test, предпоследний это val, остальные это train_period.

| Датасет | Клиенты | Месяцы |
|---|---|---|
| `train` | train | train_period |
| `val_client` | val | train_period |
| `test_client` | test | train_period |
| `val_time` | train | val month |
| `test_time` | train | test month |

Остальные сочетания помечаются `unused_combination`. Пересечение клиентов между `train` и временными выборками ожидаемо: это разные месяцы одних и тех же людей.

### Хранение

События хранятся один раз на группу клиентов, примеры это ссылки на префикс истории.

```
data/processed/<name>/
  cutoff_index.parquet                все кандидаты со статусом и причиной
  clients/{train,val,test}_clients/
      events.parquet                  client_id, seq, ts, event_type +
                                      <event_type>__<field> + __bucket для numeric
      profile.parquet                 20 полей профиля + __bucket
  {train,val_client,test_client,val_time,test_time}/examples.parquet
data/artifacts/<name>/
  bucket_edges.json  field_stats.json  unigram_baselines.json
  split_manifest.json  validation_report.json  validation_report.md
  value_counts/<namespace>__<field>.parquet
```

**Одна строка `events.parquet` это одно событие.** Заполнены только колонки своего типа, остальные пусты. `payload` разобран, JSON больше не нужен.

**Потребитель обязан брать префикс `seq < seq_end`.** События train-клиентов намеренно содержат val- и test-месяцы: они нужны примерам `val_time` и `test_time`. Защита от утечки лежит в ссылке, а не в файле.

### Поля

Каждое поле описано парой `(namespace, field)`: тип (`categorical`, `numeric`, `boolean`, `metadata`), роль и флаг `predictable`. Полный профиль это отдельный namespace `profile` и контекст, а не цель. `client_id`, `seq`, `session_id` и служебные метки времени хранятся как metadata: их не bucketize и не предсказывают. MCC это категория.

`profile` и `profile_snapshot` это разные namespace. Снимки первых двух месяцев попадают в `profile_snapshot` как события ленты, но в `profile` не попадают никогда: правило 90 дней не даёт им стать as-of ни для одного примера.

### Bucketization

Только numeric, только непустые train-значения, по умолчанию 16 квантильных корзин. Границы берутся методом `inverted_cdf`, то есть это наблюдённые значения; одинаковые схлопываются, граница, равная максимуму, отбрасывается. Тогда **ни одна корзина не остаётся пустой на train**.

Правило включения `(e[i-1], e[i]]`: значение на границе уходит в нижнюю корзину, значения вне train-диапазона попадают в крайние. Пропуск остаётся пропуском: `bucket = null`. Константа даёт одну корзину, полностью пустое поле получает `no_fit_data` и колонку из `null`. На evaluation ничего не переобучается.

### Статистики

Считаются только на `train`. Каждое событие и каждый выбранный снимок учитываются один раз, сколько бы cutoff-примеров их ни включало: fit-набор это префикс ленты до последнего валидного train-cutoff клиента. Исходная таблица и её копия в ленте не считаются дважды, потому что источник один — разобранная лента.

Для каждого содержательного поля: `n_total`, `n_missing`, `n_valid`, `missing_rate`, cardinality, `top1_frequency`, энтропия в битах, `rare_share` (доля непустых со значениями реже 20 раз) и полное распределение. У numeric распределение по корзинам лежит в JSON, полное распределение значений в `value_counts/`. Флаги `high_missing`, `near_constant`, `low_entropy` только сообщаются: ничего не удаляется автоматически. Неравномерность квантильных корзин отражается в отчёте и ошибкой не считается.

### Воспроизводимость

Два запуска на одних RAW, config и seed дают побайтово одинаковые файлы. В artifacts не попадают ни пути, ни время запуска: JSON пишется с `sort_keys` и `
`, parquet из pyarrow с явной схемой и без метаданных pandas.

## Tokenizer

Structured events → словарь → token IDs → контракт входа для модели. Энкодеров, головы предсказания и обучения здесь нет.

```bash
venv\Scripts\python -m src.tokenizer.run --name smoke
```

### Пространство ID

Единое: сначала special-токены, затем ключи полей, затем значения.

| Диапазон | Что |
|---|---|
| 0–5 | `[PAD]`, `[UNK]`, `[MASK]`, `[EVT]`, `[USR]`, `[MISSING]` |
| 6 … | ключи `namespace__field` в порядке реестра preprocessing |
| … | значения, сгруппированные по ключу |

Значение принадлежит полю: `true` у `transaction__is_online` и `true` у `communication__delivered` это разные ID. `profile__age` и `profile_snapshot__declared_income` — разные ключи, полный профиль это отдельное пространство.

Порядок назначения не зависит от частот: значения внутри ключа идут по возрастанию самого значения, numeric — по номеру корзины. Поэтому ID одного ключа образуют непрерывный диапазон, а добавление клиентов не переставляет уже выданные ID.

Словарь учится **только на train** и на том же наборе записей, что и статистики preprocessing: `fit_scope` переиспользуется как есть. Повторение записи в десятках cutoff-примеров не увеличивает её частоту. На evaluation словарь заморожен: неизвестный ключ или значение это `[UNK]`, явный пропуск это `[MISSING]`, новое значение словарь не расширяет.

### Событие

```
позиция 0   [EVT]                      одинаковый ID в key_ids и в value_ids
позиция 1   timeline__event_type
позиция 2+  поля payload в порядке реестра
```

Профиль кодируется теми же правилами, но отдельно и начинается с `[USR]`: 21 токен. Позиция считается **внутри записи** и сбрасывается на каждом событии; к позиции события в истории она отношения не имеет. Повторяющиеся ключи поддерживаются списком пар и не схлопываются. Metadata (`client_id`, `ts`, `seq`, `session_id`, `snapshot_month`) в поток не попадает.

Ширина события: transaction 9, profile_snapshot 11, product_event 7, communication 7, app_screen 6, banner 5, app_operation 5. Лимит события считается включая `[EVT]`.

`max_tokens_per_event` и `max_events_per_history` — два независимых параметра, берутся из манифеста RAW. Они **ничего не режут**: превышения только считаются и попадают в статистику.

### Хранение

```
data/tokenized/<name>/
  tokenized_manifest.json             версия формата и sha256 tokenizer_config
  clients/{train,val,test}_clients/
      events.parquet                  client_id, seq, ts, event_type, n_tokens,
                                      key_ids, value_ids, positions
      profile.parquet                 client_id, ts, snapshot_month + те же три массива
  {train,val_client,test_client,val_time,test_time}/examples.parquet
data/artifacts/<name>/tokenizer/
  special_tokens.json  key_vocab.json  value_vocab.json  field_value_ids.json
  tokenizer_config.json  tokenizer_stats.json  golden_examples.json
```

Записи хранятся один раз на группу клиентов, пример это ссылка `(client_id, cutoff, seq_end, snapshot_ts)`, как в preprocessing. События отсортированы по `(ts, seq)`, равные timestamps допустимы. Время не превращается в словарные категории: `ts` и `seq` лежат рядом с токенами для будущего временного кодирования.

`tokenizer_config.json` хранит версию формата, special ID, правила порядка и sha256 тех artifacts preprocessing, на которых обучался словарь. При загрузке хэши пересчитываются, несовпадение это ошибка, а не предупреждение.

### Runtime masking

Сохранённые датасеты содержат исходные ID: `[MASK]` в них не встречается. Masker работает с копией и своим seed, входные массивы не меняются.

Маскируются только известные непустые значения полей с `predictable=true`. Специальные токены, `[UNK]`, `[MISSING]`, metadata и весь профиль не маскируются никогда. Заменяется только `value_id`; ключи, позиции и время остаются на месте, иначе модель не знает, что у неё спрашивают.

| Режим | Что выбирается |
|---|---|
| `token` | каждая доступная позиция независимо |
| `key` | поле внутри примера, маскируются все его доступные значения |
| `event` | событие, маскируются все его доступные значения |
| `field_balanced` | бюджет масок распределяется между полями поровну |

Режимы не смешиваются. `field_balanced`: бюджет это доля доступных позиций batch, затем равновероятно выбирается поле среди неисчерпанных, затем одна его позиция, без повторов, пока бюджет не исчерпан. Редкое поле получает столько же масок, сколько частое, а не пропорционально частоте.

Target это исходный `value_id`, вне масок `-100`.

### Field-restricted prediction

`field_value_ids.json` даёт для каждого поля отсортированный список допустимых value ID: у numeric это все корзины train-artifact, у остальных полей значения, встреченные на train. Special-токены в кандидаты не входят, неизвестные и пропущенные значения целями не бывают. Targets хранятся глобальными ID, `CandidateIndex` переводит их в локальный индекс поля и обратно. Softmax по всему словарю не предполагается; сама голова предсказания пока не создаётся.


## Model: Event и Profile Encoder

Первый модельный слой: одно событие и один профиль превращаются в вектор `d_model`. History Encoder, MLM head, loss и обучение сюда не входят.

```bash
venv\Scripts\python -m src.model.smoke --name smoke --device cuda
```

### Embeddings

Одна таблица `E` на всё пространство ID tokenizer, ключи и значения живут в нём вместе:

```
обычное поле     x = E(key_id) + E(value_id) + P(position)
special-позиция  x = E(special_id) + P(position)
```

Special-позиция узнаётся по `key_id == value_id`. Это надёжно, потому что диапазоны ключей и значений не пересекаются: равенство возможно только у `[EVT]`, `[USR]`, неизвестного ключа и padding. А `[MISSING]` и `[UNK]` **на месте значения** остаются обычными видимыми токенами: ключ у них настоящий, поэтому складываются оба слагаемых.

`E` и `P` общие для обоих энкодеров, Transformer-блоки полностью независимые. Размер `E` берётся из проверенного `tokenizer_config.json`, ID не перенумеровываются, строка 0 это `[PAD]`.

### Кодировщики

Оба по два слоя `TransformerEncoderLayer`, `batch_first`, `norm_first`, GELU, двусторонний attention без causal mask, отдельный LayerNorm после стека. Блоки собираются списком отдельно созданных слоёв, а не `nn.TransformerEncoder`: тот копирует один слой, и все блоки стартовали бы с одинаковых весов.

Вход Event Encoder это одно событие целиком, `event_type` уже стоит тройкой на позиции 1 и повторно не добавляется. Выход это скрытое состояние `[EVT]` после финальной нормы. У профиля то же самое с `[USR]`. Mean pooling не используется. Разные события не видят друг друга: каждое это отдельная строка batch.

### Padding и лимиты

Padded позиция несёт `[PAD]` в обоих массивах и позицию 0. Она зануляется до слоёв, исключается из attention маской и зануляется ещё раз после финальной нормы: LayerNorm нулевой строки даёт не ноль, а bias около 2.5. Из attention исключается только `[PAD]`.

Замерено, что обе меры работают: без маски вектор события меняется на 0.37 от присутствия соседа, с маской расхождение 5e-7.

Лимиты tokenizer здесь не применяются. Единственная граница это размер таблицы позиций, и выход за неё даёт ошибку, а не обрезку. Профиль в 21 токен длиннее лимита события в 12, и это нормально: лимит события к профилю не относится.

События считаются microbatch'ами, порядок выходных векторов сохраняется. Внутри куска ширина обрезается до самой длинной записи куска, что допустимо, потому что результат от количества padding не зависит.

### Замер

`smoke.py` берёт по одному примеру на клиента из всех пяти датасетов, по умолчанию с последним доступным cutoff, и не обрезает истории. Загрузка данных измеряется отдельно от forward, на CUDA устройство синхронизируется до и после каждого замера. Если уникальных клиентов меньше ста, выводится предупреждение, а не дублирование.


## History Encoder и backbone

Векторы событий и профиля собираются в последовательность среза и превращаются в вектор клиента.

```bash
venv\Scripts\python -m src.model.history_smoke --name dev --device cuda --max-clients 100
```

### Последовательность

```
позиция 0     выход Profile Encoder
позиция 1..N  выход Event Encoder + время
```

Первая позиция это **уже посчитанный** вектор профиля, а не токен `[USR]` из таблицы. Пример это пара клиент и cutoff, поэтому cutoff и дата снимка приходят отдельной metadata: в `TokenBatch` их нет.

Перед сборкой проверяется, что события каждого примера идут по паре времени и порядкового номера, что все они строго раньше cutoff и что снимок профиля тоже раньше cutoff. Равные timestamps законны, их различает порядковый номер.

### Обрезка истории

`max_events_per_history` применяется **до** Event Encoder: кодировать то, что будет выброшено, бессмысленно. Политика `recent` оставляет последние N событий, короткую историю сохраняет целиком, профиль не трогает, `[USR]` в лимит не входит.

Обрезка строит новый корректный `TokenBatch`, поэтому runtime-masker работает на нём без изменений и маски не тратятся на выброшенные события. Рядом сохраняется соответствие оставшихся событий и токенов исходному batch: оно понадобится MLM head.

### Время и порядок

У каждого события два признака в часах:

```
gap = ts события − ts предыдущего события
age = cutoff − ts события
```

Gap сам порядок не задаёт: у равных timestamps он ноль. Порядок несёт отдельное синусоидальное кодирование позиции в истории, а age отличает недавнюю активность от давно законченной. Оба признака сжимаются `f(t) = 8·log1p(t / 8)` и проходят через `Linear(2, d_model)` без смещения, поэтому у профиля и padding временное слагаемое ровно нулевое.

Gap считается по полной истории до обрезки: у первого оставшегося события он настоящий, а не ноль. Единицы берутся честно, сначала вычитаются метки времени и только потом длительность делится на час.

### Память

Слои History Encoder несут пустой forward-хук. Причина не в логике, а в памяти: быстрый путь `TransformerEncoderLayer` материализует полную матрицу внимания, и на истории в 3637 событий это 3265 МБ вместо 51 МБ. Наличие хука отключает быстрый путь ровно у этих слоёв, не трогая глобальный флаг и не мешая Event и Profile Encoder, где записи короткие и быстрый путь выгоден.

### Выход

```
client_embedding  [batch, d_model]        позиция 0 после финальной нормы
contextualized    [batch, 1 + N, d_model] вся последовательность
padding_mask      [batch, 1 + N]          True это padding
event_embeddings  [n_kept, d_model]       без padding, в порядке оставшихся событий
```

Mean pooling не используется. Подготовка данных отделена от прямого прохода: первая это NumPy, второй это torch с сохранённым autograd, без отсоединения градиента и без кэша между вызовами. Повторное вхождение события кодируется заново, потому что маска и dropout у него могут быть другими.

### Замеры

На 100 клиентах dev, RTX 3050, вектор 64, по два слоя в каждом энкодере:

| Лимит | Обрезано | Использовано p50 | max | Событий | Forward, с | Пик GPU, МБ |
|---|---|---|---|---|---|---|
| 512 | 0.97 | 512 | 512 | 51 097 | 0.55 | 58 |
| 1024 | 0.80 | 1024 | 1024 | 96 433 | 0.83 | 81 |
| 2048 | 0.44 | 1965 | 2048 | 164 762 | 1.59 | 119 |
| 4096 | 0.00 | 1965 | 3210 | 181 937 | 1.92 | 130 |

Исходные длины: медиана 1965, максимум 3210. При лимите 4096 данные короче лимита, поэтому вместимость 4096 событий этим запуском не проверена, и отчёт это отмечает.


## MLM head, loss и обучение

Модель учится восстанавливать замаскированные значения полей и сравнивается с unigram-baseline preprocessing на тех же позициях.

```bash
venv\Scripts\python -m src.model.train overfit   --name dev --device cuda --steps 300
venv\Scripts\python -m src.model.train benchmark --name dev --device cuda
venv\Scripts\python -m src.model.train run       --name dev --device cuda --max-steps 2000
```

Порядок обязателен и зашит в команды. Каждый режим строит свою модель, каталог запуска не перезаписывается без `--force`.

### Представление замаскированной позиции

```
h_local  скрытое состояние позиции после Event Encoder
h_event  вектор события после History Encoder
h_usr    вектор клиента после History Encoder

concat → Linear(3d, d) → GELU → LayerNorm
```

Все три берутся из **одного** прохода: `Backbone.forward` принимает `gather` из пар «строка события, позиция токена» и возвращает скрытые состояния только запрошенных позиций. Повторный запуск Event Encoder ради локальных состояний считал бы другое: маска и dropout у него свои. Номера строк обязаны не убывать, иначе разбиение на microbatch переставило бы выходы.

Цели живут отдельно от входа: `ModelInputs` о них не знает. Для каждой позиции хранится пример, событие после обрезки, позиция токена внутри события, ключ поля, исходный global `value_id` и его локальный индекс, а рядом соответствие исходному batch до обрезки.

### Field-restricted prediction

У каждого predictable-поля хотя бы с двумя кандидатами своя `Linear(d, n_candidates)`. Softmax по всему словарю не считается: у `mcc` 70 кандидатов, у `direction` два, и общая голова тратила бы почти всю массу на заведомо невозможные значения.

Все головы создаются до optimizer. Параметр, появившийся внутри forward, не попал бы ни в optimizer, ни в checkpoint.

Позиции группируются по ключу, logits содержат только кандидатов своего поля. Перевод global → local это не одно вычитание смещения: проверяется, что поле predictable, что значение не special и что оно лежит в диапазоне именно этого поля. Поле с одним кандидатом помечается `degenerate`, его позиции отбрасываются до сбора представлений и в loss и агрегаты не входят.

### Loss

```
field_loss     = mean(CE по позициям поля)
field_balanced = mean(field_loss по полям batch)     основной
token_weighted = Σ field_loss·n / Σ n                рядом, для сравнения
```

Основной это `field_balanced`: позиций у `transaction__mcc` на три порядка больше, чем у `product_event__term`, и взвешивание по токенам превратило бы обучение в обучение одному полю. CE всегда в float32.

Batch без целей не шаг: backward, optimizer и scheduler пропускаются, причина пишется в лог, счётчик успешных шагов не растёт. Подряд идущие пропуски ограничены `max_consecutive_skips`.

### Precision

CPU считает в float32. На CUDA включается `autocast` в bf16, если устройство его поддерживает; модель целиком в half не переводится, GradScaler не нужен. Временные интервалы и `log1p` считаются в float32 до приведения к dtype embeddings: на bf16 у часов осталось бы восемь бит мантиссы.

### Воспроизводимая evaluation

Validation фиксируется целиком до первого шага: клиенты, порядок, состав batch, обрезка и маски со своим seed. Иначе «метрика выросла» означало бы в том числе «маски стали проще». Набор сверяется по sha256 от целей при загрузке checkpoint.

Оценка идёт в `eval()` и `inference_mode()` с форком генераторов, поэтому не трогает ни веса, ни RNG обучения.

По каждому полю считаются число целей, число кандидатов и классов с поддержкой, CE модели и unigram, NCE gain, accuracy обеих, macro F1 по полному набору кандидатов с `zero_division=0` и top-K там, где кандидатов больше K.

```
CE_unigram = mean(−ln p_train(target))
NCE_gain   = (CE_unigram − CE_model) / CE_unigram
```

Unigram берётся только из `unigram_baselines.json` preprocessing и по оцениваемым данным не пересчитывается. Вероятности ограничены снизу `epsilon = 1e-8` и нормированы по кандидатам поля; исходный artifact не меняется. При `CE_unigram < epsilon` NCE это `null` со статусом `undefined`.

Метрики копятся по всему набору и агрегируются один раз: среднее готовых batch-F1 или batch-NCE это другая величина.

### Checkpoints

Сохраняются backbone и голова, optimizer и scheduler, счётчики batch и успешных шагов, config, генераторы Python, NumPy и torch, состояние sampler, хэши artifacts tokenizer, preprocessing и `unigram_baselines.json`, а также описание фиксированной validation. При загрузке всё это сверяется. `last` пишется на каждой оценке, `best` выбирается по field-balanced CE на `val_time`; если у сплита нет целей, `best` не пишется и отчёт говорит об этом прямо, критерий сам не подменяется.

512 train-клиентов, 64 клиента на каждый validation-сплит, 2000 шагов, batch 2, история 128 событий, RTX 3050, bf16. Обучение 2.7 минуты, 0.065 с/шаг, пик 52 МБ.

| | val_client до | val_client после | val_time до | val_time после |
|---|---|---|---|---|
| field-balanced CE | 2.1982 | 1.2914 | 2.2394 | 1.2497 |
| та же CE у unigram | 1.6479 | 1.6479 | 1.6367 | 1.6367 |
| средний NCE gain | −0.7996 | +0.3032 | −0.8093 | +0.3182 |
| accuracy | 0.2416 | 0.6122 | 0.2282 | 0.6049 |

На `val_time` модель обошла unigram на 27 полях из 32 и проиграла на пяти: `banner__slot`, `banner__offer`, `banner__action`, `app_operation__status` и `product_event__amount_or_limit`. Это поля, где train-мода уже почти оптимальна, а сигнала в истории мало.

### Диагностика внимания

Откуда берётся выигрыш. Голова видит три представления, и только History Encoder смешивает информацию между позициями, поэтому на готовом checkpoint ограничивается ровно его внимание. Ничего не обучается, маски validation те же самые и сверяются по sha256 целей.

```bash
venv\Scripts\python -m src.model.train ablate --name dev --device cuda
```

Последовательность это `[профиль, событие_1..N]`; себя видит каждая позиция всегда.

| вариант | событие видит | профиль видит |
|---|---|---|
| `full` | всех | всех |
| `events_isolated` | себя и профиль | только себя |
| `events_via_profile` | себя и профиль | всех |
| `profile_isolated` | все события, не профиль | только себя |
| `self_only` | только себя | только себя |

Правило приходит аргументом `forward` и нигде не запоминается. Структурный запрет и padding складываются в одну маску `[batch·heads, L, L]`, потому что слой принимает либо `src_key_padding_mask`, либо `src_mask`, и смешивать их нельзя. Padded-запрос сохраняет открытым профиль: строка без единого доступного ключа дала бы softmax по пустому множеству.

Результат на `val_time`, checkpoint шага 2000. Пересчитанный `full` совпал с сохранённым в checkpoint до последнего разряда.

| вариант | field-balanced CE | средний NCE gain | accuracy |
|---|---|---|---|
| `full` | 1.2497 | 0.3182 | 0.6049 |
| `events_via_profile` | 1.2502 (+0.0005) | 0.3183 | 0.6049 |
| `profile_isolated` | 1.2688 (+0.0191) | 0.3013 | 0.6032 |
| `self_only` | 1.2691 (+0.0195) | 0.3022 | 0.6035 |
| `events_isolated` | 1.2702 (+0.0205) | 0.3009 | 0.6032 |

Два вывода, и оба сужают роль History Encoder.

Прямое внимание между событиями не даёт ничего: `events_via_profile` отличается от `full` на 0.0005 CE, то есть на уровне шума bf16, и ни у одного поля прирост не превышает 0.012.

Весь вклад внимания идёт через профиль как через хаб. `events_isolated` и `events_via_profile` отличаются ровно одним: может ли позиция профиля смотреть на события. Это различие стоит 0.0200 из 0.0205. Симметрично `profile_isolated` теряет столько же, сколько полный запрет.

Сам вклад мал: запрет всего внимания стоит 1.6 % CE и оставляет 95 % выигрыша над unigram. Значит предсказание держится на `h_local`, то есть на остальных полях того же события, и на as-of профиле, а не на соседних событиях.

Сильнее прочих теряют `app_screen__funnel_stage` (+0.060), `profile_snapshot__holds_deposit` (+0.048), `app_screen__firebase_screen` (+0.043), `app_operation__domain` и `profile_snapshot__contracts_count` (+0.038), `transaction__mcc` (+0.032). Поля `product_event__*` показывают больший прирост, но у них 2–3 цели, и это шум. Восемь полей от запрета слегка выигрывают, сильнее всех `app_operation__status` (−0.009).


## Combined masking и сравнение двух моделей

Гипотеза: `field_balanced` скрывает одиночные значения, которые восстанавливаются из остальных полей того же события, поэтому истории учиться незачем. Смесь token, event и key masking убирает целые события и целые поля примера, и локального контекста должно перестать хватать. Проверка это вторая модель с нуля и сравнение двух checkpoint'ов.

```bash
venv\Scripts\python -m src.model.train run     --name dev --device cuda --tag combined ^
    --masking-mode combined --token-rate 0.15 --event-rate 0.10 --key-rate 0.10 --max-steps 2000
venv\Scripts\python -m src.model.train compare --name dev --device cuda --tag combined
```

`--tag` кладёт результат в `data/runs/<name>/<tag>/<mode>`, поэтому первый эксперимент не затрагивается.

### Режим `combined`

Для каждого примера независимо разыгрываются три выборки по ещё не замаскированному входу:

```
каждая доступная позиция          с вероятностью token_rate
каждое событие целиком            с вероятностью event_rate
каждая пара (пример, ключ) целиком с вероятностью key_rate
```

Маска это их объединение, пересечения считаются один раз. Три существующих masker подряд дали бы не то же самое: второй увидел бы `[MASK]` вместо значения, счёл бы позицию недоступной и потерял бы её target.

Key работает по точному namespaced `key_id` внутри одного примера. Это не выбор ровно одного ключа и не выбор ключей на весь batch: один и тот же ключ закрывается в одном примере и остаётся открытым в другом.

Доли не складываются. При ставках 0.15, 0.10 и 0.10 ожидается не 35 %, а

```
1 − 0.85 · 0.90 · 0.90 = 31.15 %
```

Измерено на обучении: 31.0 % в среднем по 2000 шагам. Диагностика выборок хранится рядом с маской: сколько позиций взяла каждая стратегия до объединения, сколько осталось после и величина пересечений.

### Как сравниваются два checkpoint'а

CE разных режимов маскирования между собой несравнима: скрыть одно значение и скрыть событие целиком это разные задачи. Поэтому режим оценки фиксируется, и внутри него обе модели идут по одним примерам, маскам и целям.

| набор масок | настройка |
|---|---|
| `field_balanced` | доля 0.15, тот же набор, на котором оценивался первый run |
| `token` | 15 % позиций |
| `event` | 10 % событий |
| `key` | 10 % пар (пример, ключ) |

Набор `field_balanced` сверяется по sha256 целей с сохранённым в старом checkpoint. Конфигурации берутся из checkpoint'ов, и расхождение настроек, влияющих на маски, это ошибка, а не предупреждение.

Разница двух моделей сопровождается парным bootstrap по примерам, 2000 выборок. Пересэмплируются клиенты, а не позиции: позиции одного клиента зависимы. Вывод делается только когда интервал не накрывает ноль.

Второй агрегат считается без `timeline__event_type` и девяти полей `profile_snapshot__*`: первое восстанавливается из состава события, вторые дублируют as-of профиль.

### Результат: гипотеза не подтвердилась

Обе модели обучены 2000 шагов на одних данных, с одним seed, одной инициализацией и одним порядком примеров. Различаются только objective.

`val_time`, field-balanced CE, старая модель против новой:

| набор масок | старая | новая | Δ (bootstrap) |
|---|---|---|---|
| `field_balanced` | 1.2497 | 1.3538 | +0.104 [+0.050, +0.135] |
| `token` | 1.2311 | 1.2876 | +0.057 [+0.033, +0.076] |
| `event` | 1.4273 | 1.4364 | +0.009 [−0.005, +0.029] |
| `key` | 1.1379 | 1.1906 | +0.053 [−0.001, +0.127] |

Положительная Δ означает, что новая модель хуже. На `val_client`, где целей в двадцать раз больше, значимо хуже во всех четырёх режимах. На `val_time` значимо хуже в двух, в остальных разница неотличима от нуля. Ни одного режима, где combined выигрывает, нет, включая режимы `event` и `key`, под которые она и обучалась.

**Зависимость от истории не выросла, а снизилась.** Потеря от полного запрета внимания (`self_only`) на `val_client`:

| набор масок | старая | новая | разность |
|---|---|---|---|
| `token` | +0.0190 | +0.0150 | −0.0041 [−0.0078, −0.0007] |
| `event` | +0.0153 | +0.0111 | −0.0042 [−0.0100, +0.0010] |
| `key` | +0.0194 | +0.0131 | −0.0063 [−0.0133, +0.0032] |

**Прямое event-to-event внимание по-прежнему почти ничего не даёт.** Потеря от `events_via_profile` у новой модели 0.0014–0.0020 против 0.0005–0.0008 у старой. На масках `event` прирост значим, но его величина это две тысячных CE при базовом уровне 1.44.

Без `event_type` и полей профиля картина та же: ни один прирост зависимости от истории не значим.

Отдельные поля событий у новой модели всё же лучше: на масках `event` она выигрывает у 12 полей из 33, в том числе `transaction__mcc` (3.737 против 3.571) и `transaction__is_online` (0.786 против 0.643). Проигрыш идёт в основном по полям профиля и `timeline__event_type`, то есть по тому, что она стала реже видеть целиком.

Вывод эксперимента: более агрессивное маскирование в этой конфигурации не заставило модель пользоваться историей. Про качество client embedding эти числа не говорят ничего, они меряют только восстановление скрытых значений.


## Диагностика: bootstrap по клиентам и глубина истории

```bash
venv\Scripts\python -m src.model.train diagnose --name dev --device cuda --tag combined
```

Обучения здесь нет: веса заморожены, маски и цели те же, что в сравнении.

### Единица пересэмплирования

Прежний bootstrap брал месячные примеры независимо, а в `val_client` одному клиенту принадлежат двадцать cutoff'ов с пересекающимися историями. Единицей стал клиент: примеры одного клиента входят в выборку вместе и с его кратностью.

Реализовано суммированием строк клиента до розыгрыша. Field-balanced CE сначала складывает NLL и counts по полю и только потом усредняет CE по полям, поэтому сумма столбца от группировки не зависит, и «клиент с кратностью k вместе со всеми примерами» это то же, что «строка клиента с весом k». Формула сохраняется буквально, точечные оценки не меняются ни на разряд. Средним по клиентским CE она не подменяется.

Одна матрица кратностей на набор используется для обеих моделей, всех четырёх режимов масок и всех пяти правил внимания.

**Ни один вывод не изменился.** На `val_time` интервалы совпали до разряда, как и должно быть при одном примере на клиента. На `val_client` они расширились в 1.0–1.5 раза, но значимость сохранилась у всех восьми сравнений моделей.

| набор масок, `val_client` | ΔCE | по примерам | по клиентам |
|---|---|---|---|
| `field_balanced` | +0.1000 | [+0.0929, +0.1072] | [+0.0894, +0.1102] |
| `token` | +0.0876 | [+0.0688, +0.1075] | [+0.0665, +0.1092] |
| `event` | +0.0428 | [+0.0272, +0.0599] | [+0.0281, +0.0601] |
| `key` | +0.0880 | [+0.0634, +0.1110] | [+0.0666, +0.1070] |

Расширение скромное, и этому есть причина: сравниваются две модели на одних и тех же примерах, поэтому клиентские особенности в разности взаимно уничтожаются. Зависимость остаётся в самой CE, но не в её разности.

Из двадцати четырёх разностей разностей у ablation вывод сменился ровно у одной: `events_isolated` на масках `event` в `val_client` был на границе значимости и перестал ею быть. Утверждение «зависимость от истории у новой модели снизилась» держится на масках `token` в обоих наборах.

Число целей у поля больше не считается достаточной характеристикой: рядом печатается число клиентов, давших эти цели. У девяти полей `profile_snapshot__*` на `val_time` приходится примерно по одной цели на клиента, у `product_event__term` одна цель у одного клиента.

### Календарная глубина recent-окон

Лимит задан в событиях, а поведение живёт в календаре. Обе величины показываются рядом, потому что их легко перепутать: «сработал лимит» и «сколько ленты отброшено» это разные числа.

`val_time`, 64 клиента:

| окно | обрезано примеров | отброшено событий | глубина p50 | p90 | max |
|---|---|---|---|---|---|
| 128 | 100 % | 92.7 % | 43.6 дн | 117.6 | 225.7 |
| 512 | 95 % | 70.7 % | 160.4 дн | 462.5 | 2981.5 |
| 1024 | 81 % | 44.8 % | 330.4 дн | 1632.5 | 2981.5 |
| полная | 0 % | 0 % | 1839.5 дн | 2819.5 | 2981.5 |

На `train` и `val_client` истории короче, поэтому при 128 обрезано 96–97 % примеров и отброшено 85–86 % событий, а глубина медианно 46–48 дней.

Состав окна 128 на `val_time` по медиане: 56 экранов приложения, 38 транзакций, 14 операций, 9 баннеров, 7 коммуникаций, 2 снимка профиля и ноль договоров. Полная история содержит три договора, то есть при лимите 128 договоры в контекст обычно не попадают вовсе.

### Что теряется при обрезке

Правила связей объявлены до счёта и разделены на достоверные и эвристические, полный список в `link_rules.md`. Достоверный идентификатор в этих данных ровно один: `session_id` у экранов приложения.

| связь | окно 128 | 512 | 1024 |
|---|---|---|---|
| повтор подписки | 37–51 % внутри | 84–89 % | 92–96 % |
| повтор категории и города | 34–44 % | 67–77 % | 81–89 % |
| экраны одной сессии | 100 % | 100 % | 100 % |
| экран → операция | 99 % | 100 % | 100 % |

Теряются именно медленные связи. Подписка списывается раз в месяц, и при окне 128 примерно половина повторов остаётся без своего предшественника; при 512 их 11–16 %. Связи, живущие внутри секунд и минут, обрезка не задевает вовсе.

Цепочка `app_screen → app_operation → product_event` в данных не порождается: сессия заявки состоит только из экранов и операций не создаёт. Проверялись две отдельные связи, и это оговорено в отчёте.

Переход одобрения в договор редок: на `val_time` при полном окне у 40 договоров из 170 нашёлся одобрявший экран, при окне 128 таких случаев три. Данных для надёжного вывода по этой связи мало, и отчёт помечает такие ячейки.

Статистика покрытия говорит, сколько времени и связей не доходит до модели. Она не говорит, что больший контекст улучшит качество: это проверяется экспериментом, а не таблицей.

## Генератор V2.1: зависимости между событиями

Аудит `data/runs/dev/generator_audit/audit.md` показал главное ограничение V1: внутри потока почти всё разыгрывалось независимо от прошлого клиента. Статус операции брался из констант 0.93 / 0.045 / 0.025 и ни на что не влиял; экран внутри домена и операция внутри домена выбирались равновероятно и не были связаны друг с другом; MCC, город и сумма покупки рисовались заново на каждое событие; подписки не начинались и не заканчивались; сбой ни к чему не вёл.

V2 меняет **правила**, а не контракт. Схемы таблиц, значения `event_type`, горизонт, `availability`, as-of профиля, `timestamp_quality`, окна признаков и метки, шум наблюдения и детерминированный RNG остаются прежними. Preprocessing, tokenizer, masking и модель не меняются.

```bash
venv\Scripts\python -m src.generator.emit --version v2.1 --preset smoke
venv\Scripts\python -m src.generator.emit --version v2.1 --clients 1000
venv\Scripts\python -m src.generator.show app_screens --client 3 --version v2.1
venv\Scripts\python -m src.generator.compare_versions --v1 data/raw/smoke --v2 data/raw/v2.1/smoke --clients 100
```

V1 остаётся версией по умолчанию и лежит там же, где лежал: `data/raw/<preset>`. V2.1 пишется в `data/raw/v2.1/<preset|clients_N>` и ничего не перезаписывает. Ключи `generation_version` и `generation_config` добавляются **только** начиная с v2.1: манифесты v1 уже на диске, и новые поля сделали бы их невоспроизводимыми. Манифест без версии читается как `v1`.

Промежуточная версия `v2` заменена на `v2.1` и заново не собирается: генератор исправлен, а не разветвлён. Её датасет `data/raw/v2/` остаётся на диске нетронутым.

### Что изменилось в правилах

| Что | V1 | V2 |
|---|---|---|
| Сессия приложения | случайные экраны из каталога домена | сценарий: `balance_check`, `transfer`, `payment`, `card_management`, `product_explore`, `support`, `market`, `profile_settings`; сессия может нести до трёх намерений |

| Операция | равновероятна внутри домена, не связана с экраном | шаг сценария: форма → подтверждение → операция → экран результата |
| Статус операции | 0.93 / 0.045 / 0.025 для всего | зависит от типа операции, номера попытки, сбоя сервиса, кредитного стресса (только денежные), утилизации лимита (только `limit_change`), блокировки карты (только списания) |

| Последствия успеха | нет | `deposit_open` открывает договор, `deposit_close` и `loan_early_repay` закрывают досрочно, `card_block` и `card_unblock` меняют состояние карты, `pay_*` гасит счёт |
| Покупки | MCC, город и сумма заново на каждое событие | привычная точка внутри своих категорий, привычный диапазон суммы, круглые ценовые точки; часть покупок остаётся новой |
| Изменение привычек | нет | 1–3 точки перелома у каждого клиента в свои даты, смешение за 30–60 дней; эпизоды 5–21 день: поездка, всплеск покупок, затишье, затем возврат |
| Квартплата, связь, госплатежи | случайные покупки | расписание счетов: свой день, своя сумма, свой срок жизни; оплата в приложении или напрямую |
| Подписки | одна сумма весь горизонт, город перерисовывается каждый месяц | начало, прекращение, редкая смена суммы, один город на подписку |
| Зарплата | сумма заново каждый месяц (±17.5 %) | стабильный доход клиента с редким повышением; даты и задержки как в v1 |
| Баннеры | оффер не зависит от владения | оффер уже имеющегося продукта показывается в 10 раз реже |
| Заявка после просмотра | константа на любой экран | глубина изучения (корень / калькулятор / условия), повторы за 14 дней, недавний отказ, недавнее предложение |

### Связанные платежи заменяют независимые

Успешная `pay_utility`, `pay_mobile`, `pay_internet`, `pay_fine`, `pay_tax` порождает транзакцию через 5–60 секунд; `pay_qr` и `market_order` порождают покупку. Чтобы это не увеличило объём, группы `utilities`, `telecom` и `government` **полностью убраны из случайной смеси покупок**: слот покупки, выпавший на такую группу, гасится, а счёт приходит из расписания. Прошлые события из-за будущего платежа не меняются, несвязанные покупки не удаляются.

Связь идёт по внутреннему ключу операции `(день, сессия, шаг, попытка)`, а не по совпадению секунды: две операции могут совпасть по времени. В RAW новых идентификаторов не появилось.

### Причинность

Память клиента это журнал с timestamp. Любой запрос возвращает только записи строго раньше запрошенного момента. Сессии перекрываются, поэтому сбой в 09:50 в сессии, начатой в 09:00, не виден сессии, начатой в 09:15, и не виден её шагу в 09:40, но виден шагу в 09:56. Доступность продукта проверяется на момент **операции**, а не сессии, и последствие успеха наступает сразу, внутри той же сессии.

Договор, открытый операцией днём, не может попасть в реестр раньше самой операции. У депозита `timestamp_quality` почти всегда `date_only`, и время теряется — такой договор регистрируется следующим днём.

Проверка: `before(FEATURE_END)` не зависит от того, генерировали до `FEATURE_END` или до `LABEL_END`, по всем семи потокам.

### Что осталось прежним

`operation → domain` и `firebase_screen → funnel_stage` остаются однозначными: это естественные связи, и разрушать их шумом ради усложнения MLM не нужно. Производными остаются также `day_of_week` и `hour` от `ts`, `product` от экрана, `term` и `amount_or_limit` от типа продукта. Почти константны `banners.action`, `merchant_country`, `delivered` внутри канала и `timestamp_quality` внутри типа продукта. Преимущественно случайны `template`, `reject_reason`, `slot`, `product_subtype`. Редко заполнены `funnel_stage`, `reject_reason` и `status = null`. Список MLM-целей не менялся.

### Что исправлено в V2.1

V2 был промежуточным шагом. Пять его дефектов найдены сверкой с кодом и замерены на 40 клиентах до правки.

| Дефект | Было | Стало |
|---|---|---|
| Успешная оплата без последствия | 489 из 657 успешных `pay_*` (74 %) не создавали списание | 0 |
| Действие раньше входа | 1261 экран и 137 дней с действиями после провала входа | 0 |
| Договор раньше своего решения | 26 договоров опережали экран одобрения | 0 |
| Успех при заблокированной карте | 21 успешное списание; пол вероятности давал успеху 0.396 | 0; успех невозможен по построению |
| `reject_reason` вразрез с состоянием | 2 из 19 отказов | 0 |

**Авторизация.** Защищённое действие возможно только после успешного входа либо при действующей авторизации: приложение помнит вход `AUTH_TTL_HOURS` часов. Попыток входа не больше трёх; после провала клиент либо восстанавливает доступ (`device_bind`), либо уходит, и тогда сессия не оставляет ни одного экрана. Первый экран идёт строго позже момента входа.

**Платежи.** У каждой `pay_*` есть намерение: конкретный счёт или свободный платёж. Успех создаёт ровно одну запись об оплате, а каждая запись — ровно одну транзакцию. Счёт гасится один раз: он исчезает из открытых, и повтор его уже не найдёт. Неуспешная операция не создаёт ничего. Свободный платёж имеет собственные назначение и сумму и ничей счёт не гасит.

**Хронология.** Сессии дня и созревшие заявки исполняются одной очередью событий: сессия с 09:00 и сессия с 09:15 чередуются по времени своих шагов. Решение принимается на состояние своей секунды, а не на конец дня. Сортировки готового результата для этого недостаточно, поэтому сессия устроена как сопрограмма: она предлагает действие, планировщик проверяет ограничение, разыгрывает исход и применяет последствие, и только после этого сессия продолжается.

Округление времени до даты (`timestamp_quality = date_only`) больше не переносит запись в прошлое: если снятое время поставило бы договор раньше его причины, реестр учитывает договор следующим днём. Это применяется на всех путях открытия — и через заявку, и через `deposit_open`.

**Допустимость.** Сначала жёсткое ограничение, затем случайный исход. Невозможность выражается флагом, а не малым весом: при `feasible = False` вероятность успеха равна нулю, а пол вероятности применяется только к отказу и отмене. Списания по заблокированной карте не проходят; перевод между своими счетами требует второго счёта; закрыть можно только существующий открытый договор, которым уже можно распорядиться.

**Причина отказа.** `reject_reason` следует из состояния, которое к отказу привело: возраст вне диапазона → `age_limit`, неподтверждённый доход → `income_not_confirmed`, действующий кредит при заявке на кредит → `existing_debt`, высокий стресс → `scoring_declined`. Набор причин не расширен; `blacklist` остаётся редкой и не выводимой из наблюдаемого.

## Session Encoder

Экраны одной сессии приложения это одно действие клиента, а не десяток независимых событий. Session Encoder сворачивает их в один вектор, и History Encoder получает сессию как элемент истории:

```
поля                        → Event Encoder    → вектор события
app-события одной сессии    → Session Encoder  → вектор сессии
сессии, остальные события,
профиль                     → History Encoder  → вектор клиента
```

Внутри сессии: `[SES], событие_1, …, событие_N` через двусторонний Transformer, `hidden[SES]` это вектор сессии. `[SES]` — обучаемый вектор модели, а не токен словаря: tokenizer про сессии не знает, и менять словарь не пришлось. Контекстные состояния событий сохраняются, их использует MLM.

### Две структуры

`event` это прежняя лента без Session Encoder, `session` — новая. Обе доступны одновременно, и умолчания `ModelConfig` не менялись: без явного указания собирается прежняя модель, поэтому старые checkpoints грузятся со своей исходной архитектурой.

```bash
venv\Scripts\python -m src.model.sessions build --name v21_1000
venv\Scripts\python -m src.model.session_smoke --name v21_1000 --device cuda
venv\Scripts\python -m src.model.train run --name v21_1000 --structure session \
    --d-model 128 --dim-feedforward 512 --event-layers 3 --profile-layers 1 --session-layers 1
```

Архитектура нового запуска задаётся явно, а не сменой умолчаний: поля `d_model`, `n_heads`, `dim_feedforward`, `activation`, четыре счётчика слоёв и `structure` живут в `TrainConfig` со значением `None` («взять умолчание»). Готовые наборы лежат в `src/model/config.py` как `EVENT_ARCHITECTURE` и `SESSION_ARCHITECTURE`; они отличаются только структурой, чтобы сравнение шло при равных размерах.

| Параметр | Значение нового запуска |
|---|---|
| d_model | 128 |
| dim_feedforward | 512 |
| n_heads | 4 |
| dropout | 0.1, GELU, `batch_first`, `norm_first`, финальный LayerNorm |
| слои | Profile 1, Event 3, Session 1, History 2 |

### Совместимость checkpoint'ов

`as_dict()` всегда пишет `structure`; `n_session_layers` и `session_gap_unit` — только в режиме сессий. Точное равенство словарей ломало бы каждый прежний `.pt` при одном лишь добавлении ключа, поэтому сравнение мягче и по-прежнему строгое: общие ключи обязаны совпадать, ключ, появившийся позже checkpoint'а, обязан равняться унаследованному значению, а ключ, которого нет в текущем окружении, это отказ («checkpoint новее кода»).

Унаследованное значение — то, что checkpoint подразумевал, пока ключа не было: для `structure` это `event` (Session Encoder тогда не существовал), для отпечатка `sessions` это `None` (sidecar тогда не собирали). Правило одно на оба словаря — конфигурацию модели и отпечатки артефактов. Следствие: старый `.pt` грузится целиком в модель прежней архитектуры, session-модель его осознанно отвергает с сообщением по существу, а появившийся рядом sidecar не выдаётся за «тот самый».

### Sidecar сессий

`session_id` не переживает токенизацию: это metadata. Поэтому рядом с токенизированным набором лежит `sessions/<группа>_clients.parquet` с тройками `(client_id, seq, session_key)`. Ключ строится плотной нумерацией внутри клиента, а не хэшем строки: разные `session_id` не могут слиться не потому, что хэш удачный, а потому что отображение инъективно.

При загрузке проверяется отпечаток содержимого, привязка к этому же токенизированному набору по хэшу его манифеста, уникальность пар `(client_id, seq)` и поэлементное совпадение `seq` с токенизированными событиями. Совпадения числа строк недостаточно: у клиента с тем же числом событий, но другой лентой, длина совпала бы. Отпечаток sidecar входит в `artifact_hashes`, поэтому его подмена становится ошибкой несовместимости на уровне checkpoint.

### Правило группировки

Сессия это экраны с одним `session_id` внутри **одного примера**. `app_operation` и `banner` остаются отдельными событиями: `session_id` у них нет, и восстанавливать принадлежность по близости во времени значило бы придумывать метаданные. Следствие для чтения отчёта: доля сгруппированных app-событий равна доле экранов среди них, а не единице.

Порядок и границы:

- члены сессии идут в порядке `(ts, seq)`, включая ошибки и повторы;
- время сессии это время её последнего события, поэтому транзакция, случившаяся между экранами, стоит в истории **раньше** сессии;
- cutoff применён раньше самим устройством примера, поэтому сессия на границе содержит ровно доступный префикс, а её состав, границы и длительность не знают о будущем;
- одно и то же событие у разных cutoff одного клиента может занимать разные позиции истории — это верное поведение as-of, а не расхождение.

Раскладка строится из metadata и по сигнатуре не получает ни `value_ids`, ни целей: состав сессии не может зависеть от того, что замаскировано. Ни один индекс `-1` не доходит до torch — padding заменяется нулём, а правда о нём живёт в отдельной маске, потому что отрицательный индекс молча берёт последнюю строку, и такую подмену не видно ни в forward, ни в loss.

### Время

История: прежний `TimeEncoding(gap, age)` в часах, но на **элемент** истории, а не на событие — после свёртки у события другой сосед. Внутри сессии: своя проекция `Linear(1, d)` от паузы в **минутах** через ту же `squash`. В часах пауза в полминуты даёт 0.008, и после `squash` признак был бы неотличим от нуля. Ни `[SES]`, ни padding временного слагаемого не получают.

### MLM

Маски ставятся на исходные `value_ids` до всех энкодеров, режимы маскирования и loss не менялись. Маскирование по ключу действует по всей истории, включая разные сессии; session-level masking не добавлялся.

Для поля внутри сессии голова получает четыре части: состояние токена (Event Encoder), состояние события внутри сессии (Session Encoder), вектор сессии в истории (History Encoder) и вектор клиента — проекция 512 → 128. Для отдельного события прежние три: токен, событие в истории, клиент — 384 → 128. Обе проекции ведут в одни и те же полевые головы с ограниченным словарём кандидатов.

Каждое событие проходит Event Encoder ровно один раз: Session Encoder потребляет уже готовые векторы. Незамаскированные копии целей никуда не уходят — sidecar несёт только `(client_id, seq, session_key)`, а `session_id` в токены не входит вовсе.

## Подготовка к финальному запуску

Пять вещей, которые надо было закрыть до единственного дорогого прогона. Каждая меняет то, что запуск измеряет, а не то, как быстро он идёт.

### Ревизия схемы RAW: событие знает свою сессию

Версия это правила генерации, ревизия это набор колонок. Оси разные, и путать их нельзя: v2.1 первого выпуска уже лежит на диске.

| ревизия | что нового |
|---|---|
| 1 | `session_id` только у `app_screens` |
| 2 | `session_id` есть и у `app_operations`, и у `banners` |

В V2.1 каждая операция и каждый баннер рождаются внутри сессии (`v2/lifecycle.py::_commit`), и её идентификатор там известен точно. Раньше он просто не доезжал до RAW, и 46 % app-событий стояли в истории врозь от своей сессии. Теперь он едет вместе с событием. **Ничего не восстанавливается по времени**: у события либо известна принадлежность, либо оно остаётся отдельным.

`manifest.json` получает `raw_schema_revision`; манифест без ключа это ревизия 1, ровно как манифест без `generation_version` это v1. V1 заморожена и остаётся ревизией 1 — её байты проверяются золотыми хэшами и не изменились.

Схема processed тоже зависит от ревизии. Это не педантизм: добавить старому набору пустые колонки значит сделать его невоспроизводимым, и все прежние artifacts перестали бы открываться.

```bash
venv\Scripts\python -m src.generator.emit --version v2.1 --clients 1000 --out data/raw/v2.1/clients_1000_r2
venv\Scripts\python -m src.preprocessing.run --raw data/raw/v2.1/clients_1000_r2 --name v21r2_1000
```

**Сессия без экранов это не дефект.** Так выглядят два честных случая: период до 2024-12-16, когда экраны ещё не сохранялись, и сессия, в которой вход не состоялся и до экрана дело не дошло. Оба проверяются тестом, а не предполагаются.

Правило группировки теперь про метаданную, а не про тип события: `group_events` берёт в сессию всё, у чего есть ключ. Что ключ бывает только у событий приложения, проверяет sidecar при сборке, где известна колонка каждого типа.

### Состав MLM-целей

`timeline__event_type` восстанавливается из состава самого события: у транзакции есть mcc и сумма, у экрана есть `firebase_screen`. `profile_snapshot__*` дублируют as-of профиль, который модель и так видит позицией 0. Раньше оба множества исключались только из **агрегата отчёта** — модель всё равно на них училась, и их лёгкость подмешивалась в loss.

`--target-policy history` убирает их из задачи целиком, оставляя входом: значения на месте, маски на них не ставятся, полевые головы никуда не деваются. Умолчание `all` — прежнее поведение, поэтому цифры старых запусков остаются воспроизводимыми.

Исключение задаётся **паттернами имён** (`profile_snapshot__*`), а не списком идентификаторов: `MaskingConfig` уезжает в checkpoint и восстанавливается там, где словаря под рукой нет. Паттерн такую поездку переживает. Паттерн, не совпавший ни с одним полем, это ошибка — опечатка иначе тихо стала бы «ничего не исключаем».

В отчёте такое поле получает статус `excluded`, а не `no_targets`: «выведено политикой» и «в данных нечего предсказывать» это разные вещи.

### Метрика нового месяца

Метрика на полной истории отвечает «как модель в среднем читает прошлое клиента». В полной истории свежих событий единицы процентов, и улучшение на них там растворяется.

Пример это пара (клиент, cutoff), а cutoff по контракту preprocessing это начало **следующего** месяца. Значит месяц наблюдения задан самим cutoff и отдельного поля не требует: `window_start` это месяц момента `cutoff − 1 мкс`. На всех 159 300 примерах `train` и на `val_time` это ровно колонка `observation_month`, проверено.

Каждая цель помечается флагом `recent`, и оценка ведёт **два** счёта по одним и тем же маскам: полный и по свежим целям. Это срез той же оценки, а не вторая оценка. `--best-metric recent` выбирает `best.pt` по нему.

`--final-splits test_client,test_time` оценивает лучшие веса на этих наборах **один раз, после обучения**. Отдельный шаг именно поэтому: test, увиденный на каждой оценке, перестаёт быть test.

### Маски по идентичности примера

Прежняя схема тянет один поток чисел по всему batch: маска примера зависит от того, с кем он попал в batch и каким по счёту оказался. Значит смена `eval_batch_size` меняет задачу, а не только скорость.

`--mask-scheme example` засевает поток парой `(client_id, cutoff)` и разыгрывает маску примера отдельно. Селекторы переписаны на «вид»: схема `batch` подаёт им весь batch с прежней арифметикой и прежним числом розыгрышей, поэтому её результат совпадает побайтово — на нём сняты цифры всех существующих запусков.

### Потоковая validation

Держать готовые batch'и всего набора это гигабайты на полных историях. `--stream-validation` хранит не batch'и, а рецепт: `digest`, счётчики и длины считаются при сборке, сами batch'и пересобираются на каждую оценку.

Это честно ровно постольку, поскольку маска привязана к примеру, поэтому поток **требует** схемы `example` и при схеме `batch` отказывается. Дополнительно `val_time` и `test_time` берут ленты по ссылке у train-store: это те же клиенты и тот же файл событий.

### Downstream: product_open_90d

Метка живёт только в RAW и в processed не попадает намеренно. Cutoff здесь один и выбран не нами: окно метки начинается в `feature_end`, значит признаки это вся история строго раньше него, один пример на клиента.

Строки примеров берутся из `cutoff_index.parquet`, а не из каталогов датасетов: на этом срезе примеры есть только у train-клиентов (это `test_time`), а нужны все три группы.

| модель | вход |
|---|---|
| boosting | профиль as-of и 85 агрегатов истории |
| логистическая регрессия | замороженный `[USR]` |
| тот же boosting | признаки и `[USR]` |

Одни и те же клиенты и сплиты, ROC-AUC и PR-AUC на val и test с интервалом по клиентам. Все преобразования (кодировщик категорий, нормировка) обучены **только на train**. Утечка не предполагается, а проверяется: событие позже cutoff или снимок профиля позже cutoff это исключение.

```bash
venv\Scripts\python -m src.model.downstream --name v21_10k ^
    --raw data/raw/v2.1/clients_10000 --checkpoint data/runs/v21_10k/run/best.pt --device cuda
```

### Финальный конфиг

Всё выражается командой, а не правкой кода. `none` это значение, а не отсутствие значения: у обрезки истории и у числа клиентов `None` это собственная ветка кода, и большим числом её не заменить.

| Параметр | Значение |
|---|---|
| данные | V2.1, 10 000 клиентов, seed 42, ревизия схемы 2 |
| structure | session |
| d_model / FFN / heads | 128 / 512 / 4 |
| слои Profile/Event/Session/History | 1 / 3 / 1 / 2 |
| max_events_per_history | none (+ preflight) |
| max_train_clients / max_val_clients | none / none |
| masking | combined 0.15 / 0.10 / 0.10, схема example |
| target_policy | history |
| бюджет | одна полная эпоха |
| validation | потоковая, best по `val_time.recent` |
| финал | `test_client`, `test_time`, один раз |

```bash
venv\Scripts\python -m src.model.train run --name v21_10k --device cuda ^
    --structure session --d-model 128 --n-heads 4 --dim-feedforward 512 ^
    --profile-layers 1 --event-layers 3 --session-layers 1 --history-layers 2 ^
    --max-events none --train-clients none --val-clients none ^
    --masking-mode combined --token-rate 0.15 --event-rate 0.10 --key-rate 0.10 ^
    --mask-scheme example --target-policy history --epochs 1 ^
    --stream-validation --best-metric recent --final-splits test_client,test_time ^
    --batch-size 2 --eval-batch-size 2 --log-every 200 --eval-every 4000
```

«Без потери и скрытой обрезки» это не настройка, а измерение: при `--max-events none` запуск сам проходит по всем примерам и подтверждает, что `used == original` у каждого. Рядом печатается `history_over_limit` — отметка токенизатора о длине истории, которая обрезкой **не** является.

## Длинное обучение: сбой не должен стоить эпохи

Эпоха на 10 000 клиентах идёт около четырёх часов. За это время может случиться всё: закончится питание, упадёт драйвер, понадобится машина. Поэтому прогон устроен так, чтобы сбой стоил минут, а не часов, и чтобы продолжение было **тем же самым обучением**, а не похожим.

### Что сохраняется и когда

`last.pt` переписывается каждые 2000 успешных шагов независимо от оценок, а также перед каждой validation, после неё, в конце эпохи и перед финальными наборами. Отдельного файла на каждые 2000 шагов не заводится: постоянных checkpoint'ов ровно три — `last.pt`, `best.pt`, и по случаю `interrupted.pt` или `crash.pt`.

`best.pt` обновляется только после **успешной** validation и только при улучшении `val_time.recent`. Иначе он перестал бы быть лучшим и стал бы просто последним.

Запись атомарна:

1. сохранение во временный файл рядом (не в TEMP: `os.replace` атомарен только внутри одной файловой системы);
2. проверка, что файл открывается и содержит все обязательные секции;
3. подмена через `os.replace`;
4. при любой ошибке прежний `last.pt` остаётся нетронутым, а обрубок удаляется.

Перезаписывать рабочий файл напрямую значит менять «есть checkpoint» на «есть обрубок» ровно в тот момент, когда он нужнее всего.

### Продолжение

```bash
venv\Scripts\python -u -m src.model.train run --name v21_10k --resume data/runs/v21_10k/run/last.pt ...
```

Восстанавливаются веса, оптимизатор, scheduler, счётчики, позиция sampler и его перестановка, все четыре генератора случайных чисел (Python, NumPy, torch CPU, torch CUDA), история оценок, лучший результат и прогресс эпохи в micro-batch. Продолжается остаток **той же** эпохи: уже пройденные примеры второй раз не проходятся, оценка шага 0 не повторяется, расписание оценок глобальное, learning rate не сбрасывается, лог дописывается в тот же файл с событием `resume`. Финальные наборы, если они уже посчитаны, второй раз не считаются.

Совместимость проверяется **до загрузки набора**: несовпадение seed, политики целей, схемы масок, архитектуры, словаря, artifacts или sidecar сессий стоит секунды, а не полчаса чтения событий. Сверяется вся конфигурация целиком, а не выборочные поля: перечислять исключения безопаснее, чем перечислять важное и однажды забыть новое поле. Бюджет тоже часть эксперимента — продолжить «то же обучение» с другим `max_steps` нельзя.

### Остановка и сбой

Ctrl+C или файл `stop.request` — это не сбой: текущий шаг досчитывается, пишется `interrupted.pt` и `interrupted.json`, финальная оценка не запускается, код выхода 130. На Windows фоновому процессу Ctrl+C не доставить, поэтому просьба остановиться это файл; обработка та же.

OOM, ошибка CUDA, неконечные loss или градиенты — пишется `diagnostics.json` (шаг, batch, loss, норма градиента, learning rate, память GPU, конфигурация), делается попытка сохранить `crash.pt`, код выхода 1. Конечность loss и градиентов проверяется **до** `optimizer.step`, gradient clipping сохранён. Batch size и обрезка истории внутри начатого прогона не меняются автоматически: это была бы другая задача под тем же именем.

### Признаки жизни и два каталога

Каталогов ровно два, и это не педантизм:

| Каталог | Кто пишет | Что |
|---|---|---|
| `run/` | trainer | `log.jsonl`, `status.json`, `command.txt`, `pid.txt`, `stop.request`, `last.pt`, `best.pt` |
| `control/` | launcher | `stdout.log`, `stderr.log`, `pid.txt` |

Trainer отказывается работать в непустом `run/` — так он не затирает чужой результат. Значит launcher не имеет права ничего туда класть **до** старта: собственный `stdout.log` сделал бы запуск невозможным. Поэтому перенаправленный вывод и PID процесса живут отдельно, а `stop.request` создаётся именно в `run/`, где его и ждёт trainer.

`log.jsonl` пишется с `fsync` на каждой записи, `status.json` переписывается атомарно — читатель никогда не увидит половину файла. Каждые 200 шагов печатается heartbeat: шаг из общего числа, процент эпохи, loss, learning rate, норма градиента, секунд на шаг, прошедшее время, ETA, память GPU и сколько секунд назад писался checkpoint.

### Команды

Обучение идёт отдельным локальным процессом: ему не нужен ни интернет, ни открытая сессия, ни окно, из которого он запущен.

```powershell
.\scripts\epoch.ps1 start                 # запуск
.\scripts\epoch.ps1 status                # PID, фаза, шаг, ETA, последний checkpoint
.\scripts\epoch.ps1 logs -Lines 40        # хвост stdout и stderr
.\scripts\epoch.ps1 stop                  # мягкая остановка через stop.request
.\scripts\epoch.ps1 resume                # продолжить с last.pt
.\scripts\epoch.ps1 resume-interrupted    # продолжить с interrupted.pt
.\scripts\epoch.ps1 check                 # что в checkpoint, без данных и модели
```

`start` отказывается запускать второй процесс, если в этом каталоге уже работает обучение: PID из файла мало (номер переиспользуется системой), поэтому дополнительно проверяется, что процесс жив и что это python. Он же заранее говорит, если `run/` не пуст, вместо того чтобы получить отказ trainer из stderr.

`--force` не используется нигде: непустой каталог это всегда повод посмотреть, что в нём, а не повод его стереть.

Сам launcher проверяется на крошечном наборе, без эпохи:

```powershell
.\scripts\epoch.ps1 start -Preset smoke
.\scripts\epoch.ps1 status -Preset smoke
.\scripts\epoch.ps1 stop -Preset smoke
```


## Что вне V1

P2P-переводы, платежи по кредитам и просрочка (DPD), метки `default_90d` и `churn_90d`. Кредитный стресс остаётся скрытым драйвером поведения и виден только косвенно: через состав покупок, задержки зарплаты, интерес к кредитам, напоминания о платеже и утилизацию лимита.
