# mini-PRAGMA v2

Синтетический генератор истории банковских клиентов и модель поверх него. Генератор повторяет **структуру, причинность и типичные дефекты реальных данных Home Credit Bank Kazakhstan**, чтобы препроцессинг и модель писались на синтетике и переключались на реальные данные без смены архитектуры.

Порядок порождения идёт от причины к следствию, а не наоборот:

```
Скрытая жизнь клиента        черты, домохозяйство, работа, доход, жизненные события
   ↓
Финансовое и продуктовое     остатки, договоры, графики платежей, карты, депозиты
состояние
   ↓
Потребности и решения        траты, переводы, заявки, реакция на предложения, стресс
   ↓
События, наблюдаемые банком  11 источников, конверт, дефекты наблюдаемости
   ↓
Полный RAW                   единая лента событий + профиль + каталоги + скрытая истина
```

Событие не разыгрывается само по себе. Оно следует из возраста и этапа жизни, семьи, города, работы и дохода, бюджета и долговой нагрузки, уже открытых продуктов, предыдущих событий, времени суток, дня недели, сезона и праздников, устойчивых привычек, жизненных изменений и текущего режима активности.

> **Статус.** Переделан только генератор. Препроцессинг, токенизатор и модель читают прежний контракт RAW и **ожидают переделки**: их разделы ниже описывают то, что было, и пока не соответствуют новому выходу генератора.

## Быстрый старт

```powershell
venv\Scripts\pip install -e .[dev]

# данные
venv\Scripts\python -m src.generator.emit --clients 300 --out data/raw/check --seed 42

# отчёт реализма, истории клиентов, аудит proxy-утечек
venv\Scripts\python -m src.generator.report.realism --raw data/raw/check

# лента одного клиента глазами
venv\Scripts\python -m src.generator.report.show --raw data/raw/check --truth

# тесты генератора
venv\Scripts\python -m pytest tests/test_gen_smoke.py tests/test_gen_scenarios.py tests/test_gen_products.py -q
```

Пресеты: `smoke` 100, `check` 300, `dev` 10 000, `eval` 50 000 клиентов. `--clients N` задаёт произвольный размер, `--workers` — число процессов, `--chunk-clients` — размер пачки, `--community-size` — размер сообщества, `--catalog-scale` — масштаб каталога мерчантов, `--params` — JSON с переопределениями параметров, `--resume` — продолжение по недописанным сообществам.

Типизированных таблиц по источникам нет. Всё наблюдаемое живёт в одной ленте; чем именно является запись, говорят `event_type` и `source`, а состав payload описан каталогом ключей в манифесте.

## Конверт события

| Поле | Смысл |
|---|---|
| `event_id` | тождество события; исправление сохраняет его |
| `client_id` | непрозрачный идентификатор, выведенный из seed и порядкового номера |
| `event_type` | что произошло |
| `source` | система, которая это записала |
| `event_time` | когда произошло; другого времени у записи нет |
| `effective_at` | с какого момента действует, если это не момент записи |
| `time_precision` | `second`, `minute` или `day` |
| `event_version` | 1 у оригинала, +1 у каждого исправления |
| `change_initiator` | `client`, `bank`, `system`, `external` |
| `correlation_id` | цепочка: заявка, договор, перевод, кейс |
| `link_type` | чем именно связано |
| `is_test_account` | техническая учётная запись |
| `payload` | JSON с полями конкретного типа события |

**Исправление** несёт тот же `event_id` и версию на единицу больше. **Дубль** несёт ту же версию и то же содержимое. Номера записи в выгрузке нет: порядок несёт сама лента, строки клиента лежат подряд. Возврат, отмена и chargeback ссылаются на исходную операцию через `cause_event_id` в payload.

**Читать нужно последнюю версию записи.** Ошибку делает витрина: первая версия уходит с опечаткой в одном из объявленных полей, а исправление возвращает настоящее значение. Поэтому именно последняя версия сходится с проводками и остатками, а первая намеренно с ними расходится. Исправление меняет только объявленные поля и никогда не трогает счёт, направление, статус, остаток и причинную ссылку. Место события в ленте принадлежит первой версии: исправление уточняет запись, но не переносит её во времени.

## Профиль на произвольную дату

Профиль версионный: каждая строка действует со своего `valid_from`. Читать его нужно так: взять версии, у которых `valid_from <= ts`, и выбрать последнюю по `valid_from`. `valid_to` при этом не фильтрует.

Смену выражает сама следующая строка: пока её `valid_from` не наступил, действует предыдущая, а фильтр по `valid_to` создал бы между ними дыру. Готовая реализация лежит в `profile.as_of` и `profile.known_at`.

| Граница | Значение |
|---|---|
| `REGISTRY_START` | 2018-01-01, начало реестра договоров |
| `HISTORY_START` | 2024-06-01 |
| `HISTORY_END` | 2026-09-01, так что август полон |

История хранится целиком. Ни числом событий, ни числом токенов генератор её не ограничивает, срез «как есть» не делает и будущее не отбрасывает.

## Продуктовый каталог во времени

Подтверждённая хронология Home Credit лежит в `data/reference/home_product_timeline.yaml` и считается фактом. Python её только загружает и проверяет: `world/hcb_timeline.py` требует обязательные ключи, допустимую точность даты, непротиворечивый период, уникальные коды, существующие ссылки на предшественника и преемника и отсутствие кодов `SYNTH_*`. Нарушение — ошибка запуска, а не предупреждение. sha256 файла попадает в манифест.

**Месяц и год никогда не превращаются в день.** Запись хранит `known_period_start`, `known_period_end` и `date_precision`; отдельной колонкой рядом лежит `simulation_effective_at` — день, которым пользуется симуляция, выбранный политикой `params.products.effective_date_policy` (`period_start` по умолчанию). Неизвестное начало даёт `registry_start`.

**Источник обязателен.** `source` содержит только ту ссылку, которая действительно есть; владелец проекта как источник указывается лишь там, где он назван явно. Если источника нет, запись обязана нести `source: null`, `confidence: low` и `unresolved_source: true` — валидатор не пропустит иное сочетание, а отчёт реализма перечислит такие записи как требующие подтверждения.

Семь состояний продукта выводятся **только из дат вех**: `planned`, `pilot`, `active`, `temporarily_suspended`, `closed_to_new_clients`, `servicing_existing_contracts`, `archived`. Наличие или отсутствие договоров в конкретной синтетической выборке на статус не влияет. Архив — терминальное состояние.

**Закрытие продаж не закрывает договоры.** Договор запоминает версию условий и тарифа на день подписания и живёт на ней, пока обслуживается; поздние события ссылаются на ту же версию. Новая версия касается действующего договора только по `applies_to`: `existing_from_date` даёт `product_repriced` или `contract_terms_changed` после `notice_days`, `on_renewal` — `product_renewed`, `new_clients_only` — ничего. Переход на другой продукт это `product_migrated` с `previous_product_id` и `migration_reason`.

Правила владения живут на продукте: `allow_multiple`, `max_active_holdings`, `compatibility_rules`, `replacement_rules`. Общего запрета «один продукт на семейство» нет; общие правила банка (например, не больше четырёх дебетовых карт) лежат в `params.products.bank_rules`.

Вымышленные запуски, смены тарифа, приостановки и закрытия описываются в `params.products.synthetic_products` и получают **отдельные коды `SYNTH_*`**. Настоящие продукты синтетических дат и тарифов не получают никогда.

## Скрытая жизнь

**Черты управляют поведением, а не украшают истину.** Отчёт реализма считает связь каждой черты с тем поведением, ради которого она существует: импульсивность с числом покупок, цифровая склонность с сессиями, дисциплина с долей пропущенных взносов, склонность к сбережению с пополнениями вклада, аппетит к кредиту с заявками, социальность с переводами, лояльность с долей повторных точек. Значение около нуля означает, что черта ничего не решает, и это видно сразу.

**Черты.** Двенадцать непрерывных коррелированных черт — дисциплина, терпимость к риску, импульсивность трат, цифровая склонность, чувствительность к цене, лояльность к точкам, предпочтения каналов, мобильность, социальность, уязвимость к мошенничеству, аппетит к кредиту, склонность к сбережению. Архетип задаёт только средние; разброс внутри архетипа таков, что два клиента одного типа заметно различаются. Черты живут в `truth/clients.parquet`, медленно дрейфуют после жизненных событий и в RAW не попадают.

**Доход.** Потоки дохода (зарплата, пенсия, бизнес, фриланс, аренда, помощь семьи, пособие) имеют работодателя, расписание, правило дня выплаты и место зачисления. Выплата месяца бывает обычной, ранней, поздней, перенесённой из-за выходных, пропущенной, частичной с доплатой; бывают премия, отпускные, индексация, смена работодателя, несколько потоков, нерегулярный доход и увольнение. Часть дохода приходит в другой банк или наличными и видна банку лишь косвенно.

**Стресс** — это период, а не тип клиента. У эпизода есть триггер (увольнение, задержка дохода, болезнь, крупная покупка, рост обязательств, развод, переезд, случайный шок), нарастание и спад, следствия (дискреционные траты вниз, утилизация лимита вверх, пропуски платежей, обращения в поддержку, интерес к рефинансированию) и выход: восстановление дохода, рефинансирование, реструктуризация, продажа сбережений, помощь семьи. Повторный стресс возможен.

**Социальный граф** строится до симуляции для каждого сообщества: супруги, родственники, друзья, коллеги, работодатели, арендодатели, собственные счета в других банках, устойчивые и случайные контрагенты. Домохозяйство делит аренду, счета и шоки. В RAW не пишутся ни `household_id`, ни тип связи, ни идентификатор работодателя — виден только устойчивый маскированный `counterparty`.

**Мошенничество** — эпизод и риск, а не пожизненный класс: компрометация карты, необычная покупка, подозрительный перевод, социальная инженерия, захват доступа, ложное срабатывание. Цепочка идёт от шагов эпизода к срабатыванию антифрода, решению, блокировке, обращению клиента, оспариванию, возврату и перевыпуску. Флага мошенничества в RAW нет.

Форма эпизода следует его виду. Карточные виды выглядят обычной покупкой в реальной точке с её именем и её MCC: постоянная метка вроде «неизвестный мерчант» и единственный код категории были бы готовым признаком для модели. Подозрительный перевод и социальная инженерия это перевод внешнему получателю, а захват доступа начинается со входа с нового устройства. Поэтому `subject` у срабатывания бывает `card`, `account` и `session`, а не всегда `card`.

## Финансовая причинность

Деньги не возникают и не исчезают. Каждая успешная операция — проводка с явно названной второй стороной: другой счёт того же клиента, счёт другого клиента, внешний банк, наличные, мерчант, работодатель, государство, доходы и расходы банка. Каждая транзакция несёт `balance_after` своего счёта.

- Расход требует источника: собственных средств или доступного кредитного лимита.
- Отклонённая операция не меняет ни одного остатка; отменённая клиентом не порождает транзакции вовсе.
- Кредит проходит заявку, решение, выдачу, график и обслуживание; платёж соответствует договору; просрочка растёт от самого раннего неоплаченного платежа и регистрируется на вехах.
- **Долговая нагрузка это правило, а не ярлык.** Сумма кредита урезается так, чтобы платёж вместе с уже имеющимися обязательствами укладывался в `bank_rules["max_debt_service_ratio"]`, а запрос сверх этого отклоняется с причиной `debt_service_ratio` до всякого розыгрыша.
- **Платёж это поведение клиента, а не таймер.** По каждому взносу заранее решено, заплатит ли клиент, в какой из льготных дней и в котором часу. Не хватает денег на счёте — сначала подтягивают их из другого банка или наличными, потом платят частично, и только затем автосписание проваливается с `decline_reason`. Один платёж закрывает столько взносов, на сколько хватает денег: отставший клиент догоняет график, а не остаётся в вечной просрочке.
- **Рефинансирование гасит прежние долги.** Выданные деньги закрывают открытые кредиты с причиной `refinanced`, а не добавляют ещё один договор поверх них.
- **Карта рассрочки живёт по своему договору.** Покупка делится на равные части по числу месяцев из тарифа, наличные и переводы с карты копят проценты по своей ставке, а в конце месяца выходит выписка: начисление, минимальный платёж, его оплата переводом со своего счёта или пропуск и веха просрочки. Долг по такой карте растёт от новых покупок, поэтому правило убывающего долга к ней не применяется.
- Операции по депозиту невозможны раньше его открытия и позже закрытия.
- Вклад открывается только с деньгами: сумма ограничена тем, что клиент может собрать на одном счёте (недостающее подтягивается наличными или переводом из другого банка), а договор без финансирования аннулируется сразу с причиной `not_funded`. Досрочное закрытие теряет начисленные проценты: они списываются комиссией с причиной `early_closure` до выплаты остатка. Вклад, открытый до окна, живёт по тем же правилам: срок считается пролонгированным до первого окончания внутри окна. Вклад не платёжный счёт: покупки, счета, переводы и взносы идут с карт и текущих счетов, а деньги со вклада уходят только отдельной операцией `deposit_withdrawal` с проверкой условий продукта (снятие к сроку платежа — причина `withdrawal_before_payment`). Пролонгация открывает новый срок: проценты прошлого срока капитализируются и при досрочном закрытии не отнимаются.
- Перевод между своими счетами это две записи и одна проводка: вторая нога только показывает остаток. Проводка обеих ног удваивала бы пополнение вклада и проценты с него.
- Заблокированная карта не проводит успешных покупок.
- Возврат, отмена и chargeback ссылаются на исходную операцию и в сумме её не превышают.
- Внутренний перевод порождает обе стороны с одним `transfer_id`, и получатель видит деньги во всех последующих решениях.

`cause_event_id` — это всегда либо существующий `event_id`, либо `null`. Идентификатор договора, месяц или текстовая причина туда не пишутся никогда. У периодических комиссий и процентов конкретного события-причины нет: они несут `cause_event_id = null`, `contract_id`, `accrual_period` и `reason = periodic_contract_rule`.

Инварианты собраны в `finance/invariants.py` и используются и тестами, и отчётом реализма: пара проводок в сумме даёт ноль, стороны перевода совпадают по идентификатору и сумме, цепочка `balance_after` не рвётся, отклонённое не создаёт проводок, совокупное изменение остатков объясняется чистыми внешними потоками, частичные возвраты не превышают исходную операцию, остаток основного долга сходится с выдачей и платежами.

## Деньги вокруг клиента

Деньги ходят в обе стороны. Родня, друзья и постоянные контрагенты не только получают переводы, но и присылают их: у связи есть собственная входящая частота, и приход от внешнего отправителя приходит событием `transfer_in` с причиной `inbound`. Внутрибанковский приход порождает исходящий план другого клиента того же сообщества, поэтому дважды он не считается.

Зарплатный проект виден без отдельного признака: часть работающих клиентов сообщества получает деньги от одного работодателя, в один день и с одной задержкой месяца.

После зарплаты тратят охотнее, перед ней придерживают. Уровень месяца тоже разный: декабрь дороже февраля. Пенсия приходит по своему календарю, а не в любой день, как зарплата.

Зарубежная покупка проходит в чужой валюте и ложится на счёт в тенге: рядом с суммой лежат `original_amount` и `original_currency`, а курс берётся из `params.amounts.fx_rates`.

## Мерчанты

Сеть, точка и MCC — разные сущности. Популярность сетей и точек имеет тяжёлый хвост. У клиента есть домашняя и рабочая зоны и набор любимых точек в частых категориях; вероятность нового места растёт с импульсивностью, поездкой и переездом и падает с лояльностью. Выбор точки учитывает расстояние, время суток и день недели, часы работы, доход и ценовой сегмент, транспорт, поездку и конкретную потребность. Закрытая точка не обслуживает вовсе, а не просто теряет вес: покупок в нерабочий час в данных практически нет. Оплата по QR это тот же поход в магазин с другим каналом. Будний день, выходные и месячные обязательства складываются в устойчивые последовательности. Сумма покупки определяется потребностью, корзиной, ценовым уровнем точки, чертами и сезоном — не кодом MCC.

## Наблюдаемость

Дефект принадлежит источнику, а не равномерному шуму: дубли, исправления, отмены, пропуски полей с причиной, суточные сбои источника, смена схемы в середине истории, потеря времени у части записей витрины договоров, тестовые аккаунты, состояние на начало окна. Витрина теряет время у записи только там, где известна её причина, и запись никогда не оказывается раньше причины.

## Запрещённые поля и аудит утечек

Ни одно из скрытых полей не попадает в RAW: будущий отток, будущий дефолт, роль в мошенничестве, сценарий, архетип, идентификатор домохозяйства, тип связи, идентификатор работодателя, эпизод стресса, любые `trait_*`.

Аудит проверяет три вещи: имена колонок и ключей payload по всей ленте, значения скрытых черт внутри payload по выборке записей, взаимную информацию между скрытыми полями и несколькими счётчиками клиента. Отчёт печатает охват каждой проверки и говорит, что осталось непроверенным. Чистый результат означает «в выполненных проверках утечек не обнаружено», а не отсутствие утечек вообще.

## Готовность к произвольному `eval_ts`

Генератор меток и срезов не делает: он лишь обязан не мешать их построить позже. Контракт таков.

- События отбираются по `event_time`: другого времени у записи нет.
- Версия записи берётся наибольшая по `event_version`. Место записи в ленте при этом принадлежит первой версии.
- Профиль берётся по `valid_from <= eval_ts`, последний по `valid_from`. По `valid_to` фильтровать нельзя: см. раздел о профиле на произвольную дату.
- Статус продукта берётся по интервалу каталога.

Ни одно событие не содержит сведений о более поздних событиях: закрытие пишется в момент закрытия, а плановые даты графика платежей это законное знание банка на момент договора.

## Детерминизм

Случайность разделена на две: `world_seed` создаёт мир, `population_seed` создаёт клиентов и их поведение. От мира зависят география, бренды и торговые точки; продуктовый каталог и его хронология случайности не используют вовсе. Поэтому три группы одного набора задают **один** `world_seed` и **разные** seed популяции: Казахстан, бренды и точки у них общие, а клиенты и события разные и не пересекаются. Оба seed лежат в манифесте.

Единица симуляции — **сообщество**, а не пачка воркера. У клиента есть устойчивый порядковый номер, `community_id = (client_ordinal - 1) // community_size`, а `client_id` выведен из seed и номера так, что соседство номеров из RAW не читается. Пачки лишь распределяют целые сообщества по процессам.

Следствия: один seed и одни параметры дают один и тот же результат при любом числе воркеров, любом размере пачки, любом порядке завершения и любом `PYTHONHASHSEED`. Манифест хранит `content_sha256` каждой таблицы по канонически отсортированным строкам и отдельно sha256 файлов.

## Параметры

Значимые величины вынесены из кода в `src/generator/params/`: население, черты, жизненный цикл, доход, стресс, связи, мошенничество, активность, суммы, продукты, география, мерчанты, сезонность, дефекты, калибровочные эталоны. Переопределения передаются JSON-файлом через `--params`, отпечаток конфигурации входит в манифест и в ключ кэширования розыгрышей.

`params/calibration.py` хранит эталоны со статусом `reference` (есть реальный источник), `hypothesis` (гипотеза) и `no_reference` (эталона нет). У каждого записаны источник, период, география, уверенность и допустимый разброс. Там, где реального эталона нет, точное значение не выдумывается.

## Отчёт реализма

`report/realism.py` строит markdown и JSON: кредитный портфель с переходами просрочки и дисциплиной платежей, продукты на клиента, частоту и форму мошенничества, время покупок и соблюдение часов работы точек, связь черт с поведением, распределения и квантили, события на клиент-месяц **с тремя разными видами месяца**, исчезновения и возвращения клиентов, длинные хвосты, переходы жизненного цикла, повторяемость точек и контрагентов, география, доходы с задержками и пропусками, эпизоды стресса и их исходы, финансовые инварианты, продуктовые цепочки и миграции, цепочки мошенничества, дефекты по источникам, сравнение с калибровочными эталонами, список метрик без эталона, записи хронологии без источника, несколько целостных историй клиентов и аудит proxy-утечек.

### Эталон и гипотеза это разные вещи

Отчёт сверяется с двумя видами ориентиров и **никогда не складывает их в один счётчик**.

**Эталонов одиннадцать**, и все они из отчёта банка. У каждого записан допуск, и рядом печатается готовый интервал, чтобы «в допуске» можно было проверить глазами. Выход за него означает ошибку генератора.

**Гипотеза** это полоса из «плана для генератора», раздел 17.2. Данными банка она не подтверждена, поэтому расхождение с ней ошибкой не является и подгонять под неё генератор не следует. Полосы 65–85 событий на клиент-месяц и 10–15 % пустых месяцев относятся именно сюда.

### Три вида месяца и окно наблюдения

Окно наблюдения клиента начинается с фактического начала отношений, а не с начала истории, и заканчивается закрытием отношений либо концом датасета. Читать `source_coverage` надо по смыслу: `first_available_at` это дата запуска источника **в банке**, клиента учитывает только `first_seen`; `last_available_at = None` означает «конец не задан»; `client_not_onboarded` у источников приложения означает «приложение не установлено», а не «отношений нет».

Месяцы внутри окна делятся на три непересекающиеся категории, дающие ровно 100 %: нет никаких записей; записи есть, действий клиента нет; есть действия клиента. Общий показатель месяцев **без действий клиента** равен сумме первых двух.

Недостаток покрытия это **неизвестность, а не ноль**. Такой месяц не становится пустым, в знаменатель трёх долей не входит и **разрывает** паузу, а не склеивает её через себя. Календарь отдельных дней сбоя из `source_coverage` невосстановим, и отчёт это оговаривает.

### Исчезновение не равно уходу

Молчание клиента на дату конца датасета — это граница наблюдения, а не уход из банка: будущее клиента неизвестно. У паузы четыре исхода: вернулся, длится на конец наблюдения, отношения закрыты, наблюдение прервано. Доля возвращения считается от первых трёх; четвёртый в знаменатель не входит, потому что про такую паузу неизвестно ничего. Подтверждённое прекращение отношений считается отдельно и только по факту.

Молчание **до первого действия** отделено от исчезновения ранее активного клиента: клиент просто ещё не начал.

`report/show.py` печатает ленту одного клиента подряд, с профилем, покрытием и — по явному флагу `--truth` — скрытой правдой рядом.

## Спецификация будущего адаптера Pragmatiq

Адаптер не реализован; ниже контракт, по которому он строится.

- Лента → `(user_id = client_id, ts = event_time, source, fields = payload наибольшей версии по каталогу ключей манифеста)`.
- Профиль SCD2 → профиль «как на момент» по правилам раздела о `eval_ts`.
- Внутренние переводы → рёбра `(from_client, to_client, ts, amount, transfer_id)` из пар `p2p_out` и `p2p_in`.

Токенизация, ограничения длины, выбор `eval_ts` и метки задач — отдельный этап.

# Preprocessing

Пять последовательных этапов по «план для препроцессинга.txt»: 1. Проверка → 2. Структуризация в canonical → 3. История на дату → 4. Разделение train / validation / test → 5. Семантический слой. На выходе — читаемые данные с исходными значениями (сумма остаётся числом, название мерчанта — текстом) и правила их получения. Кодировщики, бакеты, словари, BPE, token ID и Masker относятся к отдельному следующему заданию.

Общие правила: RAW неизменен; `truth/*` не читается; cutoff — исключительная граница; ничего не обучается на статистике данных; работа потоковая по row group; этап переиспользуется только при совпадении отпечатка.

**Отпечаток этапа** это sha256 от четырёх частей: фактические файлы входа (манифест и parquet, кроме `truth/*`, хэшируются на диске, а не берутся из манифеста), относящаяся к этапу секция конфига, реестры и `STAGE_VERSION` — версия реализации, которую поднимают при любой правке модулей этапа (тест сверяет её с sha256 исходников). Пропуск разрешён только когда совпал отпечаток **и** выходные файлы на месте и не изменились: удалённый или правленый отчёт восстанавливается. Запись этапа в `preprocessing_manifest.json` это тоже его результат — маркер хранит её целиком и возвращает на место, если общий манифест удалён или повреждён.

При запуске нескольких групп итоговый код возврата это самый тяжёлый вердикт, а не самый большой код: `blocked` (2) тяжелее, чем `contract_mismatch` (3).

> **Статус.** Реализованы все пять этапов. Следующее отдельное задание — токенизатор с fit на train.

> **Упаковка.** В wheel входят `src.generator.*` и `src.preprocessing.*` (включая `canonical` и `semantic`). Команды `mini-pragma-tokenize` и `mini-pragma-train` убраны: модули, на которые они ссылались, ждут переделки. `data/reference/home_product_timeline.yaml` в пакет **не входит** — генератор ищет его от корня репозитория, поэтому запускать его следует из рабочей копии.

## Этап 1. Паспорт входных данных

`passport.py` отвечает на вопрос «что пришло, за какой период и можно ли этому доверять», ничего не преобразуя.

- **Сверка с манифестом**: `schema_version = 5`, обязательные файлы, `file_sha256` (кроме `truth/*` — они только перечисляются), число строк, схемы конверта, профиля и покрытия, `content_sha256` по строкам тем же алгоритмом, что у генератора. Любое расхождение блокирует группу (`status = blocked`).
- **Обязательные поля конверта** (`event_id`, `client_id`, `event_type`, `source`, `event_time`, `event_version`, `is_test_account`) проверяются на null по всем строкам. Пустое значение здесь это структурная поломка, а не расхождение с каталогом: группа блокируется, и диагностический режим этого не снимает. Canonical повторяет ту же проверку до разбора и останавливается с названием поля и номером строки.
- **Payload по каталогу ключей** проверяется потоково на всех строках: отсутствующий необязательный ключ — допустимый пропуск; отсутствующий обязательный, лишний ключ, значение не того типа и тип события вне каталога — нарушения входного контракта.
- **Содержимое**: клиенты, события, диапазон `event_time`, источники, типы, конверт, версии и дубли, повторные пары `(event_id, event_version)`, тестовые аккаунты, профиль, покрытие, справочники.
- **Источник × месяц** с тремя разными клетками: месяц вне периода генерации, источник ещё не подключён, число событий (ноль — не ошибка). Отдельно считаются записи до `history_start` и записи с `event_time ≥ extract_time`.
- **Горизонт**: `history_start ≤ 2023-01-01`, `history_end` и `extract_time` не меньше конечного cutoff группы; базовые источники доступны с согласованного начала.

Три причины не смешиваются, и вердикт это самая тяжёлая из сработавших:

| статус | что произошло | код возврата |
|---|---|---|
| `ready` | данные пригодны целиком | 0 |
| `horizon_short` | наблюдение короче согласованного; данные честны, но период неполон | 0 |
| `contract_mismatch` | выгрузка расходится с собственным каталогом ключей | 3, с `--allow-contract-mismatch` 0 |
| `blocked` | структурная поломка: нет файла, не сошлись суммы или схема | 2 |

`ready` недостижим при нарушении контракта, даже когда горизонт станет полным: такие строки чинятся в генераторе. Флаг `--allow-contract-mismatch` — режим диагностики для разработки следующих этапов; статус в отчёте он не меняет.

Выход: `data/processed/<name>/passport/<group>.{json,md}`, отпечаток `stage_fingerprints/passport__<group>.json`, запись в `preprocessing_manifest.json`. Настройки — `src/preprocessing/settings.py` (`PreprocessingConfig`, переопределяется JSON через `--config`).

На текущем `data/raw/check` паспорт даёт `horizon_short`: нарушений контракта нет, а история начинается с 2024-06-01 вместо согласованного 2023-01-01. Это честное ограничение выгрузки, а не дефект препроцессинга. Прежний дефект `communication_sent.delivered` закрыт: поле объявлено `nullable`, и неизвестный результат доставки хранится как null.

## Этап 2. Структуризация в canonical

`canonical/` разбирает ленту в типизированные поля, сохраняя происхождение каждой строки. Ничего не выбрасывается и ничего не обучается: **одна строка RAW это одна строка canonical**.

- **Поля.** Физическое поле это пара «владелец, имя»: dtype одного имени совпадает во всех типах событий, а `nullable` и `level` расходятся (у заявки канал обязателен, у операции нет). Поэтому 872 физических поля укладываются в 72 типизированные колонки, а идентичность и правила живут в `field_registry.json` вместе с единицами, взятыми из описаний каталога генератора.
- **Версии.** Четыре случая различаются сравнением **внутри одного `event_id`**: исходная запись, исправление, техническая повторная доставка (та же версия, то же содержимое) и конфликт (та же версия, другое содержимое). Разные покупки на одинаковую сумму дублями не считаются никогда. `link_type` — деловая метка связи (меток доставки в конверте нет) и в сравнение входит: та же версия с другой меткой это конфликт. Журнал решений лежит в `dedupe_log.parquet`.
- **Место в истории.** События клиента упорядочены по времени, приоритету типа из манифеста и `event_id`; приоритет типа задаёт причинный порядок внутри одной секунды (договор открыт, затем график, затем выдача) и в данные не пишется. Все версии и дубли одного события делят **один** `stable_event_index`, поэтому исправление уточняет событие на его месте, а не переезжает в конец истории.
- **Роль версии.** Роль строки задаёт номер версии, а не место в ленте: версия 3 может стоять раньше версии 2. Какая версия действует, canonical не решает; это делает этап истории на дату.
- **Время.** Значения остаются наивными, как в выгрузке; часовой пояс контракта объявлен в конфиге, а не применён. `time_finer_than_precision` помечает записи, чьё время точнее объявленной источником точности; `ambiguous_local_time` — час, прожитый дважды при переходе Казахстана на UTC+5.
- **Пропуски.** Причина ставится только там, где она следует из датированного правила схемы (`manifest.schema_changes`), и попадает в `known_missing` строки. Остальные пропуски остаются без причины.
- **Сущности.** `entities/mentions.parquet` это наблюдаемые упоминания счетов, карт, договоров, заявок, обращений и предложений; переход жизненного цикла отмечается только там, где он определён типом события. `entities/transfers.parquet` хранит **только наблюдаемые стороны**: парности и контрагента там нет намеренно, потому что обе стороны поступают в разное время и на раннем cutoff встречная ещё неизвестна. Пару собирает этап истории среди видимых строк. Итогового состояния здесь нет.
- **Адрес клиента.** `client_index.parquet` даёт `row_group` с `row_offset` внутри него и отдельно `global_row_start` от начала файла: два разных числа, и путать их нельзя. Адрес проставляется по фактическим границам row group из метаданных записанного файла, а не по предположению о писателе.
- **Связи.** `link_report` в отчёте: разрешение `cause_event_id` с причинами нехватки, парность переводов, наличие наблюдаемого открытия у сущности, состав цепочек по `correlation_id`. Ничего не достраивается по догадке.
- **Целое.** Неразобранный payload остаётся строкой с причиной и попадает в `rejects.parquet`; `opening_state` сохраняется картой всех объявленных ключей (их форма зависит от источника) и остаётся заявленным состоянием, из которого не создаются ни счета, ни события; клиент без событий остаётся в `client_index.parquet` с нулём строк.

Выход: `data/processed/<name>/canonical/<group>/` — `events.parquet`, `profile.parquet`, `coverage.parquet`, `client_index.parquet`, `entities/`, `dedupe_log.parquet`, `rejects.parquet`, `field_registry.json`, `canonical_report.{json,md}`.

Этап опирается на вердикт паспорта, и вердикт обязан описывать те же файлы: перед сборкой сверяются отпечатки входов из маркера этапа 1 с фактическими файлами RAW. При расхождении этап требует повторного паспорта, при `blocked` не запускается, при `contract_mismatch` требует `--allow-contract-mismatch` и записывает `diagnostic_mode` в общий манифест.

На `data/raw/check`: 315 008 строк RAW в 315 008 строк canonical за 16 с, 1408 исправлений, 1469 повторных доставок, 0 конфликтов, 0 неразобранных, 466 006 упоминаний сущностей, 9580 сторон переводов.

## Этап 3. История на дату

`history.py` отвечает на один вопрос: какова финальная очищенная история событий клиента **строго до** момента cutoff. Это функция чтения, а не датасет: срезов она не назначает и ничего не материализует, кроме читаемых примеров и отчёта о правилах.

```python
store = CanonicalStore(Path("data/processed/check/canonical/train"))
history = history_as_of(store, "c444232900085", datetime(2026, 3, 1))
```

- **Граница исключительная.** Событие входит, только если произошло раньше cutoff. Запись ровно на границе ещё не известна. Cutoff за пределами выгрузки отвергается.
- **Действует наибольшая версия события.** У выгрузки одно время записи — время события, поэтому исправление видно вместе с самим событием, а не «приходит позже»: прошлое в одной выгрузке неизменно от среза к срезу, меняться оно может только между выгрузками. Повторная доставка второго действия не создаёт. Исправление уточняет событие **на его месте**, потому что порядок задан временем бизнеса и местом первой версии. Две строки одной версии с разным содержимым это конфликт: действует первая в ленте, остальные считаются и попадают в ограничения.
- **Знание из будущего закрыто тремя способами.** Служебные поля выбора версии (`same_version_row`, `is_exact_duplicate`) наружу не выходят — снимает их единственная функция, через которую проходит и пустой набор. Недатированные статусы покрытия в состояние на дату не входят. Встречная сторона перевода видна только после своего `event_time`.
- **Профиль**: `valid_from < cutoff`, последняя по `(valid_from, profile_version)`; `valid_to` не фильтрует и дыр не создаёт.
- **Состояния** счетов, карт, договоров, заявок и обращений собираются из известных переходов, а переход вступает в силу по `effective_at`: заранее объявленное изменение попадает в «ещё не в силе», а не в состояние.
- **Покрытие** выводится только из датированных полей: запуск источника, первое появление клиента, объявленный конец. Причины без даты (`no_consent`, `client_not_onboarded`, `source_outage`) остаются в ограничениях.
- **Отношения**: наблюдаемое начало, длительность и признак неполноты, если наблюдение упирается в границу выгрузки, `opening_state` объявляет прежние договоры или профиль заявляет больше месяцев, чем видно.
- **Справочник продуктов** присоединяется по версии, названной самим событием, и только если она уже известна к cutoff. Событие не размножается.

Выход: `data/processed/<name>/history/<group>/temporal_report.{json,md}` и читаемые примеры `examples/<client>__<date>.md`.

`temporal_report` проверяет не данные, а правила: внутри среза (нет будущего, одна версия на событие, порядок не ломается, служебные поля скрыты) и между срезами (набор известных событий только растёт, версия только повышается, **содержимое уже известной версии не меняется** от появления новых записей). На `data/raw/check`: 25 клиентов на шести срезах, 0 нарушений.

Показательный пример: у клиента `c444232900085` на срезе 1 марта 2024 года видно одно событие и нет ни одной версии профиля, на срезе 1 ноября 2024 года — уже 95 событий, профиль и шесть сущностей. Наблюдение начинается не с начала окна, а с того момента, когда источники о клиенте заговорили.

## Этап 4. Разделение train / validation / test

`split.py` ничего не делит: клиенты уже разведены по трём независимым выгрузкам. Этап закрепляет состав групп, проверяет их независимость и называет то единственное, что разрешено видеть будущему fit.

| Группа | Окно истории | Период будущих целей MLM | Конечный cutoff |
|---|---|---|---|
| train | с 2023-01-01 | 2023-01-01 — 2025-12 | 2026-01-01 |
| validation | с 2023-01-01 | 2026-01 — 2026-05 | 2026-06-01 |
| test | с 2023-01-01 | 2026-06 — 2026-08 | 2026-09-01 |

Начало включительно, конечный cutoff исключительно. История конкретного клиента короче, если он появился позже.

- **Независимость популяций**: свой seed у каждой группы и ни одного общего `client_id`. Общий клиент это не ограничение, а поломка: статус `blocked`, разрешённый корпус не выдаётся вовсе.
- **Общий мир**: содержимое справочников продуктов, мерчантов и географии, продуктовая хронология и конфигурация генерации. Манифест генератора подписывает только ленту, профиль и покрытие, поэтому равенство справочников считается по самим файлам, а не берётся на слово. Расхождение это свойство входа, а не ошибка этапа: статус `blocked_by_input`, артефакты пишутся как диагностика, `usable = false`, код возврата 3 (с `--allow-input-mismatch` — 0). Отсутствие `world_seed` само по себе мир не разводит: если всё перечисленное совпало, мир общий, а неподтверждённое происхождение остаётся ограничением.
- **Разрешённый train-интерфейс**: события train, видимые на `fit_end = 2026-01-01` через `history_as_of`, без технических повторных доставок и тестовых аккаунтов, вместе с профилем и покрытием на ту же дату. Материализуется индексом `train_corpus_index.parquet` (`client_idx`, `stable_event_index`, `event_time`, `mlm_target_eligible`), а не копией данных. Второй реализации видимости здесь нет: «разрешено» значит ровно то же, что и в истории на дату.
- **Границу держит сам интерфейс, а не дисциплина вызывающего.** `TrainCorpus.open` отказывается открывать непригодное разделение, берёт `fit_end` из манифеста, а не из переданного конфига, и сверяет отпечаток canonical с тем, на котором разделение построено. `TrainCorpus.history` выдаёт историю только по клиентам разрешённой группы: исключённый тестовый аккаунт, клиент другой группы и неизвестный идентификатор отвергаются. Для диагностики есть явный `allow_unusable=True`, обучение открывает корпус без него.
- **Контрольная сумма train-содержимого** считается по финальной очищенной истории событий до `fit_end`: конверт и payload видимых строк, версии профиля с `valid_from < fit_end`, датированные факты покрытия. Служебные индексы, флаги, `valid_to` и итоговые статусы покрытия в неё не входят, поэтому пересборка слоёв её не меняет, а правка значения видимой строки — меняет. Замена validation и test другими выгрузками на train-содержимое не влияет.
- **`mlm_target_eligible`** это только признак периода. Выбор масок и окончательная допустимость цели для конкретного Masker решаются не здесь.
- **Исключения**: тестовый аккаунт остаётся в canonical и в списке исключённых, но в рабочую группу не входит. Клиент без событий из группы не убирается: молчание это факт, а не причина удалить человека.

- **Два вердикта, а не один.** `usable` это ТЕХНИЧЕСКАЯ исправность: файлы целы, группы независимы, мир общий. `contract_met` это выполнение договорённости о горизонте наблюдения: история каждой группы начинается не позже `required_history_start`, и паспорт не назвал горизонт коротким. Разделение бывает исправным и при этом не выполняющим договорённость; молча принимать это нельзя, поэтому `TrainCorpus.open` отказывается открывать такой корпус без явного `allow_short_horizon=True`. На текущих 30-клиентских наборах короткий горизонт ожидаем: генератор начинает историю с 2024-06-01, а договорённость требует 2023-01-01, и продление генератора оформляется отдельной задачей.

- **Корпус сверяет файлы, а не только отпечаток.** При открытии `TrainCorpus` проверяет sha256 фактических файлов `canonical_dir` против выходов маркера canonical. Отпечаток подтверждает согласие маркера с манифестом и остаётся прежним, если файл правили на месте. Так же сверяется sha256 файла `train_corpus_index.parquet` с манифестом разделения: индекс с тем же числом строк, но правленым `mlm_target_eligible`, не открывается.

Выход: `data/processed/<name>/split/{split_manifest.json, train_corpus_index.parquet, split_report.md}`.

Проверено на трёх маленьких выгрузках `data/raw/split3` (по 40 клиентов, популяции 101, 202 и 303 при общем `world_seed = 42`): клиенты не пересекаются, справочники продуктов, мерчантов и географии у групп совпадают, происхождение мира подтверждено. Статус `ok`, набор пригоден.

## Этап 5. Смысловой слой

`semantic/` объясняет, что значит каждое поле, и считает признаки банковской жизни на заданную дату. Единственный интерфейс — `semantic_as_of(client_id, cutoff)` поверх истории на дату.

- **Таблица «физическое поле → semantic key»** это данные, а не алгоритм: 147 ключей, у каждого вид значения, единица, описание и, если он расчётный, список слагаемых `derived_from`. Разделяет смыслы источник события: `channel` у операции это pos, ecom, atm, а у коммуникации call, sms, push — разные множества значений, значит разные ключи. Одинаковый смысл из разных источников объединяется только явным списком с причиной.
- **Видов значения ровно три**: `numeric`, `categorical`, `text`. Отдельного вида «дата» нет: календарь дат словарём не кодируется, поэтому плановая дата платежа остаётся в canonical, а модель получает `days_to_due`. `reference` это не четвёртый вид, а отдельная роль локальной ссылки.
- **Расчётные признаки объявлены такими же ключами, как физические поля.** Отношения к доходу, лимиту, остатку и прошлому клиенту, интервалы между событиями и признаки связи лежат в реестре с единицей и происхождением: иначе следующий этап не знал бы, чем их кодировать и вместе с чем маскировать. Проверка реестра смотрит всё, что событие отдаёт модели, а не только значения payload.
- **Цифровые коды это категории.** MCC, версия продукта и версия тарифа не числа: величиной они не являются, и складывать их бессмысленно.
- **Спорные объединения перечислены.** Сумма проводки, лимит договора, одобренная сумма и плановый платёж лежат в тенге, но это разные показатели. Продукт, семейство продуктов и текст оффера не смешиваются.
- **Значения остаются исходными**: 12 500 это 12 500, «Europharma» это текст. Ни квантилей, ни нормализации, ни корзин здесь нет — это работа токенизатора и только на train.
- **Отношения и отклонения** считаются к заявленному доходу, к наблюдаемому лимиту и к остатку счёта. Неизвестный или нулевой знаменатель это причина, а не ноль: `income_unknown`, `limit_unknown`, `no_visible_past`, `zero_denominator`. У каждого расчёта есть происхождение: событие, версия профиля, строка справочника.
- **Расшифровка точки** по справочнику мерчантов добавляет сектор, категорию, подкатегорию, бренд, район, канал и ценовой сегмент. Точка вне справочника ничего не выдумывает: остаётся причина `merchant_unknown`. Частотных порогов здесь нет.
- **Расшифровка продукта** по справочнику продуктов даёт `product_name` той версии условий, которую называет само событие, и название с семейством прежнего продукта при переходе. Версии, неизвестной справочнику к cutoff, название не придумывается: остаётся код и семейство.
- **Изменение профиля разбирается по изменившемуся полю.** `old_value` и `new_value` не общий текст: доход становится `profile_declared_income_old/new` в тенге, город — категорией `profile_city_new`, число детей — числом. Незнакомое `field_name` останавливает слой, а не превращается в текст.
- **Активность по месяцам** различает четыре случая: клиент действовал, записи есть без действий клиента, записей нет при наблюдавшихся источниках, и наблюдения не хватает. Пустой месяц сам по себе неактивностью не становится: доказать молчание можно только по источникам, которые вообще записывают действия клиента, то есть по операциям, приложению и заявкам. Месяц, начинающийся ровно в cutoff, не прожит и в счёт не идёт. Месяц покрыт, только если покрыт его последний день: источник, кончившийся в середине месяца, молчания второй половины не доказывает.
- **Цепочки** строятся по видимым шагам: заявка, решение, договор, платежи, обращения, переводы и возвраты. Конца нет — исход `in_progress`, и выдумывать его нельзя. Вместо сырого `cause_event_id` наружу идут смысловые признаки связи, и они прикреплены к самому событию-следствию: `related_event_type`, `relation_type`, `days_since_related_event`, `same_merchant`. Связь адресуется внутренним `stable_event_index`, который границу модели не пересекает.
- **Причина не происходит после следствия.** Отрицательный интервал признаком не становится: если его объясняет объявленная точность источника, длительность не передаётся вовсе, а причина названа (`time_order_ambiguous`); сама связь, её тип и вид остаются. Наблюдение при этом не обнуляется и не переворачивается — оно сохраняется рядом как объяснение. Если обе записи объявлены точными, отрицательная причинность это противоречие данных, и этап отказывается работать.
- **Интервалы считаются в объявленной точности.** У записи дневной точности час и минута не наблюдались, что бы ни стояло в поле времени: её интервалы до прошлого события, до события того же типа и до последнего дохода, возраст истории и дни до платежа считаются по датам и кратны суткам. У пары событий действует более грубая точность из двух; признак связи `days_since_related_event` считается так же, а сырое наблюдение остаётся рядом как объяснение. Само время в canonical не округляется: `time_finer_than_precision` остаётся признаком качества.
- **Календарь не дублируется**: шесть чисел берутся из общего временного канала и в смысловые значения не входят.

Выход: `semantic_registry.json`, `semantic_report.md`, читаемый пример клиента и две диагностические таблицы `activity_months__<cutoff>.parquet` и `chains__<cutoff>.parquet`. Срез назван прямо в имени файла: таблица позднего среза входом раннего не является.

Значение под ключом, которого нет в реестре, останавливает этап: смысл обязан быть объявлен заранее.

## Модельная проекция

`projection.py` — граница между данными и моделью. Всё, что выше, служит очистке: версии, дубли, конфликты, порядок, связи, трассировка к RAW. Ниже этой границы модель видит только банковский смысл.

| поле | смысл |
|---|---|
| `client_id` | чей это факт |
| `event_time` | когда произошло |
| `source` | какая система записала |
| `fields` | смысловые банковские значения |

`event_type` лежит **внутри** `fields` как смысловое поле и в проекции больше нигде не дублируется.

- **Список позитивный.** В модель проходит только явно названное поле: 59 смысловых имён payload из 72, каждое с причиной в реестре. Подход «всё, кроме нескольких исключений» запрещён, иначе новое поле выгрузки попало бы в модель само собой.
- **Сырых идентификаторов наружу не выходит.** Сущности клиента получают локальные ссылки: `account_ref = ACCOUNT_1`, `card_ref = CARD_1`, `contract_ref = CONTRACT_1`, и так же `application_ref`, `case_ref`, `offer_ref`, `merchant_ref`, `outlet_ref`. Номер выдаётся по первому появлению сущности в истории клиента, один идентификатор всегда получает одну ссылку, а между клиентами такие ссылки не значат ничего. Тип договора в ссылку не зашит: его несут `product_code` и `product_family`.
- **Внутри canonical остаются** `event_id`, `event_version`, `correlation_id`, `link_type`, `is_test_account`, `effective_at`, `time_precision`, `stable_event_index`, `client_idx`, `version_role`, `same_version_row`, `is_exact_duplicate`, `before_window`, `at_or_after_extract`, `time_finer_than_precision`, `ambiguous_local_time`, `payload_status`, `payload_violations`, `known_missing`, нормализованные копии текста, трассировка к RAW, а из payload — `product_id`, `previous_product_id`, `cause_event_id`, `timestamp_quality` и `due_date` (модель получает число дней до платежа, а не саму дату).
- **Технические поля никогда не входят в словари и токены.** Они не становятся semantic keys, не попадают в `key_vocab` и `value_vocab`, не маскируются и не доходят до Transformer.
- **`change_initiator`** попадает в `fields` только у типов событий, где различие «клиент, банк, система» несёт банковский смысл: блокировка и разблокировка карты, закрытие договора, изменение условий, реструктуризация, обращения, коммуникации, решение по мошенничеству, изменение профиля.
- **Этап 5 добавляет** к строке то, что выводится из справочника, связи или расчёта: название продукта, расшифровку точки, признаки связи вместо `cause_event_id`, `days_to_due` вместо плановой даты, интервалы между событиями и отношения суммы. Проекция пропускает только то, что лежит в самой строке, поэтому полный список добавленного объявлен рядом с ней в `SEMANTIC_LAYER_FIELDS`.

Судьба каждого поля видна в одном месте: `field_registry.json` несёт `model_role` у каждой записи и блок `model_projection` со списками, причинами и счётчиками. Незнакомое имя payload останавливает сборку: поле обязано быть названо смысловым, ссылкой или внутренним.

### Календарь

Календарь это **отдельный временной канал** модели, а не поле события. Относительное время выражает возраст записи и расстояние между записями, но не выражает периодов: зарплата приходит в свой день месяца, платежи по счетам в свой, сессии приложения в свои часы.

Из `event_time` и только из него считаются шесть чисел на событие: синус и косинус часа суток, дня недели и дня месяца. Час дробный, поэтому 09:00 и 09:30 это разные моменты суток. Понедельник начинает недельный цикл, первое число начинает месячный. Реализация одна, `preprocessing/calendar.py`.

- **В данных календаря нет.** Ни RAW, ни canonical не хранят час, день недели и день месяца: два источника правды о времени события не нужны. Полей `hour` и `day_of_week` больше нет и в payload коммуникаций: они удалены из каталога ключей генератора и из места создания события.
- **Календарь не становится токеном.** Он не входит в `key_vocab` и `value_vocab`, не проходит BPE, не бакетизируется как обычное число, не маскируется и не предсказывается. В модель он приходит отдельным числовым входом через небольшой слой.
- **Правила объявлены в конфигурации**: часовой пояс `Asia/Almaty`, длины циклов 24, 7 и 31, начало недели, нумерация дня месяца с нуля и порядок колонок. Они входят в секцию конфига этапа canonical, а значит в его отпечаток и в манифест: смена пояса или длины цикла требует пересборки.
- **Время в выгрузке наивное** и записано в поясе контракта, поэтому час суток берётся из значения как есть. Часовой пояс объявлен, а не применён повторно.
- **Цена одного фиксированного цикла**: месяц кодируется длиной 31, поэтому 31 января и 1 февраля стоят ровно на суточном шаге, а у коротких месяцев стык шире (у февраля — четыре шага). Это осознанное упрощение единого цикла, а не ошибка.

Событие без `event_time` до календаря не доходит: паспорт блокирует такую выгрузку, canonical останавливается с названием поля и номером строки, а сам расчёт отказывается считать пустое время.

**Правило точности времени для следующего этапа.** `time_precision` токеном не становится и в словари не попадает: это внутренний признак достоверности времени. Но игнорировать его нельзя — у события с дневной точностью час суток не наблюдался, и считать его точным при подготовке модельного входа запрещено. Смысловой слой уже пользуется этим правилом: порядок двух записей внутри разрешения источника считается неизвестным. Сам календарь при этом не меняется.

> **Что проверено, а что нет.** Проверена сама календарная математика: границы суток, недели и месяца на маленьких примерах. Сквозное подключение к модели **не проверено**: `src/model/time_features.py` пока не импортируется из-за старой цепочки `src/tokenizer` на прежний контракт препроцессинга. Модель берёт реализацию из `preprocessing/calendar.py`, но проверить это можно будет только на этапе нового токенизатора.

Словари, бакеты, BPE, Masker и токенизация здесь не начинаются: этап только называет границу.

Девять модулей прежнего препроцессинга — `config.py`, `raw.py`, `validate.py`, `build.py`, `fit.py`, `cutoffs.py`, `splits.py`, `stats.py`, `buckets.py` — **удалены**: они описывали контракт RAW v3 и не вызывались ни из генератора, ни из пяти этапов. Вместе с ними убран `artifacts.render_validation_md`; `artifacts.TableWriter` остался, его использует canonical. `src/tokenizer` и `src/model` их импортировали и в текущем виде не работают: оба ждут собственной переделки под новую ленту. Правками 19.09 они не затронуты; единственное изменение в `src/model` — `time_features.py` от 18.09, когда календарь переехал в `preprocessing/calendar.py` (см. выше).

# Tokenizer

> Раздел описывает прежний контракт RAW и **ожидает переделки** под новую ленту генератора.

Структурированные события → словарь → token ID → контракт входа для модели.

```powershell
venv\Scripts\python -m src.tokenizer.run --name smoke
```

## Две сущности: поле и токен

Это центральное различие, и путать их нельзя.

| Сущность | Что это | Кто пользуется |
|---|---|---|
| **`field_id`** | идентичность физического поля, индекс в реестре preprocessing | маскирование, кандидаты MLM, корзины, unigram, все пофилдовые отчёты |
| **`token_id`** | идентификатор токена в словаре | только таблица эмбеддингов |

`field_id` одинаков во всех режимах словаря. `token_id` зависит от режима. Благодаря этому склейка словаря меняет представление, но **не меняет задачу**: множество замаскированных позиций и локальные цели совпадают побайтово.

Специальные позиции (`[EVT]`, `[USR]`) получают сентинел `NO_FIELD`; все индексируемые по полю массивы имеют длину `n_fields + 1`, и ни один `-1` никуда не уезжает.

## Пространство ID

```
[0, 6)                 [PAD], [UNK], [MASK], [EVT], [USR], [MISSING]
[6, 6 + n_key_tokens)  токены ключей
[6 + n_key_tokens, …)  токены значений
```

Порядок выдачи значений: обход полей в порядке реестра, значения внутри поля в типизированном порядке (numeric — по номеру корзины). Локальный индекс кандидата это позиция в типизированном порядке **своего поля**, поэтому у numeric он равен номеру корзины — на этом держится совпадение с unigram-baseline.

Словарь учится **только на train**. На evaluation он заморожен: неизвестное значение это `[UNK]`, явный пропуск это `[MISSING]`, новых токенов словарь не заводит.

## Событие

```
позиция 0   [EVT]                      одинаковый ID в key_ids и в value_ids
позиция 1   timeline__event_type
позиция 2+  поля payload в порядке реестра
```

Профиль кодируется теми же правилами, но отдельно и начинается с `[USR]`: 21 токен. Позиция считается **внутри записи** и сбрасывается на каждом событии.

## Хранение

```
data/tokenized/<name>/
  tokenized_manifest.json             версия формата и sha256 tokenizer_config
  clients/{train,val,test}_clients/
      events.parquet                  client_id, seq, ts, event_type, n_tokens,
                                      key_ids, value_ids, positions, field_ids
      profile.parquet                 то же для снимка профиля
  {train,val_client,test_client,val_time,test_time}/examples.parquet
data/artifacts/<name>/tokenizer/
  special_tokens.json  key_vocab.json  value_vocab.json  field_value_ids.json
  tokenizer_config.json  tokenizer_stats.json  golden_examples.json
```

`tokenizer_config.json` хранит версию формата, special ID, режимы словаря, правила порядка, отпечаток реестра склейки и sha256 тех artifacts preprocessing, на которых обучался словарь. При загрузке хэши пересчитываются, несовпадение это ошибка, а не предупреждение.

## Runtime masking

Сохранённые датасеты содержат исходные ID: `[MASK]` в них не встречается. Masker работает с копией и своим seed, входные массивы не меняются.

Маскируются только известные непустые значения полей с `predictable=true`. Специальные токены, `[UNK]`, `[MISSING]`, metadata и весь профиль не маскируются никогда. Заменяется только `value_id`; ключи, позиции и время остаются на месте.

| Режим | Что выбирается |
|---|---|
| `token` | каждая доступная позиция независимо |
| `key` | поле внутри примера, маскируются все его доступные значения |
| `event` | событие, маскируются все его доступные значения |
| `field_balanced` | бюджет масок распределяется между полями поровну |
| `combined` | объединение первых трёх, пересечения считаются один раз |

Ожидаемая доля скрытых значений у `combined`: `1 − (1−token_rate)(1−event_rate)(1−key_rate)`.

**Маска привязана к примеру.** Поток случайных чисел засевается парой `(client_id, cutoff)`, поэтому маска не зависит ни от состава batch, ни от места примера в нём. Без этого нельзя ни менять `eval_batch_size`, ни собирать validation потоком.

Target это исходный `value_id`, вне масок `-100`.

## Field-restricted prediction

`field_value_ids.json` даёт для каждого поля список допустимых value ID в типизированном порядке. Special-токены в кандидаты не входят. `CandidateIndex` переводит глобальный ID в локальный индекс поля и обратно через плотную таблицу `local_lookup[n_fields + 1, size]`, где `-1` означает «не кандидат этого поля». Softmax по всему словарю не считается.

## Режимы словаря

Незаконченный эксперимент: влияет ли склейка семантически одинаковых ключей и значений на качество.

| `--key-mode` | Что склеивается |
|---|---|
| `namespaced` | ничего, каждое физическое поле несёт свой key token |
| `semantic` | поля одной семантической группы делят key token (`profile__declared_income` ≡ `profile_snapshot__declared_income` и ещё девять групп) |

| `--categorical-value-mode` | Что склеивается |
|---|---|
| `field_specific` | ничего, `true` у `is_online` и `true` у `delivered` это разные токены |
| `shared` | строки и булевы с одинаковым значением делят value token |

Реестр склейки лежит в `src/tokenizer/semantics.py` и объявлен **явно**: рядом с группами перечислены `AMBIGUOUS_KEYS` — пары, которые похожи, но не склеиваются, с причиной. Numeric-корзины и int-коды не склеиваются никогда: `age_B7` и `amount_B7` это разные величины, а `day_of_week = 1` и `children = 1` разные коды.

Склеенный словарь обязан жить в своём каталоге:

```powershell
venv\Scripts\python -m src.tokenizer.run --name smoke --vocab-tag semkeys `
    --key-mode semantic --categorical-value-mode field_specific
```

`--fit-only --all-modes` считает счётчики за один проход по train и собирает все четыре словаря, не материализуя датасеты: так узнают реальные размеры.

# Модель

> Раздел описывает прежний контракт RAW и **ожидает переделки** под новую ленту генератора.

Три уровня, один проход:

```
поля события      → Event Encoder    → вектор события
снимок профиля    → Profile Encoder  → вектор клиента
профиль и события → History Encoder  → вектор клиента
```

## Embeddings

Одна таблица на всё пространство ID: `E(key) + E(value)·[key ≠ value] + P(позиция)`. Зоны ключей и значений не пересекаются. У специальной позиции `key_id == value_id`, и слагаемое значения не добавляется дважды.

Таблица токенов разыгрывается **своим** генератором, засеянным `seed ^ VOCAB_SEED_SALT`, и глобальный поток не расходует. Поэтому размер словаря не сдвигает инициализацию Transformer, History Encoder и MLM-головы: при одном seed все не-словарные веса совпадают побайтово во всех режимах словаря.

## Время в истории

Время живёт **во внимании**, а не в векторе события. `q` и `k` поворачиваются на угол, пропорциональный `squash(часы до последнего элемента истории)`; разность углов пары и есть их относительное время. К вектору элемента не прибавляется ничего, синусоиды абсолютной позиции нет.

Причина измерена: у прежнего аддитивного кодирования норма временного слагаемого была 26 (сутки) … 143 (два года) против нормы вектора события 9 — содержание события становилось малой добавкой к направлению «возраст».

Что относительные координаты не выражают, приходит отдельными признаками:

- **календарь события** (час, день недели, день месяца — синус и косинус) прибавляется к вектору события;
- **простой клиента** (часы от последнего события до cutoff) приписывается профилю: координата последнего элемента равна нулю, и сама история не знает, когда она кончилась.

Оба признака идут через `FeatureMLP`, чей выходной слой инициализирован **нулём**: на шаге 0 вход History Encoder это чистый вектор события, а масштаб слагаемого модель выбирает сама. Следствие при чтении градиентов: на первом шаге градиент скрытого слоя равен нулю — это ожидаемо и не означает оборванного графа.

У History Encoder слои свои (`rotary.py`): собственный forward поверх `scaled_dot_product_attention`. Это не только про время, но и про память: fast path `nn.TransformerEncoderLayer` материализует полную матрицу внимания, и на истории в 3637 событий это 3.2 ГБ вместо 47 МБ.

## MLM head

Представление замаскированной позиции:

```
h_local   состояние позиции после Event Encoder
h_event   вектор события после History Encoder
h_usr     вектор клиента

concat → Linear(3d, d) → GELU → LayerNorm → голова своего поля
```

Все три состояния берутся из **одного** прохода: `Backbone.forward` принимает `gather` из пар «строка события, позиция токена». Повторный запуск Event Encoder считал бы другое: маска и dropout у него свои.

У каждого predictable-поля хотя бы с двумя кандидатами своя `Linear(d, n_candidates)`. Головы ключуются `field_id`, а не токеном словаря, поэтому во всех режимах словаря их набор и размеры одинаковы. Поле с одним кандидатом помечается `degenerate` и в loss не входит.

## Loss

```
field_loss     = mean(CE по позициям поля)
field_balanced = mean(field_loss по полям batch)     основной
token_weighted = Σ field_loss·n / Σ n                рядом, для сравнения
```

Позиций у `transaction__mcc` на три порядка больше, чем у `product_event__term`, и взвешивание по токенам превратило бы обучение в обучение одному полю. CE всегда в float32.

Batch без целей не шаг: backward, optimizer и scheduler пропускаются, причина пишется в лог. Подряд идущие пропуски ограничены `max_consecutive_skips`.

## Состав целей

`--target-policy history` убирает из задачи `timeline__event_type` (он восстанавливается из состава самого события) и `profile_snapshot__*` (они дублируют as-of профиль, который модель видит позицией 0). Убирает **целиком**: значения остаются входом, маски на них не ставятся. Исключение задаётся паттернами имён, потому что `MaskingConfig` уезжает в checkpoint и восстанавливается там, где словаря нет.

## Срез обучения

Обучающий сплит берёт **по одному примеру на клиента** — самый поздний cutoff. Оценочные сплиты берут все срезы: `val_time` и `test_time` и так по одному примеру на клиента, а `val_client` обязан остаться полной линейкой.

## Оценка

Validation фиксируется целиком до первого шага: клиенты, порядок, состав batch, обрезка и маски со своим seed. Набор сверяется по sha256 от целей при загрузке checkpoint.

Записываются **два** отпечатка набора:

| отпечаток | по чему | зачем |
|---|---|---|
| `targets_sha256` | `flat \| key_ids \| global_targets` | зависит от словаря, сверка внутри одного режима |
| `targets_field_sha256` | `flat \| field_ids \| local_targets` | инвариант: одинаков во всех режимах словаря |

Второй и доказывает, что две арки решают одну задачу.

По каждому полю считаются число целей, число кандидатов и классов с поддержкой, CE модели и unigram, NCE gain, accuracy обеих, macro F1 и top-K.

```
CE_unigram = mean(−ln p_train(target))
NCE_gain   = (CE_unigram − CE_model) / CE_unigram
```

Unigram берётся только из `unigram_baselines.json` preprocessing и по оцениваемым данным не пересчитывается.

**Метрика нового месяца.** В полной истории свежих событий единицы процентов, и улучшение на них растворяется. Каждая цель помечается флагом `recent`, и оценка ведёт два счёта по одним и тем же маскам: полный и по свежим целям. `--best-metric recent` выбирает `best.pt` по нему.

`--final-splits test_client,test_time` оценивает лучшие веса на этих наборах **один раз, после обучения**.

**Потоковая validation** (`--stream-validation`) хранит не batch'и, а рецепт: они пересобираются на каждую оценку и получаются теми же самыми, потому что маска привязана к примеру.

## Checkpoints

Сохраняются backbone и голова, optimizer и scheduler, счётчики, config, генераторы Python, NumPy и torch, состояние sampler, хэши artifacts и описание фиксированной validation. При загрузке всё это сверяется ключ в ключ: любое расхождение это другое окружение, и продолжать в нём нельзя.

## Сравнение двух арок

`train compare` берёт два checkpoint и считает их на **одних** примерах, масках и целях, с парным bootstrap по примерам. Малая разница без интервала результатом не считается.

CE разных режимов маскирования между собой не сравнивается: скрыть одно значение и скрыть событие целиком это разные задачи. Сравниваются два checkpoint внутри одного режима.

Если арки живут в разных словарях, строятся два набора splits, по одному на свой словарь, а равенство задачи доказывается совпадением `targets_field_sha256`.

# Запуск обучения

> Раздел описывает прежний контракт RAW и **ожидает переделки** под новую ленту генератора.

Обучение идёт отдельным локальным процессом: ни интернет, ни открытая сессия не нужны.

```powershell
.\scripts\epoch.ps1 start                      # пресет main
.\scripts\epoch.ps1 status
.\scripts\epoch.ps1 logs -Lines 40
.\scripts\epoch.ps1 stop
.\scripts\epoch.ps1 resume
.\scripts\epoch.ps1 resume-interrupted
.\scripts\epoch.ps1 check
```

Два каталога, и это важно:

```
run\       каталог модели: его заводит сам trainer и отказывается
           работать, если он не пуст. Launcher в него ничего не пишет.
control\   файлы запуска: перенаправленный вывод и PID.
```

Пресеты различаются **только** словарём и каталогом вывода:

| Пресет | Словарь |
|---|---|
| `main` | без тега: `namespaced` + `field_specific` |
| `vocab-semkeys` | семантически одинаковые поля делят key token |
| `vocab-shared` | одинаковые строки и булевы делят value token |
| `vocab-semkeys-shared` | и то и другое |
| `smoke` | проверка самого launcher: крошечный набор, CPU |

Всё остальное — данные, срез обучения, маски, seed, optimizer, расписание, эпохи и валидация — совпадает, иначе сравнение мерило бы не словарь.

Конфигурация запуска:

| Параметр | Значение |
|---|---|
| d_model / FFN / heads | 128 / 512 / 4 |
| слои Profile/Event/History | 1 / 3 / 2 |
| max_events_per_history | none (+ preflight) |
| masking | combined 0.15 / 0.10 / 0.10 |
| target_policy | history |
| бюджет | 3 эпохи |
| validation | потоковая, best по `val_time.recent` |
| финал | `test_client`, `test_time`, один раз |

`none` это значение, а не отсутствие значения: у обрезки истории и у числа клиентов `None` это собственная ветка кода.
