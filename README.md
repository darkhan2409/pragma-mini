# mini-PRAGMA v2

Синтетический генератор истории банковских клиентов и модель поверх него. Генератор повторяет **структуру, причинность и типичные дефекты реальных данных Home Credit Bank Kazakhstan**, чтобы препроцессинг и модель писались на синтетике и переключались на реальные данные без смены архитектуры.

Порядок порождения идёт от причины к следствию, а не наоборот:

```
Скрытая жизнь клиента        черты, домохозяйство, работа, доход, жизненные события
   ↓
Финансовое и продуктовое     остатки, договоры, графики платежей, карты, депозиты
состояние
   ↓
Потребности и решения        траты, переводы, заявки, реакция на предложения, стресс
   ↓
События, наблюдаемые банком  11 источников, конверт, дефекты наблюдаемости
   ↓
Полный RAW                   единая лента событий + профиль + каталоги + скрытая истина
```

Событие не разыгрывается само по себе. Оно следует из возраста и этапа жизни, семьи, города, работы и дохода, бюджета и долговой нагрузки, уже открытых продуктов, предыдущих событий, времени суток, дня недели, сезона и праздников, устойчивых привычек, жизненных изменений и текущего режима активности.

> **Статус.** Переделан только генератор. Препроцессинг, токенизатор и модель читают прежний контракт RAW и **ожидают переделки**: их разделы ниже описывают то, что было, и пока не соответствуют новому выходу генератора.

## Быстрый старт

```powershell
venv\Scripts\pip install -e .[dev]

# данные
venv\Scripts\python -m src.generator.emit --clients 300 --out data/raw/check --seed 42

# отчёт реализма, истории клиентов, аудит proxy-утечек
venv\Scripts\python -m src.generator.report.realism --raw data/raw/check

# лента одного клиента глазами
venv\Scripts\python -m src.generator.report.show --raw data/raw/check --truth

# тесты генератора
venv\Scripts\python -m pytest tests/test_gen_smoke.py tests/test_gen_scenarios.py tests/test_gen_products.py -q
```

Пресеты: `smoke` 100, `check` 300, `dev` 10 000, `eval` 50 000 клиентов. `--clients N` задаёт произвольный размер, `--workers` — число процессов, `--chunk-clients` — размер пачки, `--community-size` — размер сообщества, `--catalog-scale` — масштаб каталога мерчантов, `--params` — JSON с переопределениями параметров, `--resume` — продолжение по недописанным сообществам.

## Раскладка

```
data/raw/<name>/
  manifest.json              seed, горизонт, параметры и их sha256, sha256 хронологии продуктов,

  events.parquet             ЕДИНАЯ ЛЕНТА: конверт из 15 колонок + payload JSON
  profile.parquet            версионный профиль SCD2
  source_coverage.parquet    доступность источника клиенту и состояние на начало окна
  catalog/products.parquet   продуктовый каталог во времени
  catalog/merchants.parquet  сети, точки, MCC, зоны

```

Типизированных таблиц по источникам нет. Всё наблюдаемое живёт в одной ленте; чем именно является запись, говорят `event_type` и `source`, а состав payload описан каталогом ключей в манифесте.

## Конверт события

| Поле | Смысл |
|---|---|
| `event_id` | тождество события; исправление сохраняет его |
| `client_id` | непрозрачный идентификатор, выведенный из seed и порядкового номера |
| `event_type` | что произошло |
| `source` | система, которая это записала |
| `event_time` | когда произошло |
| `record_time` | когда попало в хранилище |
| `effective_at` | с какого момента действует, если это не момент записи |
| `time_precision` | `second`, `minute` или `day` |
| `sequence_number` | плотный номер в ленте клиента, только для tie-break |
| `event_version` | 1 у оригинала, +1 у каждого исправления |
| `change_initiator` | `client`, `bank`, `system`, `external` |
| `correlation_id` | цепочка: заявка, договор, перевод, кейс |
| `link_type` | чем именно связано |
| `is_test_account` | техническая учётная запись |
| `payload` | JSON с полями конкретного типа события |

**Исправление** несёт тот же `event_id`, версию на единицу больше и новый `record_time`. **Дубль** несёт ту же версию и второй `record_time`. Возврат, отмена и chargeback ссылаются на исходную операцию через `cause_event_id` в payload.

**Читать нужно последнюю версию записи.** Ошибку делает витрина: первая версия уходит с опечаткой в одном из объявленных полей, а исправление возвращает настоящее значение. Поэтому именно последняя версия сходится с проводками и остатками, а первая намеренно с ними расходится. Исправление меняет только объявленные поля и никогда не трогает счёт, направление, статус, остаток и причинную ссылку. Место события в ленте принадлежит первой версии: исправление уточняет запись, но не переносит её во времени.

## Профиль на произвольную дату

Профиль версионный, и новая версия поступает в витрину позже, чем начинает действовать. Читать его нужно так: взять версии, у которых `valid_from <= ts` и `record_time <= eval_ts`, и выбрать последнюю по `valid_from`. `valid_to` при этом не фильтрует.

Причина в том, что закрытие предыдущей версии по `valid_to` оставляет дыру. Старая версия уже закрыта, новая ещё не дошла до витрины, и профиля нет вовсе, хотя банк в этот момент знал предыдущую версию. Смену выражает сама следующая строка: как только наступает её `record_time`, она становится последней. Готовая реализация лежит в `profile.as_of` и `profile.known_at`.

## Горизонт

| Граница | Значение |
|---|---|
| `REGISTRY_START` | 2018-01-01, начало реестра договоров |
| `HISTORY_START` | 2024-06-01 |
| `HISTORY_END` | 2026-09-01, так что август полон |

История хранится целиком. Ни числом событий, ни числом токенов генератор её не ограничивает, срез «как есть» не делает и будущее не отбрасывает.

## Продуктовый каталог во времени

Подтверждённая хронология Home Credit лежит в `data/reference/home_product_timeline.yaml` и считается фактом. Python её только загружает и проверяет: `world/hcb_timeline.py` требует обязательные ключи, допустимую точность даты, непротиворечивый период, уникальные коды, существующие ссылки на предшественника и преемника и отсутствие кодов `SYNTH_*`. Нарушение — ошибка запуска, а не предупреждение. sha256 файла попадает в манифест.

**Месяц и год никогда не превращаются в день.** Запись хранит `known_period_start`, `known_period_end` и `date_precision`; отдельной колонкой рядом лежит `simulation_effective_at` — день, которым пользуется симуляция, выбранный политикой `params.products.effective_date_policy` (`period_start` по умолчанию). Неизвестное начало даёт `registry_start`.

**Источник обязателен.** `source` содержит только ту ссылку, которая действительно есть; владелец проекта как источник указывается лишь там, где он назван явно. Если источника нет, запись обязана нести `source: null`, `confidence: low` и `unresolved_source: true` — валидатор не пропустит иное сочетание, а отчёт реализма перечислит такие записи как требующие подтверждения.

Семь состояний продукта выводятся **только из дат вех**: `planned`, `pilot`, `active`, `temporarily_suspended`, `closed_to_new_clients`, `servicing_existing_contracts`, `archived`. Наличие или отсутствие договоров в конкретной синтетической выборке на статус не влияет. Архив — терминальное состояние.

**Закрытие продаж не закрывает договоры.** Договор запоминает версию условий и тарифа на день подписания и живёт на ней, пока обслуживается; поздние события ссылаются на ту же версию. Новая версия касается действующего договора только по `applies_to`: `existing_from_date` даёт `product_repriced` или `contract_terms_changed` после `notice_days`, `on_renewal` — `product_renewed`, `new_clients_only` — ничего. Переход на другой продукт это `product_migrated` с `previous_product_id` и `migration_reason`.

Правила владения живут на продукте: `allow_multiple`, `max_active_holdings`, `compatibility_rules`, `replacement_rules`. Общего запрета «один продукт на семейство» нет; общие правила банка (например, не больше четырёх дебетовых карт) лежат в `params.products.bank_rules`.

Вымышленные запуски, смены тарифа, приостановки и закрытия описываются в `params.products.synthetic_products` и получают **отдельные коды `SYNTH_*`**. Настоящие продукты синтетических дат и тарифов не получают никогда.

## Скрытая жизнь

**Черты.** Двенадцать непрерывных коррелированных черт — дисциплина, терпимость к риску, импульсивность трат, цифровая склонность, чувствительность к цене, лояльность к точкам, предпочтения каналов, мобильность, социальность, уязвимость к мошенничеству, аппетит к кредиту, склонность к сбережению. Архетип задаёт только средние; разброс внутри архетипа таков, что два клиента одного типа заметно различаются. Черты живут в `truth/clients.parquet`, медленно дрейфуют после жизненных событий и в RAW не попадают.

**Доход.** Потоки дохода (зарплата, пенсия, бизнес, фриланс, аренда, помощь семьи, пособие) имеют работодателя, расписание, правило дня выплаты и место зачисления. Выплата месяца бывает обычной, ранней, поздней, перенесённой из-за выходных, пропущенной, частичной с доплатой; бывают премия, отпускные, индексация, смена работодателя, несколько потоков, нерегулярный доход и увольнение. Часть дохода приходит в другой банк или наличными и видна банку лишь косвенно.

**Стресс** — это период, а не тип клиента. У эпизода есть триггер (увольнение, задержка дохода, болезнь, крупная покупка, рост обязательств, развод, переезд, случайный шок), нарастание и спад, следствия (дискреционные траты вниз, утилизация лимита вверх, пропуски платежей, обращения в поддержку, интерес к рефинансированию) и выход: восстановление дохода, рефинансирование, реструктуризация, продажа сбережений, помощь семьи. Повторный стресс возможен.

**Социальный граф** строится до симуляции для каждого сообщества: супруги, родственники, друзья, коллеги, работодатели, арендодатели, собственные счета в других банках, устойчивые и случайные контрагенты. Домохозяйство делит аренду, счета и шоки. В RAW не пишутся ни `household_id`, ни тип связи, ни идентификатор работодателя — виден только устойчивый маскированный `counterparty`.

**Мошенничество** — эпизод и риск, а не пожизненный класс: компрометация карты, необычная покупка, подозрительный перевод, социальная инженерия, захват доступа, ложное срабатывание. Цепочка идёт от шагов эпизода к срабатыванию антифрода, решению, блокировке, обращению клиента, оспариванию, возврату и перевыпуску. Флага мошенничества в RAW нет.

## Финансовая причинность

Деньги не возникают и не исчезают. Каждая успешная операция — проводка с явно названной второй стороной: другой счёт того же клиента, счёт другого клиента, внешний банк, наличные, мерчант, работодатель, государство, доходы и расходы банка. Каждая транзакция несёт `balance_after` своего счёта.

- Расход требует источника: собственных средств или доступного кредитного лимита.
- Отклонённая операция не меняет ни одного остатка; отменённая клиентом не порождает транзакции вовсе.
- Кредит проходит заявку, решение, выдачу, график и обслуживание; платёж соответствует договору; просрочка растёт от самого раннего неоплаченного платежа и регистрируется на вехах.
- Операции по депозиту невозможны раньше его открытия и позже закрытия.
- Заблокированная карта не проводит успешных покупок.
- Возврат, отмена и chargeback ссылаются на исходную операцию и в сумме её не превышают.
- Внутренний перевод порождает обе стороны с одним `transfer_id`, и получатель видит деньги во всех последующих решениях.

`cause_event_id` — это всегда либо существующий `event_id`, либо `null`. Идентификатор договора, месяц или текстовая причина туда не пишутся никогда. У периодических комиссий и процентов конкретного события-причины нет: они несут `cause_event_id = null`, `contract_id`, `accrual_period` и `reason = periodic_contract_rule`.

Инварианты собраны в `finance/invariants.py` и используются и тестами, и отчётом реализма: пара проводок в сумме даёт ноль, стороны перевода совпадают по идентификатору и сумме, цепочка `balance_after` не рвётся, отклонённое не создаёт проводок, совокупное изменение остатков объясняется чистыми внешними потоками, частичные возвраты не превышают исходную операцию, остаток основного долга сходится с выдачей и платежами.

## Мерчанты

Сеть, точка и MCC — разные сущности. Популярность сетей и точек имеет тяжёлый хвост. У клиента есть домашняя и рабочая зоны и набор любимых точек в частых категориях; вероятность нового места растёт с импульсивностью, поездкой и переездом и падает с лояльностью. Выбор точки учитывает расстояние, время суток и день недели, часы работы, доход и ценовой сегмент, транспорт, поездку и конкретную потребность. Будний день, выходные и месячные обязательства складываются в устойчивые последовательности. Сумма покупки определяется потребностью, корзиной, ценовым уровнем точки, чертами и сезоном — не кодом MCC.

## Наблюдаемость

Дефект принадлежит источнику, а не равномерному шуму: задержка записи, поздние поступления, дубли, исправления, отмены, пропуски полей с причиной, суточные сбои источника, смена схемы в середине истории, потеря времени у части записей витрины договоров, тестовые аккаунты, состояние на начало окна. Витрина теряет время у записи только там, где известна её причина, и запись никогда не оказывается раньше причины.

## Запрещённые поля и аудит утечек

Ни одно из скрытых полей не попадает в RAW: будущий отток, будущий дефолт, роль в мошенничестве, сценарий, архетип, идентификатор домохозяйства, тип связи, идентификатор работодателя, эпизод стресса, любые `trait_*`.

Аудит проверяет три вещи: имена колонок и ключей payload по всей ленте, значения скрытых черт внутри payload по выборке записей, взаимную информацию между скрытыми полями и несколькими счётчиками клиента. Отчёт печатает охват каждой проверки и говорит, что осталось непроверенным. Чистый результат означает «в выполненных проверках утечек не обнаружено», а не отсутствие утечек вообще.

## Готовность к произвольному `eval_ts`

Генератор меток и срезов не делает: он лишь обязан не мешать их построить позже. Контракт таков.

- События отбираются по `record_time <= eval_ts`.
- Версия записи берётся с максимальным `record_time <= eval_ts`. Место записи в ленте при этом принадлежит первой версии.
- Профиль берётся по `valid_from <= eval_ts` и `record_time <= eval_ts`, последний по `valid_from`. По `valid_to` фильтровать нельзя: см. раздел о профиле на произвольную дату.
- Статус продукта берётся по интервалу каталога.

Ни одно событие не содержит сведений о более поздних событиях: закрытие пишется в момент закрытия, а плановые даты графика платежей это законное знание банка на момент договора.

## Детерминизм

Единица симуляции — **сообщество**, а не пачка воркера. У клиента есть устойчивый порядковый номер, `community_id = (client_ordinal - 1) // community_size`, а `client_id` выведен из seed и номера так, что соседство номеров из RAW не читается. Пачки лишь распределяют целые сообщества по процессам.

Следствия: один seed и одни параметры дают один и тот же результат при любом числе воркеров, любом размере пачки, любом порядке завершения и любом `PYTHONHASHSEED`. Манифест хранит `content_sha256` каждой таблицы по канонически отсортированным строкам и отдельно sha256 файлов.

## Параметры

Значимые величины вынесены из кода в `src/generator/params/`: население, черты, жизненный цикл, доход, стресс, связи, мошенничество, активность, суммы, продукты, география, мерчанты, сезонность, дефекты, калибровочные эталоны. Переопределения передаются JSON-файлом через `--params`, отпечаток конфигурации входит в манифест и в ключ кэширования розыгрышей.

`params/calibration.py` хранит эталоны со статусом `reference` (есть реальный источник), `hypothesis` (гипотеза) и `no_reference` (эталона нет). У каждого записаны источник, период, география, уверенность и допустимый разброс. Там, где реального эталона нет, точное значение не выдумывается.

## Отчёт реализма

`report/realism.py` строит markdown и JSON: распределения и квантили, события на клиент-месяц **с пустыми месяцами двух разных видов**, длинные хвосты, переходы жизненного цикла, повторяемость точек и контрагентов, география, доходы с задержками и пропусками, эпизоды стресса и их исходы, финансовые инварианты, продуктовые цепочки и миграции, цепочки мошенничества, дефекты по источникам, сравнение с калибровочными эталонами, список метрик без эталона, записи хронологии без источника, несколько целостных историй клиентов и аудит proxy-утечек.

`report/show.py` печатает ленту одного клиента подряд, с профилем, покрытием и — по явному флагу `--truth` — скрытой правдой рядом.

## Спецификация будущего адаптера Pragmatiq

Адаптер не реализован; ниже контракт, по которому он строится.

- Лента → `(user_id = client_id, ts = event_time при фильтре record_time <= eval_ts, source, fields = payload последней доступной версии по каталогу ключей манифеста)`.
- Профиль SCD2 → профиль «как на момент» по правилам раздела о `eval_ts`.
- Внутренние переводы → рёбра `(from_client, to_client, ts, amount, transfer_id)` из пар `p2p_out` и `p2p_in`.

Токенизация, ограничения длины, выбор `eval_ts` и метки задач — отдельный этап.

# Preprocessing

> Раздел описывает прежний контракт RAW и **ожидает переделки** под новую ленту генератора.

RAW → проверенные месячные as-of примеры → сплиты → bucketization → статистические artifacts. Токенов, словаря и маскирования здесь нет.

```powershell
venv\Scripts\python -m src.preprocessing.run --raw data/raw/smoke --name smoke
```

## Пример

Пример это пара `(client_id, cutoff)`, где `cutoff` это начало следующего месяца: срез за май 2026 имеет `cutoff = 2026-06-01`. В историю входят события строго раньше `cutoff`, профиль это последний снимок строго раньше `cutoff`.

Кандидат становится примером, если от `max(HISTORY_START, first_seen[transactions])` прошло не меньше 90 дней, есть хотя бы одно событие и есть снимок профиля. Иначе в `cutoff_index.parquet` записывается причина: `no_transactions_coverage`, `insufficient_observation`, `no_events`, `no_profile_snapshot` или `unused_combination`.

## Сплиты

Группа клиента это SHA-256 от `"{seed}:{client_id}"`: 80% train, 10% val, 10% test. Python `hash()` не используется, добавление клиентов не переселяет существующих. Последний полный месяц это test, предпоследний это val, остальные это train_period.

| Датасет | Клиенты | Месяцы |
|---|---|---|
| `train` | train | train_period |
| `val_client` | val | train_period |
| `test_client` | test | train_period |
| `val_time` | train | val month |
| `test_time` | train | test month |

Пересечение клиентов между `train` и временными выборками ожидаемо: это разные месяцы одних и тех же людей.

## Хранение

События хранятся один раз на группу клиентов, примеры это ссылки на префикс истории.

```
data/processed/<name>/
  cutoff_index.parquet                все кандидаты со статусом и причиной
  clients/{train,val,test}_clients/
      events.parquet                  client_id, seq, ts, event_type +
                                      <event_type>__<field> + __bucket для numeric
      profile.parquet                 20 полей профиля + __bucket
  {train,val_client,test_client,val_time,test_time}/examples.parquet
data/artifacts/<name>/
  bucket_edges.json  field_stats.json  unigram_baselines.json
  split_manifest.json  validation_report.json  validation_report.md
  value_counts/<namespace>__<field>.parquet
```

**Потребитель обязан брать префикс `seq < seq_end`.** События train-клиентов намеренно содержат val- и test-месяцы: они нужны примерам `val_time` и `test_time`. Защита от утечки лежит в ссылке, а не в файле.

## Поля

Каждое поле описано парой `(namespace, field)`: тип (`categorical`, `numeric`, `boolean`, `metadata`), роль и флаг `predictable`. `client_id`, `seq` и служебные метки времени хранятся как metadata: их не bucketize и не предсказывают. MCC это категория.

`profile` и `profile_snapshot` это разные namespace. Снимки первых двух месяцев попадают в `profile_snapshot` как события ленты, но в `profile` не попадают никогда: правило 90 дней не даёт им стать as-of ни для одного примера.

## Bucketization

Только numeric, только непустые train-значения, по умолчанию 16 квантильных корзин. Границы берутся методом `inverted_cdf`, то есть это наблюдённые значения; одинаковые схлопываются, граница, равная максимуму, отбрасывается. Тогда **ни одна корзина не остаётся пустой на train**.

Правило включения `(e[i-1], e[i]]`: значение на границе уходит в нижнюю корзину, значения вне train-диапазона попадают в крайние. Пропуск остаётся пропуском: `bucket = null`. На evaluation ничего не переобучается.

## Статистики

Считаются только на `train`. Каждое событие и каждый выбранный снимок учитываются один раз, сколько бы cutoff-примеров их ни включало.

Для каждого содержательного поля: `n_total`, `n_missing`, `n_valid`, `missing_rate`, cardinality, `top1_frequency`, энтропия в битах, `rare_share` и полное распределение. Флаги `high_missing`, `near_constant`, `low_entropy` только сообщаются: ничего не удаляется автоматически.

## Воспроизводимость

Два запуска на одних RAW, config и seed дают побайтово одинаковые файлы. В artifacts не попадают ни пути, ни время запуска.

# Tokenizer

> Раздел описывает прежний контракт RAW и **ожидает переделки** под новую ленту генератора.

Структурированные события → словарь → token ID → контракт входа для модели.

```powershell
venv\Scripts\python -m src.tokenizer.run --name smoke
```

## Две сущности: поле и токен

Это центральное различие, и путать их нельзя.

| Сущность | Что это | Кто пользуется |
|---|---|---|
| **`field_id`** | идентичность физического поля, индекс в реестре preprocessing | маскирование, кандидаты MLM, корзины, unigram, все пофилдовые отчёты |
| **`token_id`** | идентификатор токена в словаре | только таблица эмбеддингов |

`field_id` одинаков во всех режимах словаря. `token_id` зависит от режима. Благодаря этому склейка словаря меняет представление, но **не меняет задачу**: множество замаскированных позиций и локальные цели совпадают побайтово.

Специальные позиции (`[EVT]`, `[USR]`) получают сентинел `NO_FIELD`; все индексируемые по полю массивы имеют длину `n_fields + 1`, и ни один `-1` никуда не уезжает.

## Пространство ID

```
[0, 6)                 [PAD], [UNK], [MASK], [EVT], [USR], [MISSING]
[6, 6 + n_key_tokens)  токены ключей
[6 + n_key_tokens, …)  токены значений
```

Порядок выдачи значений: обход полей в порядке реестра, значения внутри поля в типизированном порядке (numeric — по номеру корзины). Локальный индекс кандидата это позиция в типизированном порядке **своего поля**, поэтому у numeric он равен номеру корзины — на этом держится совпадение с unigram-baseline.

Словарь учится **только на train**. На evaluation он заморожен: неизвестное значение это `[UNK]`, явный пропуск это `[MISSING]`, новых токенов словарь не заводит.

## Событие

```
позиция 0   [EVT]                      одинаковый ID в key_ids и в value_ids
позиция 1   timeline__event_type
позиция 2+  поля payload в порядке реестра
```

Профиль кодируется теми же правилами, но отдельно и начинается с `[USR]`: 21 токен. Позиция считается **внутри записи** и сбрасывается на каждом событии.

## Хранение

```
data/tokenized/<name>/
  tokenized_manifest.json             версия формата и sha256 tokenizer_config
  clients/{train,val,test}_clients/
      events.parquet                  client_id, seq, ts, event_type, n_tokens,
                                      key_ids, value_ids, positions, field_ids
      profile.parquet                 то же для снимка профиля
  {train,val_client,test_client,val_time,test_time}/examples.parquet
data/artifacts/<name>/tokenizer/
  special_tokens.json  key_vocab.json  value_vocab.json  field_value_ids.json
  tokenizer_config.json  tokenizer_stats.json  golden_examples.json
```

`tokenizer_config.json` хранит версию формата, special ID, режимы словаря, правила порядка, отпечаток реестра склейки и sha256 тех artifacts preprocessing, на которых обучался словарь. При загрузке хэши пересчитываются, несовпадение это ошибка, а не предупреждение.

## Runtime masking

Сохранённые датасеты содержат исходные ID: `[MASK]` в них не встречается. Masker работает с копией и своим seed, входные массивы не меняются.

Маскируются только известные непустые значения полей с `predictable=true`. Специальные токены, `[UNK]`, `[MISSING]`, metadata и весь профиль не маскируются никогда. Заменяется только `value_id`; ключи, позиции и время остаются на месте.

| Режим | Что выбирается |
|---|---|
| `token` | каждая доступная позиция независимо |
| `key` | поле внутри примера, маскируются все его доступные значения |
| `event` | событие, маскируются все его доступные значения |
| `field_balanced` | бюджет масок распределяется между полями поровну |
| `combined` | объединение первых трёх, пересечения считаются один раз |

Ожидаемая доля скрытых значений у `combined`: `1 − (1−token_rate)(1−event_rate)(1−key_rate)`.

**Маска привязана к примеру.** Поток случайных чисел засевается парой `(client_id, cutoff)`, поэтому маска не зависит ни от состава batch, ни от места примера в нём. Без этого нельзя ни менять `eval_batch_size`, ни собирать validation потоком.

Target это исходный `value_id`, вне масок `-100`.

## Field-restricted prediction

`field_value_ids.json` даёт для каждого поля список допустимых value ID в типизированном порядке. Special-токены в кандидаты не входят. `CandidateIndex` переводит глобальный ID в локальный индекс поля и обратно через плотную таблицу `local_lookup[n_fields + 1, size]`, где `-1` означает «не кандидат этого поля». Softmax по всему словарю не считается.

## Режимы словаря

Незаконченный эксперимент: влияет ли склейка семантически одинаковых ключей и значений на качество.

| `--key-mode` | Что склеивается |
|---|---|
| `namespaced` | ничего, каждое физическое поле несёт свой key token |
| `semantic` | поля одной семантической группы делят key token (`profile__declared_income` ≡ `profile_snapshot__declared_income` и ещё девять групп) |

| `--categorical-value-mode` | Что склеивается |
|---|---|
| `field_specific` | ничего, `true` у `is_online` и `true` у `delivered` это разные токены |
| `shared` | строки и булевы с одинаковым значением делят value token |

Реестр склейки лежит в `src/tokenizer/semantics.py` и объявлен **явно**: рядом с группами перечислены `AMBIGUOUS_KEYS` — пары, которые похожи, но не склеиваются, с причиной. Numeric-корзины и int-коды не склеиваются никогда: `age_B7` и `amount_B7` это разные величины, а `day_of_week = 1` и `children = 1` разные коды.

Склеенный словарь обязан жить в своём каталоге:

```powershell
venv\Scripts\python -m src.tokenizer.run --name smoke --vocab-tag semkeys `
    --key-mode semantic --categorical-value-mode field_specific
```

`--fit-only --all-modes` считает счётчики за один проход по train и собирает все четыре словаря, не материализуя датасеты: так узнают реальные размеры.

# Модель

> Раздел описывает прежний контракт RAW и **ожидает переделки** под новую ленту генератора.

Три уровня, один проход:

```
поля события      → Event Encoder    → вектор события
снимок профиля    → Profile Encoder  → вектор клиента
профиль и события → History Encoder  → вектор клиента
```

## Embeddings

Одна таблица на всё пространство ID: `E(key) + E(value)·[key ≠ value] + P(позиция)`. Зоны ключей и значений не пересекаются. У специальной позиции `key_id == value_id`, и слагаемое значения не добавляется дважды.

Таблица токенов разыгрывается **своим** генератором, засеянным `seed ^ VOCAB_SEED_SALT`, и глобальный поток не расходует. Поэтому размер словаря не сдвигает инициализацию Transformer, History Encoder и MLM-головы: при одном seed все не-словарные веса совпадают побайтово во всех режимах словаря.

## Время в истории

Время живёт **во внимании**, а не в векторе события. `q` и `k` поворачиваются на угол, пропорциональный `squash(часы до последнего элемента истории)`; разность углов пары и есть их относительное время. К вектору элемента не прибавляется ничего, синусоиды абсолютной позиции нет.

Причина измерена: у прежнего аддитивного кодирования норма временного слагаемого была 26 (сутки) … 143 (два года) против нормы вектора события 9 — содержание события становилось малой добавкой к направлению «возраст».

Что относительные координаты не выражают, приходит отдельными признаками:

- **календарь события** (час, день недели, день месяца — синус и косинус) прибавляется к вектору события;
- **простой клиента** (часы от последнего события до cutoff) приписывается профилю: координата последнего элемента равна нулю, и сама история не знает, когда она кончилась.

Оба признака идут через `FeatureMLP`, чей выходной слой инициализирован **нулём**: на шаге 0 вход History Encoder это чистый вектор события, а масштаб слагаемого модель выбирает сама. Следствие при чтении градиентов: на первом шаге градиент скрытого слоя равен нулю — это ожидаемо и не означает оборванного графа.

У History Encoder слои свои (`rotary.py`): собственный forward поверх `scaled_dot_product_attention`. Это не только про время, но и про память: fast path `nn.TransformerEncoderLayer` материализует полную матрицу внимания, и на истории в 3637 событий это 3.2 ГБ вместо 47 МБ.

## MLM head

Представление замаскированной позиции:

```
h_local   состояние позиции после Event Encoder
h_event   вектор события после History Encoder
h_usr     вектор клиента

concat → Linear(3d, d) → GELU → LayerNorm → голова своего поля
```

Все три состояния берутся из **одного** прохода: `Backbone.forward` принимает `gather` из пар «строка события, позиция токена». Повторный запуск Event Encoder считал бы другое: маска и dropout у него свои.

У каждого predictable-поля хотя бы с двумя кандидатами своя `Linear(d, n_candidates)`. Головы ключуются `field_id`, а не токеном словаря, поэтому во всех режимах словаря их набор и размеры одинаковы. Поле с одним кандидатом помечается `degenerate` и в loss не входит.

## Loss

```
field_loss     = mean(CE по позициям поля)
field_balanced = mean(field_loss по полям batch)     основной
token_weighted = Σ field_loss·n / Σ n                рядом, для сравнения
```

Позиций у `transaction__mcc` на три порядка больше, чем у `product_event__term`, и взвешивание по токенам превратило бы обучение в обучение одному полю. CE всегда в float32.

Batch без целей не шаг: backward, optimizer и scheduler пропускаются, причина пишется в лог. Подряд идущие пропуски ограничены `max_consecutive_skips`.

## Состав целей

`--target-policy history` убирает из задачи `timeline__event_type` (он восстанавливается из состава самого события) и `profile_snapshot__*` (они дублируют as-of профиль, который модель видит позицией 0). Убирает **целиком**: значения остаются входом, маски на них не ставятся. Исключение задаётся паттернами имён, потому что `MaskingConfig` уезжает в checkpoint и восстанавливается там, где словаря нет.

## Срез обучения

Обучающий сплит берёт **по одному примеру на клиента** — самый поздний cutoff. Оценочные сплиты берут все срезы: `val_time` и `test_time` и так по одному примеру на клиента, а `val_client` обязан остаться полной линейкой.

## Оценка

Validation фиксируется целиком до первого шага: клиенты, порядок, состав batch, обрезка и маски со своим seed. Набор сверяется по sha256 от целей при загрузке checkpoint.

Записываются **два** отпечатка набора:

| отпечаток | по чему | зачем |
|---|---|---|
| `targets_sha256` | `flat \| key_ids \| global_targets` | зависит от словаря, сверка внутри одного режима |
| `targets_field_sha256` | `flat \| field_ids \| local_targets` | инвариант: одинаков во всех режимах словаря |

Второй и доказывает, что две арки решают одну задачу.

По каждому полю считаются число целей, число кандидатов и классов с поддержкой, CE модели и unigram, NCE gain, accuracy обеих, macro F1 и top-K.

```
CE_unigram = mean(−ln p_train(target))
NCE_gain   = (CE_unigram − CE_model) / CE_unigram
```

Unigram берётся только из `unigram_baselines.json` preprocessing и по оцениваемым данным не пересчитывается.

**Метрика нового месяца.** В полной истории свежих событий единицы процентов, и улучшение на них растворяется. Каждая цель помечается флагом `recent`, и оценка ведёт два счёта по одним и тем же маскам: полный и по свежим целям. `--best-metric recent` выбирает `best.pt` по нему.

`--final-splits test_client,test_time` оценивает лучшие веса на этих наборах **один раз, после обучения**.

**Потоковая validation** (`--stream-validation`) хранит не batch'и, а рецепт: они пересобираются на каждую оценку и получаются теми же самыми, потому что маска привязана к примеру.

## Checkpoints

Сохраняются backbone и голова, optimizer и scheduler, счётчики, config, генераторы Python, NumPy и torch, состояние sampler, хэши artifacts и описание фиксированной validation. При загрузке всё это сверяется ключ в ключ: любое расхождение это другое окружение, и продолжать в нём нельзя.

## Сравнение двух арок

`train compare` берёт два checkpoint и считает их на **одних** примерах, масках и целях, с парным bootstrap по примерам. Малая разница без интервала результатом не считается.

CE разных режимов маскирования между собой не сравнивается: скрыть одно значение и скрыть событие целиком это разные задачи. Сравниваются два checkpoint внутри одного режима.

Если арки живут в разных словарях, строятся два набора splits, по одному на свой словарь, а равенство задачи доказывается совпадением `targets_field_sha256`.

# Запуск обучения

> Раздел описывает прежний контракт RAW и **ожидает переделки** под новую ленту генератора.

Обучение идёт отдельным локальным процессом: ни интернет, ни открытая сессия не нужны.

```powershell
.\scripts\epoch.ps1 start                      # пресет main
.\scripts\epoch.ps1 status
.\scripts\epoch.ps1 logs -Lines 40
.\scripts\epoch.ps1 stop
.\scripts\epoch.ps1 resume
.\scripts\epoch.ps1 resume-interrupted
.\scripts\epoch.ps1 check
```

Два каталога, и это важно:

```
run\       каталог модели: его заводит сам trainer и отказывается
           работать, если он не пуст. Launcher в него ничего не пишет.
control\   файлы запуска: перенаправленный вывод и PID.
```

Пресеты различаются **только** словарём и каталогом вывода:

| Пресет | Словарь |
|---|---|
| `main` | без тега: `namespaced` + `field_specific` |
| `vocab-semkeys` | семантически одинаковые поля делят key token |
| `vocab-shared` | одинаковые строки и булевы делят value token |
| `vocab-semkeys-shared` | и то и другое |
| `smoke` | проверка самого launcher: крошечный набор, CPU |

Всё остальное — данные, срез обучения, маски, seed, optimizer, расписание, эпохи и валидация — совпадает, иначе сравнение мерило бы не словарь.

Конфигурация запуска:

| Параметр | Значение |
|---|---|
| d_model / FFN / heads | 128 / 512 / 4 |
| слои Profile/Event/History | 1 / 3 / 2 |
| max_events_per_history | none (+ preflight) |
| masking | combined 0.15 / 0.10 / 0.10 |
| target_policy | history |
| бюджет | 3 эпохи |
| validation | потоковая, best по `val_time.recent` |
| финал | `test_client`, `test_time`, один раз |

`none` это значение, а не отсутствие значения: у обрезки истории и у числа клиентов `None` это собственная ветка кода.
