# mini_pragma_v2

Синтетический генератор банковских событий, конвейер подготовки данных и
слои модели: генерация → препроцессинг → словарь → кодирование → датасет →
время → батчи → маски → эмбеддинги → событие → анкета → история → MLM.

Каждый этап это отдельная команда с одним видимым результатом. Автоматической
сквозной цепочки нет: следующий шаг запускает человек, посмотрев на предыдущий.
Исключение одно — `tokenization.run fit`, который прогоняет подряд уже
существующие этапы обучения словаря и ничего своего не считает.

## Каталоги данных

```
data/
├── 01_raw/<group>/          выгрузка генератора: события и профиль
├── 02_preprocessed/<group>/ очищенная лента: events.parquet
├── 03_vocab/                чем кодируются данные: шесть файлов словаря
├── 04_tokenized/<group>/    результат кодирования: events.parquet, profile.parquet
├── 05_dataset/<group>/      готовые примеры: samples.parquet
├── 06_temporal/<group>/     временные позиции событий: temporal.parquet
├── 07_batches/<group>/      батчи одинаковой длины: batches.parquet
├── 08_masked/<group>/       что спрятано от модели: masked.parquet
├── 09_embeddings/<group>/   вектор каждого токена: embeddings.parquet
├── 10_events/<group>/       вектор каждого события: events.parquet
├── 11_profiles/<group>/     вектор каждого клиента: profiles.parquet
├── 12_history/<group>/      он же после истории: history.parquet
├── 13_mlm/<group>/          цели и предсказания: targets.parquet
└── 14_train/                чекпойнт обучения: checkpoint.pt
```

Этапы 09–13 это слои модели. Рядом с результатом каждый кладёт `weights.pt` —
веса, которыми результат посчитан.

Номер в имени каталога это порядок этапов конвейера: каждый следующий
читает предыдущий.

`<group>` это `train`, `val` или `test`. Клиенты групп не пересекаются, словарь
и все статистики учатся только на `train`.

## 1. Генерация

```bash
python -m src.generator.emit train
python -m src.generator.emit val
python -m src.generator.emit test
```

Посмотреть на выгрузку глазами: `python -m src.generator.report.show --help`.

Результат: `data/01_raw/<group>/` — лента событий и профиль клиентов. Конверт
события: `client_id`, `event_time`, `source`, `payload`; тип события лежит в
`payload.type`. Все четыре колонки строковые.

Время события выгружается читаемой строкой ISO 8601 со смещением
часового пояса Казахстана (UTC+05:00), с миллисекундами только
там, где они есть:

```json
{"event_time": "2025-03-18T19:32:00+05:00"}
```

Локального времени без смещения в выгрузке не бывает: по нему
момент восстанавливается неоднозначно.

### Справочник названий

Названия торговых точек генератор не выдумывает: он берёт их из
`reference/merchants.json` — выборки из 2ГИС и OpenStreetMap (© участники
OpenStreetMap, ODbL 1.0). Одна запись это одно название:

```json
{"name": "Magnum", "mapped_category": "grocery", "city": "Алматы"}
```

`mapped_category` — наше сопоставление категории генератора, а не рубрика
источника и не банковский MCC: MCC не публикует ни один из источников.
`city` заполнен только там, где город назвал сам источник; вычисленный по
координатам город подтверждением не считается и равен `null`.

Два правила, которые держат справочник справочником, а не выводами из него:

- **Частота ничего не доказывает.** Сколько раз название встретилось в
  выборочном поиске — свойство выгрузки, а не размер сети, доля рынка или
  популярность компании. Ни «национальных», ни «региональных» сетей из
  справочника не выводится.
- **Название живёт только там, где подтверждено.** Точка в городе, для
  которого справочник такого названия не даёт, остаётся безымянной:
  `merchant_name` пуст, а категория, MCC, город, сумма и сама операция на
  месте. Запасных списков и имён из слогов нет.

Подтверждённые названия есть в 42 поселениях из 101 и в 283 парах
(поселение, категория) из 1919, поэтому безымянных точек в ленте много —
это честное следствие источника, а не пробел.

Ценовой сегмент, популярность, часы работы, доля онлайна и шум терминальной
строки — параметры симуляции (`src/generator/params/merchants.py`). Со
справочником они не связаны и о настоящих компаниях ничего не утверждают.

## 2. Препроцессинг

```bash
python -m src.preprocessing.run preprocess train
python -m src.preprocessing.run preprocess val
python -m src.preprocessing.run preprocess test
```

Проверяет RAW по контракту и раскрывает payload в типизированные колонки.

Здесь же и только здесь нормализуется время: строка ISO 8601
разбирается, требует часового пояса, приводится к UTC и ложится в
колонку `timestamp[us, UTC]`; события каждого клиента упорядочены по
нормализованному времени. Строка, которую нельзя разобрать
однозначно, останавливает этап.

```
RAW           2025-03-18T19:32:00+05:00
PREPROCESSED  2025-03-18T14:32:00Z
```

Все последующие этапы — словарь, кодирование, календарь, сортировка и
маска целей — читают уже нормализованное время и пояс второй раз
не переводят.

В `events.parquet` лежит широкая таблица смысловых данных: конверт
(`client_id`, `event_time`, `source`, `type`) и поля событий — суммы, валюты,
направления, статусы, причины, продуктовые и кредитные характеристики,
признаки мерчанта, коммуникации и действия в приложении.

Чего там нет:

- служебной трассировки и признаков качества (номеров клиента и события,
  ссылок на строку RAW, флагов окна и разрывов);
- идентификаторов сущностей (`contract_id`, `account_id`, `card_id`,
  `application_id`, `session_id`, `transfer_id`, `merchant_id` и прочих) и локальных
  ссылок вида `ACCOUNT_1`: точные связи модели не передаются;
- второй копии текста: нормализованное значение лежит в самих
  `merchant_name` и `counterparty`;
- календарных дат (`due_date`, `accrual_period`): время модель получает
  отдельным каналом — нормализованным `event_time` и признаками календаря.
  Месяц начисления это месяц самого события, и `event_time` уже его называет;
  словарь же превратил бы его в список конкретных месяцев, где первый же
  месяц после `train` стал бы `[UNK]`.

Порядок строк задают сами данные: `client_id`, `event_time`, затем при
равном времени причинный приоритет типа события из `EVENT_TYPES`
(заявка раньше решения по ней), затем `type`, `source` и остальные поля
в порядке имени. Ни приоритет, ни индекс сортировки рядом не хранятся.
Результат группы это ровно один файл: `events.parquet`. Анкета не
копируется — чистить в ней нечего, и следующие этапы читают её прямо
из `data/01_raw/<group>/profile.parquet`. Любая строка, которую нельзя разобрать
по контракту, останавливает этап, и частичный результат не сохраняется.

## 3. Словарь

Все словари, границы чисел и BPE учатся только на train: лента из
`data/02_preprocessed/train/events.parquet`, анкета из `data/01_raw/train/profile.parquet`.

```bash
python -m src.tokenization.run special-tokens   # data/03_vocab/special_tokens.json
python -m src.tokenization.run key-vocab        # data/03_vocab/key_vocab.json
python -m src.tokenization.run value-vocab      # data/03_vocab/value_vocab.json
python -m src.tokenization.run buckets          # data/03_vocab/buckets.json
python -m src.tokenization.run bpe              # data/03_vocab/bpe.json
python -m src.tokenization.run final-vocab      # data/03_vocab/final_vocab.json
```

Для прода те же шесть этапов запускаются одной командой:

```bash
python -m src.tokenization.run fit
```

`fit` вызывает те же функции, что и отдельные команды, поэтому результат
совпадает. При ошибке он останавливается и называет проблемный этап;
`final_vocab.json` при этом не остаётся от прежней сборки.

Каждый файл решает ровно одну задачу и не повторяет содержимое соседних.

`special_tokens.json` — служебные токены и их ID. Их пять:

```json
{"[PAD]": 0, "[UNK]": 1, "[MASK]": 2, "[EVT]": 3, "[USR]": 4}
```

`key_vocab.json` — название ключа и его ID:

```json
{"amount_due": 5, "amount_or_limit": 6, "event_type": 31}
```

`value_vocab.json` — категории train, сгруппированные по ключу. Идентификатор
определяет связка ключ + значение: одинаковая запись у разных ключей это разные
факты.

```json
{"app_domain": {"auth": 118, "home": 119},
 "profile_children": {"0": 153}}
```

Правило одно и без исключений: словарь значений у каждого ключа свой.
Одинаковая запись у разных ключей это разные факты — `active` у карты и
`active` у обращения общего номера не получают, и `2` у числа детей не делит
номер с `2` у прежнего числа детей. Ключ в последовательности лежит рядом со
значением, и что это за поле, модель узнаёт из него.

Категорией бывает и число. Небольшой дискретный счётчик и срок договора
кодируются ТОЧНЫМ значением, а не диапазоном: срок это выбор из каталожного
меню, а не величина, и между 12 и 18 месяцами промежуточных сроков не бывает;
у числа детей и числа договоров важно само число, а не порядок величины. Так
кодируются `term`, `requested_term`, `approved_term`, `installment_no`,
`profile_children` с его прежним и новым значением, `profile_contracts_count`
и `profile_active_contracts`.

Число, которого на train не было, номера не получает: на val и test оно
кодируется `[UNK]`, как и любая невиданная категория. Предел значений нигде не
выдумывается, и словарь по val и test не подгоняется.

`buckets.json` — диапазоны каждого числового ключа. Числами остались
непрерывные величины, где соседние значения близки по смыслу: деньги, ставка,
доля использования лимита, дни просрочки, возраст и длительность отношений с
банком. `min` включительно, `max` не включительно; `null` означает открытую
сторону, а `min = max = 0` — отдельный нулевой диапазон, который проверяется
первым.

```json
{"amount_due": {"amount_due_bucket_1": {"id": 283, "min": null, "max": 1000}}}
```

`bpe.json` — стандартный файл библиотеки `tokenizers`, записанный её же
`Tokenizer.save`, и читаемый обратно `Tokenizer.from_file`. Настройки обучения
живут в конфигурации, а не в файле.

`final_vocab.json` — уникальное имя токена и его глобальный ID. Имя и номер
соответствуют друг другу один к одному: иначе пространство ID перестало бы
совпадать с числом строк embedding. Префикс отделяет виды токенов друг от
друга:

```json
{"[PAD]": 0, "key:amount_due": 6, "value:app_domain=auth": 118,
 "bucket:amount_due_bucket_1": 283, "bpe:a": 470}
```

ID идут подряд от нуля: специальные, ключи, категории, диапазоны, куски BPE,
и в каждом файле возрастают по ходу чтения. После сборки словарь не меняется.

Номера ключей определены одним реестром смыслов и от данных не зависят.
Номера категорий, диапазонов и кусков BPE зависят от корпуса `train`:
в примерах выше они показывают форму записи, а не конкретные значения
вашей сборки.

## 4. Кодирование групп

```bash
python -m src.tokenization.run encode train
python -m src.tokenization.run encode val
python -m src.tokenization.run encode test
```

Вход: `data/02_preprocessed/<group>/events.parquet`, `data/01_raw/<group>/profile.parquet`
и словарь из `data/03_vocab/`. Выход: `data/04_tokenized/<group>/events.parquet` и
`profile.parquet`.

Ничего не дообучается: значение, которого на train не было, кодируется `[UNK]`.
Отсутствующее поле в последовательность не попадает вовсе, пустой после
нормализации текст — тоже.

```
events.parquet   client_id, event_time, key_ids, value_ids, positions, calendar
profile.parquet  client_id, key_ids, value_ids, positions
```

`positions` это номер куска внутри значения: `0` начинает новое значение, а
`1, 2, …` продолжают его кусками BPE. Отдельных массивов с границами значений
нет — границы и есть эти нули. Первый токен записи это маркер `[EVT]` или
`[USR]`: он тоже стоит на нуле, но значением не является и при разборе
пропускается. Два соседних значения с одним ключом остаются двумя: каждое
начинает свой ноль. Числа токенов и названия ключей не хранятся: первое
считается по длине массивов, второе восстанавливается словарём.

## 5. Датасет

```bash
python -m src.dataset.run train
python -m src.dataset.run val
python -m src.dataset.run test
```

Вход: `data/04_tokenized/<group>/` и словарь из `data/03_vocab/`.
Результат: `data/05_dataset/<group>/samples.parquet`. Строка это один клиент на
конечный cutoff своей группы.

```
client_id
key_ids, value_ids, positions          последовательность событий клиента
event_starts, event_lengths            границы каждого события
event_time, calendar                   время событий и календарный канал
target_event_mask                      что разрешено маскировать и предсказывать
profile_key_ids, profile_value_ids,    токены профиля
profile_positions
```

Событие лежит в последовательности целиком: `event_starts` и `event_lengths`
дают его окно, а внутри окна значения разбираются по `positions` — ноль начинает
значение, следующие числа продолжают его кусками BPE. Первый токен окна это
маркер события, и в разбор он не входит. Ключ значения берётся из `key_ids` по
его нулевой позиции. Числа событий, токенов и значений это длины и нули
массивов, и отдельными колонками они не хранятся.

`target_event_mask` это период целей СВОЕЙ группы: train разрешает свой период,
val только свой, test только свой. Старая история остаётся видимым контекстом,
но целью чужой группы не становится. Клиенты групп не пересекаются.

Длинная история усекается объявленной политикой контекста; для оценочных групп
потеря событий периода целей запрещена и останавливает сборку.

Выравнивания по `[PAD]` в примере нет: у каждого клиента своя длина, и `[PAD]`
в сохранённом примере запрещён. Заполнитель появляется на следующем этапе.

## 6. Временные позиции

```bash
python -m src.temporal.run train
python -m src.temporal.run val
python -m src.temporal.run test
```

Вход: `data/05_dataset/<group>/samples.parquet`.
Результат: `data/06_temporal/<group>/temporal.parquet` — тот же пример клиента,
плюс одна колонка `event_time_log` сразу после `event_time`. Открыв одну строку,
видно `event_time[i]` и `event_time_log[i]` рядом.

Позиция это расстояние в секундах до ПОСЛЕДНЕГО выбранного события клиента,
сжатое логарифмом:

```
event_time_log[i] = 8 * log1p(delta_i / 8)
```

У последнего события позиция ровно `0`, у более старых она тем больше, чем они
древнее. Пустая история даёт пустой массив. Тип `float32`, одно число на событие.

Масштаб восемь секунд взят из статьи вслед за Pragmatiq. При малых промежутках
`8*log1p(x/8)` почти равно `x`, поэтому секунды сохраняются линейно, а месяцы
сжимаются: в банковской ленте события идут то секундами, то месяцами, и без
сжатия дальний хвост забил бы всю шкалу. На настоящих данных это видно так:

```
  i      event_time (UTC)        event_time_log   прошло до последнего
  0      2024-01-01 03:44:22      127.0497          63126638 c
  2403   2025-04-20 07:30:31      118.6434          22073069 c
  4804   2025-12-31 13:07:31       62.9280             20849 c
  4805   2025-12-31 18:45:00       34.6459               600 c
  4806   2025-12-31 18:55:00        0.0000                 0 c
```

Два года истории занимают 127 единиц шкалы, а последние десять минут — 34: вблизи
настоящего шкала подробная, вдали сжатая.

Точка отсчёта это последнее ВЫБРАННОЕ событие. Отбор сделал датасет, и если он
отбросил хвост истории, отсчёт идёт от нового хвоста, а не от события, которого
в примере нет.

Это не календарь и не `positions`: календарь говорит, когда по часам произошло
событие, `positions` нумерует куски внутри значения, а здесь лежит только
расстояние между событиями. Три разных канала. Время не попадает в словарь и не
бакетизируется.

Этап ничего не отбирает, не переставляет и не кодирует. Если какой-либо этап ниже
по конвейеру удалит события или изменит их порядок, позиции придётся пересчитать,
а не переносить: батчер этого не делает, и его проверка следит, чтобы у
последнего настоящего события позиция осталась нулём.

Посмотреть на строку:

```bash
python -c "import pyarrow.parquet as pq; r=pq.read_table('data/06_temporal/train/temporal.parquet').to_pylist()[0]; print(list(zip(r['event_time'][-5:], r['event_time_log'][-5:])))"
```

## 7. Батчи

```bash
python -m src.batching.run train
python -m src.batching.run val
python -m src.batching.run test
```

Вход: `data/06_temporal/<group>/temporal.parquet` и `data/03_vocab/special_tokens.json`.
Результат: `data/07_batches/<group>/batches.parquet`. Строка это по-прежнему один
клиент, но массивы дополнены `[PAD]` до общей длины своего батча.

```
batch_index                            номер батча; он же номер группы строк
client_id                              кто это
n_tokens, n_events, profile_n_tokens   исходная длина примера до выравнивания
key_ids, value_ids, positions          последовательность событий, ширина T
token_mask                             где настоящие токены, а где [PAD]
event_starts, event_lengths            границы каждого события, ширина E
event_time, event_time_log             время событий и временные позиции
calendar                               календарный канал
event_mask                             где настоящие события
target_event_mask                      только переносится из примера
profile_key_ids, profile_value_ids,    токены профиля, ширина P
profile_positions
profile_token_mask                     где настоящие токены профиля
```

Осей выравнивания три, и ширина каждой это максимум по клиентам ЭТОГО батча:
токены событий, события и токены профиля. Календарь остаётся плоским, по шесть
чисел на событие: ширина `6 * E`.

Заполнитель у идентификаторов это `[PAD]` из словаря; у позиций — ноль, потому
что это не идентификаторы; у календаря — `0.0`; у `target_event_mask` — `false`,
потому что заполнитель целью быть не может. У `event_time` заполнителя нет
вовсе: там `null`, так как нулевого момента не существует, а настоящая дата
рядом с `event_mask = false` читалась бы как правда.

У `event_time_log` заполнитель, наоборот, именно `0.0`, и он совпадает со
значением настоящего последнего события: позиция это расстояние, у которого ноль
осмыслен. Отличить заполнитель от настоящего нуля можно ТОЛЬКО по `event_mask`.

`event_starts` заполняется концом последовательности, а не нулём: пустое событие
в конце безвредно, а ноль указывал бы на первый настоящий токен клиента.

Настоящее лежит слева, заполнитель справа. Поэтому `mask[j]` это ровно
`j < длина`, а `event_starts` и сами `positions` остаются верными внутри
выровненной строки без единого пересчёта: границы событий и значений читаются
так же, как в примере.

Клиенты складываются в батчи по длине: окно из `sort_window_batches * batch_size`
клиентов читается в порядке файла, упорядочивается по `(n_tokens, client_id)` и
режется на батчи. Так рядом оказываются истории близкой длины, и заполнителя
нужно меньше. Нумерация не означает глобального порядка по длине: внутри окна
длины растут, на следующем окне счёт начинается заново.

Порядок событий ВНУТРИ клиента при этом не меняется вовсе: этап только
дописывает `[PAD]` справа и не трогает ни одного смещения. Порядок клиентов
между строками смысла не несёт — кто в батче, говорит `client_id`.

Последний батч группы короче остальных: добивать его нечем, а выдумывать клиента
нельзя. Клиент без событий остаётся клиентом: его `n_tokens` равен нулю, и такие
клиенты собираются в начало, в батч, где заполнителя нет совсем.

Токен `[PAD]` внешне неотличим от маркера события: у него тоже совпадают
`key_ids` и `value_ids`, а `positions` равен нулю. Отличить их можно ТОЛЬКО по
маске — читать последовательность мимо маски нельзя.

Один батч это одна группа строк parquet, поэтому он читается отдельно от
остального файла:

```bash
python -c "import pyarrow.parquet as pq; print(pq.ParquetFile('data/07_batches/val/batches.parquet').read_row_group(0).to_pandas())"
```

Файл заметно больше `samples.parquet` из-за заполнителя, но заполнитель это
длинные повторы, и zstd сжимает их почти в ноль.

Этап ничего не маскирует, не выбирает значения для предсказания и не обучает:
`target_event_mask` только переносится. Маскирование, модель и обучение в
конвейер не входят.

## 8. Маскирование

```bash
python -m src.masking.run train
python -m src.masking.run val
python -m src.masking.run test
```

Вход: `data/07_batches/<group>/batches.parquet` и `data/03_vocab/special_tokens.json`.
Результат: `data/08_masked/<group>/masked.parquet`. Строка это тот же клиент и та
же строка, что в батче, поэтому модель читает два файла параллельно по группам
строк.

```
batch_index                            номер батча; он же номер группы строк
client_id                              кто это
value_ids_source                       что было до маскирования
value_ids                              что увидит модель
labels                                 что предсказывать; -100 значит «не в loss»
reason                                 чем выбрано: event, key, value или пусто
```

`key_ids`, `positions`, границы событий, время, временные позиции и календарь
здесь не дублируются: они лежат в `batches.parquet` и маскированием не
затрагиваются вовсе. Ключ остаётся видимым — предсказывается значение.

Допустимо только значение настоящего события, у которого стоит
`target_event_mask`. Заполнитель, `[EVT]`, `[USR]`, анкета, время и календарь не
трогаются вовсе: разбор идёт лишь по окнам событий, прошедших обе маски, и
начинается со следующего после маркера токена. Длина последовательности не
меняется.

Три механизма разыгрываются совместно, и сильнейшая причина побеждает:
**event > key > value**.

```
event   0.10   событие целиком, со всеми его значениями
key     0.10   ключ у клиента, со всеми его значениями в допустимых событиях
value   0.15   отдельное значение
```

Среди выбранных значений доля `0.10` уходит в `[UNK]`: значение портится, но
`labels` остаются `-100`, и причина не пишется — модель видит незнакомое
значение и не получает за него ни награды, ни штрафа. Остальные `0.90` уходят
под `[MASK]`, и в `labels` ложатся исходные `value_ids`.

Все куски одного значения получают одно решение. Название мерчанта из трёх
кусков BPE скрывается целиком:

```
индекс             0        1        2        3        4
key_ids            [EVT]    key:cat  key:name key:name key:name   не меняются
positions          0        0        0        1        2

value_ids_source   [EVT]    470      Mag      n        um
value_ids          [EVT]    [MASK]   [MASK]   [MASK]   [MASK]
labels             -100     470      Mag      n        um
reason             ""       "event"  "event"  "event"  "event"
```

У кусков общий `key_id`, а `positions` `0, 1, 2` говорят, что это одно значение.
Открыть один кусок значило бы показать модели часть ответа.

Здесь конвейер отличается от Pragmatiq намеренно. Там третий механизм —
`token`, и он разыгрывает КАЖДЫЙ токен с вероятностью `0.15`, из-за чего текст
из нескольких кусков может быть скрыт наполовину. У нас он заменён на `value`,
и **вероятность `0.15` относится к значению, а не к токену**.

Выбор детерминирован: поток розыгрыша задан `seed`, группой и `client_id`, а
порядок обхода задан явно, поэтому он не зависит ни от порядка чтения, ни от
того, в какой батч попал клиент. Результат лежит на диске, значит маска
фиксирована у всех групп, а не только у `val` и `test`.

Посмотреть на один батч масок:

```bash
python -c "import pyarrow.parquet as pq; print(pq.ParquetFile('data/08_masked/val/masked.parquet').read_row_group(0).to_pandas())"
```

## 9. Вход модели

```bash
python -m src.embedding.run train
python -m src.embedding.run val
python -m src.embedding.run test
```

Вход: `data/07_batches/<group>/batches.parquet` и
`data/08_masked/<group>/masked.parquet`, оба сразу. Ключи, номера кусков, анкета
и маски берутся из батчей, а значения — из масок: модель видит то, что ей
разрешено видеть. Результат: `data/09_embeddings/<group>/embeddings.parquet` и
`weights.pt`.

Вектор обычного токена это сумма трёх слагаемых:

```
E[key_id] · scale  +  E[value_id] · scale  +  P[position]
```

`E` — одна общая обучаемая таблица на ключи и значения: их номера живут в общем
пространстве `final_vocab.json`, поэтому отдельного номера для сочетания ключа
со значением не заводится, сочетание получается сложением. `P` — фиксированная
синусоида номера куска внутри значения: текст приходит несколькими кусками BPE
с одним ключом, и без неё они были бы неразличимы.

`[EVT]` и `[USR]` записаны одним номером в оба слота, поэтому их эмбеддинг
берётся **один раз**, без удвоения и без позиции куска. `[PAD]` зануляется
маской.

```
batch_index                            номер батча
client_id                              кто это
dim                                    длина одного вектора
tokens                                 T * dim чисел: вектор каждого токена
profile                                P * dim чисел: вектор каждого токена анкеты
```

`labels` этот этап не читает вовсе, календарь и `event_time_log` тоже: они
понадобятся энкодеру события и TimeRoPE, а не входу.

## 10. Энкодер события

```bash
python -m src.event.run train
python -m src.event.run val
python -m src.event.run test
```

Вход: батчи, маски и веса входного слоя из `data/09_embeddings/<group>/weights.pt`.
Результат: `data/10_events/<group>/events.parquet` и `weights.pt`.

Двунаправленный трансформер по токенам **одного** события: токены одного события
не видят токены другого. Маркер `[EVT]` уже стоит первым токеном события, второй
не добавляется, и вектор события читается из колонки 0. Позиционного кодирования
по полям нет — внутри события у полей нет осмысленного порядка.

Календарь события — шесть sin/cos часа, дня недели и дня месяца — проходит через
`Linear(6 → d) → GELU → Linear(d → d)` и **прибавляется к вектору события**, уже
после энкодера. Он описывает событие целиком, а не поле внутри него.

```
batch_index                            номер батча
client_id                              кто это
event                                  номер события у клиента
event_time                             когда оно случилось, UTC
vector                                 d чисел: вектор события после календаря
```

Строка это одно **настоящее** событие: заполнителя в файле нет вовсе. События
идут по клиенту подряд, в хронологическом порядке.

Посмотреть на события одного клиента:

```bash
python -c "import pandas as pd; print(pd.read_parquet('data/10_events/val/events.parquet').head())"
```

## 11. Энкодер анкеты

```bash
python -m src.profile.run train
python -m src.profile.run val
python -m src.profile.run test
```

Вход: токены анкеты из батчей и веса входного слоя. Результат:
`data/11_profiles/<group>/profiles.parquet` и `weights.pt`.

Двунаправленное внимание по всей анкете клиента; вектор клиента читается из
позиции `[USR]`, которая уже стоит первым токеном. Полей два десятка, порядка
между ними нет, и каждое вправе смотреть на каждое.

```
batch_index                            номер батча
client_id                              кто это
dim                                    длина вектора
profile                                d чисел: вектор анкеты
```

**Временного канала у анкеты нет, и это решение.** В эталоне ненулевую позицию
получают только датированные жизненные вехи; у обычных полей снимка время равно
нулю. У нас вех нет — анкета это один снимок, а её изменения лежат отдельными
событиями в ленте со своим временем. Все позиции были бы нулями, а поворот на
нулевой угол ничего не меняет.

## 12. Энкодер истории

```bash
python -m src.history.run train
python -m src.history.run val
python -m src.history.run test
```

Вход: временные позиции из батчей, векторы событий этапа 10 и вектор анкеты
этапа 11. Результат: `data/12_history/<group>/history.parquet` и `weights.pt`.

Последовательность клиента это `[вектор анкеты, события от старых к новым]`.
Вектор анкеты кладётся прямо в слот `[USR]` — второй маркер не заводится и
заново не эмбеддится.

Время входит **поворотом, а не слагаемым**: TimeRoPE вращает Q и K на угол,
пропорциональный `event_time_log`, поэтому скалярное произведение зависит от
**разности** позиций — от того, сколько времени прошло между двумя событиями, а
не от их порядкового расстояния. `[USR]` якорится на нуле, то есть в момент
самого свежего события.

```
batch_index                            номер батча
client_id                              кто это
dim                                    длина вектора
client                                 d чисел: итоговое представление клиента
```

Обновлённые векторы **событий** энкодер тоже отдаёт — они нужны MLM-голове, — но
на диск не пишутся: голова считает их сама в том же прямом проходе.

Внимание полное и точное, без окна и без капа на длину истории. Самая длинная
история группы это 23 319 событий, то есть 544 млн пар в матрице внимания;
`F.scaled_dot_product_attention` считает её блочным ядром за 0.7 с и 194 МиБ.
Наивный путь просит 8.11 ГиБ — поэтому здесь своё внимание, а не
`nn.TransformerEncoderLayer`.

## 13. MLM-голова

```bash
python -m src.mlm.run train
python -m src.mlm.run val
python -m src.mlm.run test
```

Вход: батчи и маски; веса всех четырёх энкодеров из этапов 09–12. Результат:
`data/13_mlm/<group>/targets.parquet`, `preview.html` и `weights.pt` головы.

Этап собирает в памяти **дифференцируемый** сквозной проход
`InputEmbedding → Event → Profile → History → MLM` и считает по нему
кросс-энтропию на размеченных токенах. Голова получает на каждую цель три
вектора — сам токен после энкодера события, его событие после истории и клиента
после истории, — склеивает их в `3d`, проводит через `Linear(3d → d)` и получает
логиты скалярным произведением **с той же таблицей эмбеддингов**. Отдельной
выходной таблицы нет: градиент течёт в одни и те же веса с обеих сторон.

```
batch_index, client_id, event, place, position     где лежит цель
key_id, key                                        какой ключ закрыт
label_id, label, unknown_label, reason             что было целью
top_ids, top_names, top_probs                      что предсказано: только top-k
predicted_id, correct, loss                        итог по этой цели
```

Полного массива логитов в файле нет. `preview.html` показывает один
замаскированный пример: если значение состоит из нескольких кусков BPE, видно,
что предсказания относятся к кускам по отдельности.

**Этот этап не обучает.** Веса всех слоёв — начальный розыгрыш по seed, ни
одного шага оптимизатора не сделано; обучение — этап 14. Кросс-энтропия около `ln(1239) = 7.12` означает ровно
случайное угадывание и качеством модели не является.

Цели, у которых исходное значение было `[UNK]` (в `val` 720, в `test` 1049), из
потерь **не исключаются** — так же поступает эталон, — но считаются отдельно:
предсказать «неизвестно» легко, и без отдельного счёта доля угаданного
завышается. Замены на `[UNK]`, которые сделал сам маскер, к этому отношения не
имеют: их он исключил из ошибки ещё на этапе 08, оставив метку −100.

## 14. Обучение

```bash
python -m src.mlm.train                  # одна эпоха по всем клиентам train
python -m src.mlm.train --epochs 3
python -m src.mlm.train --max-steps 100
```

Учится только `train`. Вход: батчи и начальные веса этапов 09–12.

Маска `train` из `data/08_masked/train` при обучении **не читается**: каждая
эпоха разыгрывает её заново тем же маскером этапа 08 (`choose` + `apply`) по
немаскированным `value_ids` батчей. Правила и вероятности те же; меняется только
seed — он выводится из seed маскирования и номера эпохи, поэтому одна и та же
эпоха даёт одну и ту же маску, а соседние эпохи — разные. Конфиг маскирования
передаётся `--masking-config`, тем же JSON, что у `python -m src.masking.run`.
`val`, `test` и отчёт этапа 13 читают фиксированные маски из `data/08_masked`.

После каждой полностью пройденной эпохи та же модель считает потери на `val`:
фиксированная маска, `eval` и `no_grad`, без `backward` и шага оптимизатора.
Клиенты `val` идут теми же micro-batch'ами, что и в обучении. Среднее — по всем
целям `val`:

```
epoch=1 val_loss=7.0123 val_targets=15420
```

Эпоха, прерванная `--max-steps`, validation не получает. Результат: `data/14_train/checkpoint.pt` с
`model_state_dict`, `optimizer_state_dict`, `epoch`, `step` и конфигом.

Группа строк `07_batches` здесь только хранение. Клиенты идут потоком и
собираются в **micro-batch** по бюджету позиций `token_budget` (16384). Цена
клиента — `n_tokens + profile_n_tokens + n_events + 1`: токены событий, токены
анкеты и позиции истории вместе со слотом анкеты. Клиент, который дороже всего
бюджета, идёт отдельным micro-batch'ем.

На micro-batch модель вызывается **один раз**. Micro-batch плоский, без `[PAD]`:
токены событий, события и токены анкет всех клиентов лежат подряд, а границы
хранятся в `cu_seqlens` — событий, анкет и историй (у истории клиента первым идёт
слот анкеты, затем его события). Каждый энкодер считает свои сегменты по
**корзинам длины** `ceil(log2(длина))`: прямоугольник с заполнителем есть только
внутри корзины и только до её наибольшей длины, поэтому клиент с 6500 событиями
не растягивает историю остальных. Голова считает все цели micro-batch сразу.

`grad_accum_steps` micro-batch'ей (по умолчанию 1) дают один шаг `AdamW`. `backward`
идёт по сумме потерь целей каждого micro-batch, а перед шагом градиенты делятся на
число целей окна: это градиент среднего по всем целям окна. Окно без целей шага не
делает; неполное окно в конце эпохи шаг делает. `step` и `--max-steps` считают
шаги оптимизатора. В лог идёт строка на шаг:

```
epoch=1 step=42 loss=6.8124 targets=18432 micro_batches=4
```

`learning_rate` (3e-4), `weight_decay` (0.01), `token_budget` и `grad_accum_steps`
задаются тем же JSON, что и конфиг головы: `--config`.

**Бэкенд внимания** — `attention_backend` в том же JSON:

- `auto` (по умолчанию) — `flash`, если есть CUDA и библиотека `flash-attn`,
  иначе `sdpa`;
- `flash` — varlen FlashAttention (`flash_attn_varlen_func`): плоские Q/K/V
  `[позиции, головы, размер головы]` и `cu_seqlens`, без единой позиции
  заполнителя, во всех трёх энкодерах — события, анкеты и истории. Сегмент видит
  только себя. Без CUDA или без библиотеки — ошибка, тихой подмены нет;
- `sdpa` — корзины длины, описанные выше. Это запасной путь: CPU, fp32, нет
  `flash-attn`.

Оба пути считают одну и ту же формулу на одних и тех же весах: varlen-слои
читают параметры существующих модулей, поэтому веса этапов 09–12 и чекпойнт
грузятся без изменений.

На CUDA с поддержкой bf16 прямой проход обучения, validation и отчёта этапа 13
идёт под `autocast(bfloat16)`. Веса, градиенты и состояние AdamW остаются fp32,
`backward` — вне autocast. Углы TimeRoPE считаются в fp32. На CPU всё как
раньше — fp32 и корзины.

## Чем файлы этапов 09–12 не являются

Это **снимки при начальных весах**, для просмотра. Обучать по ним нельзя:
градиент через parquet не течёт. При обучении все четыре слоя и голова обязаны
считаться вместе, в одном прямом проходе, — что этапы 13 и 14 и делают.

## Установка

```bash
pip install -e .
```

Python 3.11+. Зависимости: numpy, pyarrow, pandas, scikit-learn, scipy,
tokenizers.

Этапам 09–14 нужен PyTorch — он объявлен отдельным дополнением, чтобы конвейер
подготовки данных ставился без него:

```bash
pip install -e .[torch]
```

Varlen FlashAttention на CUDA — ещё одно необязательное дополнение (нужны
NVIDIA GPU Ampere+ и CUDA toolkit, совместимый с установленным PyTorch):

```bash
pip install -e .[torch,flash]
```
