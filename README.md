# mini_pragma_v2

Синтетический генератор банковских событий, конвейер подготовки данных и
слои модели. Путь к обучению:

```
генерация → препроцессинг → словарь → кодирование → датасет →
входной слой (06) → начальные веса backbone (07) → обучение (12)
```

Временные позиции и маски — не этапы: их считает читатель набора при каждом
чтении (разделы 5.1 и 5.3), на диске они не хранятся.

Этапы 08–11 — энкодеры события, анкеты и истории и MLM-голова по отдельности —
остаются диагностикой: обучению не нужны ни их векторы, ни их отчёты.

Каждый этап это отдельная команда с одним видимым результатом. Автоматической
сквозной цепочки нет: следующий шаг запускает человек, посмотрев на предыдущий.
Исключение одно — `tokenization.run fit`, который прогоняет подряд уже
существующие этапы обучения словаря и ничего своего не считает.

## Каталоги данных

```
data/
├── 01_raw/<group>/          выгрузка генератора: события и профиль
├── 02_preprocessed/<group>/ очищенная лента: events.parquet
├── 03_vocab/                чем кодируются данные: шесть файлов словаря и веса маски
├── 04_tokenized/<group>/    результат кодирования: events.parquet, profile.parquet
├── 05_dataset/<group>/      готовые примеры: samples.parquet — вход модели
├── 06_embeddings/<group>/   веса входного слоя: weights.pt
├── 07_backbone/             начальные веса энкодеров: event.pt, profile.pt, history.pt
├── 08_events/<group>/       диагностика: вектор каждого события, events.parquet
├── 09_profiles/<group>/     диагностика: вектор каждого клиента, profiles.parquet
├── 10_history/<group>/      диагностика: он же после истории, history.parquet
├── 11_mlm/<group>/          диагностика: цели и предсказания, targets.parquet
├── 12_train/                каталог прогона по умолчанию: checkpoint.pt, best_checkpoint.pt,
│                            epochs/epoch_NN.pt, telemetry.jsonl
├── 13_downstream/<тег>/     векторы клиентов на T и отчёт проб: <group>.parquet, report.json
└── runs/                    сохранённые прогоны (вне git); каталог прогона — --out
```

Обучение читает `05_dataset`, `06_embeddings/train` и `07_backbone` — из данных
только набор, из остального только веса и конфиги, ни одного промежуточного
parquet этапов 08–11. Промежуточное после `04_tokenized` и `05_dataset` не
хранится: время и маска считаются при чтении набора, заполнитель появляется
только в памяти этапов 06, 08 и 09. Диагностические
этапы 08–11 кладут рядом со своим результатом `weights.pt` — веса, которыми он
посчитан; при одном конфиге это те же веса, что в `07_backbone`.

Номер в имени каталога это порядок этапов конвейера и номер раздела ниже.
Время, батчи и маски номера не занимают: это расчёт при чтении набора 05
(разделы 5.1–5.3). До 2026-09-30 они были этапами 06–08, а этапы после них
шли под номерами 09–15: так их называют прежние отчёты в `audit/`.

`<group>` это `train`, `val` или `test`. Клиенты групп не пересекаются, словарь
и все статистики учатся только на `train`.

## 1. Генерация

```bash
python -m src.generator.emit train
python -m src.generator.emit val
python -m src.generator.emit test
```

Посмотреть на выгрузку глазами: `python -m src.generator.report.show --help` — он
читает только строки выбранного клиента, а не всю выгрузку.

Воркеров по умолчанию — ядра минус одно, но не больше, чем помещается в свободную
память (`MemAvailable` минус 1 ГиБ, по 512 МиБ на воркер; замер пика — 0.35–0.39 ГиБ на
пачку из 256 клиентов на горизонте test). Воркер пишет строки по сообществу, как только
оно досчитано, а не копит пачку целиком. Погибший воркер (например, от нехватки памяти)
останавливает прогон ошибкой, а не вешает его: готовые пачки сохранены маркерами, и
`--resume` с меньшим `--workers` продолжает. Выгрузка от числа воркеров не зависит —
побайтно.

Состав групп задаёт `config.DATASETS`: число клиентов, окно, seed и `registration_end`.
Последний — до какой даты персонаж, приходящий в банк внутри окна, успевает прийти. У
каждой группы он равен концу её окна: иначе дата прихода раскладывалась до горизонта
планирования, пришедший после конца выгрузки в неё не попадал, и клиентов было меньше
объявленного (train 963 из 1000). Приход — не позже чем за `registration_margin_days`
(31 день) до этой даты, поэтому у каждого есть хотя бы месяц истории. Граница записана
в `manifest.json` (`registration_end`).

Два ритма, которые раньше выдавали генератор:
- **Счёт по автоплатежу** банк проводит утром (6–12 ч). Час и минута свои у каждого
  счёта и месяца; раньше время было формулой от номера счёта, и три четверти платежей
  приходились ровно на 09:00, 10:07 и 11:14.
- **Выплаты индексируются ступенькой раз в год** в месяц индексации. У зарплаты он общий
  для всех сотрудников работодателя (чаще январь), у пенсий и пособий — январь.
  Повышение — тоже ступенька, на годовщине. Раньше сумма росла на доли процента каждый
  месяц.
- **Подписки клиента выбираются без повторов сервиса.** Раньше выбор шёл с возвращением,
  и в 28% клиент-месяцев один сервис списывался дважды с разными суммами.

**Калибровка по проверке на 1000 клиентах** (окно train, 24 месяца; цели —
`params/calibration.py`, у эталонов банка — их собственный допуск).

Правила:
- **Приложение** клиент ставит в первую восьмую окна от начала отношений, а не в первую
  половину: давний клиент жил без приложения в среднем полгода.
- **Глубина сессии** (`session_extra_screens`) задана по именам целей сессии. Ключи
  звались иначе (`balance` против `balance_check`), и шесть целей из десяти, включая
  самую частую, молча брали запасные 0.8 экрана.
- **Внешний входящий перевод** приходит тем чаще, чем больше денег клиента идёт через
  банк (множитель тот же, что у исходящих), и не приходит в паузе, где молчат его переводы.
- **Счета и подписки** тихий клиент проводит через другой банк (`recurring_in_bank_share`:
  silent 5%, rare 40%).
- **Рассылки** зависят от режима активности (`communications_mode_factor`). Клиенту,
  замолчавшему в глазах банка, их втрое меньше (`communications_silent_factor`); раньше
  молчание меняло только состав отправок. Среднее держится у якоря банка — 3.8 в месяц.
- **Подписка** продлевается в свой час: 30% ночью (0–6 ч), остальные днём. Раньше все
  продления шли с двух до шести утра.
- **Любимые категории** по умолчанию — только еда. Аптека в них больше не попадает и не
  набирает десятую часть всех покупок.
- **С 50 лет** жильё «с родителями» разыгрывается в десять раз реже.
- **Раздел платежей** без выставленного счёта открывают реже: вес цели 0.15 вместо 0.25.
- **Новые частоты по режимам и ролям:** покупки, сессии, переводы, наличные.
- **Кредиты:** одобрение, суммы (1.2–4.5 месячного дохода у кредита наличными),
  дисциплина и выздоровление просрочки.
- **Прочее:** частичная выплата зарплаты — 2% выплат вместо 5%; антифрод — 0.07 эпизода
  на клиента в год.
- **Кредитная карта, открытая до окна,** живёт так же, как открытая в окне: рассрочка
  покупок, проценты на наличные, выписка с минимальным платежом, пропуск и просрочка.
  Раньше у неё не было состояния долга, и минус копился без выписок: на 1000 клиентах у
  48 карт долг стоял без движения, медиана 630 тыс. тенге.
- **Клиент, у которого в банке одна карта,** гасит выписку прямо на неё — переводом из
  другого банка или наличными. Раньше подтяжка денег шла только на дебетовый счёт, и у
  такого клиента выписка не проходила никогда. Пропущенных выписок по картам стало 14%
  вместо 34%.

В полосах и остальные перцентили, CTR баннеров, разделы auth, cards и loans. Аптека —
3.5% покупок (было 9.3%); пенсионеров, живущих с родителями, нет (было 14 из 110).

Вне полосы одна метрика: пустых клиент-месяцев 3.7% при гипотезе плана 10–15%. Месяц
молчуна заполняют события банка и чужих действий: зарплата, взносы по кредиту, переводы
от других клиентов, снимок остатка. Так и задумано (`calibration.EVENTS_PER_MONTH_BY_MODE`:
«полоса silent начинается не с нуля»). Полосу пустых месяцев можно получить, только
убрав эти события у молчуна.

Структурная деталь: экранов приложения до 16.12.2024 нет (`config.SOURCE_LAUNCH`), поэтому
у месяцев 2024 года медиана 41 событие, у 2025-го — 133. Полосы объёма заданы
на всё окно, и медиана держится у нижней границы.

Результат: `data/01_raw/<group>/` — лента событий и профиль клиентов. Конверт
события: `client_id`, `event_time`, `source`, `payload`; тип события лежит в
`payload.type`. Все четыре колонки строковые.

Профиль — одна строка на клиента: снимок анкеты на границу выгрузки `as_of`
(`timestamp[us, UTC]`), `birth_date`, поля анкеты и два списка датированных
фактов — всё строго раньше `as_of`. Возраста и признака пенсионера в снимке нет:
единственный источник возраста — `birth_date`, а возраст на конец выгрузки был бы
неверен для любого более раннего cutoff.

```
employment  list<struct<start_date, record_time>>  записи банка о работе по найму:
                                                   начало и когда банк узнал;
                                                   без start_date — работы нет
lifelong    list<struct<type, event_time,          вехи клиента, по времени;
                        source_id>>                source_id — карта или договор
                                                   вехи о продукте, иначе null
```

Вехи — по фактическому состоянию клиента, без собственных розыгрышей:

```
bank_registered        начало отношений с банком (бывает раньше начала ленты)
app_registered         клиенту открылось приложение — не первое использование
first_card_activated   первая активация карты договора, без перевыпусков
first_loan_opened      открытие первого кредита с графиком
first_deposit_opened   открытие первого вклада
```

Вехи о продуктах учитывают и договоры до начала окна. Внутри окна у каждой из
них есть акт-источник в ленте — строки `card_activated` или открытия договора с
тем же `card_id` / `contract_id`, что в `source_id`, и в тот же момент. Лента от
вех не меняется.

Время события выгружается читаемой строкой ISO 8601 со смещением
часового пояса Казахстана (UTC+05:00), с миллисекундами только
там, где они есть:

```json
{"event_time": "2025-03-18T19:32:00+05:00"}
```

Локального времени без смещения в выгрузке не бывает: по нему
момент восстанавливается неоднозначно.

### Справочник названий

Названия торговых точек генератор не выдумывает: он берёт их из
`reference/merchants.json` — выборки из 2ГИС и OpenStreetMap (© участники
OpenStreetMap, ODbL 1.0). Одна запись это одно название:

```json
{"name": "Magnum", "mapped_category": "grocery", "city": "Алматы"}
```

`mapped_category` — наше сопоставление категории генератора, а не рубрика
источника и не банковский MCC: MCC не публикует ни один из источников.
`city` заполнен только там, где город назвал сам источник; вычисленный по
координатам город подтверждением не считается и равен `null`.

2026-09-29 справочник пополнен ручным поиском: 1527 записей «сеть — город» по сетям,
работающим в Казахстане в 2024–2026 годах. Источники — официальные сайты сетей со
списками городов (и их архивные копии), страницы филиалов 2ГИС, списки арендаторов ТЦ,
справочники i-teka.kz, jsprav.ru, be-in.ru, restoran.kz. У каждой такой записи есть
поле `source` — ссылка, по которой подтверждены название и город.

Второй вход того же формата — `reference/national_merchants.json`: сервисы для
категорий, которых в 2ГИС и OSM нет, — такси, кикшеринг, авиакомпании (в том числе
иностранные с регулярными рейсами в Алматы и Астану), продажа ж/д билетов, туроператоры,
связь, домашний интернет, подписки, маркетплейсы и интернет-магазины, госуслуги,
страховые, МФО и переводы, прокат авто, благотворительность, развлечения и продажа
билетов, детские товары. Там же городские сервисы: транспортные карты, парковки,
коммунальные предприятия и провайдеры по городам. Присутствие каждой компании
подтверждено ссылкой: в `sources` для первых записей и в поле `source` у остальных.

**Частота ничего не доказывает.** Сколько раз название встретилось в выборочном поиске,
— свойство выгрузки, а не размер сети, доля рынка или популярность компании.

**Откуда точка берёт название** (`world.merchants.brands_for`). Берётся ближайшее место,
где название подтверждено; уровни мест не смешиваются:

1. само поселение;
2. крупнейший город его области, где названия этой категории подтверждены: сельская
   корзина и малый город покупают у сетей областного центра;
3. точки справочника без города (64% `merchants.json`). Запись с городом вне
   географии генератора сюда не попадает: её присутствие подтверждено, но в другом месте.

К выбранному уровню всегда добавляются общенациональные сервисы — записи
`national_merchants.json` без города. Yandex Go есть и там, где подтверждено местное
такси. Где пул состоит из одних сервисов (подписки, связь, маркетплейсы…), каждая точка
поселения — свой сервис, по порядку, без розыгрыша. Иначе у клиента было бы несколько
разных подписок с разными суммами под одним «Spotify».

У онлайн-точки города нет ни в `merchant_city`, ни в терминальной строке — ни суффикса
города, ни номера филиала: онлайн-оплата города покупателя не называет.

Ни на одном уровне ничего нет — точка безымянная: `merchant_name` пуст, а категория,
MCC, город, сумма и сама операция на месте. Так остаются:
- штрафы и налоги: их платят в бюджет, а не сети;
- ставки: лицензии букмекеров не проверялись;
- городские сервисы (парковки, транспорт, прокат авто) там, где записи нет;
- покупки за границей.

Название не из самого поселения разыгрывается своим потоком и не сдвигает район, часы,
онлайн и MCC точки. Сеть при этом задаёт точке ценовой сегмент и популярность, как и
подтверждённая в городе.

На выборке из 200 клиентов за окно train название есть у 93.1% покупок (до пополнения
справочника — 84.8%, до запасных уровней — около пятой части). Остаток:
- места без записи ни на одном уровне — 3.6%, в основном парковки и транспорт;
- штрафы, налоги и ставки — 2.3%;
- заграница — 0.9%.

Ценовой сегмент, популярность, часы работы, доля онлайна и шум терминальной
строки — параметры симуляции (`src/generator/params/merchants.py`). Со
справочником они не связаны и о настоящих компаниях ничего не утверждают.

## 2. Препроцессинг

```bash
python -m src.preprocessing.run preprocess train
python -m src.preprocessing.run preprocess val
python -m src.preprocessing.run preprocess test
```

Проверяет RAW по контракту и раскрывает payload в типизированные колонки.

Здесь же и только здесь нормализуется время: строка ISO 8601
разбирается, требует часового пояса, приводится к UTC и ложится в
колонку `timestamp[us, UTC]`; события каждого клиента упорядочены по
нормализованному времени. Строка, которую нельзя разобрать
однозначно, останавливает этап.

```
RAW           2025-03-18T19:32:00+05:00
PREPROCESSED  2025-03-18T14:32:00Z
```

Все последующие этапы — словарь, кодирование, календарь, сортировка и
маска целей — читают уже нормализованное время и пояс второй раз
не переводят.

В `events.parquet` лежит широкая таблица смысловых данных: конверт
(`client_id`, `event_time`, `source`, `type`) и поля событий — суммы, валюты,
направления, статусы, причины, продуктовые и кредитные характеристики,
признаки мерчанта, коммуникации и действия в приложении.

Продукт идёт кодом каталога: `product_id` и `previous_product_id` становятся
категориями `product` и `previous_product`, одним ключом во всех источниках
(продуктовые события, заявки, коммуникации, баннеры, экраны приложения). Роль
продукта — открыт, запрошен, предложен, показан — называет тип события. Без кода
закрытие, активацию или блокировку кредитной карты не отличить от того же со
вкладом. Продукт, которого `train` не видел, кодируется `[UNK]`.

Чего там нет:

- служебной трассировки и признаков качества (номеров клиента и события,
  ссылок на строку RAW, флагов окна и разрывов);
- идентификаторов сущностей (`contract_id`, `account_id`, `card_id`,
  `application_id`, `session_id`, `transfer_id`, `merchant_id` и прочих) и локальных
  ссылок вида `ACCOUNT_1`: точные связи модели не передаются;
- второй копии текста: нормализованное значение лежит в самих
  `merchant_name` и `counterparty`;
- календарных дат (`due_date`, `accrual_period`): время модель получает
  отдельным каналом — нормализованным `event_time` и признаками календаря.
  Месяц начисления это месяц самого события, и `event_time` уже его называет;
  словарь же превратил бы его в список конкретных месяцев, где первый же
  месяц после `train` стал бы `[UNK]`.

Порядок строк задают сами данные: `client_id`, `event_time`, затем при
равном времени причинный приоритет типа события из `EVENT_TYPES`
(заявка раньше решения по ней), затем `type`, `source` и остальные поля
в порядке имени. Ни приоритет, ни индекс сортировки рядом не хранятся.
Результат группы это ровно один файл: `events.parquet`. Анкета не
копируется — чистить в ней нечего, и следующие этапы читают её прямо
из `data/01_raw/<group>/profile.parquet`. Любая строка, которую нельзя разобрать
по контракту, останавливает этап, и частичный результат не сохраняется.

Пример для модели — события строго раньше cutoff группы (`final_cutoff`) и
анкета на тот же cutoff (`profile_semantics:
attributes_and_lifelong_at_event_cutoff`):

```
Profile @ cutoff = Attributes @ cutoff + Lifelong: вехи строго раньше cutoff
```

Данных позже cutoff нет ни в событиях, ни в анкете. Граница у вех та же
полуоткрытая, что у событий: веха ровно в cutoff уже будущее.

Attributes — поля анкеты. Снимок лежит на границу выгрузки `as_of` (cutoff
позже `as_of` — ошибка) и на cutoff откатывается по ленте:
поля, которые меняет событие `profile_change`, возвращаются к прежнему значению
первого изменения в момент cutoff или позже. Возраст `age` — полных лет на
местную дату cutoff по `birth_date`, с учётом дня и месяца рождения; сама дата
рождения в анкету не идёт. Признака пенсионера среди Attributes нет: он был
производным от возраста и начального вида дохода, а обе части модель уже видит.

Стаж `job_tenure_months` считается по записям банка о работе: стаж на последней
работе по найму, о которой банк узнал строго раньше cutoff, — полных месяцев от
её начала до cutoff, меткой полугодия `0-5`, `6-11`, `12-17`, … Метку задаёт шаг,
а не данные. Нет такой работы или последняя запись банка — «работы нет» — поля
нет.

Всего Attributes 13: `age`, `gender`, `family_status`, `education`, `region`,
`city`, `housing_type`, `income_type`, `declared_income`, `industry`,
`income_day`, `children`, `job_tenure_months`. В анкету не идут:

- поля, выводимые из событий истории (`contracts_count`, `active_contracts`,
  `holds_*`, `credit_limit`, `credit_utilization`) — на закрытом событии они были
  бы готовым ответом;
- поля, выводимые из вехи (`relationship_months`): модель получает саму веху
  `bank_registered` с её временем, а не посчитанный из неё стаж.

Ключей у этих полей нет и в реестре смыслов (`keys_registry` берёт поля анкеты из
`INCLUDED_FIELDS`), поэтому нет и токенов в словаре: иначе ключ, числовая шкала и
значения поля, которого модель никогда не видит, лежали бы в словаре мёртвыми строками.

Lifelong — вехи снимка с временем строго раньше cutoff. Отката им не нужно: у
каждой своё время. Вехи лежат в анкете, а не в ленте, поэтому переживают окно
выгрузки: клиент, пришедший в 2017 году, остаётся клиентом с 2017 года, даже
если старые события выпали из примера по пределу `max_events`.

Сами изменения анкеты остаются событиями ленты, но целями MLM не бывают: их итог
уже лежит в анкете на cutoff. Так же не бывает целью событие-источник вехи: веха
его выдала бы. Источник находит не время, а ссылка вехи `source_id` на карту или
договор: препроцессинг помечает строки её акта (`lifelong_source`), и пометка едет
с событием до маски целей. Соседнее событие того же момента и остальные события
тех же типов учатся как обычно. Список полей и причины —
`src/preprocessing/profile_state.py`, правило целей — `src/dataset/targets.py`.

Этапы 06 и 09 пишут рядом с результатом `lineage.json` (формат набора, смысл
анкеты и набор её вех); каталог без него или с другим отвергается с командой
пересборки. Набор 05 несёт те же поля в своём `meta.json`, и его читатель сверяет
их так же.

## 3. Словарь

Все словари, границы чисел и BPE учатся только на train: лента из
`data/02_preprocessed/train/events.parquet`, анкета из `data/01_raw/train/profile.parquet`.

```bash
python -m src.tokenization.run special-tokens   # data/03_vocab/special_tokens.json
python -m src.tokenization.run key-vocab        # data/03_vocab/key_vocab.json
python -m src.tokenization.run value-vocab      # data/03_vocab/value_vocab.json
python -m src.tokenization.run buckets          # data/03_vocab/buckets.json
python -m src.tokenization.run bpe              # data/03_vocab/bpe.json
python -m src.tokenization.run final-vocab      # data/03_vocab/final_vocab.json
python -m src.tokenization.run value-weights    # data/03_vocab/value_weights.json
```

Для прода те же семь этапов запускаются одной командой:

```bash
python -m src.tokenization.run fit
```

`fit` вызывает те же функции, что и отдельные команды, поэтому результат
совпадает, и читает train один раз: словарь значений, диапазоны, BPE и веса
значений учатся на одном корпусе. При ошибке он останавливается и называет
проблемный этап; `final_vocab.json` и `value_weights.json` при этом не остаются
от прежней сборки.

Каждый файл решает ровно одну задачу и не повторяет содержимое соседних.

`special_tokens.json` — служебные токены и их ID. Их пять:

```json
{"[PAD]": 0, "[UNK]": 1, "[MASK]": 2, "[EVT]": 3, "[USR]": 4}
```

`key_vocab.json` — название ключа и его ID:

```json
{"amount_due": 5, "amount_or_limit": 6, "event_type": 31}
```

`value_vocab.json` — категории train, сгруппированные по ключу. Идентификатор
определяет связка ключ + значение: одинаковая запись у разных ключей это разные
факты.

```json
{"app_domain": {"auth": 118, "home": 119},
 "profile_children": {"0": 153}}
```

Правило одно и без исключений: словарь значений у каждого ключа свой.
Одинаковая запись у разных ключей это разные факты — `active` у карты и
`active` у обращения общего номера не получают, и `2` у числа детей не делит
номер с `2` у прежнего числа детей. Ключ в последовательности лежит рядом со
значением, и что это за поле, модель узнаёт из него.

Категорией бывает и число. Небольшой дискретный счётчик и срок договора
кодируются ТОЧНЫМ значением, а не диапазоном: срок это выбор из каталожного
меню, а не величина, и между 12 и 18 месяцами промежуточных сроков не бывает;
у числа детей важно само число, а не порядок величины. Так
кодируются `term`, `requested_term`, `approved_term`, `installment_no`,
`profile_children` с его прежним и новым значением и возраст `profile_age` —
полных лет на cutoff: каждый
возраст, встреченный на train, получает своё значение (`value:profile_age=36`),
а не диапазон вроде 35–44.

Число, которого на train не было, номера не получает: на val и test оно
кодируется `[UNK]`, как и любая невиданная категория. Предел значений нигде не
выдумывается, и словарь по val и test не подгоняется.

`buckets.json` — диапазоны каждого числового ключа. Числами остались
непрерывные величины, где соседние значения близки по смыслу: деньги, ставка и
дни просрочки. `min` включительно, `max` не включительно; `null` означает открытую
сторону, а `min = max = 0` — отдельный нулевой диапазон, который проверяется
первым.

Две настройки кодировщика числа (`--config` у `fit`, `numeric_encoders.<ключ>`):

- `negative_bins` — у ключа с разрешённым минусом минус учится своими квантилями с
  границей в нуле. По умолчанию у `balance_after` их 4: долг до −2 млн больше не делит
  диапазон с остатком 0…359;
- `split_by` — своя шкала на каждое значение категориального ключа того же события. По
  умолчанию `transaction_amount` делится по `direction`, что даёт `transaction_amount_debit_bucket_N`,
  `transaction_amount_credit_bucket_N` и `transaction_amount_no_direction_bucket_N` (у
  операций приложения направления нет): зарплаты больше не сходятся в верхний диапазон
  покупок. У таких диапазонов в файле есть `split_by` и `when`; число ищется среди
  диапазонов своего условия, невиданное train условие — `[UNK]`.

```json
{"amount_due": {"amount_due_bucket_1": {"id": 283, "min": null, "max": 1000}}}
```

`bpe.json` — стандартный файл библиотеки `tokenizers`, записанный её же
`Tokenizer.save`, и читаемый обратно `Tokenizer.from_file`. Настройки обучения
живут в конфигурации, а не в файле.

Куски BPE растут из символов train-текстов (`bpe.alphabet = "characters"`): пробел —
обычный символ куска (` res`, `ко`), без подмены `Ġ`/`Ã…`. Невиданный символ
кодируется своими байтами `<0xNN>` (byte fallback, 256 кусков), поэтому любое, в том
числе незнакомое, название разбивается без потерь. Прежний ByteLevel доступен как
`"bytes"`. Офлайн на тех же текстах границы кусков у них совпадают у 99.5% вхождений
`merchant_name` и у 100% `counterparty`, длина и покрытие те же
(`audit/2026-09-28-project/wave4/README.md`).

`final_vocab.json` — уникальное имя токена и его глобальный ID. Имя и номер
соответствуют друг другу один к одному: иначе пространство ID перестало бы
совпадать с числом строк embedding. Префикс отделяет виды токенов друг от
друга:

```json
{"[PAD]": 0, "key:amount_due": 6, "value:app_domain=auth": 118,
 "bucket:amount_due_bucket_1": 283, "bpe:a": 470}
```

ID идут подряд от нуля: специальные, ключи, категории, диапазоны, куски BPE,
и в каждом файле возрастают по ходу чтения. После сборки словарь не меняется.

Номера ключей определены одним реестром смыслов и от данных не зависят.
Номера категорий, диапазонов и кусков BPE зависят от корпуса `train`:
в примерах выше они показывают форму записи, а не конкретные значения
вашей сборки.

`value_weights.json` — статистика train для взвешенного value-маскирования
(раздел 5.3). Она не часть словаря: номера токенов не меняет, и отпечаток словаря
(`vocabulary` в `meta.json` этапа 04) её не включает. Этап `value-weights` идёт
последним, в том же проходе по train, что и остальные.

- **Что считается.** Вхождения значений ключей событий train — анкета и изменения
  анкеты целями не бывают, — записанные теми же номерами токенов, что даёт
  кодирование 04: категория, номер диапазона (со `split_by` — своего условия),
  куски BPE текста.
- **Точность счёта.** Категории и тексты сосчитаны точно. Числа — по выборке fit
  (200 тыс. значений с наименьшим хэшем на ключ): пока значений меньше, выборка и
  есть все значения, иначе счёт диапазона — оценка, и ключ помечен `estimated`.
- **По ключу:** `count`, `distinct`, `entropy`, `normalized_entropy`, `key_weight`.
- **По значению:** `tokens`, `label`, `count`, `frequency`, `value_weight`.
- **Общее:** `scale` и параметры формулы (`method`).
- **Сверка словаря.** Файл помнит отпечаток словаря, под который собран. Чтение
  отказывает, если словарь другой, и называет команду пересборки.

## 4. Кодирование групп

```bash
python -m src.tokenization.run encode train
python -m src.tokenization.run encode val
python -m src.tokenization.run encode test
```

Вход: `data/02_preprocessed/<group>/events.parquet`, `data/01_raw/<group>/profile.parquet`
и словарь из `data/03_vocab/`. Выход: `data/04_tokenized/<group>/events.parquet` и
`profile.parquet`.

Ничего не дообучается: значение, которого на train не было, кодируется `[UNK]`.
Отсутствующее поле в последовательность не попадает вовсе, пустой после
нормализации текст — тоже.

```
events.parquet   client_id, event_time, key_ids, value_ids, positions, calendar
profile.parquet  client_id, key_ids, value_ids, positions, time
```

Анкета это `[USR]`, пары Attributes по возрастанию номера ключа, затем по паре на
каждую веху Lifelong, по времени: ключ `profile_lifelong`, значение — тип вехи.
`time` — время каждого токена анкеты: у вехи её момент, у `[USR]` и Attributes
`null`. Словарь без ключа `profile_lifelong` собран прежним кодом, и кодирование
на нём останавливается.

`positions` это номер куска внутри значения: `0` начинает новое значение, а
`1, 2, …` продолжают его кусками BPE. Отдельных массивов с границами значений
нет — границы и есть эти нули. Первый токен записи это маркер `[EVT]` или
`[USR]`: он тоже стоит на нуле, но значением не является и при разборе
пропускается. Два соседних значения с одним ключом остаются двумя: каждое
начинает свой ноль. Числа токенов и названия ключей не хранятся: первое
считается по длине массивов, второе восстанавливается словарём.

## 5. Датасет

```bash
python -m src.dataset.run train
python -m src.dataset.run val
python -m src.dataset.run test
```

Вход: `data/04_tokenized/<group>/` и словарь из `data/03_vocab/`.
Результат: `data/05_dataset/<group>/samples.parquet`. Строка это один клиент на
конечный cutoff своей группы.

```
client_id
key_ids, value_ids, positions          последовательность событий клиента
event_starts, event_lengths            границы каждого события
event_time, calendar                   время событий и календарный канал
target_event_mask                      что разрешено маскировать и предсказывать
profile_key_ids, profile_value_ids,    токены профиля
profile_positions
profile_time                           время токена анкеты: у вехи её момент, иначе null
```

Событие лежит в последовательности целиком: `event_starts` и `event_lengths`
дают его окно, а внутри окна значения разбираются по `positions` — ноль начинает
значение, следующие числа продолжают его кусками BPE. Первый токен окна это
маркер события, и в разбор он не входит. Ключ значения берётся из `key_ids` по
его нулевой позиции. Числа событий, токенов и значений это длины и нули
массивов, и отдельными колонками они не хранятся.

У каждой группы два окна, оба полуоткрытые `[начало, конец)`, границы — полночь
по времени банка (`default_windows()` в `src/preprocessing/settings.py`):

```
группа  контекст                   окно маскирования (цели MLM)
train   [2024-01-01, 2026-01-01)   [2024-01-01, 2026-01-01)
val     [2024-01-01, 2026-05-01)   [2026-01-01, 2026-05-01)
test    [2024-01-01, 2026-09-01)   [2026-05-01, 2026-09-01)
```

Контекст — `[history_start, final_cutoff)` — вся выгрузка группы (`DATASETS`
генератора): эти события пример видит, анкета снята на `final_cutoff`. Окно
маскирования — `[target_start, target_end)` — единственное место, где событие
может стать целью. Кандидат в цели (`target_event_mask`) — событие, которое:

```
лежит в окне маскирования своей группы   target_start <= event_time < target_end
не изменение анкеты                      profile_change — никогда
не источник вехи Lifelong                lifelong_source — никогда
```

Событие вне окна остаётся в примере контекстом: внимание двунаправленное, и цель
`val` или `test` видит всю историю до общего cutoff. Клиенты групп не
пересекаются. Маску разыгрывает читатель набора (раздел 5.3): у `val` и `test` она
одна и та же при каждом чтении, `train` на этапе 12 получает новую каждую эпоху.
Отбор контекста `max_events` окна не меняет.

Окно группы записано в `meta.json` набора (`window`), окна всех групп — в
`lineage.json` этапов 06 и 09 (`windows`). Набор или клеймо без окон или с
другими окнами отвергаются с командой пересборки.

В `meta.json` лежит и точка отсчёта времени событий `time_anchor` (раздел 5.1):
`cutoff` по умолчанию, `last_event` — прежний отсчёт. Она задаётся конфигом
набора (`DatasetConfig.time_anchor`, `--config` с `{"time_anchor": "last_event"}`)
и одна у всех групп: обучение отказывает, если у train и val она разная.

Длинная история усекается двумя пределами сразу: по числу событий и по сумме их
токенов. Политика по умолчанию — `recent` с `max_events = 12000` и
`max_tokens = 58000` (`MAX_EVENTS`, `MAX_TOKENS` в `src/dataset/settings.py`):

```
n_events <= 12000 и n_tokens <= 58000   история целиком
иначе                                    самый длинный свежий хвост из целых
                                         событий, укладывающийся в оба предела
```

`n_tokens` — токены событий; анкета не считается и не режется. Хвост растёт от
самого свежего события, пока следующее не нарушило бы любой предел, поэтому
событие никогда не режется посередине, а порядок остаётся хронологическим.

Пределы нужны шагу обучения: память forward+backward растёт линейно с числом
токенов. У клиентов от 5 до 13 токенов на событие, и 12 000 событий — это до
99 794 токенов; при архитектуре 1/5/2 шаг на 60 021 токене занимает 2,97 ГиБ из
3,2 свободных у RTX 3050 под WSL, на 70 003 — уже не помещается. Старые события
отдельно не сохраняются — долгосрочные факты о клиенте лежат в Lifelong анкеты.
Все массивы примера (`event_starts`, `event_lengths`, `event_time`, `calendar`,
`target_event_mask`) собираются из оставшихся событий заново; анкета отбором не
затрагивается. Политика `all` берёт историю целиком, а пределы для неё — граница,
за которой сборка останавливается.

Для `val` и `test` потеря события периода целей запрещена: если хвост в пределах
не вмещает период целей, сборка останавливается с ошибкой, а не выбрасывает цели.
В `meta.json` записаны политика отбора, число усечённых примеров и отброшенных
событий.

Выравнивания по `[PAD]` в примере нет: у каждого клиента своя длина, и `[PAD]`
в сохранённом примере запрещён. Набор — единственный вход модели на диске; его
группа строк (`row_group_samples`, 32 клиента, в порядке файла) — единица
чтения обучения и этапов 06, 08–11, а её номер — `batch_index` в их результатах.

## 5.1. Временные позиции (при чтении набора)

Отдельной команды и каталога нет. Позиции считает читатель набора
`src.temporal.samples.TemporalGroup` из `event_time` и `profile_time` той же строки
`data/05_dataset/<group>/samples.parquet`, при каждом чтении: две колонки
(`event_time_log`, `profile_time_log`) не стоят отдельной копии примера на диске.
Читают через него обучение (`src.mlm.inputs`), этапы 06, 08–11 и вход на T.

Позиция это расстояние в секундах от события до cutoff T примера, сжатое
логарифмом:

```
event_time_log[i] = 8 * log1p(delta_i / 8),   delta_i = T - t_i
```

У последнего события позиция — его давность до T, у более старых она тем больше, чем
они древнее. `[USR]` (ноль, то есть T) лежит на одной оси с событиями и вехами анкеты,
и давность «последнее событие → T» модели видна. Пустая история даёт пустой массив.
Тип `float32`, одно число на событие.

Масштаб восемь секунд взят из статьи вслед за Pragmatiq. При малых промежутках
`8*log1p(x/8)` почти равно `x`, поэтому секунды сохраняются линейно, а месяцы
сжимаются: в банковской ленте события идут то секундами, то месяцами, и без
сжатия дальний хвост забил бы всю шкалу. На настоящих данных это видно так:

Пример ниже снят при прежнем отсчёте от последнего события (`--anchor last_event`),
поэтому у последнего события ноль; форма шкалы та же:

```
  i      event_time (UTC)        event_time_log   прошло до последнего
  0      2024-01-01 03:44:22      127.0497          63126638 c
  2403   2025-04-20 07:30:31      118.6434          22073069 c
  4804   2025-12-31 13:07:31       62.9280             20849 c
  4805   2025-12-31 18:45:00       34.6459               600 c
  4806   2025-12-31 18:55:00        0.0000                 0 c
```

Два года истории занимают 127 единиц шкалы, а последние десять минут — 34: вблизи
настоящего шкала подробная, вдали сжатая.

Вторая колонка — `profile_time_log`: время токенов анкеты той же шкалой и тоже
от cutoff примера:

```
profile_time_log[j] = 8 * log1p((cutoff - t_j) / 8)   у вехи Lifelong
profile_time_log[j] = 0                               у [USR] и Attributes
```

Анкета описывает клиента на cutoff, поэтому веха 2022 года дальше вехи 2025-го,
когда бы ни было последнее событие. Веха не раньше cutoff — ошибка данных.

Отсчёт от cutoff стал умолчанием 2026-09-29 по решению владельца проекта, без A/B
(эксперимент E7 волны 4). Прежний отсчёт — от последнего ВЫБРАННОГО события —
остался для сравнения: набор, собранный с `{"time_anchor": "last_event"}` (раздел 5).
Тогда у последнего события позиция ровно `0`, и если датасет отбросил хвост истории,
отсчёт идёт от нового хвоста.

Выбор записан в `data/05_dataset/<group>/meta.json` (`time_anchor`), и вход на T
берёт его из `05_dataset/train`. Набор без этой записи собран прежним кодом, и его
не читает никто. При чтении позиции проверяются: к концу ленты они не растут, ноль
у последнего события — при отсчёте от него, у недатированного токена анкеты ровно
ноль, у вехи — положительная давность.

Это не календарь и не `positions`: календарь говорит, когда по часам произошло
событие, `positions` нумерует куски внутри значения, а здесь лежит только
расстояние между событиями. Три разных канала. Время не попадает в словарь и не
бакетизируется.

Чтение ничего не отбирает, не переставляет и не кодирует.

Посмотреть на строку:

```bash
python -c "from src.temporal.samples import TemporalGroup; r=TemporalGroup('train').row_group(0).to_pylist()[0]; print(list(zip(r['event_time'][-5:], r['event_time_log'][-5:])))"
```

## 5.3. Маскирование (при чтении набора)

Отдельной команды и каталога нет. Маску разыгрывает читатель входа модели
(`src.mlm.inputs.Source`, `src.embedding.inputs.Source`) для каждого клиента при
чтении: `src.masking.choose` решает, что скрыть и что предсказать, `apply`
подставляет `[MASK]` или `[UNK]` и ставит метки. На клиента получается:

```
value_ids                              что увидит модель
labels                                 что предсказывать; -100 значит «не в loss»
reason                                 чем выбрано: event, key, value или пусто
```

`key_ids`, `positions`, границы событий, время, временные позиции и календарь
маскированием не затрагиваются вовсе. Ключ остаётся видимым — предсказывается
значение.

Допустимо только значение события, у которого стоит `target_event_mask`.
`[EVT]`, `[USR]`, анкета, время и календарь не трогаются вовсе: разбор идёт лишь
по окнам таких событий и начинается со следующего после маркера токена. Длина
последовательности не меняется.

Три механизма разыгрываются совместно, и сильнейшая причина побеждает:
**event > key > value**.

```
event   0.10   событие целиком, со всеми его значениями
key     0.10   ключ у клиента, со всеми его значениями в допустимых событиях
value   0.15   отдельное значение; в среднем — своя у каждого значения, ниже
```

Среди выбранных значений доля `0.10` уходит в `[UNK]`: значение портится, но
`labels` остаются `-100`, и причина не пишется — модель видит незнакомое
значение и не получает за него ни награды, ни штрафа. Остальные `0.90` уходят
под `[MASK]`, и в `labels` ложатся исходные `value_ids`.

Все куски одного значения получают одно решение. Название мерчанта из трёх
кусков BPE скрывается целиком:

```
индекс             0        1        2        3        4
key_ids            [EVT]    key:cat  key:name key:name key:name   не меняются
positions          0        0        0        1        2

value_ids_source   [EVT]    470      Mag      n        um
value_ids          [EVT]    [MASK]   [MASK]   [MASK]   [MASK]
labels             -100     470      Mag      n        um
reason             ""       "event"  "event"  "event"  "event"
```

У кусков общий `key_id`, а `positions` `0, 1, 2` говорят, что это одно значение.
Открыть один кусок значило бы показать модели часть ответа.

Здесь конвейер отличается от Pragmatiq намеренно. Там третий механизм —
`token`, и он разыгрывает КАЖДЫЙ токен с вероятностью `0.15`, из-за чего текст
из нескольких кусков может быть скрыт наполовину. У нас он заменён на `value`,
и **вероятность `0.15` относится к значению, а не к токену**.

Выбор детерминирован: поток розыгрыша задан `seed`, группой и `client_id`, а
порядок обхода задан явно, поэтому он не зависит ни от порядка чтения, ни от
того, в какой группе строк или процессе оказался клиент. Маска `val` и `test` с
одним конфигом одна и та же при каждом чтении — по ней сравниваются эпохи;
`train` каждую эпоху получает свою (seed эпохи, раздел 12). Конфиг маски —
`MaskingConfig`, у обучения `--masking-config`, и он действует на train и val
одинаково; лежит он в чекпойнте.

При переходе на маску при чтении она проверена на реальном train из 10 клиентов
против прежнего файла `08_masked`: те же `value_ids`, `labels` и `reason` у каждого
клиента. Порча контекста (ниже) на train ничего не меняет.

**Порча контекста выбранного ключа** (`key_context_corruption_probability`, по
умолчанию `0.5`). У `val` цели — последние 3 месяца из 27, и скрытое значение
ключа почти всегда видно в более раннем событии клиента (аудит: 98% key-целей):
`key` проверял бы копирование, а не восстановление. Поэтому значение ключа,
выбранного механизмом `key`, в событии вне целей независимо портится в `[UNK]` с
этой вероятностью — целиком, со всеми кусками BPE, `labels` `-100`, без причины;
иначе остаётся исходным. Целью такое значение не становится никогда, а цели того
же ключа — по-прежнему `[MASK]` с меткой:

```
история              цель
merchant = [UNK]     merchant = [MASK]   label = Starbucks, в loss
merchant = Magnum
merchant = [UNK]
```

Это отдельный механизм: общий `unknown_probability` от него не растёт, механизмы
`event` и `value` не меняются, а цели и их розыгрыш от настройки не меняются ни на
бит. Розыгрыш идёт своим потоком на пару (клиент, ключ) по вхождениям ключа в
порядке ленты (`seed`, группа, `client_id`, ключ, номер вхождения), поэтому он
детерминирован и не зависит от порядка чтения. На `train` период целей — весь
контекст, и портить там нечего. Закрывать весь контекст `[MASK]`, как делала прежняя
настройка, нельзя: это отнимало бы и законные подсказки.

**Взвешенный механизм value** (`informativeness_weighted_masking`, по умолчанию
включён). При одной вероятности на все значения много целей уходило на почти
константные поля: `currency` — только KZT, `merchant_country` — KZ в 98% train,
и точность MLM росла за их счёт. Поэтому вероятность цели механизма value у каждого
значения своя. Её задаёт статистика train (`value_weights.json` словаря, раздел
3), а решает, как и раньше, розыгрыш своего потока.

Для ключа k: `H_k` — энтропия его значений в train, `K_k` — число различных
значений.

```
key_weight    Hn_k = H_k / log K_k                    0 у константного ключа, 1 у равномерного
value_weight  clip((-log p(v|k) + 1) / (H_k + 1), 0.25, 3)
                                                      частое значение ниже, редкое выше,
                                                      но не выше 3: сюрприз растёт логарифмом
scale         g — средняя вероятность до обрезки по вхождениям train равна value_probability
P(k, v)       clip(value_probability · g · key_weight · value_weight,
                   min_value_probability 0.05, max_value_probability 0.35)
```

Особые случаи:
- значение, которого в train не было (новый текст, `[UNK]`), считается редким:
  `value_weight` = 3;
- ключ без статистики получает `value_probability` в тех же пределах;
- `value_probability` = 0 выключает механизм, без нижнего предела.

На train из 10 клиентов g = 1.84. Вероятности значений:

| Значение | P |
|---|---|
| `currency` (все значения) | 0.05 |
| `merchant_country` | 0.05 |
| `operation_status` | 0.06 |
| `merchant_name`, частое | 0.14 |
| `merchant_name`, редкое | 0.35 |
| `balance_after` | ~0.26 |

Средняя P по допустимым значениям — 0.153, целей примерно столько же, сколько без
взвешивания.

Взвешивание трогает только механизм value:
- механизмы event и key, `[UNK]`, метки, приоритет **event > key > value** и порча
  контекста не меняются;
- значение, уже выбранное через event или key, от веса не зависит;
- розыгрыш тот же — один на значение, в том же порядке, поэтому выключенное
  взвешивание даёт побитно прежнюю маску;
- у включённого меняются решения value, а у последующих целей event и key может
  сдвинуться только выбор между `[MASK]` и `[UNK]`: поток `[UNK]` тянется по одному
  на выбранное значение.

Куда уходят цели маски группы, показывает отчёт без модели:

```bash
python -m src.masking.report val [--masking-config маска.json] [--out отчёт.json]
```

По ключам в отчёте:
- число допустимых значений и доля ключа в данных;
- число целей и их доля — всего и по механизмам;
- сколько выбранных ушло в `[UNK]`;
- доля самого частого значения в данных и среди целей;
- средняя вероятность value;
- расстояние полной вариации между значениями ключа у целей и в данных.

Итогом идёт то же расстояние между долями ключей. На train из 10 клиентов
взвешивание отнимает у `currency` цели value 415 → 140, у `merchant_country` —
636 → 214, у `operation_status` — 574 → 262. Прибавляет `balance_after` 631 → 1043,
`merchant_name` 442 → 687, `merchant_category` 430 → 665.

## 6. Вход модели

```bash
python -m src.embedding.run train
python -m src.embedding.run val
python -m src.embedding.run test
```

Вход: `data/05_dataset/<group>/samples.parquet`. Ключи, номера кусков и анкета
берутся из набора, значения — после маски при чтении (раздел 5.3): модель видит то,
что ей разрешено видеть. Результат: `data/06_embeddings/<group>/weights.pt` —
начальный розыгрыш общей таблицы — и `lineage.json`.

Слой считает прямоугольные тензоры `[B, T]` и `[B, P]`, поэтому группа строк
набора дополняется здесь, в памяти, до самого длинного клиента по трём осям —
токены событий, события (календарь по шесть чисел на событие) и токены анкеты:

- у идентификаторов заполнитель `[PAD]`, у позиций ноль, у календаря и
  `profile_time_log` — `0.0`, у `target_event_mask` — `false`;
- у `event_time` заполнителя нет — `null`: нулевого момента не существует;
- `event_starts` заполняется концом последовательности, а не нулём: пустое
  событие в конце безвредно, а ноль указывал бы на первый настоящий токен;
- настоящее лежит слева, поэтому маска (`token_mask`, `event_mask`,
  `profile_token_mask`) — ровно «номер меньше длины», а смещения остаются теми
  же числами.

`[PAD]` внешне неотличим от маркера события: у него тоже совпадают `key_ids` и
`value_ids`. Отличить их можно ТОЛЬКО по маске. На диск выровненное не пишется.

Вектор обычного токена это сумма трёх слагаемых:

```
E[key_id] · scale  +  E[value_id] · scale  +  P[position]
```

`E` — одна общая обучаемая таблица на ключи и значения: их номера живут в общем
пространстве `final_vocab.json`, поэтому отдельного номера для сочетания ключа
со значением не заводится, сочетание получается сложением. `P` — фиксированная
синусоида номера куска внутри значения: текст приходит несколькими кусками BPE
с одним ключом, и без неё они были бы неразличимы.

`[EVT]` и `[USR]` записаны одним номером в оба слота, поэтому их эмбеддинг
берётся **один раз**, без удвоения и без позиции куска. `[PAD]` зануляется
маской.

Векторы токенов этап не пишет. Их считает модель сама, в прямом проходе этапов
08–11, по номерам токенов из набора и весам из `weights.pt`; при обучении
градиент идёт в ту же таблицу. Снимок векторов всей группы никто не читал, а
стоил он около 160 МиБ на диске на три группы и до 6 ГБ памяти при сборке.
Набор этап всё равно читает целиком: время, маска и маркеры проверяются по
каждой группе строк.

`labels` этот этап не читает вовсе, календарь и `event_time_log` тоже: они
понадобятся энкодеру события и TimeRoPE, а не входу.

## 7. Начальные веса backbone

```bash
python -m src.mlm.init_backbone
```

Вход: веса входного слоя `data/06_embeddings/train/weights.pt` и словарь.
Результат: `data/07_backbone/` — `event.pt`, `profile.pt`, `history.pt` в формате
`weights.pt` этапов 08–10 (`dim`, `config`, `state_dict`) и `lineage.json`.

Ни одного прохода по данным: набор не читается, через энкодеры ничего не идёт.
Веса энкодера определяются его конфигом, длиной вектора `d` из весов этапа 06 и
seed; разыгрываются на CPU, поэтому «тот же seed» значит «те же веса» на любой
машине, а на карту модель переносит уже обучение. Команда занимает секунды и пишет
несколько мегабайт.

Архитектура — значения по умолчанию конфигов энкодеров (`src/event`, `src/profile`,
`src/history` → `settings.py`): `d = 128`, 4 головы; событие — 5 блоков, анкета — 1,
история — 2. Переопределяются тем же JSON, что у этапов 08–10:
`--event-config`, `--profile-config`, `--history-config`.

Единственное место, где конфиг и `d` превращаются в веса, — `initial_event`,
`initial_profile`, `initial_history` в `src/mlm/backbone.py`; ими же пользуются
этапы 08–10. Поэтому `init_backbone` и `python -m src.event.run` при одном конфиге
дают бит в бит одни и те же веса — и те же, что давал код до `init_backbone`.

`lineage.json` называет, из чего собран каталог: происхождение набора, отпечатки
словаря и весов входного слоя, версии кода энкодеров. Модель собирается только из
каталога, где всё это совпадает с текущим; иначе — отказ с командой пересборки.
Модель одна: учится на `train`, и `val`, `test` и отчёт этапа 11 считаются ею же,
а не своим случайным backbone.

## 8. Энкодер события

```bash
python -m src.event.run train
python -m src.event.run val
python -m src.event.run test
```

**Диагностика.** Обучению этот этап не нужен.

Вход: набор 05 (маска и время при чтении) и веса входного слоя из
`data/06_embeddings/<group>/weights.pt`.
Результат: `data/08_events/<group>/events.parquet` и `weights.pt`. Устройство —
`device` в конфиге: `auto` (CUDA, если есть), `cpu` или `cuda`; векторы
возвращаются на CPU перед записью.

Двунаправленный трансформер по токенам **одного** события: токены одного события
не видят токены другого. Маркер `[EVT]` уже стоит первым токеном события, второй
не добавляется, и вектор события читается из колонки 0. Позиционного кодирования
по полям нет — внутри события у полей нет осмысленного порядка.

Календарь события — шесть sin/cos часа, дня недели и дня месяца — проходит через
`Linear(6 → d) → GELU → Linear(d → d)` и **прибавляется к вектору события**, уже
после энкодера. Он описывает событие целиком, а не поле внутри него.

```
batch_index                            номер группы строк набора 05
client_id                              кто это
event                                  номер события у клиента
event_time                             когда оно случилось, UTC
vector                                 d чисел: вектор события после календаря
```

Строка это одно **настоящее** событие: заполнителя в файле нет вовсе. События
идут по клиенту подряд, в хронологическом порядке.

Посмотреть на события одного клиента:

```bash
python -c "import pandas as pd; print(pd.read_parquet('data/08_events/val/events.parquet').head())"
```

Вход: токены анкеты из набора 05 с их временем (`profile_time_log`) и веса

Двунаправленное внимание по всей анкете клиента, без причинной маски; вектор
клиента читается из позиции `[USR]`, которая уже стоит первым токеном. Полей два
десятка, порядка между ними нет, и каждое вправе смотреть на каждое.

```
batch_index                            номер группы строк набора 05
client_id                              кто это
dim                                    длина вектора
profile                                d чисел: вектор анкеты
```

Время входит через TimeRoPE — тот же блок и тот же поворот Q и K, что у
энкодера истории, но со своими весами. `[USR]` и Attributes стоят на нуле, вехи
Lifelong — на своей давности до cutoff, поэтому внимание между вехой и полем
зависит от того, как давно веха случилась. Поворот на нулевой угол ничего не
меняет: без вех энкодер ведёт себя как обычный. Недатированное поле и веху
непосредственно перед cutoff различает ключ, а не время.

## 10. Энкодер истории

```bash
python -m src.history.run train
python -m src.history.run val
python -m src.history.run test
```

**Диагностика.** Обучению этот этап не нужен.

Вход: временные позиции из набора 05, векторы событий этапа 08 и вектор анкеты

Устройство — `device` в конфиге (`auto` берёт CUDA).

Последовательность клиента это `[вектор анкеты, события от старых к новым]`.
Вектор анкеты кладётся прямо в слот `[USR]` — второй маркер не заводится и

Время входит **поворотом, а не слагаемым**: TimeRoPE вращает Q и K на угол,
пропорциональный `event_time_log`, поэтому скалярное произведение зависит от
**разности** позиций — от того, сколько времени прошло между двумя событиями, а
не от их порядкового расстояния. `[USR]` якорится на нуле, то есть в cutoff T (при

```
batch_index                            номер группы строк набора 05
client_id                              кто это
dim                                    длина вектора
client                                 d чисел: итоговое представление клиента
```

Обновлённые векторы **событий** энкодер тоже отдаёт — они нужны MLM-голове, — но
на диск не пишутся: голова считает их сама в том же прямом проходе.

Внимание полное и точное, без окна и без капа на длину истории. Самая длинная
история группы это 23 319 событий, то есть 544 млн пар в матрице внимания;
`F.scaled_dot_product_attention` считает её блочным ядром за 0.7 с и 194 МиБ.
Наивный путь просит 8.11 ГиБ — поэтому здесь своё внимание, а не
`nn.TransformerEncoderLayer`.

## 11. MLM-голова

```bash
python -m src.mlm.run train
python -m src.mlm.run val
python -m src.mlm.run test
```

**Диагностика.** Обучению этот этап не нужен, и `python -m src.mlm.train` его файлов
не читает.

Вход: набор 05 группы (маска и время при чтении); модель — входной слой `data/06_embeddings/train` и
начальные веса `data/07_backbone`, та же, с которой начинается обучение. Результат:
`data/11_mlm/<group>/targets.parquet`, `preview.html` и `weights.pt` головы.

Этап собирает в памяти **дифференцируемый** сквозной проход
`InputEmbedding → Event → Profile → History → MLM` и считает по нему
кросс-энтропию на размеченных токенах. Голова получает на каждую цель три
вектора — сам токен после энкодера события, его событие после истории и клиента
после истории, — склеивает их в `3d`, проводит через `Linear(3d → d)` и получает
логиты скалярным произведением **с той же таблицей эмбеддингов**. Отдельной
выходной таблицы нет: градиент течёт в одни и те же веса с обеих сторон.

```
batch_index, client_id, event, place, position     где лежит цель
key_id, key                                        какой ключ закрыт
label_id, label, unknown_label, reason             что было целью
top_ids, top_names, top_probs                      что предсказано: только top-k
predicted_id, correct, loss                        итог по этой цели
```

Полного массива логитов в файле нет. `preview.html` показывает один
замаскированный пример: если значение состоит из нескольких кусков BPE, видно,
что предсказания относятся к кускам по отдельности.

**Этот этап не обучает.** Веса всех слоёв — начальный розыгрыш по seed, ни
одного шага оптимизатора не сделано; обучение — этап 12. Кросс-энтропия около `ln(1239) = 7.12` означает ровно
случайное угадывание и качеством модели не является.

Цели, у которых исходное значение было `[UNK]` (в `val` 720, в `test` 1049), из
потерь **не исключаются** — так же поступает эталон, — но считаются отдельно:
предсказать «неизвестно» легко, и без отдельного счёта доля угаданного
завышается. Замены на `[UNK]`, которые сделал сам маскер, к этому отношения не
имеют: их он исключил из ошибки ещё при розыгрыше маски, оставив метку −100.

## 12. Обучение

```bash
python -m src.mlm.train                  # до 5 эпох по всем клиентам train, early stopping
python -m src.mlm.train --epochs 3
python -m src.mlm.train --max-steps 100   # план cosine на 5 эпох, прогон до 100 шагов
python -m src.mlm.train --epochs 10 --resume   # продолжить до 10 эпох всего
python -m src.mlm.train --out data/runs/имя      # прогон в своём каталоге
```

Учится только `train`. Вход: набор 05 `train` и `val`, входной слой `data/06_embeddings/train`
и начальные веса `data/07_backbone` (`python -m src.mlm.init_backbone`) — только
веса и конфиги. Этапы 08–11 перед обучением запускать не нужно. Модель:
`d = 128`, 4 головы внимания; энкодер анкеты — 1 блок трансформера, события — 5,
истории — 2, всего 8 (`layers` в `src/profile`, `src/event`, `src/history`
`settings.py`; `init_backbone` записывает конфиг рядом с весами). Сквозной проход
`InputEmbedding → Event ×5 → Profile ×1 → History ×2 → MLM` учит всё сразу: AdamW
получает параметры всей модели. `test` при обучении не читается: validation, выбор
лучшего чекпойнта и early stopping идут по `val`, той же моделью, что учится.

**Устройство.** Обучение идёт только на CUDA: `device` `auto` или `cuda` без CUDA —
ошибка, тихого отката на CPU нет; CPU — только явным `device=cpu` (проверки и
совместимость). На CUDA внимание — только FlashAttention: `attention_backend=auto`
здесь значит «строго flash», без flash-attn или bf16 — ошибка; SDPA — только явным
`attention_backend=sdpa`. Активации — bf16 под autocast, параметры, градиенты и
состояние AdamW — fp32, GradScaler не нужен. Перед первым шагом печатается, что и
где учится:

```
[train] cuda: NVIDIA GeForce RTX 3050 Laptop GPU; CUDA 13.0, PyTorch 2.13.0+cu130, bf16 да
[train] внимание flash (flash-attn 2.8.3.post1, активации bf16); d 128, голов 4; блоков: анкета 1, событие 5, история 2; параметров 2,384,384
```

Где что считается:

```
генерация и препроцессинг            CPU
словарь, BPE                         CPU
кодирование, набор                   CPU
этапы 06 и 07 (init_backbone)        CPU (детерминированный розыгрыш весов)
этапы 08–11 (диагностика)            device: auto | cpu | cuda
обучение (этап 12)                   CUDA обязательна, FlashAttention, bf16
```

Маска разыгрывается при чтении набора (раздел 5.3). У `train` каждая эпоха получает
свою: seed выводится из seed маскирования и номера эпохи, поэтому одна и та же
эпоха даёт одну и ту же маску, а соседние эпохи — разные. У `val` seed тот же, что
в конфиге, и маска одна на все эпохи. Конфиг маскирования передаётся
`--masking-config` и действует на `train` и `val` одинаково; отчёт этапа 11 берёт
`MaskingConfig()` по умолчанию.

После каждой полностью пройденной эпохи та же модель считает потери на `val`:
фиксированная маска, `eval` и `no_grad`, без `backward` и шага оптимизатора.
Клиенты `val` идут теми же micro-batch'ами, что и в обучении. Среднее — по всем
целям `val`:

```
epoch=1 train_loss=… train_top1=… train_top5=… val_loss=7.0123 val_top1=… val_top5=… val_targets=15420 lr=… best_val_loss=7.0123 patience=0/3
```

Эпоха, прерванная `--max-steps`, validation не получает.

Группа строк набора здесь только единица чтения. Клиенты идут потоком и
собираются в **micro-batch** по бюджету токенов `token_budget` (48 000). Цена
клиента — `n_tokens + profile_n_tokens + 1`: токены событий, токены анкеты и слот
`[USR]`, как в `dynamiq-ai/pragmatiq`. Позиции истории (`n_events + 1`) отдельно не
считаются: у каждого события есть хотя бы токен `[EVT]`, поэтому история клиента не
длиннее его цены. Клиент, который дороже всего бюджета, идёт отдельным micro-batch'ем.

На micro-batch модель вызывается **один раз**. Micro-batch плоский, без `[PAD]`:
токены событий, события и токены анкет всех клиентов лежат подряд, а границы
хранятся в `cu_seqlens` — событий, анкет и историй (у истории клиента первым идёт
слот анкеты, затем его события). Каждый энкодер считает свои сегменты по
**корзинам длины** `ceil(log2(длина))`: прямоугольник с заполнителем есть только
внутри корзины и только до её наибольшей длины, поэтому клиент с 6500 событиями
не растягивает историю остальных. Голова считает все цели micro-batch сразу.

`grad_accum_steps` micro-batch'ей (по умолчанию 1) дают один шаг `AdamW`. `backward`
идёт по сумме потерь целей каждого micro-batch, а перед шагом градиенты делятся на
число целей окна: это градиент среднего по всем целям окна. Окно без целей шага не
делает; неполное окно в конце эпохи шаг делает. `step` и `--max-steps` считают
шаги оптимизатора. Порядок шага:

```
backward (по micro-batch'ам окна) -> grad /= цели окна -> clip_grad_norm_(max_grad_norm)
  -> optimizer.step() -> scheduler.step() -> zero_grad
```

В лог идёт строка на шаг, `lr` — с которым сделан этот шаг:

```
epoch=1 step=42 loss=6.8124 targets=18432 micro_batches=4 lr=1.26e-04 grad_norm=0.412 wait=0.00s time=0.21s
```

`grad_norm` — норма градиента окна до клипа, `wait` — сколько цикл ждал данных
(чтение группы строк, маска, сборка), `time` — время шага целиком.

**Нечисловой шаг.** Если loss окна или норма градиента не число, обучение
останавливается ошибкой **до** `optimizer.step`: один такой шаг сделал бы нечисловыми
все веса и состояние AdamW, а следующий чекпойнт сохранил бы их. Веса и AdamW не
тронуты, на диске остаётся чекпойнт прошлой эпохи. Нечисловой `val_loss` тоже
останавливает обучение — до записи чекпойнтов эпохи.

**LR.** `s` — число уже сделанных шагов, LR шага `s + 1`:

- `s < warmup_steps`: `learning_rate * (s + 1) / warmup_steps`;
- дальше cosine: `p = min(1, (s - warmup_steps) / (total - warmup_steps))`,
  `lr = min_learning_rate + (learning_rate - min_learning_rate) * 0.5 * (1 + cos(pi * p))`.

`total` — горизонт расписания, `ceil(micro-batch'ей эпохи / grad_accum_steps) * --epochs`.
Он зависит только от `--epochs`: `--max-steps` в него не входит и кривую не укорачивает —
он останавливает прогон. Поэтому `--epochs 10 --max-steps 100` — это cosine на все десять
эпох, остановленный на сотом шаге, а `--epochs 10 --resume` продолжает ту же кривую без
скачка. Число micro-batch'ей считается до обучения по длинам клиентов, без модели. Окно
без целей шага не делает, поэтому `total` — верхняя оценка.

**Чекпойнты** — каталог прогона: `data/12_train/` или заданный `--out`:

- `checkpoint.pt` — последний: после каждой полной эпохи и при остановке `--max-steps`
  посреди эпохи;
- `best_checkpoint.pt` — после validation, если
  `val_loss < best_val_loss - early_stopping_min_delta` (первая эпоха — всегда);
- `epochs/epoch_NN.pt` — веса после каждой полной эпохи: `model_state_dict`, `config`,
  `masking`, `backbone`, `data`, `history` (≈10 МБ на эпоху). Нужны, чтобы выбрать эпоху
  не только по MLM `val_loss` и строить кривые «эпоха → качество» без переобучения;
- `telemetry.jsonl` — строки JSON трёх видов (`kind`):
  - `run` — начало прогона и каждого продолжения: `epoch`, `step`, `epochs`,
    `planned_epochs`, `total_steps` (горизонт cosine), `max_steps`, `max_grad_norm`,
    `resumed`;
  - `step` — шаг оптимизатора, те же числа, что в строке лога: `loss`, `targets`,
    `micro_batches`, `tokens` (токены событий и анкет окна), `lr`, `grad_norm` (до клипа),
    `wait_seconds`, `seconds`;
  - `epoch` — полная эпоха: `train_loss`, `val_loss`, `learning_rate` (те же, что в истории
    чекпойнта), `train_seconds`, `val_seconds`, `data_wait_seconds`, `steps`,
    `grad_norm_mean`, `grad_norm_max`, `clipped_share`, `cuda_peak_allocated_gib`,
    `cuda_peak_reserved_gib`.

  Отдельно от чекпойнта: время стены не результат обучения, а продолжение обязано дать
  тот же чекпойнт, что непрерывный прогон. У эпохи, продолженной посередине, время и нормы
  описывают только часть после продолжения. Строка пишется целиком одним `write`; её
  читает живой дашборд (ниже).

Формат у обоих один и полный: `model_state_dict`, `optimizer_state_dict`,
`scheduler_state_dict`, `scheduler_total`, `scheduler_epochs`, `epoch`, `epoch_complete`, `micro_batches_done`, `step`,
`best_val_loss`, `epochs_without_improvement`, `config`, `masking`, состояние генераторов
случайности, `backbone` и `data`. Запись идёт через временный файл. Новое обучение без
`--resume` удаляет `checkpoint.pt`, `best_checkpoint.pt`, `epochs/` и `telemetry.jsonl`
прошлого прогона **своего каталога** — после того, как модель, оптимизатор, расписание и
`val` собрались: падение на сборке прошлого обучения не стоит. Чужие каталоги прогонов не
трогаются: законченный прогон, который нужно сохранить, переносится в `data/runs/` или
учится сразу с `--out`.

**Происхождение.** Чекпойнт помнит, на чём учился:

- `backbone` — `lineage.json` каталога `data/07_backbone`: архитектура энкодеров (слои,
  головы, dropout, `rope_base`), отпечатки словаря и входного слоя, версии кода;
- `data` — sha256 наборов, которые читает обучение (`05_dataset/train`,
  `05_dataset/val`), и точка отсчёта их времени (`time_anchor`); маска `val` задана
  конфигом маскирования, а он лежит в чекпойнте сам. При взвешенном value — ещё
  sha256 `03_vocab/value_weights.json`: перефит без переобучения дал бы другие цели.

`--resume` сверяет оба с текущими и при расхождении отказывает, не тронув ни одного
файла: иначе продолжение пошло бы на других клиентах или веса легли бы на другую
архитектуру — другое число голов или `rope_base` загружаются в те же тензоры молча.
Обученную модель для диагностики и оценки собирает `load_trained`: он принимает
`checkpoint.pt`, `best_checkpoint.pt` и веса эпохи и сверяет `backbone`.

**Метрики эпохи.** Кроме потерь считается точность MLM: Top-1 — доля целей, у
которых первый ответ модели равен цели, Top-5 — доля целей в первых пяти. Обе только
по настоящим целям (`labels != -100`): контекст, незакрытые токены и запрещённые цели
в знаменатель не входят; без целей доли нет. На `train` точность копится по
micro-batch'ам эпохи (в режиме обучения, по меняющимся весам), на `val` — по
фиксированной маске, поэтому `val` сравним между эпохами. После эпохи печатается
строка

```
epoch=… train_loss=… train_top1=… train_top5=… val_loss=… val_top1=… val_top5=… lr=… …
```

и та же запись добавляется в `history` чекпойнта. Лучший чекпойнт — по `val_loss`.

Следом строка о времени, градиенте и памяти и строка разбивки `val`:

```
[epoch 3] train 27.9 мин, из них ожидание данных 8.1 мин (29%), val 0.9 мин; шагов 6876, норма градиента средняя 0.412 наибольшая 3.210, клип 12.3%; пик CUDA allocated 2.35 ГиБ, reserved 3.24 ГиБ
[epoch 3] val nll 1.4123; nll/top1 по механизму: event 1.832/0.611, key 0.412/0.935, value 1.101/0.790; по длине истории: 0-100 …, 100-300 …, 300-1000 …, 1000-3000 …, 3000+ …
```

**Разбивка `val`** (`history[…]["val_detail"]`): NLL **без** сглаживания меток и Top-1 по
каждой цели, сложенные по механизму маски (`event`, `key`, `value`), по корзине длины
истории клиента (`0-100`, `100-300`, `300-1000`, `1000-3000`, `3000+` событий) и по ключу
цели. `val_loss` сглажен (`label_smoothing`), и цели в нём дают в основном длинные
истории: разбивка показывает, из чего он сложен. На выбор лучшего чекпойнта и early
stopping она не влияет.

**Early stopping.** После каждой полной эпохи: улучшение больше
`early_stopping_min_delta` обнуляет счётчик, иначе он растёт на 1. Счётчик
`early_stopping_patience` — обучение останавливается. `val` без целей не считается ни
тем, ни другим.

**`--resume`** продолжает с `checkpoint.pt`: веса, AdamW, расписание, счётчики и
генераторы. Конфиг и маскирование берутся из чекпойнта, поэтому `--config` и
`--masking-config` с ним не задаются. Полная эпоха `e` — продолжение с `e + 1`;
эпоха, прерванная `--max-steps`, — с того же места, уже пройденные micro-batch'и
пропускаются без прохода модели. Маска эпохи — та же `for_epoch(masking, epoch)`.
`--epochs` и `--max-steps` — общие пределы от начала обучения. Горизонт расписания при
`--resume` не пересчитывается: берутся `scheduler_total` и `scheduler_epochs` из
чекпойнта, и продолжение проверяет, что расписание стоит ровно на сделанном шаге. План
замораживается первым запуском, поэтому увеличенный на `--resume` `--epochs` добавляет
эпохи уже на `min_learning_rate`, а не пересчитывает пройденную часть кривой; команда
говорит об этом строкой в логе. Старый чекпойнт без новых полей продолжить нельзя —
будет понятная ошибка. `--resume --out каталог` продолжает прогон этого каталога.

`learning_rate` (3e-4), `weight_decay` (0.01), `token_budget` (48 000), `grad_accum_steps` (1),
`warmup_steps` (100), `min_learning_rate` (3e-5), `max_grad_norm` (1.0),
`early_stopping_patience` (3) и `early_stopping_min_delta` (0.0) задаются тем же JSON,
что и конфиг головы: `--config`.

**Бэкенд внимания** — `attention_backend` в том же JSON:

- `auto` (по умолчанию) — `flash`, если есть CUDA и библиотека `flash-attn`,
  иначе `sdpa`;
- `flash` — varlen FlashAttention (`flash_attn_varlen_func`): плоские Q/K/V
  `[позиции, головы, размер головы]` и `cu_seqlens`, без единой позиции
  заполнителя, во всех трёх энкодерах — события, анкеты и истории. Сегмент видит
  только себя. Без CUDA или без библиотеки — ошибка, тихой подмены нет;
- `sdpa` — корзины длины, описанные выше. Это запасной путь: CPU, fp32, нет
  `flash-attn`.

Оба пути считают одну и ту же формулу на одних и тех же весах: varlen-слои
читают параметры существующих модулей, поэтому начальные веса backbone и чекпойнт
грузятся без изменений.

**Память шага.**

- Сегменты идут в `flash_attn_varlen_func` группами подряд, а не одним вызовом:
  - backward flash-attn заводит буфер `dq_accum` fp32 на `позиции + 128·сегменты`
    строк;
  - у энкодера события сегмент — событие, и клиент из 12 000 событий требовал бы
    около 0,8 ГБ, почти целиком запаса;
  - группа держит не больше `FLASH_ROWS` = 2¹⁷ строк вместе с запасом (буфер
    ≤ 64 МиБ);
  - результат тот же бит в бит, включая маски dropout: смещение генератора у группы
    то же, что у её части одного вызова.
- Потери головы считаются кусками по `TARGETS_PER_CHUNK` = 2048 целей с пересчётом в
  backward:
  - целиком кросс-энтропия под bf16 держала бы около 12 байт на (цель, слово
    словаря), а `token_budget` число целей не ограничивает;
  - среднее и сглаживание меток те же.
- Проход обучения не строит полных логитов `[M, словарь]` (`Model.forward(…,
  logits=False)`): их граф жил бы весь backward ради одного счёта top-1/top-5, а это до
  ~0.6 ГиБ на тяжёлом шаге. Счёт идёт кусками по тем же `TARGETS_PER_CHUNK` без графа
  (`hits_in_pieces`) и приходит в `Predicted.hits`. validation и отчёт этапа 11 логиты
  строят — по ним разбор целей, — и отпускают до следующего прохода.
- Кэш аллокатора CUDA ограничен свободной памятью карты на старте минус 256 МиБ
  (`limit_cuda_memory`), а у 80% лимита аллокатор сам отдаёт свободные блоки. Без этого
  кэш кусков разного размера рос за эпохи до 4.4 ГиБ при 3.2 ГиБ свободных, и под WSL
  драйвер молча переносил перерасход в системную память: шаги шли в разы медленнее без
  единой ошибки. Явный `PYTORCH_CUDA_ALLOC_CONF` не трогается. `expandable_segments` под
  WSL не годится: там ошибка драйвера фатальна.

**Подготовка данных впрок.** Группа строк набора (32 клиента) читается, получает
время и маску в отдельном процессе (`inputs.Prefetch`, `loader_workers`, по умолчанию 1),
пока модель считает предыдущие; то же для `val`. Раньше это шло в главном потоке, и GPU
стоял около трети эпохи — провалы «каждые ~32 шага». Порядок клиентов и маски те же
(процесс `i` берёт группы `i, i + n, …`), и обучение побитно то же, что с
`loader_workers=0`: у `DataLoader` свой генератор, и глобальный поток dropout он не
трогает. Источник едет в процесс путями, а не глобалами каталогов. AdamW на CUDA —
`fused`, деление градиентов окна — одной `foreach`-операцией.

**Переключатели волны 4** (`--config` обучения, все выключены по умолчанию, и обучение
тогда прежнее; программа и порядок — `audit/2026-09-28-project/wave4/README.md`):

| поле `MlmConfig` | что делает |
|---|---|
| `restricted_softmax` | softmax головы только по значениям ключа цели, сглаживание — внутри них |
| `usr_aux_weight` | вес цели `[USR]`: доли типов событий за 7/30/90 дней до точки отсчёта времени (`RecentTypes`) |
| `shuffle_row_groups` | новая перестановка групп строк train на эпоху (seed из `seed` и номера эпохи); горизонт cosine считает каждую эпоху |
| `hide_event_keys` | у значений события под маской `event` ключ во входе — `[MASK]`, голове ключ цели подаётся запросом |

Чекпойнт хранит конфиг, и `load_trained` включает то же самое (кандидатов, цель `[USR]`,
закрытие ключей).

На CUDA с поддержкой bf16 прямой проход обучения, validation и отчёта этапа 11
идёт под `autocast(bfloat16)`. Веса, градиенты и состояние AdamW остаются fp32,
`backward` — вне autocast. Углы TimeRoPE считаются в fp32. На CPU всё как
раньше — fp32 и корзины.

### Диагностика представления клиента

```bash
python -m src.mlm.diagnostics --checkpoint data/12_train/best_checkpoint.pt \
    --group val --clients 300 --min-events 100 --out report.json
```

`client_embedding` — вектор `[USR]` клиента после последнего блока энкодера истории
(`Model.client_embeddings`, размер `d = 128`): тот же вектор, что получает голова, не
выход энкодера анкеты и не выход головы. Диагностика только читает: сравнивает его
на выборке клиентов с вариантами того же клиента из его же данных — без событий,
с переставленным по моментам содержимым событий, с последними 50 % и 25 % событий,
с анкетой из одного `[USR]` — и печатает распределения cosine и L2 (mean, median,
p10, p50, p90). Перестановка строк вместе с их моментами вектор не меняет: позиция в
истории — время, а не номер; это проверка самой диагностики. Там же — доля внимания
`[USR]` на себя и на события по блокам и головам энкодера истории; её строка
воспроизводит настоящий выход внимания, расхождение печатается. Веса внимания не
доказывают влияния — главная проверка это абляции. `test` диагностика не читает.
Чекпойнт загружается через `load_trained` — с отказом, если `data/07_backbone` собран не
так, как при обучении; годятся и веса эпохи `epochs/epoch_NN.pt`.

Как читать числа — оговорки аудита `audit/2026-09-28-project` (раздел 2 `REPORT.md`):
у косинусов нет межклиентской шкалы (косинус между разными клиентами ≈0.37), варианты «без
событий» и «анкета из одного `[USR]`» модель при обучении не видела, а доля внимания на
события при равномерном внимании и так ≈ n/(n+1).

## 13. Оценка на задачах

```bash
python -m src.downstream.embed --checkpoint data/12_train/best_checkpoint.pt   # векторы на T: train, val
python -m src.downstream.embed --checkpoint init                               # контроль: без обучения
python -m src.downstream.probe --tag best_checkpoint --control init            # пробы и сравнение на val
```

Ради чего модель учится: вектор клиента на момент T, собранный строго из прошлого, и
простая голова над ним — против CatBoost-бейзлайна на тех же клиентах.

**Момент T** у группы один (`settings.cutoff`), местная полночь, и это ровно T `churn_baseline`:

- **train — 2026-01-01**, конец окна, на котором учился backbone. С T раньше него окно метки
  train лежало бы в истории предобучения: метку backbone не видел, но события окна видел. Вход
  модели на T — вся история train, которую она знает. Метку `churn_baseline` берёт из продолжения
  тех же клиентов на 60 дней (`python -m src.generator.continuation`, хвост в
  `churn_baseline/data/future/train/`). Этапы PRAGMA этот каталог не читают: они открывают только
  `data/01_raw/<train|val|test>`.
- **val — 2026-03-02, test — 2026-07-03**: конец выгрузки минус 60 суток, окно метки
  `(T, T + 60 дней]` целиком внутри выгрузки. Backbone этих клиентов не видел.

**Протокол.** Пока идут эксперименты, train учит голову, а val выбирает эксперимент; test
не считается и не выводится — ни векторы, ни метрики, ни сравнения. Он нужен один раз, в
финальной оценке выбранной модели, и включается явно:

```bash
python -m src.downstream.embed --checkpoint <чекпойнт> --final-test   # векторы train, val и test
python -m src.downstream.probe --tag <тег> --final-test               # метрики и сравнения и на test
```

Для этого и `churn_baseline` должен быть собран с `--final-test` (его README).

**Вход на T** (`at_cutoff.ClientsAtCutoff`) собирают те же функции, что этапы 04–05 и читатель набора, но в
памяти: `Group.history(клиент, T)` — события строго раньше T и анкета, откатанная на T;
`encode_event`/`encode_profile` замороженным словарём; `build_sample` с окном,
кончающимся в T, и тем же отбором истории, на котором собран `05_dataset/train`;
`time_log` и `profile_time_log` от T. Маски нет. Обрезать готовый набор 05 по T
нельзя: анкета и вехи там собраны на конец окна группы, и будущее осталось бы во
входе. На конце окна вход в памяти побитно совпадает с тем, что обучение читает из
набора 05 (тест), а всё, что после T, не меняет его ни на бит.

**Векторы** (`embed`, `Model.readouts`), по четыре на клиента из одного прохода: `usr` —
`[USR]` после истории, `profile` — выход энкодера анкеты, `mean_event` и `last_event` —
среднее и последнее из векторов событий после истории. Рядом — число событий и давность
последнего события до T (`gap_seconds`) — контроль «только давность»; при отсчёте
времени от последнего события (`--anchor last_event`) модели она не видна. Клиенты без
событий до T пропускаются — модель такого входа не видела. `--checkpoint init` —
начальные веса без обучения: контроль того, что даёт обучение, а не сам вход. Чекпойнт
обязан быть обучен на текущем `05_dataset/train` (sha256 и `time_anchor` из его `data`): после пересборки данных под другой
эксперимент (BPE, точка отсчёта времени) прежняя модель получила бы чужой вход, и
`embed` отказывает.

**Задача** — уход клиента, строки и метки `churn_baseline`, без `truth`: признаки строго раньше
T, метка в `(T, T + 60 дней]`, событие ровно в T не входит никуда.

`churn_active90` — уйдёт ли клиент в следующие 60 дней (нет ни одного собственного действия
клиента в окне), если он был активен хотя бы раз за последние 90 дней до T
(`T − 90 дней ≤ t < T`). Давно замолчавший клиент почти наверняка не вернётся, и задачу о нём
во многом решала бы давность; среди недавно активных видно, различает ли модель уход. Строки,
метки и прогнозы CatBoost — из `churn_baseline` (`reports/*_rows.parquet`): «действие
клиента» определено там.

Рядом агрегатный бейзлайн (`tasks`) из наблюдаемой ленты `02_preprocessed`: счётчики каждого
типа событий за 30, 90 и 365 дней до T, число событий и давность. Таблица кэшируется в
`13_downstream/tasks/` и пересчитывается, если сменился файл 02, T или состав таблицы.

Строки задачи принимаются, только если каждый их источник — текущий, и сверяется он
отдельно:
- история признаков — sha256 событий текущей выгрузки группы;
- анкета признаков — sha256 её анкеты;
- метка — та же выгрузка (val, test) или продолжение train, записанное в его `future.json`.
  Продолжение само обязано продолжать текущую выгрузку.

Ещё проверяется T строк. Векторы `embed` записывают sha256 выгрузки, из которой собран вход, и
проба отказывает, если выгрузка с тех пор сменилась.

**Главное сравнение** — три модели на одних строках задачи:
- `catboost` — CatBoost-бейзлайн на полном handcrafted X;
- `usr` — только `[USR]` и логистическая регрессия;
- `catboost_plus_usr` — полный X бейзлайна и `[USR]` → CatBoost тем же протоколом
  (`churn_baseline`, `python -m churn.plus_usr --embeddings data/13_downstream/<тег>`).

Порядок запуска: `embed` → `churn.plus_usr` → `probe`. Проба берёт `catboost_plus_usr` готовым
прогнозом, только если он обучен на векторах того же тега и чекпойнта и на тех же источниках
строк, а его клиенты и метки строка в строку равны строкам `catboost`. В отчёте — PR-AUC,
ROC-AUC и F1 трёх моделей на val и парная разница `catboost_plus_usr − catboost` с 95% интервалом:
интервал выше нуля — `[USR]` даёт сигнал сверх handcrafted-признаков.

Порог для Precision, Recall и F1 зависит только от train: у CatBoost — с `inner_holdout`, у проб —
max F1 по out-of-fold вероятностям train тех же фолдов.

**Диагностика [USR]** — 2×2 на тех же строках: векторы модели и начальных весов (`init`) ×
логистическая регрессия и CatBoost только на `[USR]` (`catboost_usr`, `churn.plus_usr --usr-only`,
тот же протокол, без handcrafted-признаков и стандартизации).

```bash
python -m src.downstream.embed --checkpoint init --tag init
cd churn_baseline
.venv/bin/python -m churn.plus_usr --embeddings ../data/13_downstream/w4-b0 --usr-only
.venv/bin/python -m churn.plus_usr --embeddings ../data/13_downstream/init --usr-only
cd .. && python -m src.downstream.probe --tag w4-b0 --control init
```

Регрессия на векторах контроля — та же, что у самой модели: C и порог только по train. Парные
разницы по одним клиентам val: модель − `init` при той же голове (что дало обучение) и CatBoost −
регрессия на тех же векторах (что даёт нелинейная голова). Векторы обязаны быть сняты ровно на T
группы (запись в `meta.json` и каждая строка) и по одному на клиента, иначе проба отказывает.
Готовый прогноз CatBoost годится, только если обучен ровно на этих векторах: записи групп в его
`metrics.json` равны `meta.json` векторов, а снятые заново векторы требуют переобучения.

**Пробы** (`probe`): логистическая регрессия со стандартизацией, сила регуляризации —
3-кратной кросс-валидацией (C по декадам 1e-4…1e2) на train по log-loss. Стандартизация — часть
pipeline (`GridSearchCV`) и учится внутри каждого фолда. После выбора C вся pipeline учится на
всём train. Train учит, val только оценивается. Наборы: `recency`, `counts`, `usr`, `usr+recency`,
`usr+last_event` ([USR] и последнее событие после истории — комбинация пробы из статьи PRAGMA),
`readouts`, `readouts+recency`, `counts+usr` и те же векторы контроля (`init:…`); рядом прогноз
CatBoost. Все наборы оцениваются на одних и тех же клиентах. В отчёте — строки, положительные и
их доля, по набору — ROC-AUC и PR-AUC на val. Сравнение с эталоном (CatBoost) парное:
bootstrap по клиентам val, одни и те же выборки для набора и эталона, 95% интервал
разницы. С `--baseline <тег>` каждый набор с векторами так же парно сравнивается с
прогнозами другой модели PRAGMA на тех же клиентах и той же метке.

Фрод на уровне операции здесь не оценивается: вектор нужен на момент каждой операции
строго до неё (около миллиона на группу), а история в модели двунаправленная.

## Чем файлы этапов 08–10 не являются

Это **снимки при начальных весах**, для просмотра. Обучать по ним нельзя:
градиент через parquet не течёт. При обучении все четыре слоя и голова обязаны
считаться вместе, в одном прямом проходе, — что этапы 11 и 12 и делают. Начальные
веса обучения берутся не из этих каталогов, а из `data/07_backbone`.

## Конвейер одной командой

```bash
python -m src.pipeline                              # 02 → 05 по группам, 06 и 07
python -m src.pipeline --from encode --to dataset --groups val
python -m src.pipeline --args dataset="--config ctx.json" --report timing.json
```

Цепочка этапов записана один раз, в `src/pipeline.py`. Каждый этап — та же команда, что
запускают руками, отдельным процессом: память между этапами возвращается системе.
Строится только то, что читают обучение и оценка: после набора 05 на диск идут только
веса входного слоя (только `train`) и backbone; время и маски считаются при чтении. В конце печатается
время каждого этапа. Генерация (01) и обучение (12) сюда не входят — это долгие запуски
отдельной командой.

`04_tokenized/<group>/meta.json` помнит отпечаток словаря (`vocabulary`), и этап 05
отказывает группе, закодированной под другой словарь: пересборка словаря без
перекодирования раньше проходила молча. `fit` читает train один раз: словарь значений,
диапазоны и BPE учатся на одном корпусе.

## Установка

```bash
pip install -e .
```

Python 3.11+. Зависимости: numpy, pyarrow, pandas, scikit-learn, scipy,
tokenizers.

Этапам 06–12 нужен PyTorch — он объявлен отдельным дополнением, чтобы конвейер
подготовки данных ставился без него:

```bash
pip install -e .[torch]
```

Varlen FlashAttention на CUDA — ещё одно необязательное дополнение (нужны
NVIDIA GPU Ampere+ и CUDA toolkit, совместимый с установленным PyTorch):

```bash
pip install -e .[torch,flash]
```

Живому дашборду обучения (`python -m src.dashboard`) нужен Streamlit — тоже отдельное
дополнение:

```bash
pip install -e .[dashboard]
```

Интерактивная 3D-визуализация pipeline для показа (React, Node 22) — отдельное приложение
в `viz/`; установка, экспорт данных сцены и запуск — в [`viz/README.md`](viz/README.md).
