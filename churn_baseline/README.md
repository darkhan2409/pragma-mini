# churn_baseline

Обычная табличная модель оттока на CatBoost. Это точка отсчёта для честного сравнения:

```
обычные признаки → CatBoost                     (этот проект)
PRAGMA history → client embedding → голова      (src/downstream/probe.py)
```

Проект изолирован от PRAGMA:
- код PRAGMA (`src/`) не импортируется;
- из репозитория читается только выгрузка генератора `data/01_raw/<group>/` и, для варианта
  `catboost_plus_usr`, векторы PRAGMA `data/13_downstream/<тег>/` — только чтение;
- все датасеты, модели и отчёты лежат внутри `churn_baseline/`;
- своё окружение `.venv` и свои тесты.

## Разбиение

- Своего разбиения нет: группы — ровно группы выгрузки PRAGMA.
- Клиент train PRAGMA — train здесь; то же для val и test. Ни `train_test_split`, ни перемешивания.
- Состав групп задаёт `config.DATASETS` генератора: сейчас 25 000 / 6 000 / 6 000 клиентов. Обучение
  отказывает, если признаки собраны на другой выгрузке (sha256 событий из `manifest.json`).

| группа | роль |
|---|---|
| train | обучение: `inner_train` (80%) и `inner_holdout` (20%) — ранняя остановка и порог |
| val | только оценка — по ней выбирают эксперименты PRAGMA; CatBoost val не видит |
| test | только финальная оценка, явным `--final-test`; иначе не строится и не считается |

## Target

```
churn = 1   у клиента нет ни одного собственного действия в (T, T + 60 дней]
churn = 0   есть хотя бы одно
```

**Cutoff T**, местная полночь (UTC+5):
- **train** — конец выгрузки train. Это конец истории, на которой учился backbone PRAGMA: с T
  раньше него окно target train попало бы в историю предобучения. Выгрузка кончается ровно в T,
  поэтому target train берётся из **продолжения** тех же клиентов (ниже);
- **val, test** — 1-е число месяца, в котором лежит «конец выгрузки − 60 суток»
  (`config.month_start`): окно target целиком внутри выгрузки, а T в той же фазе месяца, что
  T train. В 23:55 последнего дня месяца банк пишет снимки остатка, кэшбэк, комиссии и
  проценты; T train стоит сразу после этой пачки, и вход PRAGMA на T val в другой день месяца
  был бы другой фазы (аудит 2026-10-05; до него T val было 2026-03-02, T test — 2026-07-03).

| группа | конец выгрузки | T | окно target | источник target |
|---|---|---|---|---|
| train | 2026-01-01 | 2026-01-01 | (2026-01-01, 2026-03-02] | продолжение `data/future/train` |
| val | 2026-05-01 | 2026-03-01 | (2026-03-01, 2026-04-30] | та же выгрузка |
| test | 2026-09-01 | 2026-07-01 | (2026-07-01, 2026-08-30] | та же выгрузка |

**Продолжение train** — те же клиенты train, прожитые генератором дальше конца выгрузки:
`python -m src.generator.continuation train --days 60 --out churn_baseline/data/future/train` (из
корня, окружением PRAGMA; около 20 минут).
- Генератор тот же. Окно выгрузки у него только режет ленту. Последний приход в банк прежний, так
  что новых клиентов нет.
- Прошлое продолжения сверяется с выгрузкой по каждому клиенту: строки до 2026-01-01 (sha256
  содержимого), вехи и записи о работе.
  - Клиент с другим прошлым исключается: его метка неизвестна.
  - Если таких больше 1 % или клиенты другие, ничего не записывается.
- В `data/future/train/` лежит только хвост с 2026-01-01 (`events.parquet`) и `future.json`:
  продолжением какой выгрузки он является (её sha256 событий и анкеты), результат сверки прошлого,
  конец продолжения, sha256 хвоста.
- Из хвоста берётся только target train. Признаки, популяция и `active90` — только из выгрузки
  до T. Этапы PRAGMA каталог `churn_baseline/data/` не читают.

**Популяция** — клиенты группы, у которых до T было хотя бы одно собственное действие. Не входят:
- клиенты без истории до T: пришли в банк позже;
- клиенты, у которых до T были только события банка: они уже неактивны, и ярлык для них тривиален.

**Действие клиента** — событие, которое начал сам клиент (`churn/activity.py`). Исходящие действия
банка — push, SMS, звонок, письмо без реакции, начисления, автоплатежи — активностью не считаются.

| активность клиента | условие |
|---|---|
| app_screen, app_operation | все, включая неудачные попытки |
| purchase | `reason=purchase` (pos, ecom, qr), включая отклонённые |
| transfer_out | кроме вывода себе в другой банк (`reason=transfer`, «Own account») |
| p2p_out, cash_withdrawal | все |
| cash_deposit | кроме пополнения под платёж и под выписку (`reason` `payment_topup`, `card_statement`) |
| bill_payment | `channel ≠ system` (ручная оплата) |
| deposit_topup | дебетовая нога |
| deposit_withdrawal | `reason=early_closure`, дебетовая нога |
| transfer_in | `reason=transfer` со своего счёта в другом банке («Own account») |
| early_repayment, application_submitted, banner_clicked, case_opened | все |
| card_blocked | `client_freeze`, `lost_or_stolen` |
| card_unblocked | `client_request` |
| product_closed | `early_closure` |
| product_migrated | `migration_reason=successor_offer` |
| profile_change | `change_source=client` |

Не активность:
- обязательства (решение владельца 2026-10-06): взнос по кредиту любым каналом, пополнение под
  платёж и под выписку кредитной карты. Ушедший клиент продолжает обслуживать долг; досрочное
  погашение остаётся действием;
- вывод денег себе в другой банк (решение владельца 2026-11-09): `transfer_out` с `reason=transfer`
  на «Own account». Так ушедший клиент выводит остаток в день ухода и потом доход, который ещё
  приходит сюда (генератор 2.0). На val 2026-03-01 с таким выводом в действиях 150 из 309 клиентов,
  ушедших по truth на всё окно, получали churn = 0. Перевод между своими счетами в банке
  (`own_transfer`) и приход со своего счёта в другом банке остаются действиями;
- автосписания: подписки, страховки, автоплатежи, автосписания по кредиту;
- зачисления от других: зарплата, пенсия, входящие переводы;
- начисления, комиссии и отчёты банка;
- учёт кредита, открытия продуктов по одобрению и автоматическая активация карты;
- перевыпуск, тарифы, rollover;
- решения по заявкам, ответы поддержки, антифрод;
- все исходящие коммуникации банка и показ баннера.

Полная таблица с причинами — в `tests/test_activity.py`: там все 55 типов выгрузки.

Действие, визит и целевое действие — разные понятия (`churn/activity.py`):
- `is_client_action` — всё, что начал клиент: метка и признаки `act_*`;
- `is_visit` — успешный вход в приложение (`login`, `biometry_login`, `status=success`): так визит
  считает банк, на нём MAU, WAU и CORE;
- `is_target_action` — первое полезное действие после регистрации: действие клиента или продукт,
  открытый по его заявке.

**Стадии CAPP** (`churn/lifecycle.py`, аудит `audit/2026-10-06-lifecycle/README.md`):
- New, Activated, Growing, CORE, Loyal, At Risk, Churn по Excel мобильной команды — на момент t,
  только по событиям раньше t.
- Это разметка для анализа: стадия на T — срез качества прогноза churn и бизнес-интерпретация.
- В признаки и в метку стадия не идёт; отдельных задач на стадиях нет (решение владельца
  2026-10-06).

Генератор не знает события «ушёл из банка». Отток здесь — это скрытые паузы активности клиента.
Банковские события во время паузы продолжаются, поэтому без исключения действий банка отток был бы
не виден.

## Задачи

Задача одна — **`churn_active90`**: «уйдёт ли клиент в следующие 60 дней, если он был активен хотя
бы раз за последние 90 дней». Из популяции остаются клиенты с действием клиента в
`[T − 90 дней, T)` — только прошлое.

Давно замолчавший клиент почти наверняка не вернётся, и задачу о нём во многом решал бы простой
сигнал давности. Среди недавно активных проверяется, различает ли модель уход. Сигнал давности
здесь не исчезает: главный признак CatBoost — `act_days_since_last`.

Все модели сравниваются на строках этой задачи.

## Защита от утечки

- **Признаки** — только события строго раньше T. Блок событий обрезается `t < T` в начале
  `features.compute`; дальше момент T и позже никому не виден.
- **Target** — только события в `(T, T + 60d]`. Событие ровно в T не входит ни в признаки, ни в
  target; ровно в T + 60d — входит. У train target читается из продолжения (`churn/sources.py`), и
  выгрузка train с событием не раньше T отвергается.
- **Популяция `churn_active90`** — только действия клиента в `[T − 90 дней, T)`: действие ровно в
  T и позже, события банка в эти 90 дней в счёт не идут (`tests/test_build.py`).
- **Анкета** откатывается на T:
  - поле, которое меняет `profile_change`, получает `old_value` первого изменения в момент T или
    позже;
  - возраст считается на местную дату T;
  - стаж — по записям о работе, известным банку раньше T;
  - вехи — только раньше T.
- **Снимочные поля анкеты на `as_of`** (`contracts_count`, `active_contracts`, `holds_*`,
  `credit_limit`, `credit_utilization`, `relationship_months`) описывают клиента на конец выгрузки,
  то есть после T. В признаки они не идут.
- **Тест `test_future_does_not_change_features`**. Добавление любых событий после T, смена снимка
  анкеты и изменения анкеты после T не меняют ни одного признака. Target при этом меняется, поэтому
  тест не пустой.
- **Группы.** Каждая группа строится из своей выгрузки. Обучение проверяет, что клиенты групп не
  пересекаются.

## Признаки

116 признаков (`reports/features.md` — имя, тип, описание). Окна — не длиннее 365 дней (`LONG_WINDOW`): признак за
всю историю мерил бы длину выгрузки, а не клиента (у train до T 24 месяца, у val 26). История до T
каждой группы обязана быть не короче года, иначе `churn.build` отказывает:
- **анкета на T:** 13 полей, возраст, стаж, давность вех;
- **действия клиента:** recency, число и активные дни за 7/30/60/90 дней, число и давность первого
  действия за 365 дней, тренд, разрывы;
- **приложение:** входы, неудачные входы, сессии, экраны, клики по баннерам;
- **покупки, переводы, снятия, взносы:** число, суммы, recency, доли отказов и онлайна, число
  различных MCC и мерчантов;
- **автоплатежи против ручных оплат:** по счетам и по кредиту; подписки;
- **доходы, входящие переводы, сумма остатков всех счетов и её изменение за 30 дней** (последний
  остаток каждого счёта; долг кредитной карты — с минусом), комиссии, отказы по недостатку средств;
- **продукты:** договоры, карты, кредиты, вклады, заявки и отказы, открытия, закрытия, блокировки,
  просрочка;
- **банк → клиент:** коммуникации по каналам, доля доставленных, winback; отзыв согласия;
  обращения; антифрод-алерты.

## Модель и оценка

- CatBoost: `Logloss`, `eval_metric=Logloss` (PR-AUC — только кривая отчёта), до 3000 деревьев, `learning_rate` 0.03, глубина 6,
  `random_seed=42`, 8 потоков. Категориальные поля анкеты идут как `cat_features`.
- Строки train задачи делятся на `inner_train` (80%) и `inner_holdout` (20%),
  стратифицированно по target, seed 42:
  1. CatBoost учится на `inner_train` с ранней остановкой по Logloss на `inner_holdout` (300 итераций).
     Не по PR-AUC: на ~80 позитивах она скачет, и случайный пик на первых деревьях обрывал
     обучение (2026-10-09: `plus_usr` остановился на 4 деревьях);
  2. по его прогнозам на том же `inner_holdout` выбирается порог — наибольший F1
     (`max F1 on train inner holdout`);
  3. CatBoost учится заново на всём train с числом деревьев лучшей модели — `best_iteration + 1`,
     потому что CatBoost считает итерации с нуля. Остальные параметры те же.
- Порог фиксируется на train и больше не пересчитывается. val — только инференс: ROC-AUC, PR-AUC
  и log-loss (средняя кросс-энтропия, та же Logloss, на которой учится CatBoost) по вероятности,
  без порога, а Precision, Recall, F1 и матрица ошибок — при этом пороге.
- test — только с `--final-test`, при том же пороге.

## Результаты

Мир 25 000 / 6 000 / 6 000 клиентов, генератор 2.0.0-a7, backbone `world25k-train-2026-11-08`
(10 эпох). T train = 2026-01-01 (метка из продолжения), T val = 2026-03-01. Только val, test не
считался.

| задача | inner_train / inner_holdout | best_iteration (деревьев) | порог | строк val | churn=1 | доля | ROC-AUC | PR-AUC | log-loss | Precision | Recall | F1 | TN / FP / FN / TP |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| `churn_active90` | 18288 / 4572 | 399 (400) | 0.241 | 5488 | 255 | 4.6% | 0.950 | 0.532 | 0.1007 | 0.479 | 0.620 | 0.540 | 5061 / 172 / 97 / 158 |

95% бутстреп-интервал PR-AUC по строкам val — [0.468, 0.597]. Случайный прогноз даёт PR-AUC,
равный доле позитивов; CatBoost выше неё в 11.5 раза.

Распределение target:

| задача | группа | клиентов | churn=1 | churn=0 | доля |
|---|---|---|---|---|---|
| `churn_active90` | train | 22860 | 1046 | 21814 | 4.6% |
| `churn_active90` | val | 5488 | 255 | 5233 | 4.6% |

Вне популяции:
- train: 365 клиентов только с событиями банка до T; клиентов без истории до T и с разошедшимся
  продолжением нет;
- val: 41 клиент без истории до T и 82 только с событиями банка.

**Продолжение train** (генератор 2.0.0-a7, 60 дней). Прошлое до 2026-01-01 совпало построчно у всех
25 000 клиентов (57 998 788 строк), исключённых нет. Хвост — 7 791 146 строк от 24 829 клиентов.

**Сравнение на тех же строках val** (`src/downstream/probe.py`, парный бутстреп, Δ к `catboost`):

| сценарий | PR-AUC | ROC-AUC | log-loss | F1 | Δ PR-AUC [95%] |
|---|---|---|---|---|---|
| `catboost` | 0.532 | 0.950 | 0.1007 | 0.540 | — |
| `usr` — логистическая регрессия на [USR] | 0.406 | 0.928 | 0.1165 | 0.451 | −0.123 [−0.174, −0.071] |
| `catboost_plus_usr` | 0.515 | 0.947 | 0.1026 | 0.531 | −0.016 [−0.040, +0.009] |
| `lora`, seed 0 (`lora-world25k`) | 0.477 | 0.935 | 0.1111 | 0.497 | −0.055 [−0.094, −0.015] |
| `lora`, seed 1 (`lora-world25k-s1`) | 0.481 | 0.941 | 0.1096 | 0.488 | −0.049 [−0.088, −0.008] |

- [USR] сверх признаков бейзлайна ничего не добавляет: интервал Δ захватывает ноль.
- LoRA-дообучение backbone под задачу (`src/downstream/finetune.py`, конфиг по умолчанию, как у
  `lora-ref`: до 10 эпох, остановка после 3 эпох без улучшения log-loss на отложенных 4 572
  клиентах train; лучшая эпоха — 4 и 2) хуже CatBoost в обоих seed: интервал Δ целиком ниже нуля.
  Замороженные векторы оно обходит: Δ к `usr` +0.068 [+0.023, +0.113] и +0.074 [+0.030, +0.117].
- Seed расходятся на 0.004 PR-AUC. Третий seed остановлен на второй эпохе решением владельца
  2026-11-10: вывод он бы не изменил.

**Правки 2026-11-09** — вывод денег себе в другой банк больше не действие, остаток — сумма по
счетам, окна признаков не длиннее 365 дней (разделы «Target» и «Признаки»).
- До них на том же мире: val 217 из 5 636 (3.9%), PR-AUC `catboost` 0.436, `usr` 0.374,
  `catboost_plus_usr` 0.456 (Δ +0.019 [−0.013, +0.055]). Отчёты —
  `data/runs/world25k-train-2026-11-08/churn-v0/`.
- Рост PR-AUC — в основном от доли позитивов: относительно неё качество прежнее (11.3× → 11.5×).
- По truth генератора (только диагностика) из клиентов val, ушедших на всё окно target, метка
  теперь ловит 68% вместо 31%. Среди позитивов не прибавилось ни одного клиента, который на
  всё окно остался активен.
- Модель «train или val» по признакам: ROC-AUC 0.983 → 0.893. Остаток — настоящие 59 дней между
  T train и T val и сезон (декабрь против февраля).

Ограничения:
- ушедший клиент с кредитом, который заходит в приложение, считается оставшимся: сессии
  приложения — действие. Из 188 клиентов val, ушедших на всё окно, churn = 0 остался у 60, в
  основном из-за таких сессий;
- T train и T val в разных сезонах: T train задан концом окна предобучения backbone.

Главные признаки (`reports/feature_importance.csv`, PredictionValuesChange): `act_days_since_last`,
`act_days_7`, `act_gap_max_90`, `loan_contracts_90`, `transfer_sum_90`, `act_days_30`,
`purchase_days_since_last`, `act_gap_mean_90`.

## Полный X + [USR] PRAGMA → CatBoost

Третий вариант сравнения: `catboost_plus_usr` — тот же полный X, на котором учится CatBoost-бейзлайн,
плюс вектор `[USR]` модели PRAGMA на T строки.

```bash
.venv/bin/python -m churn.plus_usr --embeddings ../data/13_downstream/<тег>   # train + val
```

- **X:** все признаки бейзлайна в прежнем порядке и `usr_0 … usr_{d−1}` (у B0 — 128) числами, без
  стандартизации. Категориальные — те же `cat_features`.
- **Строки, T и метки** — те же, что у бейзлайна. Протокол тот же (`fit_task`): порог и ранняя
  остановка на `inner_holdout` train, переобучение на всём train. val только оценивается, test —
  только с `--final-test`.
- **Векторы** — файл `data/13_downstream/<тег>/<группа>.parquet`, который пишет
  `python -m src.downstream.embed`. Код PRAGMA не импортируется. Отказ, если:
  - векторы сняты не с той выгрузки, из которой собраны признаки (sha256 событий и анкеты в их
    `meta.json`);
  - векторы сняты не на T строк;
  - клиент повторяется;
  - у строки нет вектора.
- **Выход:**
  - отчёт `reports/plus_usr/<тег>/`: `metrics.json` (метрики, порог, деревья, число признаков,
    провенанс векторов и источников), `eval_rows.parquet`, `train_rows.parquet`;
  - модели — `models/plus_usr/<тег>/`.

  Сравнение с `catboost` и `usr` — в пробе PRAGMA (`src/downstream/probe.py`).

## Для сравнения с PRAGMA + Head

- `reports/eval_rows.parquet` — точный список объектов оценки:
  `task, client_id, group, T, churn, active90, score`. По умолчанию в нём только val, с
  `--final-test` — ещё test. PRAGMA + Head оценивается **на этих же строках**: те же
  клиенты, тот же T, тот же target, а не просто те же группы (`src/downstream/tasks.py`).
- `score` — прогноз CatBoost; по нему сравнение делается парным (bootstrap).
- `reports/train_rows.parquet` — строки обучения в той же форме.
- `reports/metrics.json` хранит по задаче:
  - `inner_train` и `inner_holdout` — строки, положительные и их долю;
  - `best_iteration`, `trees`, `threshold` и `threshold_rule`;
  - `holdout_logloss` — Logloss на `inner_holdout` после каждого дерева ранней остановки (по нему
    выбрана лучшая итерация), `holdout_curve` — PR-AUC тех же деревьев;
  - метрики групп;
  - sha256 обоих файлов строк;
  - `sources` по группам — отдельно `feature_history_events_sha256` (история признаков),
    `feature_profile_sha256` (анкета признаков), `target_events_sha256` и `target_source`
    (`export` или `future`), T и `target_window`.

  Те же поля — в `data/<group>/meta.json`. Обучение отказывает, если источник строк изменился, а
  оценка PRAGMA сверяет каждый источник с текущей выгрузкой и продолжением отдельно.
- **Эмбеддинг PRAGMA считается по истории строго раньше T строки**, анкета — на T. У train это вся
  история, которую видел backbone (T = конец его окна обучения); окно target train в предобучение
  не попадало. Val- и test-клиентов backbone не видел.

## Воспроизведение

```bash
cd churn_baseline
python3.14 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python -m pytest
(cd .. && python -m src.generator.continuation train --days 60 --out churn_baseline/data/future/train)
for g in train val; do .venv/bin/python -m churn.build $g; done   # ≈ 9 мин
.venv/bin/python -m churn.train                                   # ≈ 30 с
```

Финальная оценка — один раз, после выбора модели PRAGMA:

```bash
.venv/bin/python -m churn.build test --final-test
.venv/bin/python -m churn.train --final-test
```

Одинаковая выгрузка и код дают одинаковые признаки. CatBoost детерминирован при том же seed и числе
потоков.
